# LESSONS LEARNED — 반복하지 말 것

라이브 워커 작업에서 **실제로 틀렸던 것**만 적는다. 각 항목은 "규칙 → 왜(실증) → 어떻게".
새 교훈은 같은 형식으로 append 한다. 추측이나 일반론은 넣지 않는다.

## 1. 계측

### 1-1. `reason=ok` 는 워커 성공이 아니다 ★ (두 번 걸림)

**규칙**: 워커 성공 판정은 **evidence 의 `worker_result.json`** 으로만 한다.
드라이버가 찍는 `[driver] result: {... 'status': 'ok' ...}` 는 **pass 단계 상태**라
워커가 죽어도 `ok` 다.

**실증**: 2026-08-15 모델 3파전에서 원장에 `reason=ok` 로 6셀을 쌓은 뒤에야, 같은 시각
evidence 가 `repeat_error_halt`(워커 실패)임을 발견했다. 이 함정은 이미 메모리에
적혀 있었는데도 그대로 밟았다.

**어떻게**: 채점기는 `worker_result.json` 의 `status` + `summary`(`terminal=True` 포함 여부)를
읽는다. 원장에는 셀 식별자만 남기고 판정은 evidence 조인으로 한다.

### 1-1b. 대시보드 숫자를 읽기 전에 **그게 언제 값인지** 먼저 본다 ★

**규칙**: 상태 테이블의 값은 대개 "마지막으로 돌았을 때의 결과"가 박혀 있는 것이다.
**나이를 확인하기 전에는 현재 상태로 읽지 마라.**

**실증(2026-08-16)**: github 대시보드의 `github.scan: claimed=5 scanned=5 errors=5` 를
보고 "오늘 스캔에서 5건 실패"라고 사용자에게 보고했다. `last_beat` 은 **25일 전**이었고,
그 시점 `github_repo_target` 에는 error 행이 **하나도** 없었다(18,722건 전부 pending).

전수를 세어보니 하트비트 31개 중 **24시간 내가 5개뿐**, 최고 45일까지 낡아 있었다.
그런데 github·confluence 대시보드는 하트비트를 **아예 렌더링하지 않았고**, smb 도 표가
없었다. dev_web 만 표가 있었으나 alive/stale 이진이라 6시간 cron 이 항상 빨갰다.

**어떻게**: DB 를 직접 볼 땐 `last_beat`/`updated_at` 을 **항상 같이 SELECT** 한다.
화면에는 나이를 반드시 붙이고, 신선도는 이진이 아니라 구간으로 낸다
(LIVE / 대기<24h / 하루+ / ★일주일+). 낡은 하트비트를 **지우지는 마라** — "마지막으로 언제
돌았나"가 그 자체로 정보이고, 지우면 "한 번도 안 돌았음"과 구분이 안 된다.

**딸린 교훈**: API 는 처음부터 `age_sec`·`alive` 를 정확히 내려주고 있었다. 빠진 건
**렌더링뿐**이었다 — 그래서 API 단위 테스트로는 절대 안 잡힌다. 회귀 테스트는 HTML 을 봐야 한다.

### 1-2. 감축량이 기대보다 크면 규칙이 다른 축을 건드리는 중이다

**규칙**: 게이트/필터 규칙을 실데이터에 역적용했을 때 **차단량이 예상보다 크면 멈추고**
차단분을 kind·경로·repo 로 쪼개 본다.

**실증**: 시크릿 게이트 fixture 규칙 1차 역적용이 10,032 → 4,880 (5,152 차단). 좋아 보였지만
**5,006건이 `kr_rrn`** 이었다 — 계측 결과 CSV(`output/test_20250918_201202.csv`)가 파일명이
`test_` 로 시작한다는 이유만으로 걸렸다. 시크릿 게이트가 PII 판정을 가로챈 계약 위반이다.
면제 추가 후 최종 146 차단.

### 1-3. 실험은 **같은 대상**을 보게 만들고 순서를 회전시킨다

**실증**: 3차 A/B 에 `_gh_unfair` 원장이 남아 있다 — 모델마다 다른 repo 를 봐서 비교가 무의미했던 회차다.

**어떻게**: github 은 `ab_round3.prime_github()`(타깃을 pending·`cycle_scanned_at=NULL` 로 되돌림),
모델 순서는 타깃마다 rotate.

## 2. 원인 진단

### 2-1. 계약/에러 메시지의 **원인 귀속**을 믿지 말고 이벤트를 직접 세라 ★

**규칙**: "왜 죽었나"는 감사 로그의 **턴별 이벤트 분류**로 판정한다.

**실증**: `terminal_contract.py` 는 실패모드를 *"tool call 을 산문/JSON 으로 적는 것"* 이라고
적어 뒀다. 실제로 세어 보니 github 8런에서 **"산문 서술" 턴은 1회뿐**이고, 실패의 100%는
**빈 턴**(assistant_text 0 + tool_call 0)이었다. 원인이 완전히 다른 곳(모델 추론 폭주)에 있었다.

**어떻게**: `.harness/audit.log.jsonl` 을 `turn_started` 기준으로 묶어
빈 턴 / 텍스트-only 턴 / 도구 턴으로 분류한다(`docs/probes/` 참조).

### 2-2. 처방은 **하나씩 실측으로 기각**하고 나서 채택한다

**실증**(빈-content 원인 추적, 전부 기각됨):
- "전송 결함이니 재시도" → reasoning 델타가 2,070개 나오는 걸 보고 기각(모델이 생각만 함)
- "예산 부족이니 `max_tokens` 상향" → 4,096→16,384 로 늘리니 reasoning 도 **정확히 4배**
- "추론 강도 과다" → medium/low/minimal 에서 폭주 4/6·5/6·4/6 **무관**

원인은 gauss-o32 고유의 폭주였고, 답은 모델 교체였다. 첫 직관대로 재시도를 넣었다면
증상이 절반만 가려진 채 원인이 남았을 것이다.

### 2-3. `information_schema` 의 FK 는 양방향 착시를 만든다

**규칙**: FK 방향은 **`pg_constraint`**(conrelid → confrelid)로 확인한다.

**실증**: DB split-brain 정리 때 `constraint_column_usage` 가 `core.chat_message → public.chat_session`
처럼 보여줘서 "core 가 public 을 참조하니 못 지운다"로 잘못 판단할 뻔했다.
`pg_constraint` 로 보니 **cross-schema FK 0개**였다.

## 3. 라이브 운영

### 3-1. 기본 LLM 프로파일이 바뀌면 **vision 을 즉시 재확인**한다 ★

**규칙**: `SA_CHAT_PROFILE` 기본값이 바뀌면 새 모델의 **이미지 입력 수용**을 실측한다.

**왜**: dev_web/smb 의 `require_vision` 예외는 "핀이 vision 미지원 목록에 있을 때만" 발동한다.
새 기본값이 목록에 없으면 예외가 안 걸리고 그 모델이 그대로 워커에 쓰인다. 이미지 400 은
`invalid_request`(재시도·폴백 **비대상**)라 **태스크가 영구히 죽는다**.

**실증**: 엔진 기본이 gemma 로 바뀐 직후 확인 → gemma 수용(응답 `SEEN`), gauss-o32 여전히 400.
안전했지만, 확인 없이 넘어갔으면 태스크킬러가 부활할 수 있었다.

### 3-2. 특정 devops_target 재현은 `cycle_scanned_at` 이다

**규칙**: 같은 타깃을 다시 태우려면 `cycle_scanned_at=NULL`. `access_count` 가 아니다.

**왜**: `devops_target_claim_next` 의 **cycle 분기** 정렬 1순위가 `(cycle_scanned_at IS NULL) DESC`다.
`access_count` 는 그 아래다.

**실증**: 2026-08-15 에 `access_count=999999` 로 세 번 시도했는데 전부 다른 타깃이 잡혔다.
(`ab_round3.prime_github` 에 이미 올바르게 구현돼 있었다 — 있는 걸 안 보고 다시 틀렸다.)

### 3-3. 프로파일 프로브에는 **프로파일당 타임아웃**이 필수다

**실증**: 전 프로파일을 훑는 도달성 프로브가 첫 프로파일에서 영원히 멈췄다.
`o4-mini`·`codex`·`qwen`·`gaussO4` 는 에러가 아니라 **무응답**이다.

### 3-4. 프로브·실험에 `external-*` 모델을 쓰지 않는다

스캔 자극에 사내 경로·식별자가 들어가고 `external-*` 은 사외(OpenAI/Anthropic)로 나간다.
게이트웨이가 서빙한다고 써도 되는 게 아니다. 기본은 **internal 계열만**.

### 3-5. 메일 허용목록의 `@도메인` 항목은 **그 도메인 전체를 연다** ★

**규칙**: 실 담당자 발송이 금지된 단계에서 `SA_DELIVERY_RECIPIENT_ALLOW` 에는
**정확한 주소만** 넣는다. `@도메인` 은 절대 쓰지 않는다.

**왜**: 코어 `_recipient_allowed`(`agent/delivery.py:140`)가 `lstrip("@")` 후
**도메인 suffix 매칭**을 한다. `@samsung.com` 한 줄이면 전사 아무에게나 자동발송이 나간다.

**실증**(2026-08-15): 값이 `"shaneee.baek,shaneee.baek@samsung.com,@samsung.com"` 이었다.
앞의 두 개만 의도한 것이고 세 번째가 전사를 열어 두고 있었다. 실제 발송 269건은 전부
dssoc(255)·본인(14)이라 사고는 없었지만, **그건 설정이 막아준 게 아니라 리포트 단계가
그 주소를 골라 왔기 때문**이다. 실제로 막고 있던 것은 `run_worker.sh` 의
`SA_DELIVERY_AUTOSEND_SINKS=""` 강제와 "TASK 드라이버는 deliver 를 호출하지 않는다"는
구조적 사실뿐이었다. → `"dssoc@samsung.com,shaneee.baek@samsung.com"` 로 좁힘.

⚠️ **좁힐 때 SOC 주소를 명시적으로 넣어라.** 이전 값엔 `dssoc@samsung.com` 이 없었고
`@samsung.com` 에 얹혀 통과하던 것이라, 도메인 항목만 지우면 정상 발송까지 막힌다.

⚠️ `dry_run` 은 설정 스위치가 아니다 — 발송 도구 응답에서 사후 감지하는 모드다
(`reply_verify_agent.py:175`). "지금 dry_run 이라 안전하다"는 성립하지 않는다.

⚠️ `.env` 는 gitignore 라 **이력이 남지 않는다.** 위험한 기본값을 발견하면 `.env` 만
고치지 말고 추적되는 `.env.example` 주석과 이 문서에 같이 남긴다.

### 3-5b. 같은 제약이 여러 곳에 있으면 **축마다 다르게 열려 있다**

**규칙**: 안전 제약은 SSOT 문서를 만들고 설정 파일들이 그걸 가리키게 한다.

**실증**: 메일 게이트는 2축(`MAIL_MODE` 수신자정책 / `SA_DELIVERY_*` egress)인데 설정이 3곳에
흩어져 있었고 **각 파일이 한 축씩만 안전**했다:

| 위치 | 축① MAIL_MODE | 축② RECIPIENT_ALLOW |
|---|---|---|
| `skill/.env` (실제로 도는 것) | `dssoc_only` ✅ | `@samsung.com` ⚠️ 전사 |
| `mail-send-safe.yaml` | `normal` ⚠️ | 2주소 ✅ |
| `k8s/runtime-configmap.yaml` | `dssoc_only` ✅ | `""` ✅ |

각각은 "지금은" 안전하지만 다른 축을 건드리는 순간 사고다. 더 나쁜 건 **사용자는 자기가
설정해 둔 안전한 파일(yaml)을 기억하는데 실제로 도는 건 다른 파일(.env)** 이었다는 점이다.
→ `docs/MAIL-EGRESS-POLICY.md` 를 SSOT 로 만들고 3곳 전부 주석으로 가리키게 함.

### 3-5c. **값이 같은 중복은 "아직 안 갈라진 중복"이다** ★

**규칙**: 설정 키는 **읽는 저장소 한 곳에만** 정의한다. 중복을 발견하면 값이 같아도 없앤다.
문서로 끝내지 말고 **테스트로 강제**한다 — 문서는 안 읽히지만 테스트는 깨진다.

**실증**: `load_runtime_env` 는 `skill/.env → engine/.env` 순으로 읽고 `if key not in os.environ`
이라 **먼저 잡힌 값이 이긴다**. 엔진 값은 죽으면서 **경고 한 줄 없다**.

- 2026-08-15 오전 시점 중복 7개. 값 불일치 3개. 그중 `SMB_USERNAME`/`SMB_PASSWORD` 는
  **계정 자체가 달랐다** → `skill/.env` 가 사라지면 다른 계정으로 SMB 접속 → **AD lockout**.
- 나머지 4개는 값이 같아서 "무해"해 보였다. 하지만 v3.90 split-brain 도 처음엔 값이 같았다.
  갈라지는 순간이 사고이고, 그 순간에는 아무 신호가 없다.

**어떻게**: 소유권 기준은 이름이 아니라 **"누가 읽느냐"** 다. `grep -rn <KEY> <repo>/src` 로 센다.

- 이름이 도메인인데 코어 소유였던 것: `WEB_USER_AGENT`(코어 web_fetch_tool),
  `SA_WEB_SSO_*`(코어 browser_tool), `SA_TASK_REASONING_EFFORT`(엔진 harness/runner.py **만**).
- 이름이 코어인데 스킬 소유였던 것: `WEB_MAX_PAGES_PER_DOMAIN`, `WEB_VULN_PROBE_ENABLED`
  (엔진 참조 0곳). `GITHUB_*`/`CONFLUENCE_*`/`JENKINS_*` 도 엔진 참조 0곳의 死값이었다.
- **다르게 유지해야 하는 "중복"도 있다**: digisecu 게이트웨이의 `SECU_AGENT_PG_DSN` 은 같은 DB 를
  read-only 롤로 읽는다. 이건 중복이 아니라 권한 분리 — 통일하면 오히려 권한이 넓어진다.

→ `docs/CONFIG-OWNERSHIP.md`(SSOT) + `service/tests/test_env_hygiene.py` 6건. 중복 7 → **0**.
⚠️ 테스트를 넣었으면 **일부러 위반시켜 실제로 깨지는지 확인**한다(안 깨지는 테스트는 장식이다).

### 3-5d. 중복을 지우면 **가려져 있던 死값이 처음으로 쓰인다** ★

**규칙**: 중복 제거 후에는 반드시 **실기동**으로 확인한다. 스위트 통과는 증거가 아니다.

**실증**: engine/.env 의 `SA_PLUGINS="${HOME}/…"` 는 원래부터 깨진 값이었다 —
`load_runtime_env` 는 값을 **원문 그대로** 대입하고 `expandvars` 를 **하지 않는다**.
skill 의 절대경로가 first-wins 로 이겨서 여태 가려져 있었다. 중복을 지우자마자
`PluginLoadError: plugin 파일 없음: ${HOME}/…` → 플러그인 0 → **도메인 능력 0 → 워커 전멸**.

- 전체 스위트 **1898 passed 가 이걸 못 잡았다**(테스트는 conftest 로 플러그인을 따로 붙인다).
  잡은 건 `load_runtime_env(load_plugins=True)` 한 줄짜리 실기동 스모크였다.
- 사전 점검도 놓쳤다: 값 동일성을 `os.path.expandvars` 로 비교해 `same=True` 가 나왔다.
  **런타임이 안 펼치는데 비교만 펼쳤다.** 검증은 런타임과 같은 방식으로 해야 한다.

**어떻게**: 중복 제거는 "같은 값 하나 지우기"가 아니라 **"이기고 있던 쪽을 내리는 것"** 이다.
져 있던 값이 처음 쓰이므로, 지운 뒤 실기동 스모크(플러그인 로드 + TaskPlan 개수 + DB 연결)를
반드시 돌린다. → `test_env_values_have_no_unexpanded_variable_references` 로 고정.

### 3-5e. 모듈을 지울 땐 **import 말고 경로 문자열도** 세라 ★

**규칙**: 파일/패키지 제거 전 참조 조사는 `import` 문법만이 아니라 **경로 리터럴**까지 훑는다.

**실증**: 루트 `webapp/` shim 제거 전에 `from webapp`·`import webapp` 만 grep 해서 "부르는 곳
없음" 으로 판단했다. 전체 스위트에서 **7건이 깨졌다** — `tests/test_webapp_agent_transcript_ui.py`
가 `Path("webapp/ui/index.html").read_text()` 로 **문자열 경로**를 읽고 있었다.

```bash
# 부족했던 조사
grep -rn "from webapp\|import webapp" --include='*.py'
```

사본 삭제 후 "되살아나지 않는지" 검사로 바꿨다.

### 3-5f. 재시도 예산을 적기 전에 **가드가 무엇을 세는지** 확인한다 ★★

**규칙**: 워커 규약에 "N회까지 허용"을 쓸 때는 코어 가드의 **카운트 단위**를 먼저 읽어라.
`repeat_error.py` 의 `HALT_THRESHOLD=2` 는 **연속(consecutive) 동일 에러 2회**다.
즉 거부 직후의 **첫 재시도가 곧 2회차 = halt** 다.

**실증(2026-08-16)**: github halt 을 고치려고 4개 worker.md 에
*"One repair attempt per finding — fix it once and resubmit once"* 라고 적었다.
같은 날 4도메인 동시 실행에서 **dev_web·smb 가 둘 다 `repeat_error_halt`**:

```
dev_web: … dev_web_browse → dev_web_submit_finding → dev_web_submit_finding  ← 죽음
smb    : … smb_task_python → smb_submit_finding → smb_submit_finding         ← 죽음
```

**내가 쓴 규약이 halt 조건 그 자체였다.** 워커는 지시대로 "한 번 더" 냈고 그게 halt 였다.

살아남은 github(같은 날 05:05)은 우연이 아니다 — 거부 후 `github_browse` 를 **사이에 끼워**
연속 카운터를 리셋했다. 그게 유일하게 재시도를 살리는 동작이다.

**어떻게**: 예산이 아니라 **인접성**으로 쓴다.
> "submit 을 **연속 두 번 부르지 마라.** 거부 후엔 ① 지금 닫거나 ② 증거를 실제로
> 가져오는 도구 호출을 **먼저** 하고 그다음에 한 번만 더 낸다."

⚠️ "한 번 더 허용"처럼 **횟수**로 쓰면 워커는 중간 증거수집 없이 바로 재제출한다.

**★★ 2026-08-17 — 자기 매칭의 더 나쁜 형태: `pkill -f` 는 자기 셸을 죽인다.**
잘못 띄운 루프 하나를 정리하려고

를 실행했다. 이 명령의 **셸 명령줄 자체에 그 문자열이 들어 있어서** `pkill` 이

⇒ **`pkill -f` 를 쓰지 마라.** `pgrep -f` 로 PID 를 **먼저 출력해 눈으로 확인**하고


     (`pass done`, `큐 소진`)을 보는 편이 자기매칭에 면역이다.

## 4. 게이트·판정 규칙 작성

### 4-1. 값-형상 규칙의 문자는 base64·비밀번호 문자집합을 피한다

**실증**: `!`/`?` 를 "코드 구두점"에 넣었더니 실제 비밀번호 `1q2w*e4r!` 가 죽었고,
`==`/`++` 를 "코드 연산자"에 넣었더니 **base64 패딩** 1,090건이 죽었다.
안전한 문자: `(` `)` `[` `]` `{` `}` `|` `&` `<` `>` `;` `,`

### 4-2. 경로 규칙에 **확장자**를 넣지 않는다

**실증**: `_CODE_OR_SAMPLE_PATH_RE` 를 구조화 시크릿에 적용하면 `.java` 매치로
#18333(진짜 private key)이 죽는다. 디렉터리 경계·파일명 규약·샘플 접미만 쓴다.

### 4-3. 생성 경로마다 규칙이 다를 수 있다 ★

**규칙**: detector 가 만든 kind 와 **모델이 지어낸 kind** 에 같은 화이트리스트를 쓰지 않는다.

**실증**: `submit_finding`(LLM 서술형) 경로에 스캔 경로용 `is_reportable_secret` 를 그대로 썼더니
**#18866(진짜 Grafana 토큰 + 동작하는 curl)이 `.md` 라는 이유로 죽었다**. submit 경로의 kind 는
모델이 만든 문자열이라 "미지 kind → 코드/문서 경로면 제외" 분기로 전멸한다.
→ `is_reportable_submitted_secret()` 분리(픽스처/벤더 + 값 형상만).

### 4-4b. hit 조각만으로 판정이 안 되면 **본문을 보여줘야** 한다 ★

**규칙**: 규칙이 못 잡는 이유가 "정보가 없어서"면 규칙을 넓히지 말고 **입력을 늘려라.**

**실증(#18900)**: `ca-cert.pem` 의 PEM 인증서 한 덩어리를 detector 가 `high_entropy_string`
**8조각**으로 쪼갰다. 게이트는 hit 단위로 `kind`/`masked`/`path` 만 보는데,

- `path` — `ca-cert.pem` 은 코드/샘플 경로가 아니라 통과
- `masked` — 조각 하나(`MIIE****…CQYD`)로는 인증서인지 개인키인지 **원리적으로 구분 불가**
  (둘 다 DER base64 라 `MII` 로 시작한다)

넓은 경로 규칙(`\.pem$`)으로 때우면 `privkey.pem` 이 같이 죽는다(4-2 와 같은 함정).
⇒ `any_reportable_hit(..., document=...)` 로 **파일 본문**을 넘겨 `BEGIN CERTIFICATE` 유무로
판정. 본문을 못 구하는 호출부는 인자를 안 주면 기존 동작 그대로다(무영향).

**딸린 규칙**: 인증서 제외는 **개인키 마커가 없을 때만**. 이 순서를 뒤집으면 KEEP #18333 이
죽는다. "공개가 전제인 것(인증서·공개키)"과 "유출이 문제인 것(개인키)"을 한 규칙에 묶지 마라.

**파일명 휴리스틱은 양방향으로 틀린다**: 후보 93건 중 3건이 `public_key.pem`(공개키인데
이름은 key), 그리고 `cert.pem` 이 개인키를 품을 수도 있다. 이름이 아니라 내용이다.

**★ 실제로 그랬다 (2026-08-16 재분류)**: 후보 92건의 본문을 되가져와 판정하니

| 판정 | 파일 | finding |
|---|---|---|
| 공개 인증서(오탐) | 12 | 68 |
| **인증서 + 개인키 동봉(진짜 유출)** | **2** | **24** |

`JASMIN/jasmin-frontend-nginx/certs/jasmin_cert.pem` — 이름은 `_cert` 인데 안에
`BEGIN PRIVATE KEY` 가 같이 들어 있었다. `aiops/redfish-proxy/…/aiops.samsungds.net.pem` 도 동일.
**파일명으로 일괄 처분했다면 진짜 TLS 개인키 유출 2건(24 finding)을 닫을 뻔했다.**
"개인키 마커가 있으면 무조건 제외 안 함" 순서가 정확히 이걸 살렸다.

### 4-4c. 역적용 0건은 "안전 확인"이지 "정리 완료"가 아니다

**실증**: 인증서 규칙을 github finding 18,112건에 역적용했더니 차단 0건 · KEEP 4건 생존.
좋아 보이지만 0건의 이유는 **저장된 finding 에 파일 본문이 없어 규칙이 발동할 수 없어서**다.
같은 부류 open finding 93건은 그대로 남는다. 역적용을 보고할 땐 **왜 그 숫자가 나왔는지**를
같이 내야 한다 — 안 그러면 "소급까지 끝났다"로 읽힌다.

### 4-4. 민감 PII/개인키가 소급 대상에 뜨면 **자동 처분 금지**

반드시 증거를 열어 본다. 2026-08-15 소급 정리 165건 중 27건이 `private_key_block`·`credit_card`
였고, 전수 확인 결과 전부 벤더 테스트 인증서(`badkey.pem`)·SVG 좌표 숫자였다 — 하지만
확인 없이 닫았다면 진짜를 닫을 수도 있었다.

## 5. 협업·경계

### 5-1. 엔진(`secu-agent`)은 무수정. 필요하면 CORE-ASK 문서로 요청한다

`docs/core-ask-*.md` 형식: 증상(라이브 재현) → 기제 → 정확한 변경안 → 검증 방법 →
**요청하지 않는 것**. 마지막 항목이 중요하다 — 가드를 약화시키자는 요청이 아님을 분명히 한다.

### 5-2. 근거가 뒤집히면 그 근거를 인용한 설정 주석까지 같이 정정한다

**실증**: 엔진 `.env` 주석이 *"GaussO3.2 벤치: 빈-content 0/3·판단품질 8/8"* 로 기본값을
정당화하고 있었는데, 재측정에서 **빈-content 5/6** 이 나왔다. 숫자만 보내지 말고
"그 주석의 결론이 뒤집혔다"를 명시해야 상대가 판단할 수 있다.

### 5-3. 사용자 결정을 뒤집는 제안은 그렇게 말하고 한계도 같이 낸다

모델 교체 제안 시 "이건 A/B 로 내린 결정을 뒤집는다" + "8타깃이 전부 클린이라 **탐지력은
비교 못 했다**" + "gauss-o32 는 같은 날 실제 유출을 찾은 실적이 있다"를 함께 냈다.
유리한 숫자만 내면 결정이 왜곡된다.

## 6. 4도메인 파이프라인은 **축마다** 갈린다 (2026-08-30)

사용자 지시: *"report 작성/발송 파이프라인은 네 개 도메인 다 동일하게 맞추라고"*

한 건씩 발견하며 매번 다른 진단을 내놨다 — "smb만 본문 저장 경로가 다르다" → 다음엔
"github만 표식을 안 단다" → 다음엔 "dev_web만 본문이 1건짜리다". **축을 하나씩 보면
끝이 안 난다.** 전 축을 한 판에 비교해야 한다.

### 6-1. 실측한 분기표 (2026-08-30)

| 축 | smb | dev_web | github | confluence |
|---|---|---|---|---|
| 스레드 만드는 곳 | 제출 도구 | 제출 도구 | 보고 패스 | 보고 패스 |
| `agent_verification` 표식 | ✗ | ✓ | ✗ | ✓ |
| 검증 게이트(스레드 전) | ✗ | ✗ | ✓ | ✓ |
| 본문이 묶는 단위 | host 전체 | **finding 1건** | repo 전체 | space 전체 |

### 6-2. ★ 표식과 게이트가 다른 자리에 있으면 조합이 어긋난다

    표식 O + 게이트 O   confluence   정상 19/19
    표식 X + 게이트 O   github       268개 대상이 스레드 없이 영구 차단   ← 사고
    표식 O + 게이트 X   dev_web      게이트가 무의미
    표식 X + 게이트 X   smb          게이트 없음

`agent_verification` 은 **제출 시점에만 정직하게 달 수 있다**(method/source 를 아는 건
그걸 찾은 워커뿐이다). 그런데 게이트는 보고 패스에 있었다. 앞뒤가 갈려서 네 조합이
생겼고 그중 하나가 사고였다.

⇒ **표식과 그 표식을 보는 게이트는 같은 계약 안에 둔다.** 도메인마다 따로 구현하지
않는다 — `finding_verification.stamp_agent_verification` 하나로 모았다.

### 6-3. ★ 조용한 누락은 `pipeline_run.detail` 에만 남는다

github 보고 패스는 매 tick `skipped_unverified: 287` 을 찍고 있었다. 그 숫자는 화면
어디에도 없었고 몇 주간 아무도 몰랐다. 게이트를 통과시키자 이번엔
`skipped_unknown_scope: 294` 가 나왔다 — **게이트가 층으로 쌓여 있었고 하나를 열면
다음 것이 나온다.** 층마다 카운터는 있는데 어디에도 안 보였다.

⇒ 큐를 걸러내는 카운터는 **화면에 올리거나 최소한 조회 가능한 자리**에 둔다.
   "0건" 과 "전량 차단" 이 같은 모양이면 안 된다.

### 6-4. ★ 같은 함정을 하루에 세 번 밟았다 — asset 형태가 둘이다

    https://github.samsungds.net/ORG/REPO/...   294건
    github:ORG/REPO/commit/<sha>                  7건

한쪽만 벗기는 코드를 세 곳에서 만났다:
1. 내가 쓴 담당자 소급 스크립트 — 193개 중 **3개**만 잡혔다
2. `repo_from_finding` — 294건이 통째로 `unknown` 이 되어 버려졌다
3. (같은 계열) 러너 최상단 import 가 부트스트랩을 끌어와 테스트 플래그가 갈렸다

⇒ **DB 에서 식별자를 뽑는 코드는 형태 분포를 먼저 재라.** `LIKE 'github:%'` 같은
   단일 접두 가정은 조용히 대부분을 버린다. 뽑은 뒤 건수를 원본 건수와 대조하라.

### 6-5. 티켓 단위와 본문 단위는 같아야 한다

콘솔의 티켓 축은 **src**(host/site/repo/space)다. 본문이 finding 1건짜리면 화면은
"발견 5" 인데 메일엔 1건만 적힌다. dev_web 이 그 상태였다.

⇒ 본문은 **src 의 finding 전부**를 묶고, **제출마다 다시 만든다.** 그래야 마지막 제출
   뒤에 완전해진다 — "전부 들어오면 만든다" 를 별도 완료 신호 없이 만족한다.
   ⚠️ 완료 신호를 따로 두면 그 신호가 안 오는 경로에서 본문이 영영 안 생긴다.

### 6-6. 결정을 모르는 적대검증은 정상 동작을 버그로 판정한다

codex 가 "앞부분만 읽고 `scanned` 로 종결 = 데이터 손실" 이라고 Critical 을 냈다.
그런데 *"파일은 앞부분이라도 보도록"* 이 사용자 결정이었다 — 상한은 **읽기 길이**지
제외 기준이 아니다. 그 결정에서 이건 의도한 동작이다.

`scan_cap_bytes` 컬럼 + 상한 사다리를 만들려다 사용자가 잡았다.
⇒ 적대검증 지적은 **결정 문맥과 대조한 뒤** 반영한다. 검증자가 모르는 결정이 있으면
   그 지적은 "코드가 결정과 다르다" 가 아니라 "검증자가 결정을 모른다" 일 수 있다.

### 6-7. DRM 은 통제가 아니다

큰 PDF 를 앞부분만 읽으려다 **PDF 가 아니라 DRM 래퍼**(`<## NASCA DRM FILE`)임을 발견했다.
"DRM 걸린 문서는 통제가 적용돼 위험이 낮다" 로 설계하려다 사용자가 잡았다 —
**사내 AD 접속이면 NASCA 권한이 열려 대부분 읽을 수 있다.**

⇒ DRM 여부를 위험도 완화 근거로 쓰지 않는다. 용도는 "왜 본문을 못 읽었나" 를 구분해
   남기는 것뿐이고, 판정은 **이름·경로·형제 파일**로 한다.
   ⚠️ ADFS/SSO 로 안 풀린다 — SSO 는 웹 시스템에 쿠키를 심고, DRM 복호화는 NASCA
      클라이언트가 깔린 엔드포인트에서 일어난다. 스캐너는 SMB 로 원시 바이트를 읽는다.

## 7. 죽은 계약을 살릴 때 (2026-08-31)

`_shared/thread_adapter.py` 는 2026-08-26 에 잘 쓰인 계약이었다. 머리말은 정확했고
테스트도 있었다. 다만 **호출부가 0** 이었다 — 닷새 동안. 그걸 4도메인에 실제로
등록하면서 배운 것들.

### 7-1. 계약이 요구하는 것과 도메인이 가진 것을 **먼저 표로 그린다**

등록을 시작하기 전에 슬롯 × 도메인 표를 실측으로 채웠다. 그러지 않았으면
빠진 것을 만나는 족족 거짓 래퍼로 메웠을 것이다.

| 슬롯 | smb | github | confluence | dev_web |
|---|---|---|---|---|
| `finding_ids` | 있음 | 있음 | 있음 | **없음**(단수 `finding_id`) |
| `schedule_retry` | `schedule_communication_retry` | `schedule_recheck_retry` | 같음 | `retry_if_status`(기대상태 필요) |
| `build_report` | **없음**(LLM 융합) | `build_report_for_thread` | 같음 | **없음**(LLM 융합) |
| `list_threads` | `mail_threads_overview` | `*_report_threads_overview` | 같음 | 같음 |

★ **필수 슬롯을 못 채우면 계약을 고친다 — 래퍼로 메우지 않는다.**
`build_report` 를 필수로 두면 smb·dev_web 이 `NotImplementedError` 를 던지는
껍데기를 끼우게 된다. 그건 계약이 거짓말하는 것이다. 선택 슬롯으로 내리고
`supports_build()` 로 물어보게 했다.

같은 이유로 `supports_recheck()` 를 고쳤다. 원래 `recheck and deliver_recheck` 둘 다를
요구했는데, 그러면 융합 도메인 둘이 **영원히 False** 다 — 재검증을 할 수 있는데
없다고 말하는 것이다. 실행 가능성은 `deliver_*` 가, 미리보기 가능성은 `build`/`recheck`
가 정한다. 두 축을 하나로 묶고 있었다.

### 7-2. `claimable_statuses` 는 **러너 호출부**에서 읽는다

dev_web 을 `("report_ready", "reverify_requested")` 로 썼다. 그럴듯했지만 둘 다 틀렸고,
`reverify_requested` 는 상태 어휘에 **있지도 않았다.** 러너를 실제로 열어 보니
`dev_web_report_agent:266 status="reported"`, `dev_web_reverify_agent:120
status="reply_received"` 였다.

맞춰 놨으면 dev_web 만 조용히 idle 이 된다 — 2026-08-26 에 겪은 그 사고다.
**상태 어휘는 정본에서 읽고, claimable 은 claim 호출부에서 읽는다.** 둘 다 추측 금지.

### 7-3. 쌍둥이는 어댑터도 쌍둥이가 된다 — 생성기로 짓는다

`github_report_agent._handle_thread` 와 confluence 판은 34줄 중 **1줄** 차이였다
(`state.<도메인>_report_thread_set_status`). 어댑터를 따로 쓰면 쌍둥이가 셋이 된다.
`_shared/report_thread_adapter.build_report_thread_adapter(domain, coord_key, …)` 하나로
짓고, 도메인 파일은 13줄이 됐다.

⚠️ 그렇다고 넷을 다 한 생성기에 넣으면 안 된다. smb·dev_web 은 상태 어휘도, 만들기/배달
융합 여부도 다르다. **넷을 같은 모양으로 맞추는 것과 같은 코드로 맞추는 것은 다르다.**

### 7-4. 목록에 본문을 실으면 안 된다 — 본문 열 이름이 도메인마다 다르다

`*_overview` 는 `SELECT *` 라 `report_html`(실측 8,882자)을 그대로 들고 온다.
리드가 큐를 훑을 때 그게 컨텍스트로 들어간다. 공용 투영기에서 한 번에 막았다.
⚠️ "없다" 와 "안 실었다" 는 다르다 — `has_report_body` 로 사실은 남긴다.

### 7-5. 요약 키가 같은 이름으로 다른 것을 담고 있었다

`report_json["summary"]` — smb·dev_web 은 문장, **github 은 통계 dict**
(`{"highest_severity":"high","masked_hit_count":785,…}`), confluence 는 없음.
첫 키를 그냥 쓰면 회신 LLM 에게 카운터 뭉치를 산문이라고 건넨다.
⇒ 산문 선택기는 **문자열만 받는다**(`_first_text`).

그리고 github·confluence 는 산문이 `report_html` **안에만** 있었다. 그래서
"우리가 뭐라고 보냈는지" 를 HTML→텍스트로 뽑아 컨텍스트에 넣었다. 이게 없으면
담당자가 "어느 폴더요?" 라고 물었을 때 우리 원문을 못 본다.

### 7-6. 양식이 굳은 게 아니라 **읽을 것이 없었다**

> "지금 메일 답장 양식이 너무 정해져있나본데? 폴더 위치를 물었는데 답변은 그냥
>  조치방법 답변이라 이상하잖아." (사용자)

원인은 양식이 아니었다. 회신 워커가 받던 정보가 **좌표뿐**이었다 —
`thread_id/host/finding_id/attempt` 와 `finding_id=N asset=…`. 담당자가 무엇을 묻든
답할 재료가 없으니 고정 `reply_kind` 셋 중 하나로 떨어졌다.

⇒ 뒤집었다. **LLM 이 문장을 쓰고, 검증된 블록을 덧붙인다.**

    이전   양식을 고른다 → 양식이 문장을 정한다
    이후   LLM 이 답을 쓴다 → 필요하면 블록을 고른다

경계는 명확히 둔다. LLM 이 쓰는 것은 `answer` 뿐이고 인사·서명·회신요청은 코드가,
절차 안내는 **블록**이 갖는다 — 틀린 절차를 그럴듯하게 지어내는 것이 이 도메인에서
가장 비싼 실수다. 블록은 LLM 이 **고르기만** 한다.

★ 블록 문구를 **새로 쓰지 않았다.** 이미 발송 중인 조치요청 메일의 문장을 그대로
가져왔다. 최초 메일과 회신이 같은 사안에 다른 절차를 말하면 담당자에겐 DSSOC 가
말을 바꾼 것으로 보인다. 드리프트는 테스트가 잡는다
(`test_reply_blocks_no_drift.py`). smb 는 아예 방향을 뒤집어 `build_how_to` 가
블록을 **읽게** 했다 — 출처가 하나면 드리프트가 원천적으로 없다.
(⚠️ 뒤집을 때 출력이 **바이트 동일**한지 원본과 대조했다. 프로덕션 메일 문구다.)

### 7-7. 티켓 번호는 회신 매칭의 1차 키다

기존 매칭은 제목 태그였고, 코드 주석이 그 취약함을 이미 적어 두고 있었다 —
*"SMB 정규식은 접두를 요구하지 않아서 순서가 바뀌면 다른 도메인 답장이 smb 로
잘못 분류될 수 있다."* 게다가 같은 host 의 이번 주/지난 주 스레드가 같은 태그였다.

`[티켓 SMB00024]` 를 제목 **앞**에 두면 `RE:`/`FW:` 가 붙어도 살아남고, 스레드 행
id 라 주차 구분 문제도 없다. 본문 서명에도 남겨 사람이 제목을 고쳐도 붙는다.

⚠️ smb 는 이미 콘솔이 `SMB%05d` 를 보여주고 있었다. **재발급하지 않았다** —
사람이 이미 본 번호를 바꾸면 같은 티켓이 두 번호로 불린다.

### 7-8. 내가 "smb 만 있다" 고 적은 것이 두 번 틀렸다

어댑터 주석에 "답장 대조는 smb 만 한다" 고 적었다. 확인해 보니 POP3 수집기는
**4도메인을 다 라우팅**하고 있었다(`mail_inbound.py:596`) — smb 는 `mail_message`,
나머지 셋은 `service_reply_message` 로 들어간다. 테이블 이름이 다르다는 이유로
셋의 답장을 못 읽으면, 담당자가 물어도 회신 워커에겐 질문이 안 보인다.

⇒ 인바운드 조회를 4도메인 공용으로 고쳤다. 다만 실측하면
`service_reply_message` 는 **0행**이다 — 배선은 있고 아직 답장을 받은 적이 없다.
"경로가 없다" 와 "경로는 있는데 데이터가 없다" 는 다르고, 고치는 방법도 다르다.

### 7-9. 회신에서 DSSOC 가 조용히 빠지고 있었다

정책은 담당자(To) + DSSOC(Cc)다. 그런데 smb reply-all 경로는 **받은 메일의 To/Cc 를
그대로** 쓴다 — 담당자가 DSSOC 를 cc 에 안 넣고 답장하면 우리 회신에서 DSSOC 가
사라진다(SMB00024 실측 `cc=[]`). 조치요청은 정책대로 나가는데 **회신만** 스레드
기록이 끊긴다. 봉투에서 되넣었다.

★ 같은 정책이 두 경로(최초 발송 / 회신)를 지나는데 한쪽만 정책을 알고 있었다.

## 8. 회신 매칭 규칙 — 한 도메인만 정하고 셋은 복사됐다 (2026-08-31)

> "이건 최초에 SMB 기준으로는 헤더+ip기준으로 정했었는데 다른 도메인 기준으로는
>  우리가 정한 적이없어서 이것도 정해야 돼" (사용자)

정확한 지적이었다. 정하려고 재보니 셋은 "덜 다듬어진" 게 아니라 **구조적으로 답장을
받을 수 없는** 상태였다. 결함이 셋 다 조용하다 — 답장이 안 붙어도 예외도 로그도 없다.

### 8-1. 실측 — 셋은 100% 미아였다

| | github | confluence | dev_web |
|---|---|---|---|
| `notified_at` (발송 경계 출처①) | 552건 중 **0** | 44건 중 **0** | **열 자체가 없음** |
| 발신 회신 기록 (출처②) | 0행 | 0행 | 0행 |
| 답장 받을 수 있는 상태의 스레드 | **0** | **0** | **0** |

그리고 `service_report_thread_find_inbound_match_at` 은 경계가 없으면 `return None`.
smb 는 경계가 없어도 매칭한다. **그래서 smb 만 동작했다.**

### 8-2. dev_web 은 다른 도메인의 어휘로 조회되고 있었다

`_service_report_table("dev_web")` 이 **ValueError 를 던졌다** — dev_web 담당자가 답장하면
POP3 수집기가 그 자리에서 죽는다. 게다가 dev_web 은 github·confluence 의 상태 집합으로
조회됐는데, 그 집합의 `awaiting_owner`·`recheck_requested`·`still_open` **셋은 dev_web
상태 어휘에 존재하지도 않는다.** dev_web 어휘는 smb 와 같다(차이는 `report_ready` 하나).

★ **복붙은 이름이 같은 것끼리 붙는다.** `github_report_thread`·`confluence_report_thread`
와 이름이 닮았다는 이유로 dev_web 이 그쪽 함수에 묶였고, 상태 어휘는 smb 쪽이었다.
이름의 유사성은 계약의 유사성이 아니다.

### 8-3. 정한 규칙 (4도메인 동일)

    1차  티켓번호   제목의 [티켓 SMB00024] → (도메인, 스레드) 를 **직접** 확정
                    · 좌표(IP/repo/space/url)를 파싱하지 않는다 → 도메인 오분류 불가
                    · 스레드 행 id 라 같은 대상의 지난 주/이번 주 혼동이 없다

    2차  제목 태그   티켓 표식 이전에 나간 메일의 답장을 위한 폴백
                    후보 = subject_tag 일치 AND status IN <그 도메인의 열린 상태>
                    경계가 있으면 : 수신시각 <= 경계 → 매칭 안 함(과거 주차 보호)
                    경계가 없으면 : **매칭한다** ← smb 규칙으로 통일

경계 요구의 의도는 "보낸 적 없는 스레드에 답장이 붙는 것" 방지였는데, 실제로 막은 건
**발송 기록이 유실된 경우**였다. 답장이 왔다는 것 자체가 우리가 보냈다는 증거다 —
우리 제목 태그를 달고 오기 때문이다. 발송 기록을 제대로 남기는 건 별개 문제이고,
**매칭 규칙이 그 결함의 인질이 되면 안 된다.**

### 8-4. 통일한 것과 통일하지 않은 것

    통일했다      매칭 규칙 · 발송 경계 해석 · 티켓 표식 · 라우팅
    통일 안 했다  상태 어휘(smb·dev_web = 답장 왕복 / github·confluence = 재검증 주기)
                  좌표 열(host / repo / space_key / url)

어휘가 다른 건 상태 기계가 실제로 다르기 때문이지 드리프트가 아니다.
**규칙을 통일하는 것과 어휘를 통일하는 것은 다르다.** 어휘까지 합치면 없는 상태를
찾는 8-2 같은 사고가 난다.

### 8-5. 스탬프는 지우지 않고 **덧붙인다**

티켓 표식은 제목 **앞**에 붙이고 기존 태그는 그대로 둔다. 이유 둘:

- 이미 나간 메일들의 답장은 태그로만 붙는다. 태그를 없애면 그것들이 전부 미아가 된다.
- 표식이 접두라 `RE:`/`FW:` 가 앞에 쌓여도 살아남고, 기존 태그 정규식도 그대로 찾는다.

⚠️ 스레드를 못 찾으면 **찍지 않는다.** 없는 번호를 지어내면 담당자가 그 번호로 답장했을 때
영원히 안 붙는다 — 태그 폴백보다 나쁘다.

### 8-6. RFC 스레딩이 최선이지만 지금은 못 쓴다

`In-Reply-To`/`References` 가 가장 강한 키다. 실측: **받은 답장에는 정상적으로 들어 있다**
(Knox 가 채운다). 그런데 우리가 보낸 메일의 `message_id` 는 전부 NULL 이고
`mail_thread.request_message_id` 는 25건 중 0, `dev_web_report_thread` 는 123건 중 0,
github·confluence 는 그 열조차 없다. **받는 쪽 재료는 있는데 보내는 쪽 기록이 없어
대조가 불가능하다** — 또 하나의 죽은 배선이다. 발송 Message-ID 를 저장하게 되면
그때 0차 키로 올리면 된다.

### 8-7. 1차 키를 도입하면 **그 키가 도메인을 뒤집는 지점**을 따라가야 한다

티켓 번호는 제목 태그보다 강해서 도메인을 갈아치울 수 있다. 그런데 수집기는
도메인으로 **적재 테이블을 고른다**(`mail_message` vs `service_reply_message`).
매칭을 중복검사 **뒤**에 두면 이런 일이 난다:

    중복검사(태그 도메인=smb) → mail_message 조회 → 없음 → "신규"
    매칭(티켓 도메인=github)  → service_reply_message 에 적재
    ⇒ 같은 메일이 매번 신규로 잡힌다(중복검사가 반대쪽 테이블을 본다)

그래서 스레드 확정을 **중복검사보다 먼저** 한다. 1차 키를 넣을 때는 "그 키가
바꾸는 값이 이미 어디에 쓰였는가" 를 역방향으로 훑어야 한다.

### 8-8. 분기가 둘이면 **중요한 쪽에 먼저** 넣었는지 본다

재검증 회신 제목에 티켓을 찍으면서 처음엔 `else` 가지(신규 발송)에만 넣었다.
정작 중요한 건 위쪽 가지 — **담당자 답장에 회신하는** 경로다. 거기 안 찍히면
다음 왕복부터 1차 키가 사라지고 조용히 태그 폴백으로 되돌아간다.
if/else 밖으로 빼서 두 경로가 같은 값을 갖게 했다.

⚠️ 둘 다 **테스트가 아니라 코드를 다시 읽다가** 나왔다. 조용한 실패는 스위트가
   안 잡는다 — 매칭이 안 돼도 예외도 로그도 안 난다.

### 8-9. 순수 코드가 조용히 **부트스트랩 의존**이 됐다

`service_reply_guidance_agent._guidance_body` 가 공용 블록을 쓰기 시작하면서
`plugin/bootstrap.register_all()` 없이는 `RuntimeError` 가 됐다. 이 에이전트는 LLM 도
도구도 안 쓰는 순수 코드라 부트스트랩을 부를 이유가 없다.

스위트에서는 **다른 테스트가 먼저 부트스트랩한 덕에 통과**했다. 그래서 증상이
"단독으로는 통과, 스위트에서는 무관해 보이는 다른 테스트가 실패" 로 나타났다
(`test_reporter_no_longer_calls_the_rest_client`). 순서 의존은 늘 **엉뚱한 곳에서**
터진다.

⇒ 등록형 자원을 쓰는 코드는 **자기가 쓰는 것을 자기가 보장한다**. 등록이 멱등이라
   부트스트랩과 중복돼도 무해하다. "누가 먼저 등록해 줬겠지" 에 기대지 마라.
