1. 현재 상태 요약

초기 분석 당시의 가장 큰 갭이었던 승인 흐름, SQLite 운영 가드, LLM fallback, tool discovery/toolset, checkpoint/rollback, finding lifecycle, scheduler history, browser evidence, report bundle은 대부분 구현 완료됐다. 지금 프로젝트는 단순 SMB 점검 도구가 아니라, 웹 UI/스케줄러/승인/보고서/검증 하네스를 가진 내부 기업 보안 agent 런타임으로 올라왔다.
정확한 설계 설명: 이 프로젝트는 Hermes Agent의 long-running goal/session/scheduler 아이디어를 참고하고, Claude Code source snapshot에서 tool metadata, deferred tool search, permission guardrail 패턴을 참고했다. 여기에 두 프로젝트와 별개로 evidence judgment, reporting contract, masking, domain scope 같은 보안 도메인 contract layer를 추가했다. Hermes가 보안적으로 취약하다고 단정하기보다는, 범용 agent framework를 내부 보안 점검 제품에 맞게 좁히고 강화했다고 보는 편이 정확하다.

프로젝트 계보

Hermes Agent의 핵심 장점은 /goal 기반 persistent goal이다. Hermes 문서에서는 이를 Ralph loop로 설명하며, 목표가 끝났는지 judge가 매 turn 확인하고 미완료면 같은 세션에 continuation을 다시 넣어 장시간 작업을 이어간다. 예약 실행은 로컬 Hermes 기준 /schedule이 아니라 /cron slash command와 cronjob tool이다. AI Secu Agent는 같은 목적의 제품 기능을 schedule tool과 scheduler history로 구현했다.

Claude Code 쪽에서 참고한 부분은 “agent가 오래 도는 구조”보다 “도구를 언제 보여주고, 어떤 권한으로 실행하고, 위험한 호출을 어떻게 승인받는가”에 가깝다. 실제 source snapshot의 Tool interface에는 shouldDefer, isReadOnly, isDestructive, isConcurrencySafe, checkPermissions, maxResultSizeChars 같은 실행 메타데이터가 있고, ToolSearch가 deferred tool schema를 필요할 때만 열어주는 구조다.

현재 가장 강한 부분

  • SMB discovery/walk/review에 특화된 도메인 모델과 안전 정책
  • agent loop, tool registry, deferred tool, capability gate, tool_search
  • approval UI와 approval audit history
  • finding lifecycle, scheduler run history, report bundle
  • browser supervisor evidence capture와 web probe lifecycle 연결
  • pytest + scenario eval + runtime doctor 하네스

Claude Code에서 반영된 패턴

  • deferred tool과 tool_search 기반 schema unlock
  • read-only/destructive/concurrency metadata
  • permission allow/deny/ask와 approval resolver
  • host edit 전 안전장치와 rollback 개념
  • plan mode와 operator 승인 중심의 작업 전환

Hermes에서 반영된 패턴

  • /goal persistent goal, Ralph loop continuation
  • /cron/cronjob 기반 scheduled automation
  • toolset, check_fn, provider fallback 개념
  • LLM provider fallback chain
  • context engine과 long-running session 압축 방향

자체 보안 contract layer

  • evidence judgment로 finding 제출 전 증거 품질 검증
  • secret/PII masking과 raw secret persistence 차단
  • web allowed domain/CIDR, same-origin, URL safety
  • heuristic result를 후보와 confirmed evidence로 분리
  • finding lifecycle, owner/ticket/SLA/report bundle 연결

한 줄 결론

지금부터의 우선순위는 “핵심 런타임 보강”이 아니라 비-SMB 에이전트 품질, 실제 사내 delivery/ticket 연동, owner/risk scoring, Linux 내 배포 운영성이다. MCP/plugin은 사내 특정 유저 환경에서는 필수 우선순위가 아니므로 보류해도 된다.

  -> ChatSession.run_turn()

6. 주요 플로우 차트

6.1 Approval Flow

Destructive tool approval

Agent decides to call host_write / host_edit / bash_evidence / browser_action
  -> Tool.check_permission()
  -> PermissionDecision(ask)
  -> WebSocketApprovalResolver emits ApprovalRequested
  -> UI renders approval card
  -> Operator clicks allow or deny
  -> decision is written to approval_audit
  -> ToolInvoker continues with approved input or fails closed
  -> Approval tab and Report Bundle can later review the decision hash

6.2 Finding Lifecycle / Report Bundle Flow

Finding handoff

AgentType/tool finds issue
  -> evidence file written under evidence_dir
  -> submit_finding or web_vuln_probe calls state.finding_upsert()
  -> finding_lifecycle row gets fingerprint, status, severity, owner/ticket/SLA fields
  -> Findings tab can inspect/update status
  -> Scheduler may create dry-run delivery records
  -> Reports tab builds JSON/HTML bundle:
       metadata + findings + evidence_refs + approval audit hashes + scheduler deliveries

6.3 Browser Supervisor Evidence Flow

Browser capture

browser_session start
  -> Playwright page created
  -> observers attached:
       request, response, requestfailed, console, pageerror
  -> browser_action navigate/click/fill/press/scroll
  -> browser_supervisor capture
       - snapshot text
       - selected HTML
       - screenshot PNG
       - network JSON with query secret redaction
       - console/pageerror JSON
       - screenshot hash diff JSON
  -> metadata JSON points to every artifact

6.4 Scheduler Flow

Scheduled task audit

schedule row due
  -> scheduler_tick starts schedule_fire
  -> child ChatSession executes agent_type prompt
  -> schedule_fire is finished with ok/error and result summary
  -> internal_report_dry_run delivery row is recorded
  -> Scheduler tab shows schedules, recent runs, delivery payload/hash
  -> Report Bundle includes scheduler run/delivery context

6.5 Context Engine Flow

Long-running session context

Chat history grows
  -> ContextEngine policy selected: off / stub / summary / hybrid
  -> cheap compactor stubs bulky tool outputs where safe
  -> LLM summarizer can compress older conversation
  -> ChatSession continues with smaller context
  -> compression stats are available for debugging and tests

7. Claude/Hermes 비교 반영

비교의 핵심은 “어느 프레임워크가 약하다”가 아니라, 각 프로젝트가 잘하는 계층이 다르다는 점이다. Hermes는 장시간 실행과 multi-platform toolset 운영, toolset 단위의 coarse-grained 제어에 강하다. Claude Code에서 참고한 부분은 그 위에서 한 turn 안에 어떤 schema를 보여주고, 어떤 위험도로 실행할지 정하는 per-tool runtime dispatch 패턴이다. AI Secu Agent는 두 패턴을 보안 점검 제품에 맞게 가져오되, finding으로 인정 가능한 증거인지 판단하는 contract layer를 별도로 둔다.

구분 실제 구조 강점 AI Secu Agent 반영
Hermes Agent toolsets.py의 _HERMES_CORE_TOOLS와 TOOLSETS로 노출 도구를 묶고, tools/registry.py의 ToolEntry와 check_fn으로 환경별 사용 가능 여부를 거른다. cron job은 enabled_toolsets로 job별 toolset을 제한할 수 있다. /goal Ralph loop, /cron/cronjob, session/memory/delegation, multi-platform gateway, broad plugin/toolset 운영. 큰 범위의 tool governance는 Hermes식 2-depth 구조가 오히려 더 명확하다. long-running goal, scheduler, context/session 유지, provider fallback, domain/agent_type 단위 tool grouping 방향을 참고했다. 다만 messaging, smart home, TTS, RL training 같은 범용/소비자 자동화 표면은 보안 점검 기본면에서 제외했다.
Claude Code Tool interface가 shouldDefer, isReadOnly, isDestructive, isConcurrencySafe, checkPermissions, maxResultSizeChars를 가진다. ToolSearch가 deferred tool을 검색/선택해 필요한 schema만 unlock한다. 도구가 많아져도 초기 prompt에 모든 schema를 넣지 않고, 위험 도구는 permission pipeline에서 allow/deny/ask로 제어한다. Hermes toolset을 대체한다기보다, 활성 toolset 내부에서 필요한 tool을 더 세밀하게 찾고 실행하는 데 적합하다. Python Tool base에 deferred, is_read_only, is_destructive, requires_capabilities를 두고, tool_search와 approval resolver/audit로 옮겼다.
AI Secu Agent 총 103개 agent tool class를 task domain별로 구성한다. core tool은 항상 보이고, 무겁거나 도메인 특화된 tool은 deferred listing에 이름과 hint만 노출한다. destructive tool은 기본적으로 operator approval을 요구하고, scheduled execution에서는 destructive tool을 차단한다. 내부망 보안 점검에 필요한 SMB/Web/GitHub/Jenkins/Confluence/browser/evidence/finding/report 흐름을 하나의 lifecycle로 묶는다. Claude Code식 tool guardrail 위에 evidence judgment, reporting contract, masking, allowed scope, finding lifecycle, report bundle을 추가했다.

Guardrail과 Contract의 차이

계층 질문 대표 구현 효과
Tool guardrail 이 도구를 지금 실행해도 되는가? is_destructive, is_read_only, requires_capabilities, check_permission, approval resolver, scheduled destructive 차단. 위험한 write/edit/bash/browser action을 무승인 실행하지 못하게 하고, UI가 처리할 수 없는 plan/approval 도구는 registry에서 보이지 않게 한다.
Evidence/reporting contract 도구 결과를 보안 finding으로 인정해도 되는가? evidence_judgment.py, reporting_contract, mask_scanned_text, URL safety, SA_WEB_ALLOWED_DOMAINS, SA_WEB_ALLOWED_CIDRS, browser same-origin response capture. LLM의 추측성 보고를 줄이고, heuristic 후보와 confirmed evidence를 분리한다. 민감값 원문은 저장하지 않고, scope 밖 URL이나 다른 PC/도메인으로 번지는 행동을 막는다.

보안 도메인에 맞지 않아 덜어낸 범용 요소

“범용 요소를 뺐다”는 말은 속도만의 문제가 아니다. 사내망 보안 점검에서는 도구 수가 늘수록 agent가 잘못된 도구를 고르거나, 결과를 증거로 과대해석하거나, 외부 채널에 민감 정보를 내보낼 위험이 커진다. 그래서 기본 노출면은 내부 보안 작업에 필요한 도구로 좁히고, 필요할 때만 deferred search로 열게 했다.

Hermes 범용 요소 왜 기본면에서 제외했나 이 프로젝트의 대응
Discord/Slack/WhatsApp/Signal/SMS/Email gateway, send_message, Yuanbao DM/sticker 보안 finding, 증거 preview, 내부 자산명이 외부/개인 메시징 채널로 나갈 수 있다. 웹 UI, approval audit, report bundle, scheduler dry-run delivery 중심. 실제 delivery는 내부 file drop/webhook부터 검토.
Home Assistant 도구: ha_list_entities, ha_call_service 등 소비자용 자동화/스마트홈 제어는 내부망 보안 점검의 기본 workflow가 아니다. SMB/Web/GitHub/Jenkins/Confluence 같은 기업 보안 도메인 도구로 대체.
TTS, image generation, 범용 vision/video 분석 보고서나 UX 보조에는 쓸 수 있지만, finding 증거 계약의 핵심 경로는 아니다. image_inspect, browser screenshot/snapshot, masked evidence preview처럼 보안 증거에 필요한 형태로 제한.
RL training, generic code execution, MoA/범용 delegation, Kanban worker 기능 장기 실행에는 유용하지만 내부 보안 에이전트의 기본 tool schema에 항상 노출할 필요는 없다. agent, goal, delegate_file_review, scenario eval처럼 보안 작업 단위에 맞춘 실행 경로만 유지.
범용 web_search/web_extract 외부 웹 리서치와 내부망 스캔은 scope, 증거, SSRF 리스크가 다르다. web_fetch, web_crawl, web_resource_probe, web_site_sweep, web_task_scan에 URL safety와 reporting contract를 붙였다.

역량 초기 평가 현재 반영 상태 판단

8. 남은 개선 로드맵

핵심 런타임은 상당 부분 완료됐으므로, 다음은 사내 반입 후 바로 쓸 수 있는 운영 기능과 비-SMB 에이전트 품질을 올리는 쪽이 효율적이다.

우선순위 개선 건 왜 필요한가 완료 기준
P0 Non-SMB agent_type e2e 품질 강화 GitHub/Jenkins/Confluence/Web은 도구 기반은 있으나 SMB만큼 검증된 runbook과 lifecycle e2e가 약하다. 각 agent_type별 seed fixture, tool mock, submit_finding/lifecycle/report bundle까지 이어지는 테스트.
P0 Scheduler controls UI 현재 Scheduler 탭은 read-only history 중심이다. 운영자는 pause/resume/run-now가 필요하다. token-protected pause/resume/run-now API, UI button, audit row, tests.
P1 Internal delivery adapter dry-run delivery는 완료됐지만 실제 사내 report/ticket/channel delivery는 아직 없다. file drop 또는 internal webhook adapter, retry/backoff, delivery status history.
P1 Owner/risk scoring finding이 많아질수록 우선순위와 담당자 추정이 중요해진다. asset criticality, severity, exposure, recurrence 기반 score와 owner field 추천.
P1 Secret validation/revocation workflow token-like 문자열이 실제 위험인지, rotate가 필요한지 판단해야 한다. allowlisted provider에 한해 dry-run validation, rate limit, no raw secret persistence.
P2 Browser downloads/HAR V2는 network summary를 남기지만, 파일 다운로드와 full HAR body capture는 아직 제한적이다. safe download capture, body size cap, retention policy, optional HAR export.
P3 MCP/plugin packaging 현재 단일 내부 사용자 환경에서는 낮은 우선순위. 조직 확장 시 필요. connector plugin interface, allowlist, install/disable lifecycle.
