# 재는 방법부터 의심하라

이 레포에서 **기술적 결함보다 재는 방법이 더 자주 틀렸다.** 2026-08-23 에 네 번,
2026-08-28 에 다섯 번. 매번 사용자에게 잘못된 숫자를 먼저 말한 뒤 정정했다.

패턴이 하나다: **잰 값이 0이거나 놀랍게 작으면, 대상이 없는 게 아니라 내가 잘못 재고 있다.**

---

## 0건이 나오면 먼저 의심할 것

| 증상 | 실제 원인 (실측) |
|---|---|
| `grep -rl KEY` 로 소비자 0 | 주석·docstring 언급을 소비자로 셌다. **읽기 패턴**(`environ.get`/`_int_env`/`getenv`)으로 다시 세라 |
| 감사 로그에 도구 호출 0 | ① glob 이 한 단계만 봤다 — 세션은 `<lead>/session-*/` **아래**다 ② 필드가 `payload.name` 인데 `d["tool"]` 을 봤다 |
| 리드가 큐를 못 본다 | `list_targets(status=None)` 로 쟀다. 리드는 `claimable_statuses` 를 **상태별로** 묻는다 |
| 목록이 잘려 도달 불가 | `limit` 상한을 확인 안 했다. 도구마다 다르다(리드 200 / hit 1000) |
| DB 규모 0 또는 이상 | `state_domain.connect()` 가 `sql.replace("?","%s")` 를 한다 — **정규식 든 SQL 을 망가뜨린다**. psycopg 로 직접 붙어라 |
| 테스트가 통과 | 실패할 수 있는지 확인 안 했다 → **mutation check** |

## 반드시 하는 것

**1. "0건" 은 방법을 함께 말한다.**
"호출 0" 이 아니라 "audit.log.jsonl 재귀 검색, `payload.name` 기준 0" 이다.
범위를 못 붙이겠으면 아직 잰 게 아니다.

**2. 배선 판정은 "언급"과 "실제 호출"을 가른다.**
`grep` 은 주석을 센다. 호출부를 찾을 땐 호출 문법으로 찾아라.
반대도 있다 — 상수를 거쳐 읽히면 문자열 grep 이 놓친다
(`RECIPIENT_ALLOW_ENV = "SA_DELIVERY_RECIPIENT_ALLOW"`). **양방향으로 틀린다.**

**3. 테스트를 쓰면 배선을 끊어서 깨지는지 본다.**
정규식 `[^)]*?` 가 `finding_update(int(fid), status=...)` 의 중첩 괄호에서 끊겨
아무것도 못 잡은 적이 있다. 되돌려도 통과하는 테스트는 테스트가 아니다.
탐지기를 쓰면 **탐지기가 실제 호출 모양을 잡는지도** 테스트로 고정하라.

**4. pytest 는 절대 동시에 두 개 돌리지 않는다.**
공유 테스트 DB 를 TRUNCATE 한다. 동시에 돌리면 행이 사라지고,
그걸 **로직 버그로 오진**하게 된다(2026-08-28 에 여러 턴을 태웠다).

⚠️ **`pgrep -f` 로 확인하면 안 된다 — 자기 자신을 잡는다.**
   `bash -c` 래퍼의 명령 문자열에 `python -m pytest` 가 통째로 들어 있어서
   `pgrep -f "m pytest"` 도 `pgrep -f "venv/bin/python -m pytest"` 도 **래퍼를 매칭한다.**
   실패 방향이 고약하다: 없는 pytest 를 "진행중" 으로 오판 → 가드에 막혀 실행 안 됨 →
   결과 없음 → 재시도 → **중복 실행**. 2026-08-29 에 같은 스위트가 3개 동시에 28분을 돌았고
   `until ! pgrep ...` 대기 루프가 **자기 자신을 기다리는 교착**까지 만들었다.

   실행파일로 판정하라:
   ```bash
   for p in $(pgrep -f "m pytest"); do
     c=$(cat /proc/$p/comm 2>/dev/null)
     [ "$c" = "python" -o "$c" = "python3" ] && echo "진짜 pytest: $p"
   done
   ```
   그리고 긴 스위트는 대기 래퍼로 감싸지 말고 `nohup … > /tmp/x.log 2>&1 &` 로 띄운 뒤
   로그 파일을 읽어라. 래퍼가 없으면 자기매칭도 교착도 안 생긴다.

⚠️ **`pkill -f` 는 쓰지 마라.** 이 워킹트리는 다른 세션과 공유한다 — 2026-08-29 에
   `pkill -f "m pytest"` 로 남의 스위트를 죽였을 가능성이 있다. 내가 띄운 PID 만 지정해서
   죽인다.

**5. 범위를 "숫자가 크다"는 이유로 좁히지 마라.**
hit 판정 기본 카테고리에서 `semiconductor_process` 4,182건을 건수가 크다고 뺐다.
그런데 여기선 **반도체 공정 자료가 핵심 위험**이다. 범위는 위험도로 정한다.

**6. 적대적 검증 결과도 그대로 믿지 마라.**
서브에이전트 조사도 같은 함정에 빠진다 — 오늘 "set_hit_verdict 0회" 라고 보고했는데
실제로는 3회 호출에 전부 success 였다. 판정이 행동을 바꾼다면 **직접 재라.**

## 이 레포 특유의 함정

- `smb_share.hits_count` 는 탐지 건수가 **아니다** — finding 유무 힌트(0/1).
  raw 15,500건인 공유가 0으로 보인다.
- smb 만 `claimable_statuses ⊂ statuses` 다(4/8). 큐의 91%가 `print$ ignored` 라
  무필터 목록은 일감이 0건이다. 다른 3도메인은 전부 claimable 이라 이 함정이 없다.
- `finding.status` 어휘는 `{open, triaged, false_positive, accepted_risk, remediated}`.
  `"resolved"` 는 없다 — 넣으면 ValueError 가 나고 호출부가 삼킨다.
- `except` 블록 안에서 없는 심볼을 쓰면 **삼키려던 실패가 더 큰 실패**가 된다.
  `state_domain` 에는 모듈 로거(`log`)가 없다.

## 보고할 때

숫자는 결론이다. "9건" 과 "53건, 그중 실제 키 1개" 는 사용자가 내릴 결정이 다르다.
틀린 방향이 **거짓 안심**이면 버그보다 나쁘다 — 잔존 0 이라고 했는데 19행이 남아 있었다.
