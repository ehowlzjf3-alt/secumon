# v3.90 — candidate ledger 침묵 게이트 (정직성 게이트 #2)

> **문제(실사고)**: gpt-oss 워커가 confluence 후보 22건을 관찰하고도 finding 을
> 하나도 제출하지 않고 text-only 로 종료 — 기존 가드는 전부 **제출 시** 발동하는
> 허풍 방지 문(evidence judge, 정책 A browser 검증)이라 발동 기회조차 없었다.
> 문이 한쪽으로만 달려 있었고, 그 비대칭이 약한 모델을 침묵 쪽으로 밀었다
> (제출=기각 위험, 침묵=무벌칙). 반대쪽 문의 원형은 github 스캐너에만 있었다
> (`scanner.py` "candidates>0 & detail 0 → error" — 도메인 로컬, 부모 미전파).

## 설계 — 장부 대조 (도메인-프리, 등록형)

**코어는 "후보"가 무엇인지 모른다.** 장부(`metadata["candidate_ledger"]`)와
대조 게이트만 코어에 두고, 후보를 세는 일은 도구/plugin 이 한다.

| 조각 | 위치 | 내용 |
|---|---|---|
| 장부 | `agent/candidate_ledger.py` | seen/submitted/triaged/sources/samples. `record_candidates_seen` / `record_candidates_accounted` 공개 API |
| counter 훅 | 〃 + `tools/invoker.py` | `register_candidate_counter(CandidateCounter)` — invoker 가 ToolSuccess 후 실행(도구 코드 0줄, 입력 deep-copy, 예외 격리, record-only). 미등록 tool 은 fast-path |
| 코어 배선 | `tools/scan_text.py`, `tools/submit_finding.py` | scan hit → seen, submit 성공(양 경로) → submitted. **기각된 submit 은 부채 미해소** |
| 합법 출구 | `tools/triage_candidates.py` | 후보별 기각 사유를 `candidate_triage.jsonl` 에 감사가능 기록(F3 마스킹) → triaged. generic fallback + operator toolset 등록 |
| 게이트 | `engine.py` text-only 분기 | plan → finding_followup → **candidate_ledger** → execution. 발동조건: enforce & seen>0 & submitted==0 & triaged==0 & `triage_candidates` 노출. 리마인더 2회 → `LoopError` + `contract_violation` |
| 게이트(terminal) | `engine.py` terminal 분기 | set_status 류 terminal 로 침묵 종료하는 우회 봉쇄(같은 조건·같은 캡 공유). 캡 도달 시엔 **완료 허용** — terminal 은 이미 성공한 작업이라 무효화하지 않고 worker_result 지표로 부모가 degrade 판정 |
| 전파 | `agent/cli.py`, `schema/worker_result.py` | 워커 종료 시 `candidates_seen`/`candidates_accounted` 필드 + summary suffix — 부모/오케스트레이터가 "무해명 침묵"을 clean 과 구분 |

## 발동 경계 (byte-for-byte 보존)

- **enforce 는 opt-in**: `metadata["candidate_ledger_enforce"]` — 워커 cli 만
  set (`SA_CANDIDATE_LEDGER=0` 운영 kill-switch, 계약 metadata 명시적 False
  존중). chat/operator 경로 미설정 → 기존과 동일.
- **triage 도구 미노출 toolset**(skill lockstep 전 도메인)에선 빌더가 None —
  이행 불가능한 요구를 하지 않는다 (finding_followup 의 todo_available 패턴).
- 후보 0(clean 대상), submit ≥1, triage ≥1 — 전부 비발동.

## skill lockstep 칩 (구현 완료 — secu-agent-skill)

도메인 헌팅 워커는 코어 CLI 가 아니라 skill 자체 러너(`service/agents/runtime.py`
`run_agent` → 코어 GuardedHarness)로 돈다. 이식 4조각:

1. **도구면**: confluence(_tool_classes 양쪽 kind)/github/dev_web/smb 헌팅 워커에
   `TriageCandidatesTool` 노출 — 미노출 도메인은 게이트가 스스로 꺼진다(안전 기본).
2. **enforce**: `run_agent(candidate_ledger_enforce=True)` (헌팅 워커 4곳만 opt-in,
   report/recheck/reply 러너는 기본 False). `SA_CANDIDATE_LEDGER=0` kill-switch 공유.
3. **terminal 즉시-break 구멍**: run_agent 는 terminal 성공 즉시 이벤트 소비를
   끊는다 → 엔진 terminal 게이트가 개입 불가. `candidate_ledger_unreconciled()`
   (코어 헬퍼)로 침묵 부채가 남았으면 break 를 미루고 계속 소비 — 엔진이
   리마인더를 주입한다 (게이트 캡 도달 시 엔진이 완료를 내보내므로 유한).
4. **counter**: `service/agents/candidate_counters.py` — detector 를 직접 부르는
   도메인 도구 7종(confluence_browser_search `candidate_pages`·web_site_sweep
   `scan_hit_summary.total`·web_task_scan `raw_finding_count`·smb_fetch_scan
   `hits_count`·smb_inspect_pdf `scan_hits`·{confluence,github}_task_scan
   `finding_count`)의 seen 등록. task_scan 류는 finding 자동적재라 seen=submitted
   동수 기록(게이트 중립·관측용). 워커 `_tool_classes()` 가 `ensure_registered()`
   호출(idempotent).
5. **전파**: run_agent 반환에 candidates_seen/accounted → 각 워커 로컬
   `_write_worker_result` 가 worker_result.json 에 기입.

**★배포 락스텝(방향 중요)**: 코어 먼저, skill 나중. 역순이면 skill 워커가 쓴
`candidates_*` 필드를 구 코어 `read_worker_result`(extra="forbid")가 스키마
위반으로 fail-closed 처리해 정상 결과가 전부 invalid 로 읽힌다.

## 정직한 경계

- **terminal deferral 은 이미 실행된 도구를 되돌리지 않는다**: set_status 류는
  ToolCallCompleted 시점에 이미 큐 row 를 닫았다. deferral 은 그걸 취소하는 게
  아니라 ① triage/제출 감사기록을 완료 전에 강제하고 ② 루프를 살려둬 모델이
  수정된 set_status(올바른 finding_count)를 **재발행**할 수 있게 한다(마지막
  쓰기 승). 재발행 없이 triage 만 하고 끝내면 row 는 첫 set_status 상태로 남되
  장부·audit·worker_result 지표에는 해명이 남는다(= 목적 달성: 침묵에 벌칙).
- **counter 는 heuristic 후보 수를 쓴다**: task_scan 류 finding_count 는 자동적재
  finding 수라 seen=submitted 동수로 게이트 중립. 후보 파싱 필드가 도구 결과
  스키마와 어긋나면 0(무해) — over-block 하지 않는다.

코어 팬아웃 경유 도메인(confluence/github)의 **부모측 completion 관측**을 위한
빈 훅. `run_fanout` 의 completion 루프에서 completion 당 **정확 1회** 발화
(valid/invalid/missing 전부), release 와 독립. observer 예외는 log 후 삼킴
(candidate_counter 예외격리 전례). 미등록 시 byte-for-byte 동일. 시그니처
`(target, spec, completion, ok)` — spec 은 `completion.spec` 편의 별칭, sink 는
`spec.env["SA_ATTEMPT_ID"]` 로 상관관계 id 를 도로 꺼낸다(코어는 attempt_id 모름).
**build_spec 예외(워커 미기동)는 completion 이 아니라 발화 안 함.** 재등록은
identity-idempotent(read-model 이중발화 방지).

**ASK-2 — `WorkerResult` additive 필드 (`schema/worker_result.py`)**:
`completion_reason: str | None`(정규화 종료 사유 — 지금까지 summary 문자열
파싱뿐이라 도메인 워커가 `_INCOMPLETE_REASONS` 분류표를 복붙하던 것을 스키마로
단일 어휘화) + `metrics_version: int | None`(candidate 계수 시맨틱 버전 —
`CANDIDATE_METRICS_VERSION=1`). 어휘 `COMPLETION_REASONS` 는 코어 소유 **권고**
(free str·미지값 통과). 코어 CLI writer 가 엔진 `LoopStopReason` 을
`normalize_completion_reason` 으로 매핑(`aborted→cancelled`·`stream_error→crash`,
나머지 통과; 외곽 crash→`crash`; SIGTERM grace→`cancelled`). **락스텝은 v3.90 과
동일**: `extra='forbid'` 라 신 필드 쓴 결과를 구 코어가 fail-closed → **코어 먼저**.
v3.90 재빌드 창에 같이 실으면 추가 배포 이벤트 0(이 창을 놓치면 별도 락스텝).

비목표(그대로): FanoutReport/PlanResult 집계 변경 없음(관측은 per-completion
원본으로 충분, 합계는 소비자가 GROUP BY) · DB·재큐·정책 판단 코어 미반입.

**codex 적대검증(2R, gpt-5.6 ultra) — 수렴 6→0**:
- R1(5): ① **notify 위치**(release/goal_record_turn 뒤라 DB 예외 시 발화 누락)
  → 분류 직후로 이동. ② label 상관관계 비유일 → **declined**(pre-existing,
  observer 는 release 와 동일 핸들 공유가 의도 — 따로 고치면 desync). ③

- R2(1): notify 를 앞당긴 뒤 goal_record_turn 예외 시 **관측됨↔claim 미반납**
