# v3.89 — 자율-능력(Autonomous Capability) 모델 (코어 lock 설계)

> **상태: 잠금 설계(구현 前). 근거 = 3독립설계(minimal-reuse / chokepoint-first / capability-spec) + 적대 채점·seam 실코드 대조 + `autonomous-browser-approval-CORE-ASK.md`(Option C) 흡수.**
> 본문(§0~§11)이 잠금 설계 원본이다. 승자 = **minimal-reuse(안1)** 를 base 로 두고, chokepoint-first(안2)의 **런타임 검문소 + 단일 `permits()`**, capability-spec(안3)의 **생성자 하드검증 + `_BROWSER_LOCK` 재진입 계약**을 그래프트했다. 버린 것 = 안1의 `field_allow`(predicate 재유입), 안2의 `SA_CHECKPOINT_ENFORCE` 프로덕션 fail-open 토글.
> 세 설계·채점이 만장일치로 정정한 핵심: **무인 워커에서 destructive 툴을 막는 진짜 기제는 `schedule_origin` 게이트가 아니라 ask→resolver-None 경로다**(§0.1). 이 문서가 여는 것은 정확히 그 ask 게이트 하나뿐이다.
>
> ⚠️ 설계 원칙(브리프): **결정론 · 최소침습 · 기본 fail-closed** 우선. MVP 는 코어 실행 파이프라인 **0줄** 변경.

## 0. 확정 결정 (한 줄 요약 + 사실 정정)

### 0.0 한 줄 요약
무인 `run_agent` 워커가 **명시·operator-상한·감사되는** 소수 destructive 툴(브라우저 navigate/login/session-start)을 쓸 수 있게, 신규 일급 `CapabilityGrant` 를 기존 `ToolContext.approval_resolver` 슬롯(`base.py:104`)에 **워커 전용으로 주입**한다. 유효 grant = `(계약 선언) ∩ (operator env 상한) ∩ (코어 auto-safe descriptor) − (NEVER_AUTO_FLOOR)`; 이 교집합이 비면 **resolver 를 아예 만들지 않아** `approval_resolver=None` → 오늘과 **byte-for-byte 동일(fail-closed)**. 권한 결정 로직(`invoker.py`/`base.py`)은 MVP 에서 **한 줄도 안 바꾼다**.

### 0.1 사실 정정 (실코드 대조 — 세 설계·채점 만장일치)
- **워커의 fail-closed 는 `schedule_origin` 게이트가 아니다.** `schedule_origin` 은 오직 `scheduler_tick.py:323`(in-process ChatSession 경로)에서만 metadata 에 주입된다. 무인 `run_agent` 워커는 `cli.py:716` 에서 `GuardedHarness(...)` 를 만들고 `cli.py:721` 에서 `charter_ref` 만 metadata 에 넣을 뿐 **`schedule_origin` 을 넣지 않는다**. → `invoker.py:141-150` 의 autonomy early-deny 는 워커 경로에 **진입조차 안 한다**.
- **워커에서 destructive 를 실제로 막는 것**: `base.py:143-145`(destructive → `PermissionDecision(behavior="ask")`) → `invoker.py:71-73`(`_apply_decision_with_approval` 에서 `resolver is None` → `ToolError(kind="permission", "approval required: ...")`). resolver 가 있어도 `resolve()` 가 None → `invoker.py:89-90` 동일 fail-closed.
- **보존해야 할 불변식은 "ask 인데 resolver 없음 → fail-closed"** 이지 schedule_origin 게이트가 아니다. 이 문서의 grant 는 이 ask 게이트 **하나만** 해소한다.
- **`context.registry` 는 실행 시점에 채워져 있다**(`engine.py:938`, `context.registry = registry`) → §7 검문소의 "합법 서브도구 조합을 `invoke_tool` 재귀로" 안이 실현 가능함을 확증.
- **실행 사실**: resolver 가 `updated_input=None` 로 allow 하면 `invoker.py:93-97` 이 **모델 원본 `validated`** 로 실행 → auto-approve 는 "ask 만 해제"할 뿐 입력을 재작성 안 함. navigate URL 은 여전히 execute 내부 `_validate_browser_url_safe`(url_safety)를, login 자격은 env(`SA_WEB_SSO_USER/PASS`)만 통과.
- **phasing 확정 사실**: `.execute(` 직접호출 테스트파일 **41개**, 툴의 `async def run(` 정의 **0개**(신규 final `run()` 충돌 없음), skill `execute` override **40개**(execute 이름 보존 시 무변경).

### 0.2 세 축 분리 (각각 다른 SAFETY-KEEP 담당 — 안1 골격)
| 축 | 메커니즘 | 위치 | 성격 |
|---|---|---|---|
| **Grant (belt)** | `CapabilityGrantResolver`(`ApprovalResolver` 프로토콜 구현) | `context.approval_resolver` 슬롯, **워커 전용 주입** | default-deny: 명시 `(tool, action)` 만 allow, 그 외 `None`→오늘 fail-closed |
| **Veto (suspenders)** | 기존 `register_tool_policy`(block-only) | `invoker.py:168` step, 승인 뒤 | 도메인이 charter/scope 로 **사후 차단**(grant 통과분도 veto). belt 와 **동일 `permits()`** 공유 |
| **Floor (하한, 코어소유)** | `NEVER_AUTO_FLOOR` 상수 | resolver·builder 내부 | operator env 에 있어도, descriptor 가 뭐라 해도 **절대 auto-approve 불가**한 위험-단위 |

세 층은 **독립 실패**한다: belt 가 뚫려도 veto 가, veto 가 없어도 floor 가 막는다. 공격/프롬프트-인젝션은 세 층을 **전부** 뚫어야 하고, belt·suspenders 는 같은 grant·같은 `permits()` 를 본다(로직 중복 0).

## 1. Q1~Q6 확답

### Q1 — 우회불가 검문소: `run()` + `__init_subclass__` consume-token (그래프트: 안2)
**shape 맞고, execute 이름을 보존하는 런타임 구조강제로 채택한다.** 단 **MVP(Phase 1)엔 넣지 않는다** — confluence 워커는 정상 tool-loop → `invoke_tool` 만 타므로 검문소에 의존하지 않는다. Phase 3 로 분리.

- **왜 lint 가 아니라 런타임인가**: 정적 lint(`\.execute(` grep)는 advisory 라 동적 dispatch(`getattr(tool,'execute')()`)를 못 잡고 리뷰를 뚫는다 — 실제로 skill `web_discovery→splunk_search.execute()` 가 그렇게 새어나갔다. `__init_subclass__` 래퍼는 **진입 즉시 토큰을 소비**해 "잊을 수 없다".
- **왜 execute rename 이 아닌가**(안3 정정): `execute`→`_run_impl` 리네임은 public 심볼 제거 → skill 40개 `execute` override 붕괴 → `load_plugins()` 죽음(CLAUDE.md·v3.85 회귀). 안2가 실증하듯 **execute 이름을 보존한 채** final `run()` + `__init_subclass__` 투명 래퍼로 동일 보장을 얻는다(skill 무변경, 검증됨).
- **정직한 신뢰경계**: `tool_policy.py:11-22` 가 명시하듯, in-process plugin 이 `other.execute()` 를 직접 부르는 건 신뢰된 plugin 의 **우발 실수 방지(defense-in-depth)** 이지 악성 샌드박스가 아니다(악성은 contextvar 모듈을 직접 import·arm 가능 — in-process 원천 불가). → 실 엔트리포인트엔 enforce 토글을 노출하지 않고 **항상 raise**(§7.4).
- 구현·마이그·재귀·성능·`_BROWSER_LOCK` 재진입 데드락 계약은 **§7 전체**.

### Q2 — Grant 표현 & belt+suspenders 인수분해
`(tool_name, allowed_action_set)` + 위험-단위 전용 필드 `login_modes`. **action 경계는 신규 `Capability` spec 에 두고(권위), belt(resolver)와 suspenders(tool_policy/deny-정련)가 같은 순수함수 `permits()` 를 호출**(그래프트: 안2). 로직 중복 0, 두 층이 같은 grant 를 본다.
- **`field_allow` predicate 는 버린다**(안1 자기경계·안3 지적): predicate 파싱은 취약. login 제약은 predicate 가 아니라 `login_modes` **전용 필드**로 표현(안2/안3 방식) → 코어 `Capability` descriptor(무엇이 auto-safe)와 `NEVER_AUTO_FLOOR`(무엇이 절대 아닌지)를 **데이터**로 두고 `permits()` 를 얇게 유지.
- action 은 pydantic-검증된 `getattr(validated, "action", None)`(browser/host/terminal 툴 모두 `action` Literal 보유, `browser_tool.py:2029`)에서 읽는다 → 취약 파싱 없음.
- 자료구조 전체는 **§4**.

### Q3 — 3개 기존 메커니즘 + grant 합성 (신규 파이프라인 층 0)
| 층 | 오늘 | 새 모델 | 변경 |
|---|---|---|---|
| **ask 게이트**(`check_permission`) | destructive→ask | **불변**. resolver 가 이 ask 만 해소 | 0 |
| **autonomy deny-정련**(`schedule_origin`, `invoker.py:141`) | `is_autonomous_tool_allowed(name)` 멤버십 deny | **일반화하되 유지** — `autonomous_allowed_capabilities()` 로 승격, `is_autonomous_tool_allowed()` 는 action-suffix strip 으로 **back-compat**(동작 무변), docstring 정정 | Phase 1 문서/헬퍼만 |
| **tool_policy block-only**(`invoker.py:168`) | 도메인 block-only veto | **불변**. 승인 뒤 최종 veto, allow-override 없음 | 0 |

**신규 층을 파이프라인에 추가하지 않는다.** resolver 는 기존 approval slot 의 새 소비자일 뿐. 순서: validate → schedule_origin(워커엔 미발화) → check_permission(ask) → **resolver(grant)** → abort → tool_policy(veto) → execute. **모든 실패모드 fail-closed**: 미선언/빈env→resolver 미주입→None; 미허가 action→None; resolver 예외→`invoker.py:86-87` 이 이미 `except→ToolError`; tool_policy veto→block.

### Q4 — 위험-단위(login) 무결 자율허용
login 은 navigate 와 **별개 capability**(risk_action). `browser_action:navigate` grant 가 `:login` 을 함의하지 않으며, operator 가 `browser_action:login` 을 **따로 opt-in** 해야 한다. 자격 구멍·lockout 완화 없음 — 상세 **§8**.

### Q5 — 기본 무변경(byte-for-byte) 구조적 보장
`build_effective_grants` 가 유효 능력 0 이면 **resolver 객체 자체를 안 만든다** → `context.approval_resolver` 는 `None` 유지 → `invoker.py:71-73` 의 `resolver is None` 분기에 정확히 착지 → **동일 ToolError**. `invoker/base/approval/tool_policy/runner` **0줄**. 신규 코드는 전부 `if grants` 가드 뒤. 상세 **§5·§6**.

### Q6 — Phasing
Phase 0(docstring) → Phase 1 MVP(confluence, 실행 파이프라인 0줄) → Phase 2(일반 capability 등록형 훅) → Phase 3(검문소). 상세 **§9**.

from dataclasses import dataclass

@dataclass(frozen=True, slots=True)

    """한 도구의 허용 action 서브셋 + 위험-단위 전용 필드."""

    login_modes: frozenset[str] | None = None   # browser_action:login 전용 (predicate 아님)

@dataclass(frozen=True, slots=True)
class CapabilityGrant:
    """이 워커에 부여된 자율 능력의 완전한 불변 서술 (일급 객체)."""
    grant_id: str                               # per-run 감사 상관 id
    capabilities: tuple[Capability, ...]
    operator_cap: frozenset[str]                # SA_AUTONOMOUS_TOOLS 스냅샷(상한 근거)
    risk_optin: frozenset[str]                  # "tool:action" operator 위험 opt-in 스냅샷
    scope: Mapping[str, str]                     # charter_ref/worker/task_type (감사)

    def permits(self, tool: str, action: str | None,
                *, login_mode: str | None = None) -> bool:
        """belt·suspenders 공유 순수함수 (그래프트: 안2). 단일 진실원."""
        cap = next((c for c in self.capabilities if c.tool == tool), None)
        if cap is None or action is None:
            return False                        # 기본-거부
        if action not in cap.actions:
            return False
        if action in cap.risk_actions and f"{tool}:{action}" not in self.risk_optin:
            return False                        # 위험 action = 이중 opt-in
        if tool == "browser_action" and action == "login":
            if login_mode not in (cap.login_modes or frozenset()):
                return False                    # login_mode ∈ {sso,auto} 만 (defaults 배제)
        return True

class CapabilityGrantResolver:                  # ApprovalResolver 프로토콜 구현
    def __init__(self, grant: CapabilityGrant, audit: "AuditLog",
                 *, registry: "ToolRegistry") -> None:
        """생성자 라이브-registry 하드검증 (그래프트: 안3) — grant 생성 시점 fail-closed.
        각 Capability 에 대해:
          · registry.get(cap.tool) is None or not is_destructive → raise

          · cap.actions ⊄ (descriptor auto_actions ∩ operator 상한) → raise
          · (cap.tool, a) ∈ NEVER_AUTO_FLOOR for a in cap.actions → raise

    async def resolve(self, req: ApprovalRequest) -> ApprovalDecision | None:
        action = req.tool_input.get("action") if isinstance(req.tool_input, dict) else None
        login_mode = req.tool_input.get("login_mode") if isinstance(req.tool_input, dict) else None
        if not self._grant.permits(req.tool_name, action, login_mode=login_mode):

## 4. Grant 스펙 자료구조

- **`Capability`**: `(tool, actions, risk_actions, login_modes)`. `actions` 가 허용 축, `risk_actions ⊆ actions` 가 이중 opt-in 축, `login_modes` 가 login 전용 제약(전용 필드 — predicate 아님).
- **`CapabilityGrant`**: `(grant_id, capabilities, operator_cap, risk_optin, scope)`. **frozen·slots** 불변 객체. `operator_cap`/`risk_optin` 은 env 스냅샷을 **감사 근거**로 동봉(사후에 "왜 이 grant 였나" 재구성). `permits()` 가 순수함수 — belt·suspenders 공유.
- **`NEVER_AUTO_FLOOR`**(코어 소유, `(tool, action)` — `""`=전체 action). CORE-ASK §4 never-auto 를 코어화 + **안1의 self-grant 열거(유일무이 강점)**:
  - egress: `deliver:""` 및 모든 egress sink

## 6. 안전 분석 (각 SAFETY-KEEP 불변식 유지 논증)

- **읽기 전용**: grant 는 `is_read_only` 를 뒤집지 않는다. `NEVER_AUTO_FLOOR` 가 host write/edit/delete/move·terminal·python_exec·browser fill/click/eval·egress 를 전부 auto-approve 불가로 못 박고, builder 교집합에서 제거되어 **grant 데이터로 표현조차 안 된다**. auto-grant 가능한 것은 read-지향 이동과 opt-in login 뿐. 쓰기 계열은 인간 승인이 있어야만 통과. ✓
- **url_safety 하드블록**: resolver 는 approval 층만 건드린다. `browser_action(navigate)` 는 execute 내부 `_validate_browser_url_safe`(`browser_tool.py:248, 2091`)→`validate_url_safe_resolved`(file/loopback/link-local/metadata/CGNAT/.local + DNS 재바인딩)를 **그대로** 탄다. grant 는 별개 층(승인 뒤 execute 내부)이라 우회 불가. ✓
- **PII/secret 마스킹**: resolver 는 값을 안 만지고 `updated_input=None`(모델 input 확장 금지). finding·외부전달 마스킹은 execute 이후 경로라 무관·불변. 감사 레코드의 `resolved_input` 도 `mask_scanned_text` 마스킹. login 은 env 자격이라 값이 로그/이벤트에 안 실림(기존 유지). ✓
- **egress 기본 dry-run**: `deliver`·모든 egress 는 `NEVER_AUTO_FLOOR`+생성자 하드거부 → grant 진입 불가. 자율발송 4조건(sink opt-in·charter·allowlist·잔존0)은 `apply_egress_gate` 로 승인과 독립. grant 는 egress 를 절대 auto-approve 안 함. ✓
- **lockout-safe**: 회로차단기(`login_halted`/`_LOGIN_FAIL_LIMIT=5`, `browser_tool.py:1173-1231`)는 `_attempt_login` 내부·**프로세스 종료로만 리셋**(SAFETY-KEEP). auto-approve 는 permission-ask 만 열 뿐 차단기를 리셋·재arm 하지 않는다 → 5연속 실패 후엔 툴 자신이 거부하고 **어떤 grant 도 못 뒤집는다**. resolver 에 login 카운터 금지, 워커 웜풀 금지(§8). ✓
- **기본 fail-closed**: 유효집합 공집합→resolver 미주입→`None`→기존 fail-closed byte-for-byte(§5). resolver 의 default 분기도 `None`(strengthen-only, allow-override 없음). ✓
- **operator 권위 > plugin**: `operator_cap = SA_AUTONOMOUS_TOOLS`(하드 상한), env 비면 grant None→하드 deny. skill 은 교집합으로 좁히기만. ✓
- **sub-agent 미상속**: grant 는 부모 워커 `ToolContext` 에만 산다. `AgentTool` 이 쓰는 `task_spec.json`(`agent_tool.py:219-225`)은 `{task_id, task_type, charter_ref, target}` 만 직렬화하고 **grant 를 넣지 않는다**(추가 안 함 — 구조적 미상속). spawn 서브에이전트는 신 subprocess 로 자기 `_run` 에서 자기 task_type 계약 ∩ env 로 grant 를 **재파생**(없으면 None→fail-closed). destructive 는 floor 라 어떤 계약도 grant 못 하므로, 스캔 콘텐츠 프롬프트 인젝션이 `agent(...)` 를 유발해도 host-write/terminal 로 **에스컬레이션 불가**. ✓
- **tool_policy 최종 veto 독립**: 합성 allow 뒤에도 `evaluate_tool_policies`(`invoker.py:168`) 실행 — allow-override 미도입. belt 와 동일 `permits()` 공유. ✓
- **결정론**: grant 는 (env + task_spec)의 순수 파생; `permits()` 는 순수함수; 감사는 append-only. 모델 출력·스캔 콘텐츠에서 grant 가 오지 않음. ✓

### 7.1 메커니즘 (원 스케치 — 위 ★구현확정으로 대체됨)
```python
# agent/tools/base.py (additive)
import contextvars, functools
_CHECKPOINT: contextvars.ContextVar[object | None] = contextvars.ContextVar(
    "sa_tool_checkpoint", default=None)
_ARMED = object()                                          # 프로세스 유일 sentinel

class ToolCheckpointBypass(RuntimeError):
    """invoke_tool/Tool.run() 밖에서 tool.execute() 직접호출 — 구조적 금지."""

class Tool[TInput: BaseModel](ABC):
    async def run(self, vi: TInput, ctx: ToolContext) -> ToolResult:   # FINAL
        tok = _CHECKPOINT.set(_ARMED)
        try:
            return await self.execute(vi, ctx)
        finally:
            _CHECKPOINT.reset(tok)

    def __init_subclass__(cls, **kw) -> None:
        super().__init_subclass__(**kw)
        if "run" in cls.__dict__:                          # run() 봉인
            raise TypeError(f"{cls.__name__}: Tool.run() is final; logic → execute()")
        impl = cls.__dict__.get("execute")
        if impl is None or getattr(impl, "__sa_guarded__", False):
            return                                         # 상속 execute 는 이미 래핑(멱등)
        @functools.wraps(impl)
        async def _guarded(self, vi, ctx, _impl=impl):
            armed = _CHECKPOINT.get()
            _CHECKPOINT.set(None)                          # 진입 즉시 소비(중첩 직접호출 차단)
            if armed is not _ARMED:
                raise ToolCheckpointBypass(
                    f"{type(self).__name__}.execute() outside invoke_tool — "
                    "route sub-tool calls through invoke_tool(ctx.registry, ...).")
            return await _impl(self, vi, ctx)
        _guarded.__sa_guarded__ = True
        _guarded.__isabstractmethod__ = False
        cls.execute = _guarded
```
`invoker._execute`(`invoker.py:104`): `await tool.execute(...)` → `await tool.run(...)` (1줄).

### 7.2 왜 동작·안전
- **arm 은 오직 `run()`, 소비는 래퍼 진입 즉시**(await 前). `run→execute` 는 같은 async 컨텍스트라 토큰이 보인다. 래퍼가 곧바로 `set(None)` → execute 본문에서 다른 툴의 `.execute()` 를 **직접** 부르면 토큰 없어 raise. 합법 서브도구 조합은 `await invoke_tool(ToolInvocation(...), ctx.registry, ctx)` 재진입(그쪽 `run()` 이 새 토큰 arm — 멱등·재귀안전). `ctx.registry` 는 `engine.py:938` 로 이미 채워짐 → 실현 가능(§0.1).
- **execute 이름 보존** → skill 40개 override·41 테스트파일 무변경(§7.3). abstractmethod 보존: execute 미정의 서브클래스는 `'execute' in cls.__dict__`=False → 미래핑 → 추상 유지 → 인스턴스화 TypeError(오늘 동일).

### 7.3 마이그레이션 (41 테스트파일 — `SA_CHECKPOINT_ENFORCE` 토글 버림)
- **알려진 우회 수정**: skill `web_discovery→splunk_search.execute()` 를 `invoke_tool(ToolInvocation(...), ctx.registry, ctx)` 재진입으로.
- **41 테스트파일**(`.execute(` 직접호출, invoker 컨텍스트 없는 cold call): per-call 재작성 대신 **`tests/conftest.py` autouse fixture 1개**가 그 파일들의 `.execute()` 를 arm 상태로 감싼다(또는 테스트 전용 `run()` 헬퍼로 라우팅). 전용 `test_checkpoint.py` 만 bypass raise 를 단정.
- **⚠️ `SA_CHECKPOINT_ENFORCE` env 토글은 도입하지 않는다**(안2에서 버림): 검문소를 끌 수 있는 env 는 미세한 fail-open 표면이고 안전-불변식으로선 약점. 검문소는 실 엔트리포인트에서 **항상 raise**, 테스트만 conftest fixture 로 우회(env 노출 0).
- **back-compat**: execute 이름·시그니처 불변(`run(` 정의 0개 확인 — 충돌 없음). `run` 은 순수 additive → `load_plugins()` 안전.

### 7.4 재귀 데드락 계약 (그래프트: 안3 — 실존 위험 교정)
검문소 **자체엔 락이 없다**(contextvar boolean) → 검문소발 데드락 0. 그러나 **조합 저자의 tool-내부 락**은 재진입에서 물린다: 툴 A 가 `_BROWSER_LOCK`(비재진입 `asyncio.Lock`, `browser_tool.py:69`, `:1830/1845/1913/2080/2322` 에서 획득)을 쥔 채 nested `invoke_tool→browser_query`(같은 락)를 부르면 **데드락**. 안1/안2의 "데드락 0" 단언은 검문소엔 맞지만 tool-내부 락엔 틀렸다.
→ **계약 명문화**: *nested `invoke_tool` 호출 전 비재진입 락을 해제하는 것은 조합 저자 책임.* 검문소는 재진입을 허용하되(토큰 스택), 공유자원 락 해제는 강제하지 않는다. 서브도구 재귀 깊이는 기존 `SA_AGENT_MAX_DEPTH` 예산으로 유계.

### 7.5 성능·병렬
- **성능**: invoke 당 contextvar get/set 2회 + 함수호출 1회 = O(1)·수 ns, 락 없음.
- **병렬 안전**: `engine._run_tool_calls` 가 `create_task` 로 read-only 배치를 병렬화(`engine.py:851`)하는데, contextvar 는 task 생성 시점 컨텍스트를 **복사**하므로 각 invoke_tool 의 arm/consume 이 task 별 격리 → 교차오염 0.

## 8. 위험-단위(login/write/delete/egress) 처리

login 을 lockout/자격 구멍 없이 자율 허용할 수 있는 이유 = **위험한 부분이 이미 툴 내부에 구조적으로 박혀 있기 때문**:

1. **자격 = env-only(모델 무관)**: `_perform_login`(`browser_tool.py:1236`)이 `SA_WEB_SSO_USER/PASS` 를 툴 **내부에서** fill. 모델 입력은 `login_mode`(소스 선택)뿐, password 없음. resolver 는 `updated_input=None` 강제라 모델 주입 경로 **0**(confused-deputy 차단).
2. **모드 clamp(floor)**: `login_modes ⊆ {sso, auto}` — `login_mode=defaults`(기본자격 브루트, `browser_tool.py:1069-1073, 1276`)는 **auto-grant 영구불가**. 이미 `SA_WEB_DEFAULT_CREDS_ENABLED`(기본 off) 위에 belt 를 더 얹음.
3. **이중 opt-in(위험단위 격리)**: `Capability(tool="browser_action", actions={"navigate","login"}, risk_actions={"login"}, login_modes={"sso","auto"})`. `permits()` 는 `login` 을 operator `SA_AUTONOMOUS_RISK_ACTIONS="browser_action:login"` 스냅샷에 있을 때만 통과 → navigate 를 grant 해도 login 은 자동으로 안 열림.
4. **lockout-safe 유지**: 회로차단기는 승인 결정과 완전 독립·프로세스 종료로만 리셋. auto-approve 는 차단기 미접근. 워커는 `WorkerPool` 이 매 spawn 마다 신 subprocess → fresh breaker, 사이트당 SSO 1회라 최대 5사이트 후 halt. **설계 제약: resolver 에 login 카운터 금지**(차단기 은폐), **워커 웜풀 금지**(SAFETY-KEEP 재확인 — 자율-login grant 는 1-shot subprocess 워커 한정).

**write/delete/egress**: 전부 `NEVER_AUTO_FLOOR`+생성자 하드거부(§4·§6) → grant 데이터로 표현 불가. egress 는 오직 자기 게이트(수신 allowlist+scan+dry-run)로만 통제, 자율 grant 와 영구 분리. host write/edit/delete/move·terminal·python_exec 는 인간 승인이 있어야만 통과.

## 10. Confluence CORE-ASK 흡수 (`autonomous-browser-approval-CORE-ASK.md` Option C)

ASK 의 Option C(hardened)를 이 일반 모델의 **첫 소비자**로 매핑하고, ASK §5 미해결 8문항을 전부 닫는다:
- **#1 브라우저 action 세분화**: 전용 read-only 툴 신설 대신 `Capability.actions` action-단위 화이트리스트. navigate/login 만, fill/click/press/eval/click_xy 는 `NEVER_AUTO_FLOOR`. `{browser_session, browser_action}` 통째 grant 는 생성자가 거부(never-auto 충돌 해소). action-level 파싱은 pydantic-검증 `input["action"]`(Literal)이라 취약 파싱 없음.
- **#2 operator vs skill 권위**: `operator_cap = SA_AUTONOMOUS_TOOLS`(하드 상한), env 비면 grant None→하드 deny. skill 은 좁히기만.
- **#3 per-run 데이터소스**: `task_spec`(skill `run_agent` 작성) ∩ operator env. least-privilege = skill 저자 선언 + operator env clamp.
- **#4 생성자 assertion**: resolver 생성자가 라이브 registry 대조로 `is_destructive` 확인·`_NEVER_AUTO_TOOLS`·wildcard·operator-상한 subset·floor 를 **grant 생성 시점 raise**(§2, 그래프트: 안3).
- **#5 sub-agent 미상속**: grant 는 워커 `ToolContext` 한정, `task_spec.json` 에 미직렬화(§6). spawn 서브에이전트는 재파생(재grant) 필요.
- **#6 감사 스키마**: `CapabilityGrantResolver` 가 사람 승인과 동일 shape `autonomous_approval` 레코드를 harness `AuditLog`(SHA256 체인)에; grant 자체는 기동 시 `autonomous_grant_configured`. auto/human 동일 쿼리. (Phase 2 에서 `state.approval_audit_*` 재사용 검토.)
- **#7 staleness**: 영속 grant 없음. operator=per-deploy env, per-run=task_spec ephemeral.
- **#8 docstring 정정**: Phase 0.
- ASK 요청대로 **권한 결정 로직(invoker/base) 0줄**, 기본 fail-closed 유지, 모델 `updated_input` 미반영.

## 11. 열린 위험 / 미결정

- **`login_modes=auto` 의 이중 의미**: `auto` 는 "SSO 페이지면 sso, 아니면 defaults(미 opt-in 시 skip)"(`browser_tool.py:2033-2039`). grant 가 `auto` 를 허용하면 non-SSO 페이지에서 defaults 경로로 흐를 수 있으나, `SA_WEB_DEFAULT_CREDS_ENABLED`(기본 off)로 실제 자격 제출은 차단된다. **미결정**: grant login_modes 를 `{sso}` 로만 좁혀 `auto` 의 애매성을 원천 제거할지, 아니면 `auto` 허용하되 defaults 하드-off 에 의존할지. 보수적 기본 = `{sso}` 권장, confluence 실측 후 확정.
- **cli.py reach-in vs 생성자 배선**: MVP 는 `harness.context.approval_resolver = ...` reach-in(runner 0줄 우선). 감사 타이밍·캡슐화상 GuardedHarness 생성자 파라미터가 더 깔끔 → Phase 2 승격 시점·back-compat 영향 미결정.
- **Phase 3 검문소의 실 랜딩 조건**: in-process plugin 은 신뢰 경계 안(우발 방지가 목적)이라 MVP 는 검문소 없이 안전하다는 판단. 그러나 skill 표면이 커지면 우발 `.execute()` 누수 재발 가능(선례 존재). 검문소를 Phase 3 로 미룬 것이 옳은 트레이드오프인지 skill 저장소 규모·리뷰 밀도에 따라 재평가.
- **41 테스트파일 conftest fixture 설계**: autouse fixture 가 cold `.execute()` 를 arm-wrap 하는 방식이 per-test 의도(특정 테스트가 bypass 를 단정하려는 경우)와 충돌하지 않는지 — 전용 opt-out 마커 필요 여부 미확정.
- **`register_tool_capability` 등록 시점**: Phase 2 등록형 descriptor 가 plugin import 시점에 등록되는데, `build_effective_grants`(cli.py `_run`, registry build 후) 시점에 이미 채워져 있어야 한다. `build_registry_for_task`(cli.py:705) 이후 호출이므로 순서상 안전하나, 등록 누락 시 descriptor 공집합→해당 action 이 조용히 grant 에서 탈락(fail-closed, 정상)인지 감사 경고 필요한지 미결정.
- **operator env 파싱 엄격도**: `SA_AUTONOMOUS_TOOLS`(bare tool = 전체 action)와 `SA_AUTONOMOUS_RISK_ACTIONS`(tool:action)의 혼용 시 오설정(예: risk action 을 bare tool 로 오등록) 검출을 builder 가 얼마나 엄격히 raise 할지 — CORE-ASK #4 생성자 assertion 범위와 겹침, 실 운영 env 관례 확정 후 잠금.

## 12. codex 독립설계 교차검증 반영 (2026-07-13)

Workflow 3자세 패널과 **별개로** codex 가 개방형 독립설계를 냈고, **핵심 골격이 수렴**했다(belt+veto+floor,
compiled `(tool,action)` grant·no-wildcard, operator 상한·env비면deny·skill좁히기만, 기본=empty→byte-for-byte,
login=별도 위험unit·env자격·고정 state machine, sub-agent 미상속, contextvar permit 검문소, ASK 흡수). 이
수렴 자체가 설계 검증이다. codex 가 **추가로 짚어 이 문서에 그래프트**하는 실질 하드닝:

### 12.1 [높음·필수 그래프트] login 피싱-리다이렉트 방어 = origin 재검증 state machine (§8 강화)
codex 지적: `login` 에서 **SSO 버튼 클릭 후 redirect 된 origin 을 검증하기 前에 자격을 fill 하면 phishing
redirect 에 credential 을 넣을 수 있다.** Workflow §8 은 "env 자격·고정 셀렉터"만 다뤄 이 축을 빠뜨렸다.
→ 자율 login 은 **고정 state machine** 으로만:
```
자격 존재 확인 → (run/auth-realm) one-shot attempt reserve → entry origin 검증
→ 고정 SSO 버튼 1회 클릭 → **credential fill 前 IdP origin 재검증** → 고정 field 에 trusted 자격 fill
→ submit 정확히 1회 → final origin + authenticated marker 검증 → success 또는 attempt 소진/latch
```
entry origin / IdP origin / final origin 각각을 **operator 소유 `BrowserAuthProfile` 의 exact allowlist** 로
관리. 모델이 제어 가능한 건 오직 `action="login"` 선택뿐 — username/password/credential-ref/SSO·submit
selector/IdP URL/submit 횟수/auth profile 은 모델 input·`updated_input` **어디서도 안 받음**. 실패(timeout·
ambiguous·invalid)도 attempt 소비, explicit lockout=process-global latch·reset API 없음, audit 엔 profile
ID/hash·origin·outcome 만(자격값·fill값 절대 없음). 구현 seam: `browser_tool.py` `_perform_login`.

### 12.2 [높음·필수 그래프트] 단일 login-worker 계약 (§8 lockout 강화)
codex 지적: breaker 가 process-local 이라 fresh worker 여럿에 login grant 를 주면 **매 프로세스가 재시도 →
lockout 배수**. Workflow §8 "웜풀 금지"보다 강한 제약으로:
- **auth-realm 당 login-capable worker 정확히 1개**, 한 로그인 세션 안에서 tenant/space 전부 탐색.
- **부모가 worker spawn 前에 attempt 를 소비 상태로 reserve**, crash/unknown 도 둘째 login-worker 미생성.
- 여러 worker fanout 은 부모 소유 `AuthAttemptLeaseBroker(run_id, auth_realm)` 도입 **後에만**(일반화 단계).

### 12.3 [중간·그래프트] 검문소 permit 를 identity-결박 (§7 강화)
Workflow §7 은 boolean `_ARMED` sentinel. codex: permit 을 **정확한 `(tool object identity, ToolContext,
invocation_id)` 에 결박**하고 구현 진입 前 소비 → 동시 interleave 시 tool A 용 permit 이 tool B 의 execute 로
재사용되는 것까지 차단(방어심화). contextvar 는 task-isolated 라 boolean 도 대체로 안전하나, identity-결박이
더 엄격. §7.1 의 `_ARMED` 를 `RunPermit(tool, context, invocation_id)` 로 승격.

### 12.4 [phasing 이견 — 사용자 결정 필요] 검문소 先행 vs 지연
**Workflow**: MVP(P1)는 검문소 없이 — confluence 워커는 정상 tool-loop 라 검문소 미의존, 검문소는 P3.
**codex**: 검문소를 **先행**(P2)하고 core+skill 을 **원자 릴리스**로 전환 — "구 ABI compat shim 은 우회를
남긴다". 즉 grant 모델을 우회가능 perimeter 위에 얹지 말라는 것.
→ **판단**: 검문소와 grant 는 직교한다. grant MVP 는 새 우회경로를 만들지 않고(ask 게이트만 열고 나머지 게이트
전부 유지), 우회(web_discovery→splunk.execute)는 **오늘 이미 존재하는 별개 홀**이라 grant MVP 가 악화시키지
않는다. 따라서 Workflow 의 "grant MVP 먼저"는 안전상 방어가능. 단 codex 말대로 그 홀은 알려진 상태이므로
**검문소를 뒤로 너무 미루지 말 것**. → **사용자 결정 항목**: (A) grant MVP 먼저(P1)·검문소 P3, 또는
(B) 검문소 先행(P2)·원자 전환 후 grant.

### 12.5 [Phase 2 옵션으로 기록] codex 의 더 완전하지만 더 침습적인 안
- **모든 active-grant 호출을 synthetic ask 로 승격**(비파괴 툴 포함) → 자율 실행 전부를 인간승인과 동일
  `ApprovalRequest/Decision` 감사 shape 로. 감사 완전성↑, 단 invoker 변경 필요(MVP 0줄 깨짐). → P2 관측성 옵션.
- **`SA_AUTONOMOUS_CAPABILITIES_JSON`**(action-level JSON 상한, strict parser·dup key 거부)·**registry_digest/
  spec version** 감사(plugin 업데이트로 의미 변화 가시화). MVP 는 2-env(`SA_AUTONOMOUS_TOOLS`+`_RISK_ACTIONS`)로
  충분, JSON·digest 는 P2 엄격화.
- **per-run 이 상한 초과 시 조용히 축소말고 전체 run 거부**(fail-loud). Workflow 는 교집합 축소 + resolver
  생성자 하드검증(초과 시 raise)로 이미 loud — 수렴. builder 도 초과를 raise 로 통일 권장.

### 12.6 codex 대비 Workflow 가 더 강한 점 (유지)

  모든 top-frame redirect hop 을 요청 前 url_safety 로 차단** + login origin state machine 과 함께 처리.
  그때까지 navigate/login grant 는 dormant(계약 미선언·env 미설정)라 실 위험 없음. capability.py 상단에 명문화.

operator_cap·감사) 건전 확인. 잔여 "높음"(navigate redirect)은 브라우저 하드닝(Slice3)이 처리할 별개 층이고
기본 dormant. Slice3 = navigate redirect 사전차단 + login origin state machine + 단일 login-worker.
