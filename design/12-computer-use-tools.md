# 컴퓨터 유즈 도구 재설계

2026-09-05 · v0.12 논의용 설계 · 브라우저·데스크톱 조작의 효율과 검증 · 구현 전

## 1. 목표와 적용 범위

**관찰 → 대상 선택 → 행동 → 필요한 결과 확인을 짧고 검증 가능한 도구 계약으로 묶는다.** 모델과 도구 사이 왕복, 불필요한 전체 화면 전송, 고정 대기, 오래된 대상 참조와 무의미한 재시도를 줄이는 것이 목표다. 실제 성공률·근거 품질·권한 경계를 유지한 상태에서 완료 지연과 총비용으로 평가한다.

웹 브라우저와 OS 데스크톱을 공통 계약으로 다루되 실제 조작은 각 driver가 담당한다. 브라우저는 Playwright 기반을 우선 재사용 후보로 두고, 데스크톱은 대상 OS·앱·원격 화면 환경을 확인한 뒤 접근성 API/화면 입력 driver를 선택한다. 기존 Knox MCP의 전송 같은 정형 기능도 재사용 대상으로 유지한다. GUI 기능을 만들었다고 모든 도구를 GUI 조작으로 대체하지 않는다.

사용자는 컴퓨터 유즈 관련 도구 자체의 재설계를 설계 범위에 추가했다. 이 문서는 그 요구의 설계안이며 실제 사내 화면 조작·도구 수정·성능 시험 결과가 아니다.

## 3. 실행 경로 선택

| 상황 | 우선 검토할 경로 |
|---|---|
| 계약이 검증된 API/MCP로 동일한 업무를 수행 가능 | 그 도구를 사용. 인증·대상·의미·결과 검증이 같은지 확인 |
| 웹 요소를 의미 있게 식별 가능 | 역할/이름/label/관리되는 test ID 등으로 대상 선택 |
| 네이티브 앱이 접근성 요소를 제공 | OS 접근성 정보와 앱/창 identity로 대상 선택 |
| canvas·원격 화면·접근성 정보 부족 | 필요한 영역의 이미지 관찰과 좌표 행동 |

이 표는 엄격한 직렬 fallback 순서가 아니다. 사용 가능한 관측 채널, 화면 품질, 데이터 정책과 실제 성공률로 선택하고 필요하면 구조 정보와 이미지를 함께 사용한다. DOM 접근 권한이 있다고 보이지 않는 모든 자료를 수집하지 않는다. 기존 등록 API와 UI의 업무 의미가 다르면 API로 임의 대체하지 않는다.

브라우저의 의미 기반 locator와 행동 전 자동 대기는 [Playwright locators](https://playwright.dev/docs/locators), [actionability](https://playwright.dev/docs/actionability)를 참고한다. 이는 앱 수준 성공이나 데이터 권한까지 보장하지 않으므로 별도 결과 조건을 둔다. 데스크톱 후보는 [Windows UI Automation](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-uiautomationoverview), [macOS AXUIElement](https://developer.apple.com/documentation/applicationservices/axuielement)이며 대상 앱 지원·권한·원격 세션 적합성은 실측 대상이다.

## 4. 관찰 비용과 대상 참조

관찰 요청에는 목표, 화면/창/페이지 범위, 필요한 정보, 허용된 반환 크기와 현재 관측 ID를 전달한다. 도구는 현재 관측 ID·시각·대상 identity·반환 범위·잘림/추가 조회 가능 여부와 필요한 텍스트/요소/artifact 참조를 돌려준다.

- 처음에는 대상 앱/창과 필요한 부분의 구조·상태를 확인한다. 시각 판단에 필요한 경우에만 이미지를 추가한다.
- 변경된 부분의 관측을 반환할 수 있으면 기준 관측 ID와 범위도 함께 전달한다. 기준이 없거나 불일치하면 새 snapshot으로 복구한다.
- 이미지 확대/잘라보기에는 원본 artifact와 좌표 변환 정보를 보존한다. 화면 전체, viewport, 스크롤 위치, DPI/scale, 여러 모니터의 좌표계를 섞지 않는다.
- 이미지가 같거나 변화량이 작아도 저장·전송 성공을 증명하지 않는다. 시각 변화와 업무 결과 확인은 다른 검사다.
- 장식·반복 네비게이션·무관한 영역은 필요한 관찰에서 제외할 수 있지만 목표 관련 오류·경고·모달은 누락하지 않는다. 누락 범위를 명시한다.

대상 ref는 영구 이름이 아니다. 세션/페이지/프레임/창, 관측 세대와 대상 특징에 결합한다. 의미 기반 selector도 다시 매칭한 요소가 같은 대상인지 확인한다. 여러 항목이 매칭되면 임의로 첫 항목을 선택하지 않는다.

탐색·페이지/창 전환·스크롤·크기 변경·모달·사용자 개입 후 관련 ref와 좌표를 재검증한다. 모든 DOM 변경마다 전체 화면을 다시 보내지는 않고 대상에 영향을 주는 변경을 구분한다. 영향 판단이 불확실하면 필요한 범위만 다시 관찰한다. 오래된 좌표를 기억에서 읽어 곧바로 클릭하지 않는다.

## 5. 행동과 결과 확인을 묶는 도구 계약

최종 도구 이름은 구현 시 확정하며 다음 책임을 제안한다.

| 책임 | 핵심 입력 | 핵심 반환 |
|---|---|---|
| 세션 관리 | 실행 환경·소유 업무·허용 앱/대상·수명 | session ID, capability, 소유/lease, 연결 상태 |
| 관찰 | session·대상·목적·영역/필드·기준 관측 | 버전 있는 관측·대상 ref·필요 이미지·범위/누락 |
| 행동과 확인 | 관측/대상 ref·행동 또는 짧은 단계 묶음·전제·기대 조건·deadline | 단계별 실행 사실·조건 확인·새 관측/차이·중단 이유·비용 |
| 조건 대기/조회 | 상태/사건 조건·job ID·기한 | 완료/대기/timeout/취소와 관측 근거 |
| 진단 조회 | attempt·관측/trace 참조·필요한 구간 | 허용된 오류·경과·기록. 기본 응답과 분리 |

예를 들어 등록된 내부 문서 앱의 **검색 조건 입력 → 검색 → 결과 목록 준비 확인**을 한 호출 안에서 수행하고 결과 목록의 필요한 부분을 반환할 수 있다. 모델이 각 입력·대기·snapshot마다 왕복하지 않아도 된다. 실제 UI 조작 횟수는 줄지 않을 수 있으므로 모델 왕복 감소와 driver 호출 감소를 구분한다.

묶음은 조건과 상한이 있는 짧은 실행 구간이다. 각 단계의 대상·허용 범위·전제·완료 여부를 확인한다. 새 판단이 필요한 분기, 예기치 않은 화면, 사용자 개입, 승인 범위 변화가 있으면 멈추고 현재 관측과 미수행 단계를 반환한다. 화면을 보지 않고 긴 매크로를 끝까지 실행하지 않는다.

UI 단계 묶음은 DB 트랜잭션이 아니다. 중간 단계가 실패해도 앞 단계의 효과는 남을 수 있다. 양식 입력도 자동 저장 등 효과가 있을 수 있으므로 동작별 계약으로 분류한다. 최종 제출·발송 같은 효과의 권한과 사후 대조를 묶음 내부에서도 적용한다. 지원되지 않는 롤백이나 정확히 한 번의 UI 실행을 보장하지 않는다.

범용 임의 스크립트를 기본 조작 인터페이스로 삼기보다 검증 가능한 typed action과 제한된 조건을 우선한다. 예외적인 스크립트/앱 전용 도구가 필요하면 별도 capability·입출력·효과 계약으로 등록하고 같은 Broker를 통과시킨다.

## 6. 대기·성공·재시도

행동 전에는 대상의 식별·준비 상태를 검사하고, 행동 후에는 목표와 연결된 조건을 확인한다. ‘입력이 전달됨’, ‘화면이 바뀜’, ‘요청한 업무 결과가 확인됨’을 다른 상태로 기록한다. 클릭 성공만으로 상위 업무를 완료하지 않는다.

고정 sleep을 반복하기보다 필요한 요소 상태·목록 변경·다운로드 완료·앱이 제공하는 완료 사건 등을 기다린다. 페이지 전체 네트워크의 조용함만을 모든 앱의 준비 조건으로 삼지 않는다. driver의 auto-wait도 각 동작의 준비 검사이며 모든 사후 조건을 대신하지 않는다.

관찰·준비 검사·행동·사후 확인·재시도는 하나의 남은 시간 예산을 공유한다. 하위 단계마다 전체 timeout을 다시 부여해 지연이 누적되지 않게 한다. 오래 걸리는 외부 처리는 지원되는 job/event로 넘기고 필요한 경우 제한된 polling으로 대조한다. 실패 이유는 최소한 다음처럼 구분한다.

| 상황 | 다음 처리 |
|---|---|
| 오래되거나 모호한 대상, 초점/창 변경 | 영향받는 범위를 다시 관찰하고 대상을 재선택 |
| 대상은 맞지만 아직 준비되지 않음 | 같은 deadline 안에서 조건 대기 |
| 입력 전달 후 결과가 불명확 | 현재 결과를 대조. 같은 제출/발송을 무조건 반복하지 않음 |
| 예상 밖 화면·모달·사용자 개입 | 묶음 중단과 현재 상태 저장, 필요한 재계획/인계 |
| 권한·인증 만료 또는 지원하지 않는 앱 | 허용된 재인증/사용자 입력 대기 또는 차단 사유 반환 |

LLM이 추측한 성공 문구는 결과 근거가 아니다. 입력 전달 후 장애가 발생하면 attempt의 효과 상태를 unknown으로 남길 수 있어야 한다. ‘화면 재조회’와 ‘외부 효과 재실행’은 서로 다른 재시도다.

## 7. 세션·동시성·사람과의 인계

각 실행 환경에 owner·lease·업무/attempt 연결을 둔다. 같은 페이지나 데스크톱의 상충하는 입력은 직렬화하고, 독립된 브라우저 context 또는 격리 환경만 자원 한도 안에서 병렬로 운영한다. 하나의 OS 화면에서 창만 다르다고 독립 마우스/키보드가 생기는 것은 아니다.

네이티브 입력 직전에 앱·창·초점과 관측 유효성을 다시 검사한다. 사람이 조작하거나 창이 바뀌면 후속 입력을 멈추고 인계/재관찰 상태로 둔다. 유효한 lease가 있어도 외부 UI 전체를 원자적으로 잠글 수 있다고 가정하지 않는다.

브라우저 프로세스는 짧은 idle 기간 동안 재사용할 수 있으나 인증·사용자·데이터 경계를 넘는 context 재사용은 하지 않는다. 에이전트가 만든 세션과 사용자가 제공한 기존 세션을 구분하고, 해제/정리 시 소유한 자원만 종료한다. 긴 대기에는 상태·재접속 단서를 남기고 UI 프로세스 수명은 별도로 관리한다.

재시작하면 저장된 task/근거/의도를 복원한 뒤 실제 앱 상태를 다시 관찰한다. 메모리의 세션 ID만으로 아직 창·로그인·미저장 양식이 유지된다고 가정하지 않는다. 프로세스 정리·재접속·실행 소유권에 관한 기존 코드와 테스트는 재사용 후보다.

## 8. memory·skill·롱 호라이즌 연결

UI 작업 이력에는 목적·앱/버전·허용 범위·관측·행동 의도·단계 결과·사후 조건·남은 작업을 연결한다. 원문 화면/DOM·민감 입력을 공통 장부에 전부 복제하지 않는다. 완료된 업무의 근거와 다음 클릭에 사용할 실시간 관측은 구분한다.

반복 업무의 유용한 절차는 입력·전제·대상 의미·분기·중단 조건·완료 기준을 가진 버전 있는 지침/레시피로 재사용한다. 단순 좌표열이나 한 번 성공한 selector를 장기 기억의 정답으로 고정하지 않는다. 재사용 시 앱 변경과 실제 관측을 확인하고, 절차 승격은 합성 평가를 거친다. skill은 지침이고 실제 실행은 Tool Broker가 집행한다.

compact에는 목표·앱/업무 identity·현재 실행 단계·근거 ID·미확인 효과·다음 확인 조건을 남긴다. 화면 ref/좌표는 재개 후 검증 대상이라는 사실도 보존한다. 모델에 전체 스크린샷 이력을 다시 보내는 것을 복구 기본값으로 하지 않는다.

자동/빠르게/깊게는 관찰·탐색 예산과 추가 검토 범위를 조절한다. 빠르게에서도 대상 확인·필수 사후 조건·효과 대조는 유지하며, 깊게에서도 매 행동 후 전체 화면과 모든 진단을 수집하지 않는다. 사용자 채팅에는 작업 수준의 접수·질문·결과를 보이고 세부 클릭/스크린샷 사건은 진단 경로로 둔다.

## 9. 중요파일과 모델 접근 경계

화면 이미지·접근성 텍스트·DOM·OCR·trace도 사내 원문을 포함할 수 있다. 파일 읽기만 제한하고 화면으로 같은 자료를 외부 리드에 보내는 설계가 되지 않도록 [데이터 접근 정책](/Users/seunghanee/Documents/secumon/design/05-data-boundary-options.md)을 모든 관측 채널에 적용한다.

세션이 자료를 볼 수 있는 권한, 도구가 반환할 수 있는 범위, 모델 목적지와 최종 사용자 공개 권한을 각각 확인한다. 원문 관측이 필요한 실행자는 허용된 환경에 배치하고 리드에는 허용된 상태·검증 결과·근거 참조를 반환하는 대안을 비교한다. 가림/잘라보기는 보조 수단이며 모든 민감 자료 제거를 보장하는 것으로 취급하지 않는다. 인증 정보는 driver가 참조로 사용하고 모델 입력·trace에 값을 복사하지 않는다.

관찰된 페이지·문서·메신저 본문의 지시는 사용자 승인이나 실행 권한이 아니다. 기존 권한을 넘는 행동을 도구가 자동 수행하거나, 속도를 위해 권한 검사를 생략하지 않는다. 필요한 승인/인계가 이미 확보된 범위에서는 같은 허가를 행동마다 반복해서 묻지 않는다.

## 10. 구현 언어와 재사용

브라우저 adapter는 새 TS 코어와 Playwright의 TS/Node 경로를 우선 비교한다. Playwright 자체의 locator·대기·세션·trace 기능을 다시 만들지 않고, 업무별 관측·묶음·사후 조건·장부 계약을 그 위에 구현한다.

네이티브 데스크톱은 해당 플랫폼의 검증된 driver를 우선 검토한다. Rust helper는 성능·배포·권한 격리·OS 연동 요구로 선택하고, TS/Rust만으로 모든 OS 기능을 같은 비용에 구현할 수 있다고 가정하지 않는다. 필요한 플랫폼 바인딩/외부 구성요소의 운영 비용도 언어 비교에 포함한다. 기존 Python driver 유지도 선택 비교 대상이나 새 코어의 필수 의존성으로 고정하지 않는다.

재사용 대상은 실행 코드뿐 아니라 오류 분류·세션 정리·대상 선택·artifact 계약·합성 시험 사례다. 기존 broad action enum을 그대로 번역하는 것으로 새 설계를 완료하지 않는다. 기존 코드의 모든 기능을 새 범용 GUI capability로 자동 노출하지 않고 필요한 업무 계약으로 선별한다.

## 11. 구현 순서와 평가

단계는 [v0.12 통합 플랜](/Users/seunghanee/Documents/secumon/design/03-migration-plan.md)을 따른다. 단일 에이전트의 실제 도구/채널/컴퓨터 유즈는 P3, 다중 역할과의 통합은 P4로 구분한다. 사내 화면에 접근하는 경로는 P3 이전에도 해당 배치의 G-DATA 조건을 만족해야 한다.

| 단계 | 추가할 작업 | 확인할 결과 |
|---|---|---|
| P0 | 대상 OS/앱/원격 환경, 기존 driver/MCP, 대표 GUI 업무와 실제 계약 확인 | 재사용/재구현 표와 baseline. 브라우저 외 환경은 별도 확정 |
| P1 | fake driver와 버전 있는 관측/행동/조건/attempt 계약 | stale 대상·부분 실패·unknown 효과·취소의 상태 의미 |
| P2 | 합성 관찰/행동 fixture로 묶음·조건 대기·선택 관찰 전략과 비용 기록 계약 준비 | 부분 효과·왕복·이미지·대기 비용의 구분. 실제 driver 성능과 구분 |
| P3 | 로컬 합성 웹 앱의 TS adapter → 선택 환경의 driver/실제 계약 | 단일 행동 기준선 대비 품질/총비용, 세션·stale 대상·인계·재시작 검증 |
| P4 | 여러 역할의 세션별 배정·격리 | 같은 화면 충돌, 부모 취소, 소유권·예산 검증 |
| P5/P6 | 두 업무군·실제 배치/운영 환경의 view·재사용 절차 평가 | 원문 경계를 배치 범위에서 재확인, 회귀·관찰 비용 확인 |

합성 사례는 검색·필터·가상 입력 양식·저장 확인·다운로드·모달, 동적 재렌더, 목록 가상화, 접근성 없는 canvas, 크기/DPI 변경, 늦은 결과, 사용자 초점 변경, 재시작을 포함한다. 실제 사내 앱 조작은 범위가 정해진 통합 단계이며 이번 설계 작업에서 실행하지 않는다.

측정은 모델 왕복 수, MCP 왕복과 driver 내부 호출 수, 이미지/텍스트 전송량과 모델 비용, 관측·대기·행동·검증·큐 지연, 세션 시작 비용, 성공한 업무당 p50/p95 시간·총비용, 잘못된 대상·중복 효과·거짓 완료·복구율로 나눈다. 묶음 호출 하나 안의 수십 번 조작을 호출 1회만으로 성능 개선이라고 보고하지 않는다.

기존 방식 → 행동+필요 관찰 → 조건 대기 → 짧은 묶음 → 목적별 관찰 순으로 요인을 나눠 비교하고 모델·앱·업무 조건을 맞춘다. trace 수집 자체의 비용도 측정한다. 실패/선택 구간의 상세 진단과 필수 장부를 구분하고, trace가 없는 과거 UI 실행을 완전 재생할 수 있다고 주장하지 않는다. [Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer)는 활용 후보이며 기록 열람은 실제 효과 재실행과 구분한다.

초기 설계에서는 속도·호출 수·토큰 절감의 수치를 측정하지 않았다. 이후 [P3-04 합성 첫 단위](/Users/seunghanee/Documents/secumon/design/chapters/P3-computer-use-result.md)에서 두 저장소의 묶음/개별 호출 4실행을 같은 목표로 비교했다. 도구 호출·driver 내부 호출·원본 bytes는 관측했고 실제 모델/GUI의 지연·이미지·토큰 비용은 아직 측정하지 않았다. 명시 효과 대조와 단계 이어가기 뒤 실제 로컬 Web driver 및 선택 환경 비교를 진행한다.
