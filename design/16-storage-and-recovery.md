# 저장소의 역할, 일관성, 복구 설계

2026-09-05 · v0.12 · 설계 제안, 구현 전

저장소 설계는 어느 DB를 쓸지와 함께 **무엇이 기준 데이터인지, 누가 갱신하는지, 어느 정보까지 함께 커밋해야 하는지, 무엇을 다시 만들 수 있는지**를 정하는 일이다. 범용 에이전트의 목표·추론/근거 상태·기억·파일·검색·작업 공간을 구분하되 논리적 역할마다 별도 DB를 만들 필요는 없다.

기존 [전체 기억 구조](/Users/seunghanee/Documents/secumon/design/02-target-design.md), [코어 상태 커밋](/Users/seunghanee/Documents/secumon/design/08-core-framework.md), [정정·삭제 정책](/Users/seunghanee/Documents/secumon/design/14-scope-and-priorities.md), [컨텍스트 수명](/Users/seunghanee/Documents/secumon/design/15-context-lifecycle.md)을 저장/복구 계약으로 구체화한다.

## 저장소 독립성 — 사용자 확인 요구

**기존 시큐몬의 PostgreSQL 사용은 새 에이전트 본체의 의존 조건이 아니다.** 코어는 업무 의미가 있는 저장 포트에 의존하고, 구체 DB/파일/검색 엔진은 바깥 adapter가 구현한다. 배포 구성에서 adapter를 주입하며 코어 내부에 `if postgres/sqlite` 같은 분기를 두지 않는다. 아래의 물리 배치와 PostgreSQL 설명은 후보 구현 예시다.

| 코어가 필요로 하는 포트 예시 | 코어 계약 | adapter 안에 둘 내용 |
|---|---|---|
| WorkStateStore | snapshot 조회, 예상 revision 기반 상태 전이 커밋, 입력/결과 중복 처리 | SQL/문서 API, DB transaction·잠금·고유 키·재시도 구현 |
| ArtifactStore | 범위 있는 바이트 저장/조회/완결성 확인, 버전 참조 | 로컬 경로·객체 SDK·업로드·암호화/서명 전달 방식 |
| KnowledgeReader | 근거 ID 조회, 범위/조건 검색, 출처·신선도·완전성 반환 | SQL 조건·색인·embedding·검색 엔진 query |
| CatalogStore | 검토된 도구/지침 revision 조회·승격 상태 | Git/배포 bundle/DB metadata·캐시 구현 |
| ExecutionEngine 경계 | 작업 배정·대기/재개·소유권·취소의 의미 | 자체 durable queue 또는 선택한 workflow 엔진의 저장/실행 방식 |

이는 제안된 책임 이름이며 모든 포트를 별도 서비스로 만들라는 뜻이 아니다. 상태·사건·결과 수락 metadata·outbox 의도를 함께 커밋해야 한다면 하나의 원자적 저장 계약에 포함한다. 여러 저장소 adapter를 임의로 조합한 뒤 전역 transaction이 있다고 가정하지 않는다. 배포가 저장 경계를 나누면 준비/확정·대조 같은 별도 protocol이 필요하며 미완료 중간 상태를 명시한다.

코어에 SQL 문자열, table/schema 이름, DDL, ORM 모델/transaction 객체, DB 오류 코드, PostgreSQL 알림·잠금·RLS API를 노출하지 않는다. 사용자/조직 범위는 업무 개념으로 정의하고 PostgreSQL schema/search_path와 동일시하지 않는다. 오류는 충돌·중복·미발견·권한 거부·일시 장애·자료 손상 등 공통 의미로 변환하되 내부 진단에서는 원인을 추적한다. 강한 검색 기능은 선택 capability이며 특정 벡터 연산자가 핵심 판단의 전제는 아니다.

필수 보장은 내구성 있는 커밋, 조건부 갱신/충돌 판정, 중복 식별, 범위/권한 있는 조회, 원본 참조와 복구 의미다. 특정 DB 기능으로 어떻게 구현할지는 adapter 책임이다. 요구를 충족하지 못하는 backend를 '인터페이스가 맞는다'는 이유로 장기 실행용으로 등록하지 않는다. 알림·근사 검색·공유 캐시처럼 선택적인 최적화는 없어도 허용된 기본 경로로 동작하게 하거나 해당 기능만 명확히 제한한다.

초기에는 코어의 fake/in-memory 대역으로 업무 규칙을 시험하고, 선택한 영속 adapter에서 재시작·동시성·중복·장애 계약을 시험한다. 저장소 독립성을 검증하는 통과 조건에는 **DB/ORM 패키지 없이 코어 빌드·시험 가능**, **코어 수정 없이 서로 다른 영속 구현 두 종류로 대표 시나리오 실행**, **같은 계약 시험에서 보장 유지**를 넣는다. 첫 단계에 여러 backend의 운영 지원 전체를 만들 필요는 없으며 두 번째 구현은 제한된 적합성 실험으로 시작할 수 있다. 메모리 대역 통과만으로 영속성/운영 성능이 증명되지는 않는다.

현재 소스에도 [StatePort](/Users/seunghanee/Documents/secumon/extracted/secu-agent/src/secu_agent/persistence/port.py:24)와 [PostgresStateAdapter](/Users/seunghanee/Documents/secumon/extracted/secu-agent/src/secu_agent/persistence/postgres_adapter.py:31)가 있다. 다만 확인한 포트는 SQL 실행 connection, schema DDL 등록, 보안 finding 작업을 함께 노출한다. [모듈의 기본 adapter export](/Users/seunghanee/Documents/secumon/extracted/secu-agent/src/secu_agent/persistence/__init__.py:13)도 확인했다. 포트/adapter 분리 의도와 fixture는 참고하되 새 범용 코어는 업무 의미의 저장 계약과 도메인 모듈의 저장 요구를 구분한다. 이것은 해당 파일의 정적 관찰이며 저장소 전체의 독립성이 검증됐다는 뜻은 아니다.

## 1. 논리 저장소와 초기 물리 배치

| 논리적 역할 | 저장할 내용 | 구현 후보/예시 | 권위와 손실 시 처리 |
|---|---|---|---|
| 업무·실행 상태 | goal, plan/task graph, 의무, 가설 상태, attempt, wait, 예산, 소유권 | 영속 상태 adapter | 업무 진행의 기준. 단순 캐시처럼 초기화 불가 |
| 사건·호출·전달 장부 | 사용자 변경, 도구 의도/결과 참조, 상태 전이, inbox/outbox, 전달/효과 상태 | 상태와 원자적 커밋을 제공하는 저장 경계 | 상태 변경의 근거와 중복/복구 대조. 보존 정책 적용 |
| 근거·관계 | observation/claim/hypothesis, 지지/반증, 출처, entity 관계, 적용 시간/범위 | 구조화 레코드/관계 저장 adapter | 검증 상태와 연결을 보존. 관계가 있다고 전용 graph DB가 필수는 아님 |
| 원본·산출물 | 문서, 로그 구간, 표, 이미지, 화면, 보고서, 검증에 필요한 모델/도구 응답 | 보호된 파일 저장소, 필요 시 객체 저장소 | 바이트/버전은 여기, metadata/권한/관계는 DB. 복구 가능한 보존이 필요 |
| 에이전트/조직 기억 | 경험, 확인된 사실, 절차 후보, 적용 범위·소유자·정정 이력 | 기억 레코드 저장 + 원본 참조 | 개인 관측과 검토된 조직 지식을 구분 |
| 도구·skill·방법 registry | 검토된 명세, 버전, 배포 상태, 활성 정책 | 버전 있는 배포 묶음 + DB 등록/승격 기록 | 사용한 revision을 재현. 실행 권한은 별도 정책 |
| 검색 색인 | 키워드, 문서 조각, embedding, 검색용 관계 projection | 처음은 DB 검색, 필요 시 pgvector/별도 엔진 | 원본/권한/추출 버전에서 재생성. 사실/업무 상태의 유일한 저장소로 쓰지 않음 |
| 컨텍스트·캐시 | ContextPacket, 선택 명세, 조회 결과 캐시, 화면용 projection | DB/프로세스 내 캐시, 필요 시 공유 캐시 | 정본에서 다시 구성. 미확정 효과·작업 소유권을 TTL 캐시에만 두지 않음 |
| 작업 공간 | 실행 중 파일, 체크아웃, 임시 변환/다운로드 | work/attempt별 격리된 디렉터리·볼륨 | 필요한 산출물/체크포인트를 승격 저장한 뒤 정리 |

필드명과 테이블 수는 아직 제안 수준이다. 공통 실행 조건은 타입/제약으로 관리하고 도메인별 확장 자료를 별도 schema 버전으로 연결한다. 전체 상태를 의미 검증 없는 JSON 한 칸에 넣거나, 검색 색인만 남겨 원래 관측과 판단을 잃지 않도록 한다.

## 2. 에이전트별 기억은 어떻게 나누나

에이전트 ID는 지속되는 역할/담당 범위를 식별하고 실행 프로세스·대화 세션과 분리한다. 여러 담당자가 같은 저장 엔진을 사용해도 조직·주체·업무·자료 등급별 권한과 namespace로 접근을 제한할 수 있다. 더 강한 원문 격리가 필요하면 별도 계정·저장소·마운트·서비스로 배치한다.

기억을 다음처럼 구분한다.

- **경험 기록:** 어떤 업무에서 무엇을 관측·시도했고 결과가 어땠는지. 당시 조건·버전·실패도 포함한다.
- **사실/지식:** 출처·적용 범위·유효 시점·검토 상태가 있는 주장. 과거 사실을 현재 사실로 자동 확정하지 않는다.
- **절차:** 특정 조건에서 사용할 방법·도구 조합과 검증 기준. 실행 성공 한 번으로 기본 정책이 되지 않는다.

서브넷 담당자 예시에서 자산의 식별 정보는 공유 entity 카탈로그에 두고, 각 담당자의 관측은 그 entity에 연결한다. 주소·계정·이름이 같다는 이유만으로 시간/조직 범위가 다른 객체를 합치지 않는다. 관측 시각, 시스템에 기록한 시각, 원자료 버전과 근거 위치를 구분한다.

개인 기억 → 게시판 공개 → 동료 검토 → 조직 지식의 변화는 권한과 근거가 있는 사건이다. 공유는 원본을 모든 에이전트에게 복제하는 동작이 아니라 허용된 주장/관계/참조를 게시하는 동작으로 설계한다. 게시판에 올라온 내용도 검증 여부와 반증 관계를 유지한다.

## 3. 쓰기 소유권과 한 번의 커밋

모델·도구는 결과/변경을 제안하고 코어의 검증된 명령 처리기가 상태를 갱신한다. Worker가 DB의 목표·완료·권한 레코드를 임의 수정하는 경로를 만들지 않는다. 도구 결과를 관측으로 수락하는 것과 그 결과로 가설/업무 상태를 변경하는 것은 구분한다.

초기 기본안은 **현재 상태 + 변경 사건을 같은 DB 트랜잭션으로 저장**하는 방식이다. 이벤트 로그와 현재 상태를 서로 독립적으로 수정하지 않는다. 모든 상태를 오직 전체 사건 replay로만 만드는 완전한 event sourcing은 초기 필수 조건으로 두지 않는다. 복구는 커밋된 현재 상태/필수 장부부터 시작하며, 과거 재구성에는 사건 schema·원본 보존 범위가 충분한지 확인한다.

| 원자적으로 묶을 후보 | 목적 |
|---|---|
| 요청 수락 + work 생성/변경 + 입력 중복 키 + 접수 응답 outbox | 접수했다고 답한 요청의 유실·중복 방지 |
| 실행 의도 + attempt + 예산 예약 + 실행 소유권 revision | 재시작 후 무엇을 하려 했는지 판정 |
| 결과 수락 기록 + 근거 metadata/참조 + 검증된 상태 변경 + 관련 사건/outbox | 결과와 현재 상태가 서로 어긋나는 문제 방지 |
| 전달 응답 + 외부 메시지 ID + 전달 상태/의무 변경 | 분석과 답변 전달의 별도 복구 |

DB 트랜잭션 안에서 LLM·MCP·파일 업로드·메신저 응답을 기다리지 않는다. 짧게 의도를 커밋한 뒤 외부 작업을 하고, 응답을 별도 트랜잭션으로 반영한다. 외부 작업과 DB를 하나의 원자적 실행으로 가정하지 않는다.

공통 제약·고유 키·revision 비교·필요한 잠금/격리 수준으로 동시 갱신을 제어한다. transaction 충돌을 재시도할 때 이미 수행한 외부 효과를 반복하지 않는다. 정확한 전략은 선택한 저장소에서 동시성 fixture로 시험한다. [PostgreSQL 트랜잭션 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html)

Temporal 등 실행 엔진을 선택하면 그 엔진의 실행 이력/스케줄링과 애플리케이션의 업무·근거 상태 사이 소유권을 먼저 정한다. 같은 실행을 자체 queue와 외부 엔진이 동시에 배정하지 않는다. 엔진 저장소와 업무 DB 사이에도 중복 키·대조/재개 계약이 필요하며 같은 DB 트랜잭션이라고 가정하지 않는다.

## 4. 원본 파일과 DB가 따로 있을 때

파일의 논리 artifact ID, 바이트 버전/hash, 저장 위치, 자료 유형/크기, 접근 정책, 원본/파생 관계, 사용 상태를 기록한다. 모델은 필요에 맞는 artifact 참조를 받고 저장소 자격증명이나 실제 경로를 직접 소유할 필요가 없다. 같은 hash는 동일 바이트 확인에 쓰며 독립된 증거의 수나 출처 신뢰도를 뜻하지 않는다.

쓰기 흐름의 제안:

1. 업로드/생성 의도와 범위를 기록하고 완료 전 객체를 임시 상태로 관리한다.
2. 파일/객체 저장소에 바이트를 저장하고 선택한 backend의 내구성·완결성 확인을 통과한다.
3. DB에서 artifact를 사용 가능 상태로 전환하고 근거/산출물 참조와 상태 변경을 커밋한다.
4. 색인/추출/알림 작업은 커밋된 사건에서 배정한다. 같은 이벤트 재처리는 멱등하게 처리한다.

파일 저장 후 DB 커밋 전에 중단하면 미참조 파일이 생길 수 있다. 오래된 미완료 업로드·고아 파일은 진행 중 의도/참조/보존 정책과 대조한 뒤 정리한다. 아직 완료되지 않은 업로드를 단순 나이만으로 삭제하지 않는다. DB에서 완료로 표시했는데 원본이 없다면 정상 근거로 제공하지 않고 손상/복구 상태를 드러낸다.

사용 중 객체를 같은 키로 덮어쓰기보다 새 버전을 저장하고 명시적으로 참조를 갱신하는 방식을 우선 검토한다. 삭제도 DB 논리 삭제/정책 적용과 실제 바이트 삭제의 진행 상태를 분리해 실패를 재처리한다. 모델이 제안한 임의 경로로 파일을 읽거나 쓰게 하지 않고 정해진 작업 공간·artifact 인터페이스로 검증한다.

## 5. 검색과 읽기의 일관성

실행 여부·취소·권한·예산·완료 판정은 커밋된 기준 데이터에서 확인한다. 지연 가능한 검색 색인이나 읽기 복제본만으로 실행 허용을 판단하지 않는다. 복제본을 사용하는 경우 필요한 revision에 도달했는지 확인하거나 기준 저장소로 읽기를 전환한다.

방금 수집한 근거는 색인 완료를 기다리지 않고 ID로 조회할 수 있어야 한다. 색인에는 원본 revision, 추출/조각화/embedding 버전, 갱신 cursor를 둔다. 색인 지연·실패와 '자료가 없음'을 구분한다. 캐시도 정책·자료·질의 범위의 버전으로 구분하며, 권한 철회/정정 후 낡은 결과를 그대로 반환하지 않는다.

기본 조회 순서는 업무 상태/정확한 ID → 범위 있는 조건·키워드 검색 → 필요 시 의미 검색이다. 상황에 맞는 경로만 사용하고 매번 모든 저장소를 순회하지 않는다. 의미 유사도는 관련 자료를 찾는 신호이며 사실 확정·이상 탐지·접근 허용 판정이 아니다.

pgvector는 PostgreSQL 안에서 정확/근사 벡터 검색을 지원하는 후보다. 근사 검색은 속도와 회수율의 교환이 있고 필터와 함께 쓸 때 결과 수/회수율을 따로 확인해야 한다. [pgvector 공식 저장소](https://github.com/pgvector/pgvector)

조직/권한 필터를 검색 계층에서 적용하고, 상세 원본 반환 직전에도 현재 권한을 검사한다. 권한 없는 제목·요약·후보 수를 모델에 먼저 보내고 나중에 본문만 가리는 방식에 의존하지 않는다. 한국어/업무 용어의 검색 품질과 필터 뒤 회수율을 합성 fixture로 측정한 뒤 tokenizer/색인/엔진을 선택한다. 처음부터 벡터 DB·그래프 DB·검색 엔진을 모두 도입하지 않는다.

## 6. 장기 실행의 큐와 장애

자체 실행 관리자라면 선택한 영속 adapter의 durable jobs/waits, inbox/outbox로 시작할 수 있다. PostgreSQL에 함께 저장하는 것은 구현 예시이며 코어의 필수 조건은 아니다. 대기 조건은 프로세스 메모리나 대화창에만 두지 않는다. wake 사건을 중복 수신해도 하나의 논리 작업에 중복 반영하지 않도록 주체/출처/ID 범위가 있는 키를 사용한다.

Lease 만료와 worker 소유권 revision을 확인하고 늦은 결과의 채택 여부를 검증한다. 오래된 worker의 DB 갱신을 막았다고 이미 발생한 외부 효과까지 사라지는 것은 아니다. 실제 변경/발송은 대상 서비스의 멱등성·외부 ID·상태 조회를 이용해 대조하고, 판정할 수 없으면 unknown으로 유지한다.

| 장애 | 초기 처리 원칙 |
|---|---|
| 기준 DB 연결 실패 | 저장되지 않은 접수를 확정하거나 새 외부 효과를 배정하지 않음. 이미 진행 중 효과는 연결 복구 후 대조 |
| 객체 저장소 실패 | 원본 저장/조회가 필요한 작업을 실패·대기로 표시. 필수 근거 없이 완료 처리하지 않음 |
| 검색 색인 실패 | 범위 있는 직접 조회가 충분하면 진행, 검색 불완전성 표시 |
| 캐시 손실 | 기준 데이터에서 재구성. 캐시 miss가 완료 작업 재실행을 뜻하지 않음 |
| 저장 공간 부족 | 새 수집 제한/역압, 작업 한도 적용. 필수 상태·원본을 무차별 삭제하지 않음 |

실제 연결 단절 중 로컬 spool을 허용할지는 자료 등급·복구 의미를 확인한 뒤 정한다. 초기에는 기준 DB가 없는 상태에서 조용히 독립 실행하는 경로를 추가하지 않는다. 수집 cursor/watermark를 언제 전진시키는지도 정한다. 원본 수락·체크포인트와 연결되지 않은 cursor 갱신으로 수집 자료가 건너뛰어지지 않아야 한다.

## 7. 중요자료 경계와 보존/삭제

저장 엔진 공유와 원문 접근 허용은 다른 선택이다. [리드 원문 접근 대안](/Users/seunghanee/Documents/secumon/design/05-data-boundary-options.md)에 맞춰 제한된 원본 영역, 내부 추출/검증 서비스, 공개 가능한 view를 배치한다. 외부 리드에 원문 DB/파일 계정·볼륨을 제공하지 않는 안을 구현할 수 있어야 한다.

조직·업무·주체·자료 범위는 실제 인증된 실행 맥락에서 가져온다. 모델이 제시한 tenant/agent ID만으로 접근을 허용하지 않는다. PostgreSQL의 행 수준 보안은 DB 방어 계층 후보이며, 소유자/관리 역할에는 적용 예외가 있으므로 런타임 역할과 connection pool의 요청 맥락을 검증한다. RLS만으로 파일·색인·모델 목적지까지 통제된다고 보지 않는다. [PostgreSQL 행 수준 보안 문서](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

임시 파일·배포 로그·오류 trace·검색 색인·embedding·백업에도 자료 등급과 권한을 적용한다. 객체 반환은 인증된 artifact 서비스 또는 범위/만료가 제한된 전달 방법으로 설계한다. 미리 발급한 링크의 즉시 철회 여부는 전달 방식의 실제 계약으로 확인한다. 자격증명/암호화 키는 별도 비밀 관리 체계에서 참조한다.

정정·삭제는 원본 → 추출 → claim/요약 → 색인/캐시 → 진행 중 packet/산출물까지 lineage로 전파한다. 내용 삭제와 필요한 최소 감사 metadata의 보존은 분리하고 정책으로 결정한다. 중복 파일의 공유 바이트를 삭제할 때 허용된 참조와 보존 상태를 대조한다. 조직 간 무조건적인 content dedup은 접근/삭제 의미를 먼저 검토한다.

## 8. 백업·복구·버전 변경

DB 백업 하나로 원본 객체·키·배포 schema까지 복구된다고 가정하지 않는다. 선택한 DB 백업 방식, 원본/버전 보존, 설정/암호화 키의 복구 절차, index 재생성 방법을 함께 준비한다. PostgreSQL은 dump, 파일 수준 백업, 연속 아카이빙 등의 방법을 구분한다. [PostgreSQL 백업·복원 문서](https://www.postgresql.org/docs/current/backup.html)

목표 복구 시점과 연결된 DB/artifact manifest, 참조 해석/해시 검사로 저장소 간 누락을 확인한다. 원하는 데이터 유실 허용량(RPO)과 복구 시간(RTO)은 조직 요구를 확인해 정한다. 특정 수치를 미리 보장하지 않는다.

복원은 외부 실행을 멈춘 격리 환경에서 시작한다. DB·필수 객체·정책/키 접근을 복구하고 삭제/철회 기록을 재적용한 뒤 원본 참조와 unfinished intent/전달 상태를 대조한다. 검색/캐시를 재생성하고 실행 소유권을 한 곳으로 정한 다음 신규 배정을 연다. DB를 과거로 돌렸다고 이미 발송된 메시지나 적용된 변경이 되돌아가지는 않으므로 대조 전 무조건 재전송하지 않는다. 불명확하면 unknown 처리한다.

복구 시점 이후의 삭제/권한 철회 이력을 잃으면 백업에서 금지 자료가 다시 살아날 수 있다. 해당 이력의 별도 보존·복원 절차 또는 최신 기준과의 대조 수단을 포함한다. 복제본은 백업·삭제 정책·실제 복원 시험을 대체하지 않는다.

Schema/이벤트/자료 추출/embedding 버전은 각각 추적한다. 진행 중 업무가 읽는 구버전의 처리와 backfill/색인 전환을 정의하고, 지원하지 않는 버전을 조용히 새 의미로 해석하지 않는다. 변경은 호환되는 확장 → 이행/검증 → 이전 형식 정리 순서를 우선 비교하며, DB를 무조건 과거 schema로 덮는 rollback을 약속하지 않는다.

## 9. 개발 저장소와 업무 파일 공간

코어·adapter·CLI/Web·업무 모듈·계약/fixture는 같은 TS 저장소에서 시작하는 안을 비교할 수 있다. 별도 배포나 소유권 요구가 생기면 분리한다. 코드/검토된 skill·방법·schema는 Git 등으로 버전 관리하고 실행 시 어느 revision을 썼는지 기록한다.

사용자 첨부·원본 증거·자격증명·실제 대화/실행 DB는 소스 저장소와 분리한다. 작업 공간은 work/attempt별 소유권·한도·수명을 가지고 여러 작업이 같은 파일을 덮지 않게 한다. 파일 이름이나 로컬 경로만으로 artifact를 식별하지 않는다.

검증할 산출물은 작업 공간에서 versioned artifact로 승격한 뒤 완료 상태에 연결한다. 중요 미완료 파일이 필요하면 체크포인트로 보존한다. 정리기는 실행 중 lease·미완료 의무·승격 완료를 확인한 후 임시 파일을 제거한다. 컨텍스트에서 내용이 빠졌다는 이유로 작업 디렉터리를 지우지 않는다.

현재 설계/학습 기록은 Markdown 파일로 계속 저장한다. 이는 제품의 동시 실행 상태를 Markdown만으로 관리하겠다는 선택은 아니다. 읽기 쉬운 업무 브리프/내보내기와 실행 정본의 역할을 구분한다.

## 10. 초기 구성과 확장 조건

단계별 구현 순서는 [v0.12 통합 플랜](/Users/seunghanee/Documents/secumon/design/03-migration-plan.md)을 따른다. P3은 단일 에이전트 실제 연동, P4는 협업/A2A/상시 임무다. 저장소 독립성과 기본 복구는 그보다 앞선 P1/P2에서 확인한다.

기본 구조는 **저장소에 독립적인 TS 코어 + 주입된 영속 상태 adapter + artifact adapter**다. PostgreSQL+파일/객체 저장소는 가능한 참조 구성 중 하나다. 기존 시큐몬의 DB와 같은 제품을 써야 할 필요는 없다. 상태·근거·기억·등록 metadata·장부를 논리적으로 나누되 원자적 변경 경계는 보존한다. 캐시는 작게 시작하고 벡터/그래프/분산 큐는 측정된 요구에 따라 추가한다. 정확한 버전·제품·배치 구조는 미선택이다.

단일 사용자 로컬 학습용에는 SQLite도 비교할 수 있다. SQLite는 DB 파일당 동시 writer가 하나이므로 여러 worker/서버의 동시 갱신 요구와 구분해 평가한다. SQLite에서 통과한 잠금/격리 시험을 PostgreSQL 운영 동시성 검증으로 대신하지 않는다. [SQLite 적용 기준](https://sqlite.org/whentouse.html)

| 단계 | 포함할 저장/복구 검증 |
|---|---|
| P0 계약 | 데이터 종류/소유권/등급, DB·artifact 정본, 외부 엔진 책임, 트랜잭션 경계·보존/RPO/RTO 요구 |
| P1 수직 경로 | 하나의 격리 DB와 artifact backend, 상태/사건 동시 커밋, 요청/결과 중복, 파일 저장-DB 커밋 사이 장애, 복구 후 재배정 |
| P1/P2 교체 적합성 | DB/ORM 없는 코어 검사, 공통 저장 계약 시험, 두 종류의 영속 구현에서 코어 수정 없이 대표 시나리오·복구 의미 비교 |
| P2 기억·컨텍스트 | ID 직접 조회, 색인 지연/재생성, 정정/철회, 작업 공간 체크포인트, 미사용 컨텍스트 재로딩 |
| P3 연동·P4 협업 | P3 실제 adapter/외부 효과 대조, P4 공유 entity·개인 관측·동시 수정·소유권/lease·중복 wake |
| 실제 자료 적재 전 | 주체/조직/파일/색인/모델 목적지 권한, 임시 자료/백업 정책, 철회/삭제 적용 |
| P6 도입 | 격리 복원 연습, DB/원본/키/버전 정합성, 삭제 재적용, 중복 발송 방지, 용량/보존/비용 관측 |

검증은 장애 구간별 필수 데이터 유실, 중복 반영/외부 효과, 끊어진 artifact 참조, 색인 회수율/지연, 권한 간 노출, 실제 복구 시간과 저장 비용을 본다. 현재는 설계 문서이며 DB·저장소 구축, 실제 복원, 제품 테스트를 수행한 결과가 아니다.
