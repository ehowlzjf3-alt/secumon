# C09 여러 임무의 종료와 완료 직후 복구

2026-09-08 · checkpoint383 · 기준선 `32739e5fab460fc9fd4e1de07bce6d21dae7b69a`. 시작 시 작업 트리는 깨끗했다. 직전 단위는 실제 독립 담당 비교·게시판/임무 결합의 수정, 소스별115개 로컬 통과, 문서·커밋·원격 일치 확인으로 진행했다. 전체 goal과 C09는 미완료다.

업무를 완료했다는 사실과 임무의 종료 기록을 모두 저장했다는 사실은 다르다. 현재 실행기는 완료할 때 모든 구독 메타데이터를 closed로 바꾸지만 MissionRuntime은 자신이 점유한 규칙의 본문 체크포인트만 마감한다. 완료 후 재시작하면 terminal 조기 반환 때문에 빠진 마감을 복구하지 않는다. 이 둘을 원 완료 영수증에 근거한 종료 정리 단계로 연결한다.

1. 기존 일반 질문 입구·SQLite 담당·mission.events 목록/원문·모델 답변·전달/완료 시험을 재사용한다. 여러 규칙의 실제 완료, 완료 후 workflow 반환과 종료 체크포인트 게시 사이 예외, 실제 프로세스 SIGKILL/reopen을 신규 시험으로 먼저 실행한다. 완료 상태를 합성하거나 한도·claim 시간을 줄이지 않는다.
2. 일반 notifications.refresh는 완료 업무에서 기존 동작을 유지한다. workflow.finish가 이 함수를 호출하므로 여기서 먼저 정리하지 않는다. tick의 완료 업무 진입과 정상 workflow 반환 뒤 동일한 private 종료 정리 경로를 사용한다.
3. 실제 control_selected 완료 event와 commandId·receipt·원 시각/리비전, 현재 담당·목표·정책·세션·자료 세대를 확인한다. 원 완료 상태 이후 허용되는 변화는 해당 규칙의 종료 checkpoint 게시뿐이다. 각 원 checkpoint와 마감 영수증을 순서대로 검증해 현재 전체 상태와 대조한다. 계획·근거·답변·사용량·다른 제공자 기록을 비교에서 제외하지 않는다.
4. 처리하는 규칙의 원 체크포인트는 status/reason/claim/pendingRun만 종료 값으로 바꾸고 사건 원문·커서·seen·읽기 확인 등을 유지한다. 완료 전에 이미 닫힌 규칙은 그 이유와 원문을 보존한다. idle 규칙에 실행 claim을 요구하지 않되, 사건 원문이 있으면 정확한 읽기 확인이 있어야 한다. 공개 read 검증은 완화하지 않는다.
5. 여러 규칙 중 일부만 마감하고 중단된 경우 원 완료→이미 게시한 마감→현재 상태를 확인하고 남은 것만 처리한다. CAS 경쟁·중복 commit 반환 뒤에도 정당한 결과와 현재 권한을 재확인한다. 복구는 새 모델·도구·전달·원천 poll을 호출하지 않는다.
6. 작성자를 동결한 뒤 root만 Node v24.20.0으로 빌드·신규 시험·실패 교정·직접 영향 회귀를 수행한다. 살아 있는 시험 중 dist를 재빌드하지 않는다. 직전 단위115개와 접수 직후 기존 SIGKILL 시험을 반복하지 않는다. 결과·실패 원문·소스 지문·남은 작업을 저장하고 단위를 커밋·푸시한다.

후속 검토 반영: 상태·사건·영수증은 독립 조회이므로 정상 마감 경쟁으로 revision이 바뀌면 제한 재조회한다. 저장 후 응답이 불명인 경우는 미게시로 단정하지 않고 다음 tick/reopen에서 같은 원 영수증과 체크포인트를 확인한다. 임무 목록이 비었다는 이유로 완료 증명 검사를 건너뛰지 않는다. 파일 저널의 특정 응답 불명 오류 주입과 장기 사건 조회 비용은 이번 SQLite 복구 시험과 별도로 남긴다.

이번 첫 범위는 실제 완료가 기록된 업무의 마감이다. 취소·목표 변경·일시정지의 의미를 완료와 혼동하지 않는다. 이 경계에서 새로 발견된 미완료 항목은 따로 명시한다. 이어 C10의 서로 다른 유효 릴리스 전환/백업/기존 신원·세션·기억 재열기를 수행한다. C05/C06 잔여, 현재 Linux/native Windows 및 실제 사내 서비스·Knox·A2A·PostgreSQL·최종 통합은 계속 남아 있다. 실제 모델/API 중단과 외부 서비스 연결0회를 유지한다.
