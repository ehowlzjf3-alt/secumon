# C10 고정 전달 형식과 compact 세션의 배포 전환

2026-09-08 · checkpoint385에서 정리한 다음 소단위. 아래 구현·시험은 아직 수행하지 않았다.

이전 설치의 전역 입구가 새 엔진의 모든 옵션을 알 필요는 없다. 담당 경로를 고르는 작은 외곽 형식과 실제 엔진 명령을 분리하고, 내부 argv는 선택된 엔진이 해석하게 한다. 예를 들어 `dispatch --directory 담당 -- 선택엔진명령 …` 형태를 검토한다. 실제 사용자 원문의 `--directory` 문자열을 스캔해서 경로를 추측하지 않는다.

1. 기존 `resolveAgentEngine`·호스트 등록표·배포와 pin 재검사·자식 프로세스 종료 관리를 재사용한다. 외곽 parser는 명시 담당 경로만 읽고 내부 argv를 그대로 전달한다. 선택 엔진은 자신이 해석한 실제 담당과 외곽 선택이 같은지 실행 전에 검증한다. 관리 명령과 잘못된 옵션의 오류 주체도 명확히 정한다.
2. 정상 bundler로 만든 실제 A/B에서 B만 아는 옵션을 전달하여 B 코드가 처리하는지 확인한다. 외곽/내부 담당 불일치·옵션처럼 보이는 원문·누락 엔진을 검사한다. 등록표/프로세스 경계의 이미 통과한 시험을 복제하지 않는다.
3. 같은 A/B 후보를 사용해 실제 지속 세션에 여러 입력과 compact를 적용한다. 원 이력·활성 문맥 요약 참조·개인 기억·진행 업무·영수증을 기록하고 B 전환/재열기/후속 요청에서 연결을 확인한다. 합성 compact는 의미 품질 평가가 아니다. 이전 task 목표·계획을 새 task에 합치지 않는다.
4. root가 작성 완료 후 소스를 고정하고 새 인수와 직접 영향 회귀만 실행한다. 결과·남은 범위·다음 단위를 저장하고 커밋/푸시/원격 일치를 확인한다. 실제 모델/API 중단과 외부 서비스 미연결을 유지한다.

자동 최초 pin은 이어지는 별도 소단위다. 신규 initialize 작업의 증명에 검증 release를 고정하고 setup 완료 공개 전에 no-replace로 게시해야 한다. 자기 runtime lease를 연 뒤 `pinAgentEngine(...offline:true)`를 부르는 방식은 피한다. 중단은 같은 setup operation·같은 release로 재개하고, 기존 무핀 담당·clone·restore는 새 담당으로 취급하지 않는다. npm/개발 디렉터리에는 정본 `release.json`이 없으므로 원 디렉터리를 수정하지 않고 기존 bundler/installer로 호스트 소유의 공통 release를 준비·등록하는 연결이 필요하다. 이 설계는 구현 시 기존 setup publication·동시성·복원 계약을 직접 확인하고 확정한다.
