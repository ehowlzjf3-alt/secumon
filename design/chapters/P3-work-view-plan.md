# P3-02 업무 화면: 공통 조회 계약과 CLI 계획

2026-09-06 · P3-02의 첫 구현 단위 · Web 화면과 채널 연동은 후속 단위

## 개념과 목표

챕터별로 개념 설명 → 구체 계획 → 구현 → 정상·실패·복구 검증 → 학습·결과 저장을 이어간다. 이전 P2-06은 로컬 정보 공개 계약을 검증한 진전이다. 전체 P0–P6 목표와 실제 모델 시험 중단은 유지한다.

이번에 확인할 질문은 “같은 업무를 다른 창에서 다시 읽어도 실행이나 전달이 반복되지 않고, 현재 허용된 정보만 표시되는가?”다. 업무 상태, 사람이 읽는 화면, 외부 채널의 전달 영수증을 구분한다. 화면 접속은 실행 요청도 발송 요청도 아니다.

## 구현 단위와 재사용

1. **이번 단위: 공통 조회와 CLI.** 기존 StateRepository, ConversationService의 결과 판정, 자료·기억 유효성, 목적지별 공개 정책을 재사용한다. 안쪽 application 계층에 조회 서비스를 두고 domain에 작은 화면 계약을 둔다. Node·HTTP·SQLite·터미널은 안쪽 계약에 들어가지 않는다.
2. **다음 단위: 로컬 Web과 재접속.** 같은 계약을 HTTP 조회/명령과 공개 상태 스트림으로 연결한다. 인증된 로컬 세션, origin/명령 검증, 중복/순서/재접속 처리를 구현한다. 화면은 업무 목록·대화·상세 영역으로 나누고, 입력 초점·스크롤·좁은 화면·키보드를 실제 브라우저에서 검수한다.
3. **챕터 통합:** CLI/Web 간 같은 업무 조회와 명시 변경·취소를 검증한다. Knox/MCP의 실제 계약은 별도 P3-01/03 조건이며 대역 성공으로 통과 표시하지 않는다.

이번 첫 단위로 P3-02 전체나 Web 사용성이 완료됐다고 표시하지 않는다. 현재 CLI의 접수/실행/제어 명령과 JSON 형식은 유지하고 새 `work-view` 명령으로 공통 조회를 노출한다. 기존 `status/messages/events` 명령을 신규 화면 계약의 공개 경계로 간주하지 않는다. 후속 Web은 새 조회 서비스만 사용한다.

## 조회 계약

- `read(workId, actor, access, { level, cursor? })`는 최신 전체 `snapshot` 또는 내용이 같은 `unchanged`를 반환한다. `access`는 신뢰된 채널이 정한 사람·대화·목적지·진단 권한이다.
- 등록된 대화 binding, 현재 소유권/읽기 권한, 누적 자료 등급과 목적지의 `screen` 공개 정책을 검사한다. 진단 조회에는 별도 진단 권한과 `log` 공개 정책이 모두 필요하다. 화면을 접는 것은 권한 검사가 아니다.
- 기본 조회에는 짧은 업무 식별/상태와 접수·현재 필수 질문·유효한 최종 답변만 포함한다. 상태 갱신을 새 대화 메시지로 만들지 않는다. 계획·가설·근거 카드는 명시 상세 조회에만, 사건 번호/종류/시각은 명시 진단 조회에만 포함한다. 원문 bytes, 도구 input/output, 모델 입력/내부 context는 포함하지 않는다.
- 커서는 업무·사람·채널/대화·조회 수준 및 허용된 표시 내용에 묶는다. 같으면 `unchanged`, 오래됐거나 다른 조회의 커서면 최신 전체 상태로 교체한다. 커서로 실행 이력을 재생하지 않는다. 권한 철회는 `unchanged`로 감추지 않고 거절한다.
- 결과/근거는 현재 목표·출처·기억·자료 수명과 일치해야 한다. 이미 전달된 과거 답변을 현재 결과로 되살리지 않는다. 조회 중 상태가 바뀌면 제한된 횟수로 다시 읽고, 일관된 화면을 만들지 못하면 고정 오류를 반환한다.
- 다른 채널의 등록된 연결에서도 업무를 조회할 수 있다. 기존 주 답변 경로는 유지하고 재발송·읽음 표시·목표 완료 처리는 하지 않는다.
- 조회는 state commit, artifact put, workflow, 모델/도구 호출, checkpoint 저장을 수행하지 않는다. 원본 무결성과 공개 허용 여부를 확인하는 읽기는 수행할 수 있다.

## CLI와 검증

`work-view <work-id> --level conversation|details|diagnostics [--cursor 값] [--json]`을 추가한다. non-TTY/JSON은 ANSI를 출력하지 않는다. 기본 출력은 접수·현재 질문/답변과 한 줄 상태이며 상세/진단은 명시 선택한다. 로컬 합성 profile의 진단 권한은 신뢰된 로컬 실행 구성에서 정한다.

두 상태 저장소에서 정상/빈 업무·다중 업무·등록되지 않은 대화·다른 사람·읽기/공개 권한 철회·진단 권한·커서 범위·목표 변경·현재 근거 철회·손상된 결과·조회 도중 변경·재시작을 검증한다. 반복 조회 전후 정본 revision/사용량/전달 수가 같고 새로운 모델/도구/발송이 없는지 확인한다. CLI 프로세스를 다시 시작해 커서와 업무 상태를 대조한다.

관련 시험 후 기존 `npm run verify`를 실행하고 원본 아카이브/추출물, dependency lock, 이전 검증 기록을 보존한다. 새 결과·실제 명령/로그·변경 소스 hash와 남은 Web 항목을 저장한다. 네트워크·키 탐색·실제 모델/MCP/Knox/컴퓨터 유즈는 이 단위의 검증에 필요하지 않다.

## 다음 Web 단위로 넘길 구현 관찰

조회 서비스의 거절/현재 자료 무효화가 오면 Web은 예전 결과를 여전히 현재 답변처럼 표시하지 않도록 상태를 갱신해야 한다. 접속할 때 전체 실행을 호출하지 않으며, 공개 snapshot의 교체와 대화 메시지의 중복 제거를 구분한다. 접속별 주체/대화/표시 수준이 바뀌면 이전 커서와 화면 구독도 분리한다.

현재 원본 무결성 검사는 실물 읽기를 수행하고, 진단은 전체 이력 조회 후 최근 50개만 반환한다. Web의 반복 갱신 전에는 접속/조회 빈도와 검증 읽기량을 측정하고 제한하며, 긴 사건 이력은 tail/pagination 포트로 개선할 수 있는지 검토한다. 출력 크기 제한이 I/O 비용 제한을 뜻하지 않음을 다음 계획과 검증에 포함한다.
