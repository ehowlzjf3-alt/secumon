# P4-01 다음 단위: 요청 발견과 사건 기반 재개

2026-09-06 · 요청 발견/영속 알림 로컬 검증 완료 · 역할 dispatcher/자율 추론은 후속 범위

요청/수락/답변/확인과 각 작업의 의무를 연결한 다음, 시험 실행기가 요청 ID를 전달하던 자리를 일반적인 발견·이벤트 전달 경로로 바꾼다. 단순 대기는 모델 호출을 만들지 않고, 의미 있는 변화가 도착했을 때 현재 상태를 확인하고 필요한 작업만 재개한다.

## 구현 순서

1. 현재 역할이 받을 수 있는 요청의 목록/상태 조회를 추가한다. 요청 ID·질문 참조·상태·기한·현재 게시판 revision을 제한된 크기로 반환하고 질문/답변 본문은 이미 존재하는 게시판 읽기로 가져온다. 조회 결과의 시점과 현재 유효성을 구분한다. 대기 중 취소/거절을 명시 계획한 경우에도 필요한 현재 revision을 얻는 경로를 검증한다.
2. 저장소 중립적인 변경 조회 port를 정의한다. 게시판 변경과 함께 확정되는 이벤트 ID, 대상 역할, revision/cursor를 사용하고 SQLite와 파일 저널에서 같은 계약을 검증한다. 모델이나 메신저가 임의로 수신 주체를 결정하지 못하게 한다.
3. 각 runtime의 수신 cursor와 처리 결과를 영속화한다. 중복 전달은 한 번만 처리하고, wake를 놓쳤거나 프로세스가 재시작된 경우 누락 구간을 다시 조회한다. 이벤트는 다시 확인할 계기이며 실제 요청 상태가 완료 판정의 근거다.
4. 모델 실행을 시작하기 전에 기존 의무를 갱신한다. 여전히 대기 중이면 외부/모델 호출을 하지 않고 종료하고, 답변 확인이나 새로운 할당이 필요하면 기존 작업 큐로 보낸다. 한 역할이 상대 WorkState를 직접 수정하지 않는다.
5. 두 runtime의 문서 검토와 합성 관측에서 지시 수신→요청 발견→수락→응답→확인→재개를 실행한다. 중단 위치별로 저장된 cursor·작업 의무·도구 및 모델 호출 수를 확인한다.

## 완료 기준

- 요청 대상 이외의 역할·비활성 역할·다른 tenant/scope에는 발견 결과나 wake가 노출되지 않는다.
- 빈 결과, 큰 목록, 오래된 cursor, 중복 이벤트, 재시작, 처리 도중 권한 변경을 다룬다. 크기/개수/시간/재시도 한도가 명시돼 있다.
- 답변과 취소의 순서가 바뀌거나 완료 이후 근거가 철회돼도 현재 상태를 다시 확인한다. 이벤트의 문구만으로 완료하지 않는다.
- 변경 없는 대기는 모델 호출 0, 도구 쓰기 0이며, 중복 wake로 같은 요청을 다시 수락/답변하지 않는다.
- 웹/CLI/Knox는 같은 작업 상태를 표시한다. 내부 이벤트마다 새 채팅 메시지를 만들지 않고 접수·의미 있는 진행·사용자 입력 필요·최종 결과를 구분한다. 실제 Knox 연결은 별도 사내 환경에서 검증한다.

## 뒤이어 진행할 내용

역할 간 예산, 두 runtime의 실제 계획·가설·반증·재계획, 많은 장기 작업의 공정한 스케줄링은 후속 범위로 유지한다. 이번 단위의 이벤트 전달 성공만으로 자율 추론이나 전체 P4 완료를 선언하지 않는다. Python 코드 비교는 선행 조건이 아니다.
