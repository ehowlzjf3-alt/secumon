## 이제 구분되는 것

| 이름 | 쉬운 설명 | 이번 구현에서의 역할 |
| --- | --- | --- |
| 담당 `agentId` | 한 업무 담당 에이전트의 고유 번호 | C01에서 확인한 프로필이 공급한다. 폴더 이름이나 요청에 적힌 번호를 그대로 믿지 않는다. |
| 사용자 `tenantId`·`principalId` | 조직과 사람의 구분 | 같은 담당을 쓰더라도 다른 사용자의 이력을 섞지 않는다. 현재 로컬 표면은 호스트가 정한 합성 사용자이며 사내 인증 연동은 별도다. |
| 대화 `sessionId` | 여러 업무를 이어가는 한 대화의 번호 | 업무 완료·프로세스 종료와 별개로 남는다. 명시적으로 새 대화를 만들면 새 번호를 사용한다. |
| 업무 `workId` | 한 목표를 수행하는 작업의 번호 | 대화 하나에 여러 업무가 연결된다. 과거 업무의 근거·완료 상태·사용량은 새 업무로 복사하지 않는다. |
| 대화 이력 | 실제 입력과 전달된 응답의 순서 있는 기록 | 원문을 보관하는 기록이다. 그 전체가 항상 모델 입력에 들어가는 것은 아니다. |
| 현재 문맥과 `head` | 이번에 사용할 이력 범위와 버전을 가리키는 정보 | 원문에서 다시 확인할 수 있는 파생 결과다. 세션의 head와 기존 작업의 `contextHead`는 별개다. |
| 개인 장기기억 | 담당이 선별해 다시 사용할 지식 | 별도 저장 책임을 유지한다. 대화가 이어진다는 이유로 모든 발언을 장기기억에 자동 등록하지 않는다. |

접근 범위에는 조직·담당·사용자·대화 번호를 함께 넣는다. 기본으로 이어갈 대화의 별칭도 사용자와 채널 경로별로 저장한다. 하나의 전역 기본 세션을 여러 담당이 공유하지 않는다. CLI와 Web에서 다른 세션의 업무는 자동으로 목록에 섞거나 조회·제어하지 못하며, 과거 세션을 명시적으로 선택해야 한다.

## 원문, 이력, 현재 문맥의 저장

기본 대화 저장소는 담당의 `.secumon/channel.sqlite`다. [SQLite 세션 어댑터](/Users/seunghanee/Documents/secumon/runtime/src/infrastructure/sqlite-sessions.ts)는 세션 정보, 입력 접수함, 순서 있는 이력 참조, 세션 문맥 버전을 구분한다.

- 사용자 원문과 구조화된 요청은 입력 접수함에 보관한다. 이력은 그 입력을 참조한다.
- 응답 원문은 기존 `local_messages`에 남는다. 응답 저장과 세션 이력 참조를 같은 SQLite transaction으로 기록한다. 한쪽만 성공한 상태를 전달 완료로 오인하지 않는다.
- 세션 head에는 반영 위치, 내용 지문과 정책 지문, 버전을 둔다. `digest`는 내용이 바뀌었는지 비교하기 위한 지문이다. 원문 이력을 head에 별도 정본으로 복제하지 않는다.
- 모델 입력에는 해당 작업이 반영한 위치까지의 허용된 대화가 들어간다. 과거 발언의 업무·입력·응답 출처를 유지하며 새 업무의 검증된 근거로 자동 승격하지 않는다.

작업 상태가 SQLite이든 file-journal이든 대화와 개인 장기기억은 각각의 SQLite 저장소를 사용한다. **file-journal 지원은 작업 상태 저장 방식의 선택이며 대화 이력까지 파일 저널로 저장한다는 뜻이 아니다.** 대화용 파일·문서·PostgreSQL 어댑터와 기억 선별·정정은 C03에 남는다.

세션 번호가 없는 기존 작업과 응답은 이전 조회 경로를 유지한다. 과거 원문이 없는데 목표 설명을 원문처럼 꾸미거나 새 세션에 자동 편입하지 않는다. C01 세션 표면의 `attach`는 현재 `session_attach_unsupported`로 거절한다. 과거 업무를 다른 세션에 명시적으로 가져오거나 공유하는 절차는 이번 단위에 포함하지 않았다.

## 접수부터 재시작까지

처리 순서는 원문 접수 → 기존 작업 생성 또는 명령 적용 → 적용 상태 확정 → 접수·결과 전달이다. 원문이 저장됐다는 사실과 작업에 적용됐다는 사실을 구분한다.

| 중단 위치 | 다시 열었을 때의 처리 |
| --- | --- |
| 원문 저장 후, 작업 생성 전 | 보관한 입력과 고정 업무 ID로 생성 절차를 이어감 |
| 작업 commit 후, 세션 적용 확정 전 | 같은 명령 영수증과 내용 지문을 확인하여 연결을 마침 |
| 적용 후, 클라이언트가 응답을 확인하기 전 | 같은 입력 ID·같은 내용이면 원래 업무를 반환. 다른 내용이면 충돌로 거절 |
| 로컬 응답 저장 후, outbox 확인 전 | 기존 응답과 세션 참조를 조회하여 전달 확인을 이어감 |

작업 DB와 대화 DB를 하나의 거대한 transaction으로 묶지 않았다. 서로 다른 저장소 사이에서 같은 입력 ID, 고정 업무 ID, 내용 지문과 기존 처리 영수증으로 복구한다. 여기서 ‘한 번 반영’은 **같은 요청을 재전송해도 입력·업무 생성·로컬 응답 이력이 중복되지 않는 저장 의미**다. 함수·모델 호출, 외부 도구 효과나 사람이 메시지를 읽는 일까지 정확히 한 번이라고 보장하지 않는다.

입력 저장·작업 commit·로컬 응답 저장 직후에 실제 child process를 SIGKILL로 중단하는 시험을 두 작업 backend에서 수행했다. 단순 예외 발생 시험과 구분되며, 재개 후 같은 입력·업무·전달 ID가 유지되는지 확인했다. [실제 중단 시험](/Users/seunghanee/Documents/secumon/runtime/src/tests/session-flow-kill.test.ts)

## 새 지시와 오래된 결과가 만났을 때

작업에 적용한 입력은 `messageId`·순서 번호·내용 지문으로 기록한다. 이를 `basis`, 즉 이번 결과가 의존하는 입력 기준이라고 부른다. 단순히 새 메시지가 접수됐거나 다른 업무의 응답이 도착했다는 이유로 모든 실행 기준을 바꾸지 않는다. 아직 적용되지 않은 해당 업무의 입력이 있으면 다음 실행·문맥 사용 전에 확인한다.

적용된 추가 입력은 기존 계획·근거·실행 장부를 보존하면서 `sessionReviewRequired`를 설정한다. 이는 ‘새 지시를 반영한 계획 검토가 필요함’이라는 표시다. 이전 근거만으로 즉시 완료하지 못하고 검증된 다음 계획을 채택해야 한다. 늦게 도착한 모델 계획이 새 입력 기준과 다르면 채택하지 않으며, 이미 사용한 자원은 기존 정산 경로에 남긴다.

모델 호출의 새 의미 버전 3에는 이 입력 기준이 포함된다. 기존 비세션 호출의 버전 1·2 의미는 유지한다. 입력 패킷을 만들 때와 결과를 채택할 때 원문·소유 범위·공개 정책·출처 참조를 다시 검사한다. 일반 실행 가능 여부 확인은 적용 입력과 대기 입력을 확인하므로 매번 대화 본문 전체를 읽지 않는다. [문맥·모델 대역 시험](/Users/seunghanee/Documents/secumon/runtime/src/tests/session-context-runtime.test.ts)

세션 문맥 게시에는 CAS를 사용한다. CAS는 ‘읽었던 버전이 아직 같은 경우에만 새 버전을 게시’하는 검사다. Y 문맥을 먼저 만든 뒤 X의 과거 문맥이 필요해도 X의 고정된 앞부분을 따로 보존한다. 최신 세션 head나 새 입력 위치를 과거로 되돌리지 않는다. 같은 범위·내용·정책의 문맥은 같은 버전을 재사용한다.

## CLI와 Web에서 확인되는 흐름

설치형 진입점은 `secumon-agent work <명령> --directory <담당 경로>`다. `session`은 대화를 열거나 다시 연결하고, `accept`·`demo`의 `--text`는 실제 원문을 접수한다. `history`는 입력과 응답을 조회하며 `input <업무 ID>`는 해당 업무에 추가 원문을 넣는다. `--session`은 기존 대화를 선택하고 `--new-session`은 새 대화를 만든다. 저장 backend는 담당 설정을 따르며 임의의 다른 DB로 바꾸지 않는다.

Web의 `web.js --directory <담당 경로>`도 같은 C01 저장소 조합을 사용한다. ‘업무 제목’과 ‘요청 원문’을 따로 받고 최초 질문 응답·추가 입력을 같은 세션 서비스에 연결한다. `run`은 별도의 명시적 실행 제어로 유지한다.

쿠키·CSRF를 사용하는 Web 접속 세션과 지속 대화 세션은 서로 다르다. 서버 재시작 뒤 새 인증 연결로 들어와도 같은 대화를 다시 열 수 있다. 접속을 종료해도 대화 기록을 삭제하거나 업무를 취소하지 않는다. 긴 이력은 ‘이 대화의 기록’이라는 접힌 영역을 열 때만 페이지 단위로 읽고, 내부 도구 사건을 모두 대화 말풍선에 넣지 않는다.

최소 화면은 연결했지만 새로고침 후 마지막 업무 카드의 자동 선택, 긴 업무 ID·기술적인 종류 이름의 표현은 C06에서 다듬어야 한다. Web이 받은 텍스트를 이해하고 범용 계획을 만드는 모델 연결은 C04에 남는다.

## 최초 Web 실패와 수정

최초 표면 시험은 64개 중 62개가 통과했고 새 Web 시험 두 개가 실패했다. 실패 지점은 원문 접수나 질문 응답 저장이 아니라 **질문에 답한 뒤 `run`으로 실행을 시작하는 순간**이었다. HTTP에는 `500 / request_failed`가 보였고, 같은 controller를 직접 호출해 원래 오류 `session_current_input_unavailable`을 확인했다. ### 실제 브라우저에서 확인한 것

숨김 상태의 Codex in-app browser로 localhost 합성 작업실을 조작했다. 첫 한국어 요청을 입력해 접수와 합성 결과가 한 번씩 표시되는지 확인하고, 이력을 펼쳐 원문·접수·결과와 출처 식별자를 화면에서 확인했다. 같은 세션에 두 번째 요청을 넣어 완료 업무 두 개와 순서 있는 이력 여섯 개를 확인했다. 새로고침 후에도 같은 세션 ID, 업무 카드 두 개, 양쪽 원문과 결과가 유지됐다.

이는 브라우저 새로고침 검증이며 서버 프로세스 재시작은 CLI/HTTP 시험의 별도 검증이다. 스크린샷은 도구 출력에서 검토했고 이미지 파일로 내보내지는 않았다. 확인 뒤 탭을 닫고 서버에 SIGINT를 보내 종료를 확인했으며 임시 담당 폴더를 정리했다. 합성 결과가 자연어 형식 지시를 이해했다는 증거로 사용하지 않는다. [브라우저 검증 기록](/Users/seunghanee/Documents/secumon/runtime/evidence/C02-session-browser-verification.json)

## 아직 남은 조건

현재 세션 문맥은 적용한 입력까지의 원문 이력 중 **최대 256개 항목·직렬화한 문맥 본문 64KiB**를 확인하는 제한된 방식이다. 넘으면 서비스가 `session_context_capacity`로 거절하며 원문은 저장소에 보존한다. 오래된 합의를 자동 요약하거나 일부를 버리고 성공한 것처럼 진행하지 않는다. 이 한도 자체가 자동 의미 요약이나 반복 compact를 구현했다는 뜻은 아니다.

Web의 현재 공개 오류 목록에는 일부 문맥 용량·입력 불가 오류가 없어 일반 `request_failed`로 표시될 수 있다. 서비스의 원문 보존과 명시 오류 반환은 구현됐지만 사람이 이해할 수 있는 용량 안내 UX는 남아 있다. 소스를 변경하지 않고 후속 compact 단위의 인수 조건으로 넘긴다.

다음 작업은 [C02 세션 compact 계획](C02-session-compact-plan.md)이다. 현재 요청·합의·미해결 질문·반론·원본 참조를 유지하는 증분 문맥과 반복 compact를 연결한다. 요약 중 새 입력이 와도 반영 위치를 건너뛰지 않도록 하고, 중단·재시작·취소·늦은 결과를 검증해야 한다. 이번 원문 이력, 적용 입력 기준과 세션 head 검사를 재사용한다.

개인 기억과 추가 저장 어댑터는 C03, 실제 모델의 자연어 해석·계획·응답 품질과 범용 프롬프트는 C04, 채팅 UX·Knox·사내 인증 연동은 C06에 남는다. 실제 Windows 파일 경계와 설치·실행, 호스트 임의 코드 격리는 C01 잔여 조건이다. **이번 첫 연결 단위의 검증을 C01 전체, C02 전체 또는 전체 구현 goal 완료로 표시하지 않는다.**
