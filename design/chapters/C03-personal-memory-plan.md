# C03 개인 장기기억: 명시적 등록부터 새 대화의 회상·정정·잊기까지

2026-09-07 · 다음 사용자 흐름의 구현 계획 · 구현/시험 완료 기록 아님

**이번 단위는 담당 A에게 명시적으로 맡긴 기억을, 같은 사용자가 A의 새 대화에서 필요한 만큼 불러오고 정정하거나 잊게 하는 흐름을 CLI와 Web까지 완성한다.** 기본 저장소는 담당 디렉터리의 SQLite다. 대화 이력이나 compact 요약을 장기기억에 자동 복사하지 않는다. 모델의 자연어 판단 없이도 저장·출처·격리·회상·취소를 검증할 수 있어야 한다.

## 1. 착수 조건과 현재 근거

[C02 최종 검증 근거](../../runtime/evidence/C02-compact-verification.json)에서 **최종 Linux 전체 2,836/2,836, compact 46/46 통과와 전용 시험 프로세스 0개·SSH 종료를 확인했다. 이 계획의 명시적 개인 기억 사용자 흐름에 필요한 범위별 착수 gate는 충족했다.** 최종 sourceDigest는 `2193685e0a64d0f88e40113b2838afc03c8c24b8430d6a6c36847613b77e0967`이다. C03 구현 자체나 C01/C02 전체·전체 goal의 완료를 뜻하지 않는다.

C02의 초기 42/46, 첫 NAS 2,830/2,831 실패와 각 원로그/pin은 [후속 감사](C02-post-compact-audit.md)와 [결과](C02-session-compact-result.md)에 역사적 근거로 보존했다. 첫 NAS의 정확한 throw 줄은 미확정이며, 이후 동일 오류 경로의 고정 재현·수정·최종 통과를 구분한다. build2 브라우저와 합성 계측 1회는 별도 pin의 관측으로 남기고 최종 소스에 소급하지 않는다. 이번 문서 갱신에서 시험·계측을 재실행하지 않았다.

C03 착수 시 다음 경계를 유지한다.

- 최종 소스의 C02 반복 compact·CLI/Web 등록 시험·중단·복구·정산·출처 경계와 별도 build2 브라우저 관측을 각 근거 범위에서 재사용한다. 변경 전 빌드의 통과를 최신 소스 통과로 옮겨 적지 않는다.
- 최초 설정 오류는 고정 재현·수정 후 최종 Linux 전체에서 통과했다. 실패·수정 근거를 유지하며, 최초 NAS의 정확한 throw 줄까지 확정한 것처럼 쓰지 않는다. 이제 이 실패를 조사 중인 C03 차단 조건으로 표시하지 않는다.
- 사용자 원문 receipt와 적용 상태, 담당 ID, 저장 owner, 요약의 원문 참조 계약을 이번 단위의 안정된 입력으로 삼는다. C01 파일 경계나 C02 compact를 다시 구현하는 일을 끼워 넣지 않는다.
- 실제 모델/API 실험 중단은 유지한다. 합성 provider의 의미 정답은 시험 자료이며, 임의 모델의 기억 선별·자연어 이해·반론 보존 품질을 검증한 것이 아니다. Windows의 별도 실행 미검증도 해당 플랫폼의 잔여로 표시한다.

## 2. 사용자가 경험할 한 흐름

1. 담당 A의 대화 X에서 “답변은 한국어로, 먼저 세 문장으로 요약해 줘”라고 말하고 **기억하기**를 명시한다. 저장한 문구, 적용 범위, 출처 대화를 보여 준다.
2. X를 완료하고 프로세스를 재시작한다. A의 새 대화 Y와 새 업무를 열고 “답변 형식” 기억을 검색하여 선택한다. Y의 실제 모델 입력 packet에 그 기억과 버전이 포함된다. X의 WorkState나 대화 전체를 Y로 복사하지 않는다.
3. Y에서 “이제 첫 요약 뒤에 자세한 설명도 붙여 줘”를 **정정**한다. 이미 불러온 옛 기억을 사용하는 입력 프레임과 늦게 도착한 계획은 그대로 채택할 수 없다. 새 버전을 다시 불러오면 진행할 수 있다.
4. **잊기**를 실행한다. 재검색·직접 조회·재시작·기존 프레임 재사용에서 그 기억을 활성 장기기억으로 돌려주지 않는다.
5. 같은 SQLite를 쓰는 담당 B와 다른 사용자의 조회에서도 A/원래 사용자의 개인 기억이 보이지 않는다. 다른 사용자의 변경 명령으로 원래 기억이 바뀌지 않는다.

첫 인수는 명시적 버튼/명령으로 등록하고, 검색어와 선택으로 회상한다. 자유 문장 속 “기억해”를 모델이 정확히 감지하거나 새 업무에 필요한 기억을 스스로 고르는 기능까지 통과했다고 주장하지 않는다. 그 자동 선택은 이후에도 동일한 저장·권한·출처·의존성 경로를 사용한다.

## 4. 기억의 소유자와 저장 방식

### 논리 격리

개인 기억 소유자는 `tenantId + agentId + principalId`로 고정한다. tenant는 조직, agent는 담당의 지속 ID, principal은 인증된 사용자다. sessionId는 원문 출처에 포함하지만 기억 소유자에는 포함하지 않아 새 대화에서도 회상할 수 있게 한다. namespace는 “개인 기억/업무 경험” 같은 분류이며 접근 권한을 대신하지 않는다.

- agentId는 C01의 저장된 담당 ID를 호스트가 주입한다. 폴더 경로·표시 이름·모델 인자에서 새로 추론하지 않는다. 디렉터리를 이동해도 동일 담당이고, 복제된 새 담당에 기억이 자동 귀속되지는 않는다.
- `KnowledgeRecord`와 내부 `MemoryRef`에는 소유 범위를 명시한다. private 개인 기억의 키는 소유 범위와 id를 결합한다. `get/receipt/commit/candidates/indexHead/rebuildIndex`, 캐시 키, 부모 기억 참조와 dependency 검증까지 동일 범위를 전달한다. 호출자가 임의 agentId를 지정해 어댑터 경계를 바꿀 수 없게 한다.
- 기존 shared/reviewed 업무 기억은 기존 공개 정책을 유지한다. 개인 기억은 별도 종류/적용 범위로 private를 강제하고, reviewer 권한이 있다는 이유로 타인의 개인 기억을 읽을 수 없게 한다. 개인 기억을 공유 지식으로 승격하는 정책은 이번 흐름 밖이다.
- 개인 기억이 여러 업무에서 쓰일 수 있다는 것은 업무별 allowedScopes/labels/destination 제한을 제거한다는 뜻이 아니다. 개인 선호를 읽을 권한과 해당 원문을 현재 모델 목적지로 보낼 권한을 모두 확인한다. 기억은 최신 사용자 지시나 보안 정책을 덮어쓰는 지시가 아니다.

### 기본값과 공유 DB

기본은 **담당 디렉터리의 SQLite 정본**이다. 짧은 기억의 버전 변경·명령 중복 방지·삭제·색인을 한 트랜잭션으로 관리할 수 있고 서버 설치가 필요 없다. 원문 대화는 channel 저장소, 실행 상태는 state 저장소에 그대로 둔다. 개인 기억 DB를 대화 로그 DB와 합치지 않는다.

동일 DB 격리를 검증하려면 SQLite 어댑터에 명시적 다중 담당 저장 모드를 둔다. 이 모드는 배치 호스트가 고정한 저장소 등록과 담당별 scoped handle로 연다. 기존 `bindAgentDatabase`의 단일 담당 owner 확인을 삭제하거나 기존 DB가 갑자기 여러 담당을 허용하게 바꾸지 않는다. 기본 경로는 기존 단일 담당 소유권을 계속 사용한다. 공유 모드의 owner/schema는 구별하고 등록되지 않은 담당의 열기를 거절한다. 동일 파일의 두 연결에서 같은 id/명령 id를 써도 소유 범위가 다르면 충돌·교차 조회가 없어야 한다.

이는 애플리케이션의 논리 격리다. DB 파일 전체를 직접 읽을 OS 권한을 가진 사람까지 차단하는 암호화나 별도 프로세스 격리를 확보했다고 주장하지 않는다. 사내 인증/Knox 연결 전체는 후속 채널 작업으로 남기고, 이번 CLI/Web은 호스트가 정한 사용자에 고정한다.

파일 디렉터리의 Markdown 기억과 등록형 PostgreSQL은 후속 어댑터로 유지한다. 같은 소유 범위·버전·출처·삭제·중복 명령 계약을 통과해야 정본으로 사용할 수 있다. Markdown을 사람이 수정하면 검증할 새 revision 후보가 되며, 파일 내용이 즉시 신뢰된 기억으로 바뀌지 않는다. SQLite 장애 시 빈 파일 기억으로 자동 전환하거나 원문 전체를 다시 복사하지 않는다.

## 5. 사용자 발언 출처를 추가하되 Evidence의 의미는 유지

출처를 버전 있는 구별 가능한 유형으로 확장한다. 기존 Evidence 출처는 sourceVersion/generation/정책/근거 상태/효과·입력 계보 검사를 그대로 유지한다. 새 `session_user_receipt` 유형은 다음 정보를 고정한다.

- 원래 `SessionScope`, messageId, sequence, digest, workId와 선택한 정확한 문구. 새 기억의 소유자와 원문의 tenant/agent/principal은 같아야 한다.
- 원문 receipt가 applied인지, 저장된 원문 본문·payload·kind·workId의 digest와 history entry가 일치하는지. pending/rejected 입력이나 assistant 출력은 사용자 명시 기억의 근거로 사용할 수 없다.
- 원문 업무의 현재 정책·데이터 세대와 labels, 현재 조회자의 권한 및 목적지. 원문 또는 원본 참조가 없어졌거나 접근이 철회되면 파생 기억을 계속 유효하다고 반환하지 않는다.
- “사용자가 요청한 선호/기억”이라는 해석. 사용자 발언의 존재를 확인한 것과 그 발언이 외부 세계의 검증된 사실이라는 주장을 구분한다. 기존 fact의 완전한 Evidence coverage나 완료 근거로 승격하지 않는다.

기억하기 버튼/명령이 새 문구도 받으면 C02의 정상 입력 접수·적용을 먼저 완료하고 그 receipt를 참조한다. 기존 발언 선택은 이미 applied인 receipt를 그대로 사용한다. 기억 저장 명령의 commandId와 원문 messageId를 구분해 재전송에도 원문을 또 만들지 않는다. 출처 검증과 기억 등록이 서로의 완료를 기다리는 순환 상태를 만들지 않는다.

정정은 새 applied 사용자 원문을 근거로 현재 기억의 내용·출처·contentRevision을 바꾸고 이전 revision을 무효화한다. 현행 `revise`는 title/body만 바꾸므로 개인 기억에는 출처 교체를 함께 검증하는 명시적 정정 경로가 필요하다. 기존 Evidence 기억의 일반 revise 의미를 몰래 바꾸지 않는다. 정정 전후 revision, 출처 참조, 명령 digest의 최소 감사 기록을 남긴다. 현행 정본 행과 receipt가 모든 과거 revision 본문을 보존한다고 가정하지 않는다.

## 6. 선택적 회상과 현재 문맥의 연결

회상은 **후보 검색 → 선택한 정본 읽기 → 출처/버전 재검사 → 현재 업무 입력으로 적용** 순서다. SQLite 검색은 우선 현재의 정규화된 문자열 검색을 재사용한다. 벡터 DB나 모델 임베딩은 첫 흐름의 의존성이 아니다. 초기 기본 한도는 카드 5개·합산 8 KiB 정도로 두고 실제 packet 크기에서 조정한다. 넘치면 더 좁은 검색/선택을 요청하며 전부 넣거나 조용히 누락하지 않는다.

검색 캐시는 현재처럼 정본 본문 대신 후보 id만 보관한다. 소유 범위·권한·query·index head가 캐시 키에 들어가고, 반환 전에는 정본과 출처를 재검사한다. 색인 지연/오류/잘림은 부분 결과로 표시한다. 개인 기억 commit과 해당 색인 갱신을 함께 처리하거나 갱신 receipt를 회복하여 “저장 성공했지만 새 대화에서 계속 찾을 수 없음”을 끝까지 처리한다. 검색할 때마다 전체 namespace 색인을 재구축하는 방식은 피한다.

명시적 CLI/Web 회상은 범용 계획을 가짜로 만들거나 가짜 도구 시도를 추가하지 않는다. 현재 업무에 **선택한 기억의 ref/revision/dependency와 적용 입력 basis**를 좁은 영속 선택 상태로 저장하고, compiler와 현재성 검사가 기존 도구 관측의 knowledgeDependencies와 함께 읽도록 연결하는 방식을 우선한다. 이는 새로운 장기기억 사본 저장소가 아니라 이번 업무가 무엇을 입력으로 사용했는지 표시하는 상태다. 본문은 검증된 읽기 결과로 bounded packet에 조합하며 프레임 basis/digest에 선택 참조가 들어간다.

`core.memory.get/search`를 모델/계획이 사용하는 기존 경로는 그대로 실제 도구 호출·사용량 수명을 따른다. 개인 범위 검색을 허용할 때도 같은 서비스와 반환 dependency를 사용한다. 호스트의 명시적 회상을 모델 도구 사용량으로 허위 정산하지 않고, 저장소 읽기 비용은 별도로 계측한다. 후속 자율 회상도 두 경로의 권한·현재성 검사를 우회할 수 없다.

현재성 검사는 compile 시점뿐 아니라 모델 호출 직전·지연 응답 채택·도구 실행·결과 전달·복구에도 적용한다. 정정/잊기가 먼저 확정됐으면 이전 revision을 사용하는 계획과 답변은 채택하지 않는다. 선택 상태 변경은 기존 plan/근거를 복사·완료 처리하지 않고 필요한 재검토를 요구한다. 취소된 업무에 늦은 회상 결과가 적용되지 않게 상태 revision과 입력 basis를 확인한다.

“잊기”는 기억 정본의 tombstone(다시 활성화하지 않는 삭제 표식)과 현재 본문 제거, 검색/캐시/입력 참조의 사용 중단이다. 과거 원문·백업·이미 전달된 대화를 물리적으로 삭제했다는 뜻이 아니다. 원문에 남은 이전 지시는 ‘과거 발언’이며 정정/잊기 이후의 유효 선호와 구분한다. 기억을 인용한 관리 메시지/자동 요약에는 해당 memory ref/revision을 연결해 철회된 기억을 다시 활성 선호로 유입시키지 않게 한다. 임의의 과거 자유 문장에 같은 내용이 있다는 것까지 완벽히 지웠다고 주장하지 않는다. 기존 요약에 이 참조를 검증할 수 없으면 안전한 원문 재구성/재요약 경로를 사용하고, 정책 검사를 생략한 오래된 요약으로 회복하지 않는다.

## 7. CLI/Web의 끝단과 실패·경합

CLI는 `memory remember/search/recall/revise/forget`에 해당하는 명시적 동작을 제공한다. 최종 명령 철자는 기존 파서 규칙에 맞춘다. 관리 요청은 source message/ref와 안정된 commandId를, 정정/잊기는 expectedRevision을 받는다. 회상은 대상 업무와 현재 입력 basis를 확인한다. 기억 관리는 일반 업무 실행이나 모델 planning을 자동 시작하지 않는다.

Web에는 대화 발언의 기억하기, 개인 기억 목록/검색, 이번 업무에 적용, 정정/잊기 동작을 붙인다. 내부 원문·권한 stamp·DB 경로를 채팅 메시지마다 출력하지 않는다. 한 번 접수 상태를 표시하고 확정 뒤 짧은 결과와 접을 수 있는 기억 카드를 보여 준다. 재접속하면 저장된 결과를 재조회한다. 기존 localhost 인증·CSRF·소유자 검사와 오류 노출 규칙을 재사용한다. 호스트 사용자 선택은 모델/HTTP body가 공급하는 임의 principalId로 대체하지 않는다.

| 발생 상황 | 필요한 결과 |
| --- | --- |
| 원문 적용 뒤 기억 commit 전 중단 | 같은 messageId/commandId로 재개한다. 원문은 유지하고 기억 등록 성공을 미리 표시하지 않는다. |
| DB commit 성공 뒤 응답 유실 | scoped command receipt로 같은 결과를 반환한다. 이중 등록/새 revision 생성/채팅 중복 통지를 막는다. |
| SQLite commit 결과 불명·busy·읽기 실패 | 성공/기억 없음으로 둔갑시키지 않는다. 결과 불명은 receipt 재조회로 해소하고 횟수를 제한한 재시도 또는 명시 오류로 끝낸다. |
| 정정/잊기 동시 요청 | expectedRevision CAS로 하나를 확정한다. 오래된 요청은 충돌이며 새 기억을 덮어쓰지 않는다. 삭제 후 이전 create 재전송으로 복원하지 않는다. |
| 회상 중 정책 변경·정정·삭제·취소 | 마지막 검증과 업무 적용 CAS에서 거절한다. 저장된 이전 프레임·늦은 모델 응답도 같은 dependency 검사를 통과해야 한다. |
| 기억 DB commit과 WorkState 무효화 사이 중단 | 다른 DB까지 원자적이었다고 주장하지 않는다. 정본 revision 검사가 다음 소비를 막고 재개 시 무효화한다. 원문 출처/권한을 검증할 수 없는 기록도 사용할 수 없다. |
| 출처 소실 후 잊기 요청 | 권한 있는 소유자는 철회/삭제할 수 있다. 이미 소실된 출처를 다시 검증해야만 잊을 수 있는 막힘을 만들지 않는다. |
| 색인 지연 또는 손상 | 정본 직접 조회의 권한 검사는 유지한다. 검색은 부분/오류를 표시하고 인덱스 복구를 수행한다. 정본을 임의 삭제하거나 타 담당 색인으로 대체하지 않는다. |

두 저장소 사이의 경쟁은 최종 검사만 여러 번 넣는 것으로 원자성이 생기지 않는다. 개인 기억의 논리 사용 조건을 ‘현재 정본 revision + 유효 원문 + 현재 소유 범위/정책 + 적용된 업무 선택’으로 명시한다. 검증 실패 후보는 이미 행이 존재하더라도 모델 입력에 쓰지 않는다. 기존 모델/도구 unknown 결과와 사용량은 메모리 변경을 이유로 유실시키지 않는다.

## 8. 구버전과 이행

기존 Evidence 출처/dependency는 명시적인 legacy 읽기 경로로 계속 검증한다. 새 source/record/dependency schema는 버전을 구분한다. 과거 WorkState나 모델 입력 artifact의 JSON에 agentId를 덧붙여 기존 해시가 맞는 것처럼 바꾸지 않는다. 새 개인 기억의 필수 소유 범위를 생략한 옛 reader는 이를 읽지 못하게 한다.

기존 단일 담당 DB의 agentId는 확인된 C01 owner에서만 매핑한다. 기존 private 업무 기억의 authorId와 의미는 보존하고 개인 선호로 일괄 변환하지 않는다. owner가 없거나 여러 담당의 자료가 이미 섞인 DB는 자동 추론해 합치지 않는다. 별도 이행 입력/검토가 필요하다. shared 업무 지식의 사용자 간 공개 의미를 새 개인 기억 격리와 혼동하지 않는다.

SQLite 이행은 백업 가능 상태 확인, schema 전환/소유 키 채움/색인 재생성, 중단 재개를 한 경로로 검증한다. 변환된 DB를 이전 바이너리가 읽으며 담당 구분을 무시하지 못하도록 최소 지원 schema 검사를 둔다. downgrade는 호환되는 백업 복원 또는 명시적 내보내기 절차이며 자동 롤백으로 원문·기억을 합치지 않는다. 새 공유 모드로의 이행은 원래 단일 owner를 자동으로 약화하지 않는 명시적 등록 절차다.

## 9. 구현 순서와 한 단위의 인수

진행은 다음 순서로 하되, 각 항목을 독립 helper 제작 완료로 나눠 사용자 흐름을 미루지 않는다.

1. **소유자와 출처를 실제 등록 경로에 연결한다.** 버전 있는 개인 기억/원문 receipt 계약, scoped SQLite와 단일·공유 owner 정책, 명시적 등록·정정·잊기 서비스를 함께 연결한다. 기존 Evidence 경계 시험을 유지한다.
2. **새 대화의 회상을 실제 입력까지 연결한다.** bounded 검색/정본 검증/영속 선택 상태와 dependency, compiler·frame·실행·복구의 현재성 검사를 완성한다. 입력 변경 시 리뷰와 기존 자원 정산 경로를 재사용한다.
3. **같은 API로 CLI/Web 사용자 흐름을 끝낸다.** 등록→완료/재시작→새 대화 회상→정정→잊기를 두 표면에서 실행한다. 독립 관리자 API만 만들어 놓고 이번 단위를 완료하지 않는다.
4. **아래 실패·격리·이행을 같은 소스 pin에서 검증하고 결과를 남긴다.** 관련 회귀와 필요한 통합 검증을 마친 뒤 비용/한계를 기록한다. 변화 없이 광범위 검증을 계속 반복하지 않는다.

인수 범위:

- 실제 C01 담당 + SQLite + SessionService + KnowledgeService + compiler를 사용한 X→Y 흐름. 새 Y의 원문 history에는 X가 없지만 실제 packet과 저장 입력 artifact에는 선택한 유효 기억이 있다. Y는 자신의 goal/plan/state를 가진다.
- 실제 CLI 프로세스와 Web 동작으로 기억하기·검색·적용·정정·잊기·재접속을 확인한다. Web HTTP 계약만 통과한 경우 화면 조작까지 검증했다고 쓰지 않는다. 읽기 완료와 모델의 실제 자연어 활용 품질은 분리한다.
- 동일 SQLite 파일에서 담당 A/B, 사용자 U/V, 충돌하는 memory id/commandId를 사용한다. 직접 get, 검색, 부모 ref, receipt, cache, index head/cursor, 프레임 재사용 모두에서 교차 접근이 없다. private 개인 기억에 reviewer 권한도 우회 수단이 되지 않는다.
- 개인 기억은 허용된 새 업무에서 사용할 수 있고, 업무 범위 기억은 기존 scope 밖에서 계속 거절된다. source labels/목적지 권한 축소, receipt 본문/hash 불일치, pending 입력, 원문/업무 소실을 거절한다.
- 정정/잊기 후 이미 준비된 프레임·실행 중 synthetic 모델의 늦은 응답·선택 중 취소·재시작에서 낡은 기억이 채택되지 않는다. 기존 unknown 외부 효과와 보고된 사용량/정산은 남는다. 이 시험에서의 의미 답변은 합성 자료다.
- commit 뒤 응답 유실/강제 종료, 같은 명령 재전송, stale CAS, 색인 지연, legacy DB 이행 중단을 확인한다. 실제 강제 종료를 하지 않은 오류 주입을 kill 복구 검증이라고 부르지 않는다.
- 정상 사용에서 대화/요약/아카이브 검색 결과가 개인 기억에 자동 복제되지 않는다. 잊기는 활성 기억을 철회하지만 과거 원문·백업의 물리 삭제를 보장하지 않는다는 표시를 확인한다.
- 기존 Evidence 기억의 출처·effect custody·입력 의존성·공유 리뷰 검증을 약화하지 않는다. 메모리 카드가 목표 완료의 새 Evidence로 통과하지 않는다.

비용은 검색 후보 수, 실제 반환 카드/바이트, 정본·원문 receipt·state 조회 수, 캐시 적중, 프레임 입력 바이트, 지연을 구분해 기록한다. 가능하면 출처의 필요한 단일 발언을 직접 확인하고 C02의 전체 원문 prefix 검증을 무조건 복제하지 않는다. 이 최적화가 원문 receipt와 history 일치 검사를 생략하는 이유가 되어서는 안 된다. 모델/API 없는 명시적 기억 작업에는 가상의 토큰 절감률을 붙이지 않는다.

## 10. 이번에 끝내지 않는 부분

자연어 자율 등록/선별의 실제 모델 품질, 문서 기억/등록형 PostgreSQL의 운영 어댑터, 자동 임베딩, 게시판·아카이브, 담당 간 기억 공유 승인, 원문/백업까지 포함한 물리 삭제, 사내 사용자 디렉터리·Knox 인증 연동은 후속으로 남긴다. 후속 기능도 이번에 확정할 소유 범위·출처·버전·삭제·현재성 계약을 따른다. 이 계획은 코드나 백로그 상태를 변경하지 않는다.
