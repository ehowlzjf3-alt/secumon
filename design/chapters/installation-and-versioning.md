사용자는 공통 실행기를 담당 디렉터리에서 호출하려면 설치형 제품과 버전 관리가 필요하다고 확인했다. 이 문서는 `workspace-agent-defaults.md`의 공통 엔진/담당 데이터 분리를 설치·업데이트 수명에 연결한다.

## 1. 기본 원칙

- 설치되는 것은 공통 실행기다. 담당마다 본체 소스를 복사하지 않는다.
- 담당 디렉터리의 정체성·설정·대화·기억·작업 상태는 설치 패키지 밖에 유지한다.
- 엔진 업데이트와 담당 데이터의 형식 이행을 구분한다. 엔진 교체가 곧 데이터 초기화가 되지 않는다.
- 실행 중인 담당의 엔진을 몰래 교체하지 않는다. 체크포인트와 진행 중 실행의 상태를 확인한 전환 지점에서 재개한다.
- 패키지 삭제는 기본적으로 담당 데이터를 삭제하지 않는다.
- 제품 릴리스 번호, 설계 문서의 개정 번호, 개별 데이터 레코드의 수정 번호는 별개다.

## 2. 설치 패키지와 배치

초기 배포 목표는 현재 TypeScript/Node 기반 코드를 빌드한 CLI 패키지다. 지원 Node 버전과 의존성을 명시하고 전역 명령 `secumon-agent`를 제공한다. 초기 설치에서 사용자가 제품 저장소의 소스를 직접 빌드해야 하는 흐름은 목표로 삼지 않는다.

사내 배포는 내부 패키지 저장소 또는 검증된 설치 묶음을 통해 제공할 수 있다. 인터넷 없는 배치를 지원하려면 런타임 의존성까지 포함하거나 사내에서 해결할 수 있어야 한다. 일반 npm tarball만 만들었다고 외부 의존성 없는 오프라인 설치가 자동 보장되는 것은 아니다. Node까지 포함하는 운영체제별 단독 실행 패키지는 필요에 따라 확장하며 첫 구현에 모든 배포 형식을 동시에 강제하지 않는다.

전역 명령은 설치된 엔진 버전을 선택해 실행하는 진입점으로 둔다. 업데이트 시 새 릴리스를 별도 위치에 설치하고 확인한 뒤 사용 버전을 전환할 수 있게 한다. 모든 담당이 매번 ‘최신 버전’을 내려받아 실행하는 기본값은 두지 않는다.

## 3. 버전의 종류

| 종류 | 설명 | 예시의 의미 |
|---|---|---|
| 엔진 버전 | 실행기와 공개 CLI/확장 계약의 배포 버전 | 1.2.3 같은 주·부·수 형식 |
| 설정 형식 버전 | config 파일을 어떤 구조로 읽는가 | 예: 설정 형식 2 |
| 저장 형식 버전 | 세션/작업/기억을 어떤 구조로 읽고 쓰는가 | 예: 상태 형식 4, 기억 형식 2 |
| 확장 계약 버전 | 도구·스킬·저장 어댑터의 호환성을 식별 | 도구 schema/지침 내용 개정과 활성 버전 |

위 숫자는 설명용이며 현재 배포 버전이 아니다. 엔진 버전에는 SemVer의 공개 계약 변경 의미를 적용하는 안을 사용한다. 호환되는 버그 수정은 수 버전, 호환되는 기능 추가는 부 버전, 호환되지 않는 공개 계약 변경은 주 버전으로 구분한다. 초기 0.x는 안정된 공개 API를 보장하는 단계로 표시하지 않는다. 버전 번호만으로 저장 데이터의 읽기/쓰기 호환성을 추정하지 않고 별도 호환 정보로 검사한다. [SemVer 공식 명세](https://semver.org/lang/ko/)

현재 `runtime/package.json`에는 개발 패키지 버전 `0.1.0`과 `private: true`가 있다. 이 번호가 검증된 설치형 릴리스나 이전 문서의 v0.50 같은 구현 기록 번호와 같은 뜻은 아니다. 전역 실행 명령 등록과 릴리스/이행 체계는 아직 구현하지 않았다.

## 4. 담당별 버전 선택

담당 초기화 때 검증된 설치 버전으로 시작하고, 그 담당이 사용하는 정확한 엔진 버전을 기록한다. 같은 호스트의 A를 먼저 업데이트해 확인한 뒤 B를 전환할 수 있다. 특정 버전 고정은 엔진 파일을 담당마다 복제하는 방식 대신 공통 설치된 해당 릴리스를 선택하는 방식으로 제공한다.

요청한 버전이 설치되어 있지 않으면 설치 필요 상태를 표시한다. 호환 확인 없이 다른 버전으로 조용히 대신 실행하지 않는다. 엔진 설치 경로는 담당이 임의로 바꾼 실행 파일을 로딩하는 권한이 되지 않도록 설치된 릴리스 목록에서 확인한다.

모델·스킬·도구 계약이 달라져도 동작이 달라질 수 있으므로 실행 기록에는 실제 사용한 엔진/모델/지침/도구 계약 식별자를 남긴다. 이것은 같은 결과의 완전한 재현을 보장한다는 의미는 아니다. 단순 Markdown 스킬에도 읽은 내용의 개정/hash를 연결할 수 있어 모든 지침을 별도 배포 패키지로 만드는 복잡성을 피한다.

## 5. 업데이트 절차

1. 새 엔진 패키지를 별도 위치에 준비하고 버전·내용·지원 환경·형식 호환성을 확인한다.
2. 대상 담당의 현재 버전, 설정, 저장 형식과 진행 중 작업을 확인한다. 가능하면 실제 변경 전 이행 내용을 점검한다.
3. 새 실행 배정을 멈추고 이미 진행한 모델/도구 호출을 완료 또는 중단·대조한다. 문맥·작업 상태를 체크포인트로 저장한다.
4. 형식 변경이 필요한 경우 일관된 백업과 소유권을 확보한 뒤 이행한다. 실패/중단 후 중복 이행하지 않도록 완료 상태를 기록한다.
5. 선택 엔진을 전환하고 세션·기억·근거·대기 상태를 확인한 뒤 같은 담당으로 재개한다.

새 설치 패키지를 준비하는 것과 실행 중인 담당을 전환하는 것은 다른 단계다. 기본 업데이트는 관리 동작으로 수행하며 담당 에이전트의 일반 업무 도구에 공통 본체 수정 권한을 부여하지 않는다.

SQLite, PostgreSQL, 파일 기반 저장은 같은 이행 결과 계약을 구현하지만 백업/잠금/원자성 확보 방법은 각 어댑터가 소유한다. Markdown 기억도 metadata 형식이나 참조 규칙이 바뀌면 버전/이행을 고려해야 한다.

## 6. 되돌리기와 실패 복구

- 데이터 형식이 이전 엔진과 호환되면 엔진 선택을 이전 버전으로 되돌려 같은 최신 데이터로 재개할 수 있다.
- 데이터 형식이 호환되지 않으면 구버전 실행기를 강제로 열지 않는다. 지원되는 역이행 또는 데이터 복구 절차를 사용한다.
- 업데이트 전 백업 복원은 백업 이후의 대화/기억/실행 기록을 잃을 수 있으므로 자동 롤백과 동일시하지 않는다. 실제로 되돌릴 범위를 명확히 해야 한다.
- 코드/DB 버전을 되돌렸다고 이미 발생한 외부 발송·변경이 취소되는 것은 아니다. 실행 영수증과 현재 효과를 대조해 중복 수행하지 않는다.
- 형식 이행 중단 시 동일한 이행을 재개하거나 이전 상태를 복원할 수 있는지 검사한다. 낡은 엔진과 새 엔진이 같은 상태에 동시에 쓰지 않도록 한다.

## 7. 릴리스 기록과 확인

릴리스에는 엔진 버전, 소스/빌드 식별자, 지원 실행 환경, 포함 파일, 설정/저장/확장 호환 범위, 변경 내용, 실행한 검사와 미실행 범위를 기록한다. 이미 배포한 같은 버전의 패키지 내용을 바꿔 덮어쓰지 않는다.

소스 변경 이력과 배포 이력도 구분한다. 소스 버전 관리, 설치 패키지 생성, 내부 배포 등록은 각각 수행 결과로 확인해야 하며 문서에 버전 번호를 적었다고 완료로 표시하지 않는다. 이번 턴에 Git 초기화·커밋·패키지 공개/설치·업데이트 명령은 실행하지 않았다.

검증 범위는 신규 설치/첫 설정, 같은 버전 재실행, 기존 담당 업데이트 후 지속 세션, 형식 변경 없는 엔진 되돌리기, 이행 중단/재개, 비호환 구버전 거절, 담당별 버전 고정, 모델 미연결 로컬 검증, 패키지 제거 후 데이터 보존이다. 오프라인 설치를 제공하는 릴리스는 네트워크 없는 환경에서 의존성 해결까지 실제로 확인해야 한다.

## 8. 구현 순서에 연결

담당 초기화와 전역 실행기 단계에서 패키지 버전 표시·저장 형식 버전·담당의 사용 엔진 기록을 함께 설계한다. 지속 세션/기억 계약을 구현한 뒤 업데이트·이행·복구 시험을 추가하고 설치형 릴리스를 만든다. 설치 후 가짜 예제만 실행되는 상태와 실제 모델을 사용한 업무 품질 검증을 구분한다.

현재 실제 모델/API 시험 중단은 유지한다. 제품 코드와 설치 환경은 이번 설계 추가에서 변경하지 않았다.
