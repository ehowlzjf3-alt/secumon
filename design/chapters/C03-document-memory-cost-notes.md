# C03 문서 기억의 단회 비용 관측과 C05 검토

2026-09-07 작성. **문서 기억의 실제 등록·회상·문맥 조합·재열기 흐름은 이번 계측에서 통과했지만, 호출 효율 개선을 완료한 것은 아니다.** 105B 본문 한 개의 문맥 준비에서 공통 파일 경계의 파일 열기 1,104회와 읽기 378,810B가 관측됐다. 동기화 재사용과 후보 캐시가 있어도 여러 계층의 정본·출처 확인은 반복된다. 이 문서는 그 비용과 개선 조건을 기록한다. 제품·스크립트·시험 변경이나 추가 계측은 수행하지 않았다.

근거: [계측 JSON](../../runtime/evidence/C03-documents-measurement1.json), [실행 로그](../../runtime/evidence/C03-documents-measurement1.log), [계측 스크립트](../../runtime/evidence/C03-documents-measure.mjs), [기존 SQLite 비용 검토](C03-personal-memory-cost-notes.md), [C05 계획](../03-migration-plan.md).

## 1. 어느 실행을 관측했는가

macOS arm64, Node v24.20.0에서 새 임시 C01 담당을 등록했다. 설정은 v2의 `personalMemory: documents`이며, 상태·업무 기억·대화 원문은 SQLite, 증거·프레임 자료는 파일 저장을 사용했다. 실제 profile/store/KnowledgeService/SessionService/ContextCompiler를 연결했으며, 합성 사용자 한 명·기억 한 개·두 세션만 사용했다.

16개 구간을 한 번씩 실행했다. X의 적용된 발언을 명시적으로 기억하고, 같은 서비스 객체에서 두 번 검색했다. 새 세션 Y에서 해당 기억을 선택해 실제 프레임 파일을 만들고 읽어 확인했다. 저장소를 닫았다 다시 연 뒤 직접 조회·선택 회상·문맥 준비를 수행했다. 원문 보존, Y에 X의 대화 이력을 복사하지 않음, 선택 버전 1 유지가 확인됐다. 실제 모델·도구 호출은 각각 0, 외부 API 호출도 0이다. 저장소 닫기와 임시 디렉터리 제거·부재 확인까지 `passed`다.

JSON의 `buildBefore`와 `buildAfter`는 일치한다. 실제 필드명과 값은 다음과 같다.

| 필드 | 값 |

| `sourceDigest` | `f50ac21e0cebb54efbc55921f62076737e29e9ce679fab18ee9cd44f055e6034` |
| `filesDigest` | `0118e8db9c0050c93e54362c9f4814c2e92a0c9237851adc5d59c827fc827687` |
| `fileCount` | 1,338 |
| `scriptSha256` | `efbc88f007090110658e5e5107f2c0d8b18ee594d9c331fa43279f73db98ef25` |

실행 시각은 2026-09-07 00:48:17.149–00:48:20.465 UTC다. 실행 조율 기록에 따르면 같은 기기에서 target2 시험 묶음이 병행됐다. CPU·파일 캐시·디스크 부하를 통제하지 않았으므로 **시간은 부하가 섞인 단일 관측값**이다. 이후 Linux 검증의 결과나 비용, native Windows 지원, 실제 모델 품질 또는 C03 전체 완료를 이 실행으로 입증하지 않는다.

## 2. 공통 파일 경계에서 관측한 비용

`hostMetadataFiles().diagnostics()`의 단계별 차이를 사용했다. 파일 열기는 이 경계의 성공한 읽기용 `open`, 읽은 B는 실제 반환된 바이트 누계다. `directoryChecks`는 경계 안에서 수행한 디렉터리 상태 검사 횟수이며 서로 다른 디렉터리 개수가 아니다. `directorySyncs`는 이 경계가 디렉터리 `fsync`를 실제로 시도하기 직전에 증가하는 값이다.

| 구간 | 파일 열기 | 읽은 B | 디렉터리 검사 | 디렉터리 fsync 시도 | 관측 시간 |
|---|---:|---:|---:|---:|---:|
| 문서 담당 초기 등록·열기 | 35 | 6,962 | 4,083 | 37 | 388.23ms |
| 원문 기억 등록 | 106 | 32,058 | 17,089 | 12 | 153.43ms |
| 같은 서비스 첫 검색 | 144 | 49,410 | 25,614 | 0 | 110.17ms |
| 같은 서비스 즉시 재검색 | 128 | 43,920 | 22,768 | 0 | 85.43ms |
| Y에 기억 선택 | 336 | 115,290 | 59,766 | 0 | 236.96ms |
| 선택된 문맥 준비 | 1,104 | 378,810 | 196,374 | 0 | 834.54ms |
| 같은 담당 저장소 재열기 | 17 | 2,673 | 1,638 | 9 | 109.03ms |
| 재열기 후 첫 직접 조회 | 64 | 21,960 | 11,418 | 2 | 48.78ms |
| 같은 직접 조회 즉시 반복 | 64 | 21,960 | 11,384 | 0 | 54.29ms |
| 저장된 선택 회상 | 112 | 38,430 | 19,922 | 0 | 78.28ms |
| 재열기 후 문맥 준비 | 1,104 | 378,810 | 196,374 | 0 | 817.16ms |

문맥 준비에는 스크립트가 준비할 업무 상태를 읽는 호출 1회와 준비 동작 자체의 프레임 게시·재확인이 포함된다. 준비된 프레임을 계측 스크립트가 다시 읽어 비교하는 별도 검증은 포함하지 않는다. 첫 프레임의 별도 읽기는 실제로 5,984B를 반환했지만 이 공통 metadata 경계의 읽기 카운터는 0이었다. 프레임 저장소가 별도의 비동기 파일 경로를 사용하기 때문이다.

전체 관측 합계는 파일 열기/닫기 각각 3,214회, `dataReads` 6,428회, `dataBytes` 1,090,283B, 디렉터리 검사 566,430회, 디렉터리 fsync 시도 60회다. `dataReads`에는 파일 끝을 확인해 0B를 반환하는 읽기도 포함되므로 실제 바이트가 있는 읽기 횟수와 같지 않다. 열기와 닫기의 일치는 이 경계의 계수이며 프로세스의 모든 핸들 수명을 검증한 결과는 아니다.

위 카운터는 전체 파일시스템 호출을 세지 않는다. 문서 어댑터의 직접 `opendir/lstat`, 변경 계층의 파일 쓰기·파일 fsync, SQLite 내부 I/O, 비동기 artifact I/O 등은 빠져 있다. `siblingLists=0`도 디렉터리를 전혀 열거하지 않았다는 뜻이 아니다. OS 캐시 아래의 물리 디스크 읽기·쓰기·전원 장애 내구성을 측정하지 않았으며, sync 0을 파일 접근 0 또는 모든 계층의 fsync 0으로 해석하지 않는다. 합계는 마지막 정리 직전까지이고, 전체 경과 3,310.95ms에는 최종 닫기·임시 폴더 제거가 포함된다.

## 3. 본문·이벤트·확인 기록·실제 문맥의 크기

문서 디렉터리만 제한적으로 열거해 일반 파일의 논리 길이를 측정했다. 등록 직후와 재열기·회상 뒤의 파일 수와 길이는 같았다.

| 대상 | 파일 수 / 크기 | 의미 |
|---|---:|---|
| 기억 본문 | 105B | 명시적으로 기억한 사용자 발언 |
| `ns-…/00000001.md` | 1개 / 1,882B | 본문·기억 메타데이터·출처·명령 영수증·이전 이벤트 연결을 담은 정본 이벤트 |
| `witness-…/00000001.json` | 1개 / 242B | 소유 범위·순번·이벤트 해시를 기록한 외부 확인 기록 |
| `owner.json` + `format.json` | 2개 / 207B | 이 문서 저장소의 등록 정보 |
| 남은 pending 후보 | 0개 / 0B | 계측 종료 시 임시 게시 후보 없음 |
| 공개 기억 카드 | 651B | 본문·이름·버전·소유자·출처 참조 |
| 실제 패킷의 개인 기억 영역 | 803B | 선택한 참조·입력 기준·본문 등 |
| 전체 `ContextPacket` | 3,514B | 모델 입력으로 준비된 목표·정책·세션·기억 등 |
| 실제 저장 `ContextFrame` | 5,984B | 패킷과 문맥 복구·검증용 기준 등 |

이벤트와 witness 합계는 2,124B, 위 등록 파일까지 합하면 2,331B다. 이는 이 fixture의 문서 디렉터리 안 일반 파일 길이만 더한 값이다. 파일시스템 할당 블록·DB·대화 원문·외부 등록 파일·증거 자료·프레임을 포함한 담당 전체 저장량은 아니다.

[문서 codec](../../runtime/src/infrastructure/document-knowledge-codec.ts)은 본문 필드를 Markdown 본문으로 한 번 저장하고 JSON 메타데이터에서 같은 `body` 필드를 제외한다. 출처의 정확한 인용문은 메타데이터에 따로 들어갈 수 있으므로 “본문 문자열이 파일 전체에서 단 한 번만 등장한다”는 보장은 아니다. witness에는 본문 사본 대신 범위·순번·해시가 들어간다. 별도 DB 사본을 개인 기억 정본으로 두지 않는다.

105B와 전체 패킷 3,514B의 차이가 전부 기억 저장 비용은 아니다. 목표·정책·현재 세션 등 다른 정보가 들어간다. 계층별 반환 JSON도 같은 내용을 반복 포함할 수 있어 합산을 고유 저장량·네트워크 전송량으로 해석하지 않는다. 실제 tokenizer와 모델을 호출하지 않았으므로 토큰 절감은 측정하지 않았다.

## 4. 동기화는 재사용하지만 정본과 출처는 다시 읽는다

[DocumentKnowledgeRepository](../../runtime/src/infrastructure/document-knowledge.ts)의 `#snapshot`은 변경이 없는 경우에도 해당 소유 범위의 이벤트·witness 전체를 두 번 읽고 같은 검증값이 나오는지 확인한다. 이벤트 순서·이전 해시·레코드 전이·명령 영수증과 witness의 순서·해시를 검증하며, 각 읽기는 [공통 파일 경계](../../runtime/src/infrastructure/posix-metadata-files.ts)와 [문서 디렉터리 경계](../../runtime/src/infrastructure/document-knowledge-owner.ts)의 객체·권한·읽는 동안의 변경 검사도 통과해야 한다. 읽기 전후 등록 정보 재확인도 반복된다. 따라서 기억 한 개 조회를 파일 한 번 읽기로 구현한 상태가 아니다.

`signature`는 암호학적 서명이 아니라 **이미 확인한 파일 상태를 비교하기 위한 해시 값**이다. 이벤트 순번·마지막 해시, 이벤트/witness 디렉터리 객체 ID, 파일별 inode·크기·시각·권한 등의 변경 토큰을 조합한다. `#synced`는 이 값을 저장소 객체 안에 보관해 동일하게 검증된 범위의 디렉터리 fsync를 재사용한다. 본문 검증을 건너뛰는 캐시는 아니다.

재열기 후 첫 직접 조회에서는 이 캐시가 비어 있어 이벤트와 witness 디렉터리를 각각 동기화해 2회가 기록됐다. 다음 직접 조회는 0회였지만 열기 64회와 읽기 21,960B는 그대로였다. 첫 조회보다 반복 조회 시간이 길게 나온 것만 보아도 이 조건의 단회 시간을 캐시 성능 효과로 단정할 수 없다. 동기화 캐시의 재사용 범위는 해당 저장소 객체이며 재열기·종료를 넘어 검증 사실이 자동 승계되지는 않는다.

서비스 계층의 반복도 그대로 관측됐다. 다음은 파일 호출과 다른 계층인 공개 저장소 포트 호출 횟수다.

| 구간 | `state.get` 업무 상태 | `knowledge.get` 기억 | `session.input` 입력 영수증 | `session.history` 대화 이력 | 검색 후보 |
|---|---:|---:|---:|---:|---:|
| 기억 등록 | 18 | 4 | 18 | 6 | 0 |
| 첫 검색 | 12 | 4 | 12 | 4 | 1 |
| 즉시 재검색 | 12 | 4 | 12 | 4 | 0 |
| Y에 기억 선택 | 71 | 21 | 65 | 21 | 0 |
| 문맥 준비 | 256 | 69 | 228 | 75 | 0 |
| 재열기 후 첫/반복 직접 조회, 각각 | 12 | 4 | 12 | 4 | 0 |
| 저장된 선택 회상 | 25 | 7 | 21 | 7 | 0 |
| 재열기 후 문맥 준비 | 256 | 69 | 228 | 75 | 0 |

[KnowledgeService](../../runtime/src/application/knowledge-service.ts)의 카드 조립·안정된 의존성 확인, [SessionKnowledgeSources](../../runtime/src/application/session-knowledge-sources.ts)의 원문·영수증·원본 업무·권한 확인, 회상 및 프레임 조합 전후 현재성 검사가 중첩된다. 각 `knowledge.get`도 문서 저장소의 전체 검증을 다시 시작한다. 이것이 비용이 누적되는 코드 경로다. 이번 계측은 호출 스택별로 시간을 배분하지 않았으므로 75회 이력을 전부 같은 X 원문의 불필요한 조회로 분류하지 않는다. 현재 Y 세션 문맥 검증도 포함된다.

반복 검색은 동일 서비스 객체를 보관했을 때 후보 ID 캐시만 사용했다. `cached: false→true`, 후보 조회 1→0과 파일 열기 144→128, 읽기 49,410→43,920B가 함께 관측됐다. 원문·기억 조회는 줄지 않았고, 검색 결과는 같은 카드·본문·버전이다. 현재 CLI/Web의 서로 다른 요청은 새 scoped service를 만들므로 이 후보 캐시 적중을 요청 간 효과로 확대하지 않는다. 같은 Web profile이 보관하는 문서 저장소의 sync 캐시와 서비스별 검색 후보 캐시는 서로 다른 수명이다.

[이전 SQLite 관측](C03-personal-memory-cost-notes.md)은 소스 `658c9bd5…`, 빌드 파일 `c6a2ce1c…`, 1,296개 산출물의 별도 역사적 결과다. 공통 서비스의 선택·문맥 준비 호출 수가 겹치는 점은 중복 검증 검토에 참고할 수 있다. 그러나 fixture의 발언·식별자·진행 단계, 계측 범위, 빌드와 병행 부하가 같지 않다. 두 문서의 시간을 나누어 “문서가 SQLite보다 몇 배 느리다/빠르다”거나 패킷 길이 차이를 저장 방식의 압축 효과로 계산하지 않는다.

## 5. C05에서 줄일 부분과 유지할 경계

우선 검토 대상은 반복 fsync 자체보다 **한 번의 서비스·문맥 준비 안에서 같은 정본과 출처를 여러 번 처음부터 확인하는 부분**이다. 이미 이 표본의 반복 검색·문맥 준비에서 공통 디렉터리 fsync는 0이다. 다음은 후속 검토안이며 아직 구현·검증된 최적화가 아니다.

| 제안 | 줄일 수 있는 작업 | 반드시 유지할 조건 |
|---|---|---|
| 한 요청 안에서 검증한 범위 결과를 내부적으로 함께 전달 | 같은 namespace의 `get`·영수증·index head가 각각 전체 이벤트를 재파싱하는 중복 | 소유자·등록·파일 정체성·전체 이벤트/witness 연속성의 근거 포함. 독립 공개 API는 그대로 검증하며, 검증 사실을 확인할 수 없으면 전체 읽기 |
| 여러 기억·출처를 한 번에 확인하는 선택적 저장소 기능 | 같은 원문 업무·발언·범위를 기억별로 반복 읽는 부분 | SQLite 전용 기능을 코어 필수로 만들지 않음. 사용자가 다른 DB의 기억·원문을 바꾸는 경우까지 업무 revision 하나로 대표하지 않음 |
| 문맥 조합 단계 사이의 검증 결과 전달 계약 | `get` 직후 `validateDependencies`, context 조합 직후 동일 조합 재시작 | 적용 입력·개인 선택·원문 영수증·본문·권한·세대·만료의 현재성 및 최종 저장·채택 전 확인 보존. 비동기 대기·새 입력·취소 뒤 낡은 결과 사용 금지 |
| 디렉터리 검사 위치의 책임 정리 | 깊은 경로와 root/부모를 여러 중첩 메서드가 반복 검사 | 모델이 검증 완료를 주장할 수 없는 호스트 내부 계약. root/ancestor 교체·권한 변경·정본 소실 거절을 보존하고 path recheck를 핸들 고정이나 원자적 snapshot으로 표현하지 않음 |
| 범위별 파생 검색 결과·파싱 결과의 제한된 캐시 | 매 검색의 후보 생성·같은 bytes 재파싱 | 크기·수명·owner/권한별 격리. 해시 검증된 bytes 재사용과 파일을 아예 재확인하지 않는 것은 구분. 저장된 TTL만으로 본문·영수증 현재성을 대신하지 않음 |

동기화·복구 의미는 비용을 줄이기 위해 제거할 대상이 아니다. 정식 이벤트만 게시되고 witness가 빠진 경우의 제한된 복구, witness가 있는데 정식 이벤트가 사라진 경우의 거절, 게시 결과가 불확실한 오류와 원인 보존, 동일 명령 재시도 전에 필요한 동기화 완료를 유지해야 한다. 서비스가 receipt/get을 먼저 호출해도 그 경계가 적용돼야 한다. 본문과 witness를 같은 OS 사용자 권한으로 동시에 과거 상태로 돌리는 경우까지 현재 구조가 탐지하는 것은 아니며, sync 캐시가 별도의 신뢰 가능한 영구 최고 순번을 제공하지도 않는다.

이행 순서는 한 사용자 흐름을 기준으로 잡는다. 먼저 검증 단계별 카운터를 더 구분해 X 원문·Y 문맥·owner/format·이벤트/witness·파싱 비용을 나눈다. 그다음 한 요청 내부의 중복 조립부터 줄이고 같은 실제 packet/frame과 같은 오류 의미를 확인한다. 마지막으로 정정·잊기·권한 축소·만료·원문 손상/삭제·디렉터리 교체·새 입력·취소·재시작·게시 응답 유실을 검증 사이에 넣어 늦은 결과가 여전히 거절되는지 확인한다. 전체 검사 횟수만 줄이고 이 조건을 약화한 변경은 효율 개선으로 채택하지 않는다.

후속 비교는 같은 fixture와 호출 범위, 별도 기록한 source/build pin으로 수행해야 한다. 시간 비교가 필요하면 다른 시험과 분리하고 반복 수·부하 조건을 명시한다. 기억/이벤트 수와 공유 출처가 늘어날 때의 비용은 별도 제한된 표본으로 확인한다. 현재 전체 namespace 검증은 이력 증가에 영향을 받지만, 이번 한 이벤트로 그 증가율·처리량·운영 상한을 측정한 것은 아니다. 실제 모델/API 실험 중단과 native Windows 미검증은 계속 유지한다.
