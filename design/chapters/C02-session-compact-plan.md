# C02 세션을 유지하는 반복 compact — 계획과 최종 검증 연결

2026-09-07 · 초기 구현 계획 보존 + 최종 구조 검증 연결

**최종 Linux 전체 2,836/2,836, compact 46/46 통과와 전용 시험 프로세스 0개·SSH 종료를 확인했다. C03 개인 기억의 명시적 사용자 흐름에 착수할 범위별 gate는 충족했다.** 판정 근거는 [최종 검증 JSON](../../runtime/evidence/C02-compact-verification.json)과 [결과](C02-session-compact-result.md)다. 아래는 구현 전에 정한 의도와 인수 계획을 보존한 것이며, 모든 설계 항목·C01/C02 전체·전체 goal이 완료됐다는 뜻은 아니다.

최종 sourceDigest는 `2193685e0a64d0f88e40113b2838afc03c8c24b8430d6a6c36847613b77e0967`이다. 첫 로컬 42/46과 첫 NAS 2,830/2,831 실패는 원로그/각 pin의 이력으로 남긴다. 최초 NAS의 정확한 throw 줄은 미확정이고, 이후 동일 오류 경로의 고정 재현·수정과 최종 통과를 구분한다. build2 브라우저와 계측 1회는 별도 pin의 관측으로 보존하며 최종 소스에 소급하지 않는다.

다음 단위의 결과는 **같은 담당·사용자가 대화를 이어가다가 문맥이 커지면 앞부분을 요약하고, 새 입력은 원문으로 붙여 작업한 뒤, 재시작과 반복 요약을 거쳐도 중요한 합의와 미해결 사항을 유지하는 것**이다. 원문 저장, 모델 입력 조합, 사용량 정산을 하나의 사용자 흐름으로 연결한다. 파일 함수나 저장 포트별로 완료 단위를 계속 쪼개지 않는다.

중단한 외부 모델/API 실험은 재개하지 않았다. 이번 구현에서 확인한 것은 등록된 저장·범위·수명·검증·반복 조합의 구조 시험이며, 실제 모델의 요약 정확도와 네이티브 Windows 실행은 별도 미검증 항목으로 남긴다. 최종 소스의 macOS 전체/브라우저 재검증도 수행한 것으로 표시하지 않는다.

## 1. 초기 계획 시점의 구현에서 출발하기

이 표의 “현재/아직”은 compact 구현 전 기준이다. 이후 요약 계약·원문형 v1/요약형 v2·호출 목적·CLI/Web 오류 연결이 추가됐으며, 현재 구현과 검증 범위는 위 결과 문서를 따른다. 아래 빈 곳을 지금도 미구현이라고 읽거나 재구현 목록으로 사용하지 않는다.

| 실제 확인한 코드 | 현재 하는 일 | 아직 하지 않는 일 |
| --- | --- | --- |
| [SessionService](../../runtime/src/application/session-service.ts)의 `applied` / `snapshot` | 담당·사용자·세션과 적용된 입력을 확인한다. 대기 입력은 최대 256개를 확인하고 가득 찬 페이지는 보수적으로 거절한다. 모델용 원문은 적용 입력 순서까지 최대 256개, 직렬화한 본문 65,536바이트를 읽으며 초과하면 `session_context_capacity`로 멈춘다. 원출처 권한·모델 목적지·artifact 존재도 확인한다. | 이전 대화를 자동으로 의미 요약해서 이 한도를 넘겨 이어가지 않는다. |

`ContextCompiler`의 현재 `extraModelCalls: 0`은 문맥 조합 자체가 모델을 추가 호출하지 않는다는 계측이다. 다음 구현도 이 값을 조용히 바꾸어 요약 호출을 감추지 않는다. 요약 호출은 별도 식별되는 호출 기록으로 정산한다.

## 2. 원문, 앞부분 요약, 새 입력을 나누기

세션의 수명은 작업 X/Y의 수명보다 길다. X가 끝나도 세션 원문과 요약 참조를 유지하며, Y는 자신의 목표·계획·근거·자원 장부를 새로 가진다. 같은 세션이더라도 다른 담당/사용자의 저장 영역과 섞이지 않는다. 개인 장기기억·게시판·아카이브에 자동 등록하지 않는다.

다음 모델 입력은 아래 세 부분으로 조합한다.

1. **현재 작업 정본:** 현재 목표·제약·계획·검증된 근거·미정산 효과·현재 의무. 기존 WorkState와 compiler가 계속 책임진다.
2. **검증한 prefix 요약:** 세션 원문의 앞부분 중 어느 범위까지 요약했는지와 원문 참조를 가진 파생 문맥. prefix는 ‘대화의 앞부분’, tail은 ‘그 뒤에 새로 추가된 구간’이라는 뜻이다.
3. **새 원문 tail:** 요약 끝 다음 순서부터 현재 작업에 적용된 입력까지의 원문. 현재 사용자의 입력은 반드시 원문으로 남긴다. 아직 적용하지 않은 inbox 입력은 적용 대기 상태로 구분한다.

관계는 `요약 끝 < 현재 입력 순서`를 기본으로 한다. 보호해야 하는 최근 발언을 원문으로 더 남길 수 있다. 중복 인용이 있으면 출처 ID로 식별하며, 같은 문장을 독립 근거 두 개로 세지 않는다. compact 때문에 `lastSequence`나 입력의 applied 상태를 앞당기지 않는다.

현재 SessionHead는 ‘입력까지 조합한 문맥’의 head이므로 이를 곧바로 ‘요약 완료 위치’로 바꾸지 않는다. **적용 입력 basis, 조합된 문맥 head, prefix 요약 head를 별도 의미로 둔다.** 기존 immutable head 조회·CAS 방식을 재사용하되 요약 head의 종류/포인터와 검증 기록을 구별한다. CAS는 ‘내가 읽은 head 버전이 아직 같을 때만 새 head로 바꾸는 검사’이다.

새 문맥 형식은 명시적으로 버전 관리한다. 예를 들어 v2 문맥은 요약 참조·보존 항목·tail을 담고, 기존 원문형 v1은 그대로 읽는다. 요약 artifact 하나만으로는 채택할 수 없다. 다음을 함께 고정한다.

- 세션 scope, 요약 대상 prefix 끝, 이전 요약 참조와 digest.
- 원문 source ID/순서/workId와 내용·적용 상태의 검증용 manifest. manifest는 사용한 원문 목록과 그 내용을 확인하기 위한 기록이다.
- 원출처 권한·데이터 세대·목적지 정책과 검증 시점의 기준.
- 요약 본문, 보호할 원문 인용/참조, 검증 결과, 생성한 호출 ID와 정책 버전.

이것들은 전부 파생 자료다. 입력 원문과 실제 응답 기록의 정본을 대체하거나 삭제하지 않는다. 요약만 반복해서 다시 요약하는 구조를 피한다. 이전 요약을 재사용하더라도 원문 참조 목록이 유지되어야 하며, 새로 변경된 합의·반론·의무는 해당 원문까지 다시 확인할 수 있어야 한다.

## 3. 무엇을 반드시 유지할 것인가

모델이 쓴 자유로운 문장 하나만 저장하지 않고, 사람이 검토할 수 있는 요약과 출처가 있는 보존 항목을 함께 둔다. 필드명은 구현 시 계약으로 확정하되 다음 의미는 유지한다.

| 보존할 내용 | 보존·갱신 규칙 |
| --- | --- |
| 사용자와 합의한 응답 방식, 명시적 제약·금지 | 원문 source ID와 짧은 정확 인용을 보관한다. 후속 사용자가 바꾸면 이전 항목을 조용히 삭제하지 않고 어떤 발언이 변경했는지 연결한다. 현재 사용자 원문이 과거 요약보다 우선한다. |
| 가설과 반론·반증 | 주장, 반론, 반증 조건과 당시 상태를 구분한다. ‘검토 중’을 ‘확정’으로 바꾸거나 반론만 빠뜨리지 않는다. 관련 evidence/source ref를 유지한다. |
| 미해결 질문·의무·외부 효과 | 미해결임을 명시하고 원출처 작업을 연결한다. 현재 work 의무는 WorkState가 정본이다. X의 미해결 사항을 Y의 실행 의무로 자동 복사하지 않는다. |
| 결정·성공·실패와 수정 이유 | 무엇을 시도했고 무엇이 관측되었는지 구분한다. 실패 경로를 성공처럼 줄여 쓰지 않고 이후 번복의 출처를 남긴다. |
| 원문·산출물 참조 | 검증한 source ID와 artifact ref를 보관한다. 파일 경로나 DB 주소를 모델이 추측하여 새 권한으로 만들 수 없다. 원본이 사라지면 파생 요약만으로 접근 허용을 복구하지 않는다. |

현재 목표·수용 조건·미정산 도구 호출·부작용 확인 의무는 요약 대상으로 밀어 넣어 제외하지 않는다. 컴팩트한 대화 서술과 업무 상태의 정본을 계속 구분한다. 대화 속 예전 답변은 `conversation_history_not_verified_evidence`의 의미를 유지한다.

검증기는 먼저 scope·prefix 범위·출처 실재·해시·권한·형식·길이를 검사한다. 보호 목록에 있던 항목을 삭제하거나 상태를 바꾸려면 이를 뒷받침하는 새 원문 참조가 필요하다. 단순히 ‘처리됨’이라는 요약 문구로 미해결 항목을 닫을 수 없다. 원문 속 지시도 요약 입력 자료로 취급하며 시스템 권한·도구 권한으로 승격하지 않는다.

이 구조 검증은 임의의 자유 서술이 원래 의미와 완전히 같다는 증명이 아니다. 자연어의 생략·왜곡 여부는 실제 모델별 평가가 추가로 필요하다. 중요한 부정문·수치·합의는 정확 인용과 원문 참조를 남겨 그 불확실성을 줄인다.

## 4. 한 번의 compact 수명과 반복 조합

정상 경로는 **필요성 판단 → 고정된 원문 구간 준비 → 모델 호출 예약/실행/정산 → 후보 검증 → 요약 head CAS → 새 tail 조합 → 실제 작업 재개**이다. compiler의 `prepare()` 안에서 숨겨진 모델 호출을 하지 않는다. 준비 결과가 ‘compact 필요’임을 실행 조정자에게 알려 정식 호출 수명으로 들어간다.

| 단계 | 이번 단위에 포함할 동작 |
| --- | --- |
| 필요성 판단 | 전체 모델 요청의 bytes·추정 tokens, 보호 입력 크기, 요약되지 않은 tail 크기를 측정한다. 짧은 대화는 그대로 쓰고 용량이 커지기 전에 compact를 준비한다. 빠른 모드도 현재 요청을 잃지 않는 원칙은 같다. |
| 구간 고정 | 가장 최근 구간과 현재 입력을 남기고 이전 구간을 선택한다. 전체 원문을 한 번에 읽어 한도를 키우지 않고 검증된 cursor로 제한된 페이지를 읽는다. 요약 구간도 호출 입력 한도 안에서 나눈다. |
| 호출 준비 | 원문 목록, 이전 요약, 보호 항목, 정책, 예상 사용량을 저장한 입력 artifact로 고정한다. 모델에게는 구조화된 요약 후보를 요청하고 업무 계획·도구 실행 권한은 주지 않는다. |
| 검증·게시 | 반환 원문과 사용량을 먼저 기록한다. 후보의 구조·출처·권한·보호 항목을 검사하고 현재 head에 대해 CAS한다. 게시 영수증을 남겨 재시작 시 동일 후보의 처리 여부를 조회한다. |
| 다시 조합 | 게시된 prefix 요약 + 그 뒤의 현재 tail + 현재 WorkState를 조합한다. 실제 입력 artifact를 다시 측정한다. 크기가 줄었다는 이유만으로 검증을 생략하지 않는다. |
| 다음 compact | 앞선 요약의 출처와 보호 항목을 유지하면서 추가 원문 구간을 반영한다. 요약 사슬의 깊이/본문/manifest도 제한하고 필요하면 원문에 근거해 재구성한다. |

초기 정책 제안은 세션 문맥 사용량이 사용 가능한 입력 용량의 80%에 가까워지면 준비하고, 성공 후 60% 정도의 사용량을 목표로 하는 것이다. 이 값은 **측정 전 초기값**이며 기존 도구 선택의 90%/70% 설정과 같은 변수가 아니다. 사용 가능한 입력 용량은 현재 요청·필수 업무 상태·필수 도구 정의를 먼저 반영한 뒤 계산한다. 모델의 입력 한도와 출력 예약량을 구분하고, 공급자가 총 문맥 한도를 제공하면 두 값의 합도 확인한다.

일반적으로 검증된 후보 한 개를 만들고, 실패한 같은 prefix를 즉시 무한 반복하지 않는다. 수정 재시도는 추가 사용량 예약이 허용될 때 한 번으로 제한하는 정책부터 시작한다. 보호 항목 자체가 창을 넘거나 요약 뒤 절감이 없으면 명시적인 용량 상태를 반환한다. 사용자가 강제 compact를 요청할 수도 있지만 그것이 권한·원본 검사 생략을 의미하지 않는다.

### 기존 호출 장부를 통과시키기

현재 PlanningRuntime의 예약·dispatch·receive·usage 정산·lease 회복을 재사용한다. 성공 응답이 PlanProposal에 고정되어 있으므로 요약 결과를 가짜 계획으로 포장하지 않는다. **호출 목적을 planning/session_compact로 구분하고 공통 호출 수명만 좁게 공유**하며, 계획 검증과 요약 검증·게시를 각 목적에 연결한다. 별도의 SDK 직호출이나 무료로 취급되는 보조 에이전트 경로를 만들지 않는다.

첫 연결에서는 compact를 필요로 하는 활성 work가 요약 호출의 자원 소유자이다. 완료된 X의 장부를 다시 열거나 세션이라는 이유로 무제한 자원을 만들지 않는다. Y가 대화를 계속하기 위해 compact하면 Y의 허가된 자원에서 예약·반환·정산하고, 결과 요약은 같은 세션에서 재사용할 수 있다. 활성 work가 없는 유휴 시점에는 이번 단위에서 자동 모델 호출을 시작하지 않는다.

요약 호출의 의미 기준은 적용 입력, prefix 원문 manifest, 이전 요약, 정책, 취소 상태를 포함한다. 기존 semanticVersion 1/2/3 호출은 당시 규칙으로 회복하고 새 목적/형식은 명시적으로 구분한다. 일반 planning 호출의 v3가 고정한 적용 입력은 표현 방식인 요약 head가 바뀌었다는 이유만으로 달라지지 않는다.

미전송 예약은 반환 가능하지만 이미 호출한 모델의 토큰·시간은 요약 실패/취소/CAS 충돌이어도 정산한다. 사용량을 모르면 기존 unknown 상태를 유지한다. 응답을 이미 저장했다면 재시작 후 재검증·게시를 먼저 시도하고 같은 요약을 만들기 위한 모델 재호출부터 하지 않는다.

### 경합과 실패 시 동작

| 사건 | 반드시 유지할 결과 |
| --- | --- |
| 요약 준비 중 새 tail 접수 | 고정 prefix 밖의 원문을 그대로 추가 보관한다. 기존 prefix 검증이 유효하면 해당 구간 요약은 사용할 수 있지만 tail과 현재 입력을 새 packet에서 빠뜨리지 않는다. |
| prefix 내부의 pending 입력이 뒤늦게 적용됨 | eligible 원문 집합이 바뀐 것이므로 기존 후보의 prefix manifest를 그대로 채택하지 않는다. 미적용 입력을 건너뛰고 ‘여기까지 모두 요약됨’이라고 표시하지 않는다. |
| 같은 work에 새 입력 적용 또는 취소 | 현재 적용 basis/취소 경계가 먼저 이기면 늦은 호출을 새 지시에 대한 성공으로 채택하지 않는다. 사용량과 원응답은 보존한다. 취소된 호출이 활성 요약 head를 뒤늦게 바꾸지 않도록 게시 직전에도 확인한다. |
| 다른 실행기가 먼저 head 게시 | CAS 실패 후보가 최신 포인터를 덮거나 원문 cursor를 움직이지 않는다. 최신 head와 아직 남은 tail로 다시 조합하고, 유효한 기존 후보를 재사용할 때도 새 기준을 검증한다. |
| 더 오래된 작업의 문맥 필요 | 현재 요약 head를 과거로 돌리지 않는다. 해당 입력 이하의 immutable prefix와 tail을 조합한다. 현재 `retainHead`의 과거 prefix 보관 원칙을 유지한다. |
| head가 바뀌었지만 진행 중 모델의 적용 입력은 같음 | 이미 고정한 입력 artifact의 요약/원문 참조를 검증한다. 최신 표현과 바이트가 다르다는 이유만으로 정상 호출을 무효화하지 않는다. 새 조합에는 최신 사용 가능한 요약을 선택한다. |
| source 권한 축소·목적지 변경·원본 부재 | 요약을 경유해 가려진 원문을 계속 전달하지 않는다. 영향받은 요약을 사용하지 않고 허용되는 원문에서 재구성하거나 명시적으로 중단한다. artifact의 tenant/labels 일치만으로 충분하다고 보지 않는다. |
| 모델 거절·잘림·잘못된 후보·시간 초과 | 이전에 검증된 요약과 원문을 유지한다. 전체 원문이 창에 들어가면 그 경로로 진행하고, 들어가지 않으면 용량/요약 실패로 대기한다. 빈 요약을 게시하거나 새 세션으로 교체하지 않는다. |
| 응답 저장 뒤 프로세스 중단 | 같은 호출 ID의 저장 응답과 사용량 상태에서 검증·게시를 재개한다. 중단을 사용량 0으로 바꾸지 않는다. |
| head CAS 성공 뒤 work 정산 전 중단 | 게시 영수증으로 동일 후보의 성공을 확인하고 정산만 마친다. state 저장소와 channel SQLite가 하나의 transaction이라고 가정하지 않는다. |

현재 `SessionService.current(state, context)`는 원문형 문맥을 다시 만들어 비교한다. 새 형식에서는 **고정된 요약 참조의 유효성**과 **적용 입력까지 tail의 원문 동등성**을 검증하도록 바꿔야 한다. 항상 최신 요약으로 다시 생성한 문자열과 비교하면 정상적인 반복 compact가 기존 모델 호출을 불필요하게 무효화한다. 반대로 요약 ID만 비교하면 원출처 권한 변경을 놓친다.

## 5. 재사용·수정·신규 범위와 구현 순서

| 구분 | 범위 |
| --- | --- |
| 재사용 | C01 담당/저장 소유권, session scope·입력 접수/적용 영수증, channel SQLite 원문 참조, immutable head/CAS, artifact 무결성·라벨 검사, work 상태 CAS, 모델 사용량 장부·취소·회복, 도구 선택/축출, 기존 컨텍스트/세션 회귀. |
| 수정 | SessionContext와 frame basis의 버전 계약, SessionService의 prefix/tail 조합과 현재성 검사, 제한된 원문 구간 조회, head와 요약 포인터 구분, compiler의 compact-needed 결과와 조합, 모델 호출 목적 및 성공 응답 검증 분기, Recovery의 고정 요약 참조 복원. |
| 신규 | 출처가 있는 요약 후보/보호 항목/manifest 계약, 제한된 compact 조정 흐름, 구조·원문 인용 검증기, 요약 게시 영수증과 사용량 연결, 같은 사용자 흐름의 반복·중단 시험. |
| 제외 | 스토리지 재작성, C01 파일 경계 재추출, 모든 호출 엔진의 범용화, 자동 장기기억 등록, 게시판/아카이브 도입, 전면 채팅 UI 개편, 외부 모델 실험·Windows 지원 완료 주장. |

구현 순서는 네 단계지만 **아래 사용자 흐름 전체가 완료 단위**이다.

1. 원문형 호환을 유지한 요약 참조·보호 항목·prefix/tail 계약과 immutable 저장/조회/게시를 연결한다. scope·권한·stale CAS 검사를 함께 만든다.
2. 기존 호출 장부를 통과하는 compact 목적을 연결하고, 합성 응답으로 후보 생성→검증→게시→현재 packet까지 완성한다. raw-only 경로를 실패 복구로 유지한다.
3. 같은 담당에서 반복 compact·새 입력·재시작을 이어 붙이고 사용량·게시 영수증을 회복한다. CLI/Web은 같은 서비스 경로를 사용하고 필요한 상태만 노출한다.
4. 사용자 흐름·실패 경합과 기존 context/planning/session/state backend 회귀를 통합 실행하고, 구조 결과와 실제 모델 품질 미검증을 구분해 기록한다.

불필요한 사전 helper 추출 목록을 만들지 않는다. 재사용할 호출 수명 코드의 범위는 구현 전에 현재 코드에서 확인하되, 위 흐름을 완성하는 데 필요한 부분만 분리한다.

## 6. 한 가지 실제 흐름으로 인수하기

일반 문서 비교 업무를 예시로 사용하되 보안 업무에 특화하지 않는다.

**A담당/U사용자/S세션에서 ‘한국어 세 문장’ 형식 합의 → X의 초기 해석에 반론과 정정 발생 → X 완료 → Y에서 원문이 늘어 첫 compact → 중요한 질문 하나가 미해결인 채 추가 대화 → 두 번째와 세 번째 compact → 프로세스 종료 → 동일 S에서 Z 재개**까지 실행한다. 모델은 외부 API 없이 지연·잘림·틀린 후보를 주입할 수 있는 합성 provider를 사용한다. 작은 시험 한도를 사용해 대형 fixture 없이 같은 용량 분기를 재현한다.

이 흐름의 실제 planner `ContextPacket`과 저장 input artifact에서 다음을 확인한다.

- S는 유지되고 X/Y/Z의 workId·계획·검증 근거·자원 장부는 각각 독립적이다.
- 형식 합의·정정 전 주장·반론·정정 근거·미해결 질문이 출처와 상태를 유지한다. 이전 요약의 오류를 다음 요약이 확정 사실로 증폭시키지 않는다.
- 요약 끝과 tail 사이에 입력 누락이 없으며 현재 사용자 원문은 그대로 존재한다. 처음부터 원문을 조회해 확인할 수 있다.
- 세 번의 compact 후에도 새 입력이 가능한 용량이 확보된다. 요약·manifest·보호 목록이 무제한으로 커지는 경로는 명시적으로 제한된다.
- 각 compact 호출은 예약/사용/반환/unknown 상태를 남긴다. 재시작 후 이미 받은 응답의 재채택에서 모델 호출·과금 기록이 중복 생성되지 않는다.
- 요약은 파생 문맥이며 별도 장기기억 항목이나 다른 담당의 문맥으로 자동 등록되지 않는다.

같은 흐름의 경계 시점에 새 tail, 같은 work 입력 변경·취소, 경쟁 head 게시, 저장 후 실제 프로세스 종료를 각각 삽입한다. 잘린 후보·잘못된 출처·반론 삭제·보호 인용 변경·미해결 항목의 근거 없는 완료 처리도 넣어 게시 거절과 원문 보존을 확인한다. 결과가 불명확하면 이전 유효 head 유지 또는 명시적 대기로 끝나야 한다.

state=SQLite와 state=file-journal에서 같은 의미를 검증하며 두 경우 모두 대화 저장은 기존 channel SQLite를 사용한다. 담당/사용자/session 분리, 원본 참조 부재, 목적지 권한 축소, legacy 원문형 프레임 복구도 회귀에 포함한다. 실제 원격 모델·Knox·Windows·전원 장애 검증을 이 합성 흐름의 통과로 대체하지 않는다.

### 비용과 컨텍스트 건강 기록

내부 계측은 compact 전후 실제 요청 bytes·추정 tokens, 원문 tail 크기, 보호 항목 크기, 요약 횟수·비율·소요 시간, 원문 재조회 횟수/bytes, 호출 사용량, 후보 검증 실패·CAS 충돌·복구 재사용을 남긴다. 기존 도구 eviction/reload 계측과 세션 의미 요약 계측을 합치지 않는다.

성공률만으로 품질을 판단하지 않는다. 합의 보존율·반론 누락·근거 없는 상태 변경·원문 추적 가능성을 정해진 fixture 기준으로 비교한다. 구조 검증이 보장하는 항목과 합성 provider가 정답을 준 항목을 구분하고, 실제 사내 모델의 의미 보존 품질은 모델 실험을 다시 명시적으로 허용받은 뒤 평가한다.

사용자 화면에는 필요할 때 ‘이전 대화를 정리하며 계속 진행 중’, 완료 또는 용량/요약 실패 상태만 표시한다. 원문과 출처를 확인하는 경로는 제공하되 내부 호출·후보·재시도마다 채팅 말풍선을 추가하지 않는다. 원문 전체를 읽지 않는 효율 최적화는 source 무효화·권한 재검증의 정확성이 확보된 뒤 측정값을 기준으로 적용한다.

계획 당시 [Web 오류 변환](../../runtime/src/presentation/web-server.ts)의 허용 목록에는 `session_context_capacity`가 없어 서비스의 용량 제한이 화면에서 일반 `request_failed`로 표시됐다. 이번 구현은 compact 필요·진행·복구 가능한 실패·보호 내용 자체의 용량 초과를 공통 서비스 결과와 CLI/Web 안내에 연결했다. 다른 담당이나 원출처의 민감한 내용을 오류 설명에 노출하지 않으면서, 원문이 보존되어 있다는 사실과 계속할 수 있는 조건을 알려주는 것이 인수 조건이다. 전체 채팅 UI 개선과 실제 모델의 안내 품질까지 완료한 것은 아니다.
