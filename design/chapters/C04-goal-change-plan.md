# C04 일반 대화의 명시 목표 변경

2026-09-07 · 이 작은 구현 단위는 지원 POSIX에서 구현·검증을 마쳤다. macOS 변경 범위57/57·관련249/249, NAS Linux 전체3,284/3,284·필수8단계·원로그 회수·정리까지 확인했다. [확정 결과](C04-goal-change-result.md)를 따른다. 아래는 실행한 계획과 구현 중 결정이며 C04 전체 완료를 뜻하지 않는다. 실제 모델/API 시험은 중단 상태다.

사용자가 기존 업무를 “문서 비교”에서 “확인한 차이를 보고서로 작성”으로 바꾸면 같은 담당·대화·업무에서 새 목표를 적용한다. 기존 원문·근거·시도·사용량은 남긴다. 추가 설명, 같은 대화의 새 업무, 기존 목표 교체는 각각 구분한다. 자연어를 읽은 모델이 사용자의 목표를 임의로 교체하게 만들지 않는다.

## 재사용과 필요한 연결

`SessionService.command`는 원문을 먼저 기록하고 안정적인 명령 ID로 업무에 적용한 뒤 영수증을 정리한다. `ExecutionRuntime.command(kind:'goal')`는 목표·제어 버전 검사, 이전 결과 무효화, 대기 전달 대체, 미송신 예약 반환과 실행 중 호출 중단을 이미 처리한다. `GeneratedAnswer`와 outbox의 현재성 검사도 재사용한다. 새 명령 장부나 실행 루프를 만들지 않는다.

`AgentTurnService`에 명시 목표 변경 메서드를 추가한다. 사용자 입력은 담당 세션·업무·메시지 ID, 변경 원문, 기대 목표·제어 버전과 선택한 실행 모드다. 새 목표의 revision·원문 digest·응답 요구는 호스트가 만든다. HTTP에서 정책·scope·임의 완료 조건·응답 검증 객체를 받지 않는다. 현재 일반 응답 업무의 범위와 권한을 보존한다.

CLI에는 별도 `chat goal` 명령을 두고, Web에는 일반 요청용 목표 변경 화면을 연결한다. 기존 사실 조건 예제 편집과 일반 원문 편집을 구분한다. 접수 사실은 즉시 알리고, 일반 Web의 변경 접수만으로 모델을 자동 실행하지 않는 기존 실행 방식을 유지한다. API와 화면 모두 변경 완료와 업무 완료를 구분한다.

## 이번에 함께 해결할 세 경계

1. **재전송에는 처음 저장한 명령을 쓴다.** 현재 상태를 먼저 검사해 이미 성공한 요청을 stale로 거절하거나, 바뀐 모드·목표에서 새 payload를 만들지 않는다. 같은 메시지 ID가 있으면 현재 권한·세션을 확인한 뒤 요청 원문과 고정 인수의 동일성을 검증하고 기존 payload·영수증을 재사용한다. 같은 ID의 다른 원문은 충돌이다. 최초 요청과 적용 사이 중단도 동일한 경로로 복구한다.
2. **편집을 시작한 뒤 들어온 입력을 조용히 덮지 않는다.** 기존 goal/control revision은 일반 후속 입력마다 증가하지 않는다. 일반 목표 변경에는 현재 적용된 입력의 ID·sequence·digest도 고정하고, 기존 업무 commit 내부에서 이전 입력 기준과 비교한 뒤 새 원문을 적용한다. 화면의 사전 확인만으로 대체하지 않는다. Web 편집 화면은 권한 있는 읽기에서 이 기준을 얻고, CLI는 명령 접수 시 이를 확보한다. 이미 저장된 동일 요청의 재전송은 그 최초 기준을 유지한다. 기존 저수준 명령의 호환성은 유지하되 일반 변경 입구에서는 이 검사를 반드시 사용한다.
3. **이전 목표에서 생성한 확인 질문만 대체한다.** 현재 코어는 목표 변경 시 delivery 의무만 대체하므로 과거 모델 질문이 새 목표를 막을 수 있다. 기존 `agent-question:<callId>`와 원 model call의 목표 버전·종류를 확인해 이전 일반 주턴의 질문 의무만 변경된 목표에 의해 대체되었음을 기록한다. 효과 불명, 자원 정산, 자료 수집, 게시판 요청 등 다른 의무를 일괄 면제하지 않는다. 원 질문과 전달 이력은 보존한다.

위 비교는 모델 응답 채택과 같은 저장 경합 경계에 둔다. 동시 후속 입력, 모드 변경, 권한 변경으로 기준이 어긋나면 적용하지 않고 현재 상태를 다시 확인하게 한다. 수신 원문이 이미 저장되었다면 거절 사유와 영수증도 남긴다. 입력 순서나 미결 영수증을 건너뛰어 성공으로 꾸미지 않는다.

## 구현 중 확인한 추가 연결

일반 요청의 원문 검증기는 최초 `work` 접수만 허용했다. 목표 변경은 `command` 접수이므로, 변경 명령의 이전·새 목표 버전과 원문·범위·응답 요구가 현재 목표와 맞는지 확인한 뒤 같은 원본 조회기를 사용하도록 확장했다. 일반 추가 입력을 목표 변경으로 인정하지 않는다. 원문이 컴팩트 구간에 들어간 경우도 정본 접수 기록에서 확인한다.

이전 목표의 작업 계획은 이력으로 남지만 새 답변의 필수 작업은 아니다. 답변 완료 판정에서 현재 목표 버전의 계획만 검사한다. 아직 실행 중인 과거 시도와 미확정 효과·정산 의무는 기존의 별도 검사로 계속 완료를 막는다. 이전 가설 평가는 기존 `hypothesesRequireReview`의 목표 버전 검사로 재검토 대상이 된다.

편집 기준 조회는 같은 사용자라도 현재 허용 라벨이 업무 원문의 라벨보다 좁으면 거절한다. Web의 `run`과 세션 명령은 기존 업무 영수증의 같은 요청 ID를 CAS로 먼저 고정한다. CAS는 저장 직전의 버전이 예상과 같을 때만 반영하는 검사다. 서로 다른 명령이 같은 ID로 동시에 들어오면 하나만 그 ID를 차지하며, 그 원문과 명령 내용은 기존 업무 이벤트에 남는다. 세션 접수 전 중단도 고정한 요청으로 재개한다. 기존 세션 접수만 남긴 과거 형식은 원문 영수증으로 재전송을 검증한다.

CLI에서 같은 `goal` 요청을 재전송하면 저장된 명령을 확인하고 현재 상태를 표시한다. 자동으로 모델을 다시 실행하지 않는다. 접수 후 중단된 작업은 명시적인 `resume`으로 이어간다. Web도 목표 변경을 접수한 뒤 별도 ‘실행’을 유지하고, 응답 수신 실패 시 같은 원문·요청 ID로 재전송한다. [CLI 사용 설명](C04-goal-change-cli-usage.md)을 함께 제공한다.

## 유지할 의미

- 완료된 업무의 명시 목표 변경은 기존 코어처럼 다시 준비 상태로 만든다. 취소·실패로 종료한 업무는 임의 부활시키지 않는다.
- 목표 변경은 같은 업무의 사용량·잔여 배정·deadline을 초기화하지 않는다. 새로 배정해야 하는 자원은 기존 자원 체계에서 처리한다.
- 이미 받은 이전 응답·늦은 도구 결과는 새 목표의 완료로 채택하지 않지만, 실제 발생한 사용량은 정산한다. 같은 범위의 기존 근거는 원본과 현재성 검사를 거쳐 다시 사용할 수 있다.
- 이전 목표에 종속된 가설은 현재 목표의 검토 기준으로 자동 인정하지 않는다. 기존 가설 현재성 검사를 확인하고, 필요하면 과거 평가를 이력에 남긴 채 새 목표를 검토하도록 최소한만 연결한다.

## 구현 순서와 인수

먼저 application 계약과 원문·영수증 재사용을 연결하고, 필요한 입력 기준 비교·이전 질문 대체만 기존 명령 코어에 보강한다. 이어 CLI와 Web의 같은 경로를 연결한다. 업무 상태를 시험에서 직접 고쳐 성공시키지 않는다.

필수 인수는 같은 세션의 목표 1회 변경과 새 답변, 동일 요청 재전송, 원문 수신 후/업무 적용 후 중단·재접속, 편집 중 후속 입력·제어 버전 변경, 다른 담당·사용자·세션의 거절, 이전 응답/대기 전달 무효화, 질문 중 목표 교체와 다른 의무 보존이다. 원문·근거·시도·알려진 사용량은 유지되어야 한다. CLI와 실제 localhost HTTP 접수·조회·명시 실행도 확인한다.

제품 코드 변경에 맞는 신규·관련 시험, 저장소 기본 경로, 타입·계층 검사를 수행한다. 다음 Linux 필수 통합에 이번 복합 인수와 목표 변경 시험을 함께 포함한다. 앞선 등록 소스의 Linux 3,253개 결과를 새 소스의 통과로 표시하지 않는다. 실제 브라우저 조작은 가능할 때 별도 확인하고, 미실행이면 HTTP 시험과 구분한다.
