# P2-05 부모·자식 예산의 실행 연결

2026-09-05 · 착수 기준 v0.26 / 1,078개 로컬 시험

## 문제와 구현 선택

지금은 work별 사용량/예약량이 독립적이다. 자식에 복사한 상한을 부모가 다시 쓰지 못하게 하는 연결이 없다. 기존 StateRepository는 한 work의 CAS를 보장하므로 여러 work의 동시 갱신을 하나의 원자적 쓰기로 가정하지 않는다. [독립 검토](/Users/seunghanee/Documents/secumon/design/chapters/P2-budget-review.md)의 revoke/refund 경합과 실제 보고 토큰 초과를 포함한다.

부모에 자식의 예산 전액을 먼저 잡아 두는 escrow를 사용한다. 각 예산은 논리 도구 호출·모델 호출·모델 토큰·재계획 네 차원으로 구분하고 기한은 별도로 계승한다. 원문이나 근거 본문을 부모에 복제하지 않고 ID·정책/목표 binding·숫자 사용량과 배정 차단 상태만 연결한다. 첫 배치는 현재 owner 계약에 맞춰 같은 tenant/principal과 더 좁은 자식 정책을 사용한다. 서로 다른 principal의 권한 위임은 별도 capability 설계가 필요한 범위로 남긴다.

## 순서와 계약

1. **엄격한 예산 계약.** BudgetVector, 부모 link, grant와 exposure 계산을 만든다. 활성/정산 중 grant는 할당 전액과 알려진 사용+예약 중 큰 값을 잡아 둔다. 초과 보고를 숨기지 않고 debt를 보존하며 정수 overflow는 새 할당을 거부한다. 순수 계산 검증만으로 실제 실행 연결을 완료 처리하지 않는다.
2. **미승인 자식 생성 → 부모 예약 → 활성화.** 자식을 genesis CAS부터 pending link로 만들고 모든 배정을 금지한다. 부모가 escrow를 예약한 뒤 같은 link를 active로 바꾼다. 이 순서는 부모 예약만 있고 자식이 없는 상태에서 취소/반환과 늦은 자식 생성이 엇갈리는 경합을 피한다. 실패한 pending 자식은 실행되지 않으며 같은 명령의 재시도와 정리를 구분한다. 기존 독립 work에 뒤늦게 link를 붙이지 않는다.
3. **실제 배정과 진입.** 도구/model 예약과 추가 재계획에 남은 예산을 적용하고, 도구/model의 실제 진입 직전에도 현재 grant와 영속 fence를 확인한다. 목표/모드/상태 변경, 더 낮아진 부모 한도, 부모 기한, 권한 축소를 검사한다. 부모의 새 배정도 자식 escrow를 포함한 총량을 사용한다. 기존 결과 정산·복구는 계속 허용한다.
4. **취소와 정산.** 부모 grant를 draining으로 만든 뒤 자식에 영속 배정 fence를 설치한다. 미호출 예약을 취소하고 이미 호출한 결과/unknown은 정산한다. fence와 drain이 확인되기 전에는 예산을 반환하지 않는다. 자식의 누적 상태 revision을 사용해 중복 정산을 막고 알려진 비용을 유지한다. 부모 한도 하향은 이미 발생한 비용을 지우지 않는다.
5. **계층과 관측.** 부모/자식 연결의 순환과 깊이를 제한하고 중첩 grant도 전액 예약 원칙을 따른다. 컨텍스트에는 작은 집계, 정본에는 세부 장부를 남긴다. 접수/모드/진전과 동일하게 조회와 상태 변경을 구분한다. 미해결 예산 정산은 부모의 완료 판정에서 숨기지 않는다.

## 실행 검증과 완료 조건

두 영속 backend에 같은 정상·실패·경합 시험을 적용한다. 부모/형제의 이중 가용액 거부, 실제 child tool/model 진입과 replan 차감, pending link의 resume/goal 우회 거부, grant/activation ACK 유실 재시도, revoke 중 activation/reserve 경합, child fence 후 늦은 응답, 알 수 없는/부분/초과 토큰 보고, 중복 정산·재개·한도 하향·기한·정책 축소를 확인한다. 부모에 본문을 전달하지 않는 것도 검사한다.

이 단위는 실제 새 model/tool 배정 경계까지 연결해 위 의미를 검증해야 한다. 고정 fresh/replay 전체 실행 평가는 다음 필수 단위이며 P2-05 전체 로컬 계약은 그 뒤 판정한다. 실제 모델/API·사내 서비스 시험 중단은 유지한다. 요청 상한은 승인된 예약을 제어하며 provider가 상한보다 큰 사용량을 보고하지 않는다는 외부 보증까지 뜻하지 않는다.

## 학습 질문

자식에게 100을 맡겼다면 부모가 쓸 수 있는 금액은 얼마인가? 취소 요청을 저장한 것과 실제로 더는 실행되지 않는 것은 왜 다른가? 사용량을 모르는 호출에 대해 남은 예산을 돌려줘도 되는가? 저장소 CAS가 한 업무에만 적용될 때 서로 다른 두 업무를 어떻게 안전하게 연결할 수 있는가? 구현 기록과 장애 시험으로 답을 확인한다.
