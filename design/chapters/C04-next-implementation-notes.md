# C04 다음 구현 연결 메모

2026-09-07 · 현재 소스 읽기 기반 제안 · 제품 변경·새 검증·모델 호출 없음

기존 실행 루프를 재사용하고 **자연어 입력을 실제 작업·모델 호출·결과 전달로 연결하는 한 흐름**부터 구현하는 것이 가장 작다. `enablePlanning`만 켜는 것으로는 충분하지 않다. 현재 로컬 진입점은 합성 시나리오에 묶여 있고, 모델의 반환 형식과 완료 판정은 계획·사실 확인에 집중되어 있다.

이 문서는 [통합 계획의 C04](../03-migration-plan.md)와 [백로그](../implementation-backlog.json)를 보충한다. 같은 목적의 별도 C04 메모는 없었으며, [기존 프롬프트 범용성 검토](prompt-generality-review.md)의 원칙을 다시 설계하지 않고 현재 연결 공백만 좁힌다. D2 최종 Linux 검증은 이 메모 작성 시 확정 전이다. 이 메모가 현재 C03 실행 순서를 바꾸거나 C03 완료를 선언하지 않는다.

## 2. 현재 빠진 연결

- **로컬 구성:** `composeLocalProfile`은 fixtures를 읽고 합성 actor/정책과 `FixtureReadTool`, `ScriptedPlanner([])`를 사용하며 `enablePlanning:false`다. CLI `demoPlan`과 Web `fixturePlan`이 지정 근거 ID로 계획을 직접 만든다. 일반 입력의 `rawText`를 저장해도 목표는 선택한 scenario에서 나온다. [CLI](../../runtime/src/presentation/cli.ts) · [Web 진입점](../../runtime/src/presentation/local-workbench.ts)
- **설정에서 모델 요청까지:** 설정의 `purpose/model.profile/skills.mode`가 범용 모델 프로필·공통 프롬프트 조합으로 연결되지 않았다. 지침 소스도 현재 엔진의 `runtime/guidance`다. 담당 목적을 프롬프트에 넣되 목적 문구가 도구·자료 권한을 늘리지 않게 해야 한다.
- **계획 이외의 모델 결과:** [Planner 포트](../../runtime/src/application/ports.ts)는 `propose → PlanProposal`, 선택적 `compact → candidate`만 제공한다. 직접 답변·질문·작성 결과를 계획 JSON으로 위장하지 않고 구분해서 채택할 계약이 필요하다.
- **범용 완료 의미:** [Criterion](../../runtime/src/domain/model.ts)은 `key + equals/present + 근거 수/coverage`이고, `renderResult`도 그 사실값·출처를 문자열로 조합한다. 글쓰기·교정·직접 답변을 `facts.done=true` 같은 가짜 관측으로 처리하면 안 된다. 작성 산출물과 그 검증 결과를 사실 관측과 구분하는 좁은 완료 계약이 필요하다.
- **입력 해석의 실행 순서:** 현재 `SessionService.accept`는 원문과 함께 이미 정해진 `Goal/Policy/Limits`를 요구하며, 모델 호출은 WorkState에 자원을 귀속한다. “모델로 목표를 정한 뒤 accept”를 장부 밖 호출로 구현할 수 없다. 첫 목표의 출발점과 입력 해석 호출의 자원 주인을 먼저 정해야 한다.

## 3. 권장하는 첫 사용자 흐름

**담당 열기 → 원문과 호출 주인 고정 → 현재 문맥 조합 → 한 모델 턴 → 답변/질문/계획 검증 → 기존 실행·결과·전달 → 같은 세션의 후속 입력**을 CLI와 Web의 같은 application 진입점으로 연결한다. 기존 합성 예제는 명시적인 demo 경로로 남긴다.

1. **호스트가 구성한다.** C01 담당 ID·기존 저장소·사용자 신원·허용 정책을 사용하고, 모델 프로필을 주입하는 작은 factory를 연결한다. 첫 구현의 provider는 명시적인 결정적 대역이다. 기본값에서 실제 API를 연결하거나 키를 탐색하지 않는다. `skills=off`는 실제 조합에도 반영하고 전체 스킬/도구 본문을 처음부터 넣지 않는다.
2. **새 요청의 기준을 모델 전에 정한다.** 권장 출발점은 사용자 원문을 설명으로 갖는 정상 WorkState와 “이 요청의 답변/산출물을 확인한다”는 새 유형의 완료 조건이다. 이는 모델이 만들어 낸 가짜 사실이 아니다. 새 업무는 여기에 자원을 귀속해 입력 해석과 작업 제안을 같은 첫 모델 턴에서 받는다. 기존 업무 대상은 호스트가 선택한 세션·업무와 원문 receipt에 묶고 예상 revision을 검사한다. 모델이 임의 workId·정책을 지정해 다른 업무를 고치지 못한다.
3. **모델 결과의 작은 분기를 추가한다.** 예컨대 답변/추가 질문/계획 제안을 구분하는 주 턴 결과를 기존 호출 수명에 붙인다. 별도 SDK 직호출, 가짜 PlanProposal, 요청 해석 전용 두 번째 budget 장부는 만들지 않는다. 공통 호출 부분을 필요한 만큼 재사용하되 planning/compact의 기존 해시·복구 의미는 보존한다. 사용자 목표 변경 제안은 검증된 원문과 현재 업무 기준을 통해 기존 command로 적용하며, 계획자가 독자적으로 목표를 바꾸는 것과 구분한다.
4. **현재 검사와 결과 전달에 연결한다.** 계획 분기는 기존 validator·task graph·executor로 보낸다. 답변/작성 분기는 생성한 본문 artifact와 요구 충족 검사 결과를 따로 보관한 뒤 기존 결과/outbox로 보낸다. 모델의 “완료했다” 한 마디가 완료 증거가 되지 않게 한다. 직접 답변에는 불필요한 조회 작업이나 가설을 만들지 않는다. 결과 생성 실패는 근거·도구를 처음부터 재실행하는 이유가 아니다.
5. **반복과 현재성은 기존 루프가 맡는다.** 새 입력·취소·권한 축소·기억 정정 후 늦은 응답은 채택하지 않되 발생한 usage는 보존한다. 반론은 필요한 경우 같은 모델 턴에서 제안받고 기존 가설의 반증 조건·판별 작업·관측에 연결한다. 독립 서브에이전트는 C08 후속이며 이 첫 흐름의 필수 조건이 아니다.

프롬프트는 공통 원칙·담당 설정·현재 packet·선택 지침·목적별 반환 계약을 조합한다. 그 버전/지문과 실제 전체 요청 크기를 고정 입력에 포함하고, 바뀐 설정/모델의 오래된 호출을 재개할 때 검사한다. 현재 어댑터의 `utf8_bytes_estimate`는 보수적 대역 추정이며 모델의 실제 토큰 계산이 아니다. 요약 입력, 도구 명세, 상태, 출력 여유를 포함한 한도 검사를 기존 compact 예약 경로와 맞춘다. 이 결선 없이 작은 모델의 모든 창 크기를 지원한다고 주장하지 않는다.

첫 구현에서 확정할 핵심은 **원문/업무 귀속, 주 턴 결과, 답변·산출물 완료 조건** 세 가지다. 이들은 필요 계약이며 새 범용 워크플로우 엔진·별도 기억 엔진을 만드는 이유가 아니다. 정확한 schema는 이 메모로 고정하지 않고 실제 연결 코드와 함께 좁힌다.

## 4. C03 잔여 중 실제 선행조건

| 항목 | 첫 C04에 필요한 정도 |
|---|---|
| 담당·사용자 격리, 적용 원문 receipt, 선택 기억의 출처/버전 현재성 | 필수다. 기존 C01~C03 서비스와 실제 packet을 그대로 사용해야 한다. 새 주 턴도 같은 현재성 검사를 통과해야 한다. |
| D2 최종 회귀와 열린 실패 진단 | 현재 변경을 합쳐 구현하기 전 정확한 소스 지문과 진단 결론을 인계받아야 한다. 미확인 실패를 C04 변경에 섞거나 미재현만으로 해소됐다고 표시하지 않는다. |
| D3 기존 SQLite→문서 이관 | 기본 SQLite 또는 이미 등록된 문서 담당의 자연어 루프에는 기술적으로 필요하지 않다. 기존 사용자 데이터를 옮겨 운영할 때의 gate다. 현재 합의한 D3 실행 순서는 이 메모가 변경하지 않는다. |
| PostgreSQL, 공유 DB 이관, 모든 저장 형식 지원 | 첫 대역 흐름의 선행조건이 아니다. 미등록이면 기본 SQLite를 쓰고 등록된 정본의 장애를 다른 저장소 생성으로 우회하지 않는다. |
| 문서 읽기 최적화·자율 기억 선별 | C05의 후속이다. 첫 C04에서 기존 기억을 필요할 때 검색·선택하는 연결은 재사용하되 현재성 검사를 비용 때문에 생략하지 않는다. |
| 네이티브 Windows, Knox, 독립 반론/A2A | 해당 환경 배치·협업의 별도 gate다. 지원 POSIX의 합성 C04 흐름에 강제하지 않으며 Linux 결과로 완료 처리하지 않는다. |

백로그의 C04 `depends_on: C02,C03`은 기능 계약과 필요한 검증의 의존성으로 좁혀 검토할 수 있다. C03 모든 선택 어댑터의 완료를 기다려야 한다는 판정이나 순서 변경은 별도 상위 계획에서 한다.

## 5. 결정적 대역으로 확인할 5개 인수 시나리오

| 실제 사용자 흐름 | 대역과 검사 |
|---|---|
| **단순 질문·문장 교정** | 고정 자연어 요청에 주 턴 대역이 짧은 답변/교정 산출물을 반환한다. 시나리오 ID·미리 제출한 계획 없이 CLI/Web 접수부터 전달까지 간다. 불필요한 도구·가설·스킬 호출 0, 모델 호출의 입력·응답·usage·완료 판단이 실제 장부에 남는다. 문장 의미의 정답은 시험 fixture이며 실제 모델 품질 증거가 아니다. |
| **완료한 X 다음 Y** | X 결과 뒤 같은 세션에서 “위 형식으로 다른 내용을 정리해 줘”를 받는다. 최근 대화 또는 accepted 요약+tail과 선택 기억이 실제 요청에 있고 X의 작업 그래프·근거·예산을 Y에 복사하지 않는다. 같은 messageId 재전송·재시작도 원문과 답변을 중복 생성하지 않는다. |
| **비교 중 반론과 도구 실패** | 대역이 A/B 조회를 계획하고 서로 모순된 근거 뒤 판별 작업 C를 제안한다. 이미 성공한 조회는 재사용하고 실패한 부분만 회복한다. 반론 문장이나 대역의 동의를 새 사실로 만들지 않으며, 독립 근거·출처·완료 조건을 기존 검사로 통과해야 결과를 보낸다. |
| **진행 중 수정·취소·기억 정정과 중단** | 대역 응답을 지연시키고 사용자 목표 변경/취소 또는 선택 기억 정정을 적용한다. 늦은 답변·계획·전달을 거절하면서 원 usage를 보존한다. 응답 artifact 저장 후 재시작 사례에서는 현재성이 유지된 received 결과를 재사용하고 provider를 다시 부르지 않는다. |
| **입출력 한도·잘못된 반환** | 작은 창, 잘린 JSON, 거절, 불명 usage를 반환하는 대역으로 오류·유한 재시도·대기를 확인한다. 필요한 compact는 기존 예약/정산을 거치고 실패 시 오래된 packet으로 우회하지 않는다. 형식 복구나 모드 전환도 원 입력·호출 ID·정산 기록을 바꾸어 숨기지 않는다. |

대역의 응답은 예상되는 경계를 결정적으로 재현하기 위한 것이다. 실제 C01 저장소·SessionService·ContextCompiler·PlanningRuntime·WorkflowRuntime·CLI/HTTP를 조합하고, 새 저장/모델 대역만으로 루프 전체를 흉내 낸 시험으로 끝내지 않는다. 실제 모델/API 평가는 사용자가 중단한 상태를 유지하며 이번 인수에 자동 포함하지 않는다.
