## 첫 실행에서 확인한 사실

build1은 새 일반 입구 fixture의 JSON 객체 타입 좁히기 누락으로 종료했다. 명시 타입 판정을 추가한 build2는 exit0, sourceDigest `3909e4e76af72af4120fae1b30e860a1b12361c78cfb49cd8cb49d163c546676`다. 제품 변경 전에 실행한 target1은 **31개 중25개 통과·6개 실패**, exit1이었다.

상시 담당의 일반 입구5개는 실제 독립 SQLite 프로필에서 통과했다. 사건 A/B는 같은 세션을 사용하지만 업무·목표·계획·근거·사용량이 분리된다. 제어 업무의 모델/도구 호출은 0이다. 다른 담당에 같은 rule/event ID를 주어도 원문과 세션은 섞이지 않는다. 동일 원 사건의 재접속 재전달은 새 업무를 만들지 않고, 같은 ID의 다른 원문은 거절한다.

사건 접수 완료 직후 예외를 주입하면 제어 체크포인트에는 아직 workId가 없다. 이 상태에서 실제 세션 compact를 게시하고 저장소를 다시 연 뒤, 원 접수 영수증으로 같은 업무를 이어가는 것을 확인했다. 다음 모델 호출은 게시된 요약을 사용했고 원 목표·원문과 사용량을 보존했다. 이는 **예외 주입과 reopen**의 결과이며 실제 프로세스 종료 결과와 구분한다. 추가 질문 대기 중 빈 관측은 추론을 반복하지 않고, 명시 답변 뒤 같은 세션에서 다음 사건을 처리했다. 관측 중 stop이 오면 늦은 사건을 새 업무로 접수하지 않았다.

실패는 다음 경계로 좁혀졌다.

- 일반 `mission.events` 목록→원문→답변 루프가 기본 무진전 한도3에서 중단됐다. 조회된 임무/사건을 준비 진전으로 연결하는 부분이 빠져 있었다. native 도구 표식과 의미 기반 분류를 추가하며 근거나 자동 완료로 승격하지 않는다.
- 호스트 등록3개는 호출자의 tenant/principal/labels/destination 범위와 raw source의 authorize·취소·종료 검사가 누락된 문제다. 현재 업무와 호출 권한을 읽기 전후 대조하고, 반환한 관측 참조에도 수명·정리 처리를 연결한다.
- 한 업무의 임무 시험1개는 tick의 취소 신호가 실제 관측 poll까지 전달되지 않았다. 신호를 관측과 저장 직전까지 이어 주고, 취소를 무시하는 원천의 늦은 응답은 게시하지 않도록 수정한다.
- 협업 집계1개는 같은 owner/work/revision/budget의 실행 이력이 다르더라도 뒤 snapshot으로 덮어 진행 중 사용량을 숨길 수 있었다. 전체 저장 내용이 같을 때만 중복으로 인정하고 객체 키 순서는 무시한다.

첫 실행 시점에는 후속 진전 회귀·비협조 원천·실제 프로세스 종료가 미실행이었다. terminal 구독/영수증 불일치라는 정적 후보는 당시 실패하지 않아 변경하지 않았으며, 아래 target4에서 실제 실패한 뒤에만 교정했다.

## 두 번째 실행과 실제 프로세스 복구

build3은 exit0, sourceDigest `3cb9ef52c443a669fe9b48bbe794fd64bda51393aa6e76a260a84d560ab2aeee`, 산출물2,292개다. 같은 소스의 코어 타입 검사 exit0과 구조196개/위반0을 확인했다. target2는33개 중32개 통과·1개 실패였다. 첫 실행의 권한·취소·전체 snapshot 중복 교정은 통과했고 사건 조회 준비 진전도 기본 한도3에서 동작했다.

남은 일반 입구 실패는 완료된 업무가 되살아난 것이 아니다. 원문 도구 조회와 답변 뒤에도 mission 알림이 남아 완료/전달을 막았고, tick은 workflow가 끝난 뒤에만 알림을 비우므로 step-limit yield와 추가 답변이 반복됐다. 읽은 원 사건을 정확히 확인한 후 알림을 처리하는 경계를 교정한다. terminal 영수증 후보와 별개다.

실제 자식 프로세스에서 사건 접수를 저장한 직후 SIGKILL하고 exit와 close를 확인했다. 같은 SQLite/디렉터리를 다시 열면 원래60초 claim이 남은 동안 실행하지 않고 기다린다. 실제 만료 뒤 원 업무/세션/접수 영수증을 재사용하여 모델1회·도구0회로 완료했고 같은 사건 재전달은 추가 실행하지 않았다. 원 목표·정책·사용량 한도·기존 대화·원 체크포인트 bytes를 보존했다. crash1은1/1,61,494ms,exit0이다. 이는 현재 macOS의 실제 POSIX 프로세스 결과이며 native Windows나 사내 배포 인수를 대신하지 않는다.

공통 진전·A2A/자원 진전·실행 집계의 직접 관련 회귀91개도 build3에서 통과했다. 이번 실행에 실제 모델/API·외부 서비스 호출은 없다.

## 원문 읽기 확인과 완료 저장의 최종 교정

build4의 target3은24개 중21개 통과·3개 실패였다. 기존 WorkResources 결과 조회를 재사용하면서 전달한 표시 크기 한도262,144가 기존 계약65,536을 초과했다. 이 인자만 고친 build5의 선택 target4에서는 원문 확인2개가 통과했고 일반 입구1개가 `mission_state_changed`로 실패했다. 원 materialized 결과는 표시 크기와 별개로 원문을 유지한다.

읽기 확인은 현재 native 등록, 원 dispatch·receive·adopt 기록, 현재 rule/page/cursor와 전체 원문의 일치를 확인한 뒤 체크포인트에 남긴다. 목록·부분 응답·이전 목표의 읽기·표식 없는 등록으로는 처리하지 않고 결과 조회 중 등록이 철회되면 거절한다. 다른 임무와 다른 provider의 알림은 보존한다. 여기서 다른 provider 보존은 sentinel 시험이며 실제 게시판 결합을 검증한 것은 아니다.

읽기 확인으로 완료가 가능해지자 실행기는 subscription 상태를 closed로 바꿨지만 원 임무 체크포인트는 active라서 onStep의 원문 검사가 거절하는 실제 경계가 드러났다. 공개 read 검사는 완화하지 않았다. tick 내부에서 실제 control_selected 완료 영수증과 원 active subscription의 나머지 모든 내용이 일치함을 확인하고, workflow 반환 뒤 동일 완료 근거를 다시 확인해 종료 체크포인트를 저장한다. claim은 해제하고 원 events/ACK는 남긴다. 완료 영수증 관측을 변조하면 원 checkpoint/head/claim을 보존한 채 거절한다.

이 교정 뒤 build6의 target5 **20/20**, exit0을 확인했다. 이번에 변경하지 않은91개 공통 회귀와61초 실제 프로세스 복구를 다시 실행하지 않았다. 모든 빌드·시험 세션은 종료했다.

## 범위와 남은 일

모델과 원천 관측은 로컬 유한 대역이며 API·사내/외부 서비스는 호출하지 않았다. 비교 시험은 기록된 fixture 원장에 대한 집계 검증으로, 실제 담당들을 같은 문제에서 실행한 비교나 사내 모델의 협업 품질 평가를 대신하지 않는다. 원 사건 목록 장기 보존과 삭제·board/mission 알림 합성 등은 해당 실행 증거에 맞춰 후속으로 남긴다. 다중 rule의 종료 체크포인트 정리와 업무 완료→후속 임무 종료 체크포인트 저장 사이에 프로세스가 죽는 경우의 재시작 복구도 미검증이다. 이번 정상 종료/reopen이나 접수 직후 SIGKILL과 구분한다. 다음은 계획의 동일 문제 독립 프로필 비교→게시판/임무 결합→C10 순서다. 일반 생성 응답과 기존 평가기 criteria 조건의 관계는 정적 검토 후보로 남기며 실행 전 결함으로 확정하지 않는다. C10, 기존 C05/C06·현재 Linux/native Windows·PostgreSQL·실제 연동·운영 인수·최종 통합과 전체 goal은 미완료다.
