# C03 개인 기억 비용 관측과 C05 후속 검토

2026-09-07 작성. **C03은 개인 기억의 저장·격리·출처 확인·명시 회상 흐름을 구현한 단위이며, 호출 효율 개선을 완료한 단위는 아니다.** 아래는 이미 실행된 계측 결과와 현재 코드의 읽기 검토다. 이 메모를 작성하면서 제품 코드를 수정하거나 추가 계측을 실행하지 않았다.

근거는 [단회 계측 결과](../../runtime/evidence/C03-personal-measurement1.json), [계측 스크립트](../../runtime/evidence/C03-personal-measure.mjs), [C05 범위와 통과 기준](../03-migration-plan.md)이다.

## 1. 관측된 사실

계측은 macOS arm64, Node v24.20.0에서 새 C01 담당과 SQLite 저장소를 만들고 수행했다. 한 사용자, 두 세션, 개인 기억 한 개를 사용했다. 상태·대화·기억의 공개 저장소 포트를 감싸 원래 함수에 그대로 전달했고, 내부 원문·영수증·권한 검증은 생략하지 않았다. 결과는 `passed`, 저장소 닫기와 임시 디렉터리 삭제·부재 확인까지 완료했다.

실행 전후 확인한 빌드 식별자는 같다.

- 소스: `658c9bd59fc1c1be7c8e71969082ae811839cfb8554634d255cb2a098ab1b824`
- 빌드 파일: `c6a2ce1cbabe723eb92c0ee46e80a08bf88e2af16f1c426e2bab8c5e0a9f914d`, 1,296개

표의 숫자는 각 단계에서 관측한 **공개 포트 메서드 호출 횟수**다. SQL 실행 횟수, 서로 다른 자료의 개수, 물리 디스크 읽기 횟수를 의미하지 않는다. `state.get`은 업무 상태 조회, `knowledge.get`은 기억 레코드 조회, `session.input`은 입력 영수증 조회, `history`는 대화 이력 조회다.

| 단계 | 상태 조회 | 기억 조회 | 입력 영수증 조회 | 이력 조회 | 검색 후보 조회 | 관측 시간 |
|---|---:|---:|---:|---:|---:|---:|
| 원문을 명시적으로 기억 | 18 | 4 | 18 | 6 | 0 | 10.64ms |
| 같은 서비스의 첫 검색 | 12 | 4 | 12 | 4 | 1 | 4.25ms |
| 같은 서비스의 즉시 재검색 | 12 | 4 | 12 | 4 | 0 | 4.11ms |
| 새 세션 Y에 버전 1 선택 | 71 | 21 | 65 | 21 | 0 | 22.01ms |
| 선택된 문맥 버전 1 준비 | 256 | 69 | 228 | 75 | 0 | 91.85ms |
| 정정 후 기억 직접 조회 | 12 | 4 | 12 | 4 | 0 | 2.75ms |
| 정정 후 같은 서비스 검색 | 12 | 4 | 12 | 4 | 1 | 2.78ms |

문맥 준비 단계에는 계측 스크립트가 `context.prepare`에 넘길 업무 상태를 읽는 호출 1회도 포함된다. 준비된 프레임 파일을 계측에서 다시 읽어 비교하는 검증은 별도 단계이며 위 준비 수치에 합치지 않았다. 준비 동작 자체의 프레임 게시·재확인은 포함된다.

바이트는 실제 UTF-8 직렬화 크기다.

| 버전 1의 대상 | 크기 | 의미 |
|---|---:|---|
| 기억 본문 | 105B | 사용자가 기억하도록 지정한 정확한 발언 |
| 카드 한 개 | 651B | 본문과 이름·버전·소유자·출처 메타데이터 |
| 문맥 안의 개인 기억 영역 | 817B | 선택 참조와 입력 기준 등을 포함 |
| 전체 ContextPacket | 3,547B | 목표·정책·세션 문맥 등을 함께 포함 |
| 저장된 ContextFrame | 6,022B | 전체 문맥과 검증 기준·계측 메타데이터를 포함 |

105B가 3,547B로 “부풀었다”거나 둘의 차이가 전부 기억 관리 비용이라고 단정할 수 없다. 전체 패킷에는 기억 외에도 필요한 업무 정보가 들어 있다. 계층별 반환 JSON 바이트를 더하면 동일 내용이 여러 번 포함되므로 고유 저장량이나 네트워크 전송량으로 해석하지 않는다.

첫 검색과 재검색의 카드·본문·버전은 동일했다. 재검색에서는 `index.cached=true`와 후보 조회 1→0을 확인했지만 상태·기억·영수증·이력 조회는 줄지 않았다. 재검색 전체 결과 JSON이 1B 작은 것은 `false`와 `true`의 직렬화 길이 차이이며 내용 압축 효과가 아니다.

정정 뒤 직접 조회와 검색은 버전 2의 120B 본문을 반환했다. 같은 검색어라도 인덱스 버전이 바뀌어 후보 캐시는 사용되지 않았다. 버전 1 문맥은 무효로 판정됐고, 새 버전을 명시적으로 다시 선택한 뒤 새 문맥을 만들었다. 실제 모델·도구 실행과 모델 토큰 사용은 모두 0이었다.

각 단계는 한 번만 실행했다. 시간 차이는 최적화 효과나 평균 지연으로 판단할 근거가 아니다. 파일저널·Linux·Windows의 비용, 동시 사용자, 대규모 기억, 실제 모델의 검색 품질도 이 결과로 설명하지 않는다.

## 2. 코드에서 확인한 호출 중첩과 원인 추정

아래 호출 연결은 현재 소스에서 확인했다. 다만 이 계측에는 호출 스택별 시간이나 SQL별 원인 추적이 없으므로, 전체 256/69/228/75회를 특정 호출 지점별로 정확히 배분한 결과는 아니다.

**직접 조회 한 번 안에서도 같은 기억의 출처 확인이 반복된다.** [KnowledgeService](../../runtime/src/application/knowledge-service.ts)의 278–282행 `#materialize`는 레코드 조회와 출처 검증을 수행한다. 367–370행 `#read`는 이를 수행한 뒤 `#stable`을 다시 호출한다. `#stable`은 두 번 연속 같은 검증값을 확인해야 끝나므로 변경이 없는 경우에도 `#snapshot`이 최소 세 번 수행된다(285–305행, 354–364행). 개인 기억의 각 snapshot은 다시 원문 출처를 확인한다. 안정된 단일 기억에서 직접 조회가 기억 조회 4회로 나타나는 관측과 연결된다.

이 안정성 확인은 별도 저장소들이 읽는 동안 변경되지 않았는지 살피기 위한 것이다. 같은 검증값을 반복해서 봤다는 사실이 여러 DB에 걸친 원자적 읽기를 제공하지는 않는다. 처음 `#materialize`에서 즉시 거절하던 오류의 의미도 있으므로, 단순히 첫 읽기나 반복 횟수를 삭제하는 변경은 이 메모의 제안이 아니다.

**출처 확인 한 번이 다시 여러 원본 조회를 만든다.** [SessionKnowledgeSources](../../runtime/src/application/session-knowledge-sources.ts)의 32–52행은 적용된 입력 영수증과 원본 업무 상태를 읽고, [SessionOriginals](../../runtime/src/application/session-originals.ts)의 17–40행을 통해 해당 발언의 이력·영수증·원본 상태를 확인한 다음, 처음 값과 바뀌지 않았는지 다시 읽는다. 이는 다른 사용자의 발언, 아직 적용되지 않은 입력, 바뀐 본문·정책·원문 수명 버전 등을 거절하는 경계다. 원문 수명 버전은 삭제·제한 등 원본의 유효성이 바뀌었는지 구분하는 값이다.

**회상 조립과 최종 확인이 동일한 검증을 다시 시작한다.** [PersonalMemoryService](../../runtime/src/application/personal-memory-service.ts)의 32–54행 `read`는 `service.get`으로 카드를 읽은 후 `validateDependencies`를 호출한다. 후자는 다시 안정된 snapshot을 만든다. `current`는 저장해 둔 본문을 단순 비교하는 함수가 아니라 `context`를 새로 조립한다(56–74행). [readPersonalMemoryContext](../../runtime/src/application/personal-memory-context.ts)도 `context` 다음에 `current`를 호출한다. 선택 시에는 게시 전 검증, CAS 안팎의 검증, 게시 후 사용 가능 확인이 반복된다. CAS는 다른 입력이 먼저 반영됐다면 오래된 상태를 덮어쓰지 않게 하는 비교 후 저장 방식이다.

**문맥 준비의 여러 경계가 이 경로를 각각 호출한다.** [ContextCompiler](../../runtime/src/application/context-compiler.ts)의 준비 전·후 `fresh`(146–149행, 162–170행, 436–453행)는 입력과 기억 의존성을 확인한다. `sourcesCurrent`는 시작과 끝에서 개인 기억의 현재성을 확인한다(75–78행, 142–143행). [ContextFrameStore](../../runtime/src/application/context-store.ts)도 이전 프레임 조회와 새 프레임 게시·읽기 전후에 상태·기억·세션을 검사한다(23–30행, 47–90행). 각 계층은 독립 호출에서도 안전해야 하므로, 상위에서 검증한 같은 기억을 하위에서 다시 깊게 읽는 구조다. 이것이 선택·문맥 준비에서 조회가 크게 늘어나는 유력한 원인이다.

현재 포트 카운터는 기억의 출처인 X의 발언 검사와 현재 세션 Y의 문맥 검사를 합쳐 센다. “이력 75회를 모두 같은 발언에 불필요하게 사용했다”는 결론까지는 확인하지 않았다.

## 3. CLI/Web의 캐시 수명은 이번 재검색 계측과 다르다

[표면의 searchPersonal](../../runtime/src/presentation/local-personal-memory.ts) 57–59행은 요청마다 `profile.personalKnowledge(actor)`를 호출한다. [local-profile](../../runtime/src/presentation/local-profile.ts) 93–96행과 [composeRuntime](../../runtime/src/application/compose-runtime.ts) 71–75행을 거쳐 `KnowledgeService.forPersonal`로 들어가며, 이 함수는 매번 새 서비스 객체를 반환한다([KnowledgeService](../../runtime/src/application/knowledge-service.ts) 32행, 39–51행).

후보 캐시는 그 서비스 객체 안에 있다. 따라서 **현재 CLI/Web의 서로 다른 요청 사이에는 이 서비스 후보 캐시의 재사용 효과가 없다.** CLI는 프로세스도 매번 새로 시작한다. Web이 같은 profile을 보관해도 개인 기억 서비스 객체는 요청마다 새로 만든다. OS나 SQLite 내부 캐시까지 없다는 뜻은 아니다.

이번 스크립트는 서비스 객체 하나를 명시적으로 보관하고 같은 검색을 두 번 실행해, 구현된 캐시가 무엇을 생략하고 무엇을 재검증하는지만 확인했다. Web 화면에서 재검색이 빨라졌다는 증거로 사용하면 안 된다. 현재 표면의 회상 helper는 소유자 없는 `id/revision` 요청을 확인하기 위해 카드를 먼저 읽고, application의 선택 서비스가 다시 검증한다. 이 표면 비용도 직접 application 서비스를 호출한 이번 선택 단계의 수치에는 포함되지 않았다.

## 4. C05에서 검토할 최소 최적화 방향

우선순위는 후보 캐시의 수명 확대보다 **한 번의 선택·문맥 준비 안에서 같은 자료를 여러 계층이 반복 검증하는 비용을 확인하고 줄이는 것**이다. 이번 표본에서는 캐시가 후보 조회 한 번만 줄였다. 다음 항목은 구현된 보장이나 확정 설계가 아닌 C05 검토안이다.

| 후보 | 줄일 수 있는 부분 | 유지해야 하는 조건 |
|---|---|---|
| 한 번의 읽기·검증 결과를 내부에서 함께 전달 | `get` 뒤 동일 자료의 `validateDependencies`, 문맥 조립 뒤 즉시 재조립 | 확인한 owner·권한·기억 버전·원문 영수증·수명 버전·만료 시각과 현재 입력 기준이 같음을 마지막 경계에서 확인 |
| 한 작업 단계 안의 원본 조회 묶기 | 같은 원문 업무·발언을 여러 기억이나 계층에서 다시 조회 | 단계 밖으로 무조건 재사용하지 않음. 입력·정정·잊기·취소·권한 변경·원본 손상 시 거절하며, 비동기 대기 전후 검증을 보존 |
| 검증 책임을 조정하는 내부 계약 | 상·하위 계층이 각각 전체 검증을 재시작하는 부분 | 독립 호출되는 하위 API의 검증을 없애지 않음. 검증 사실을 증명할 수 없는 호출은 현재의 전체 검사 유지 |
| 권한별 서비스/후보 캐시 수명 관리 | Web 요청마다 버리는 후보 캐시 | tenant·agent·principal·허용 범위·검색 조건·인덱스 버전으로 격리. 크기·수명 제한과 권한 변경·종료 시 폐기. 본문 검증과 구분 |
| 필요한 저장소 단위의 일관된 읽기 기능 | 메서드 사이의 반복 레코드 수신·파싱 | SQLite 전용 구현을 코어 필수 조건으로 만들지 않음. 서로 다른 state/channel/memory DB를 하나의 원자적 snapshot처럼 설명하지 않음 |

검증 결과를 재사용할 때 업무 revision만 같다는 조건으로는 부족하다. 다른 DB의 기억 정정·잊기, 같은 자료 식별자의 원문 변조, 권한 축소, 만료, 원본 제한·삭제가 업무 revision 증가 없이 먼저 발생할 수 있다. 자료 본문과 영수증의 일치 검증을 TTL(일정 시간 동안 무조건 신뢰하는 유효기간)만으로 대체하지 않는다. 기존에 오류로 거절하던 읽기를 캐시된 성공으로 바꾸지도 않는다.

## 5. C05 최적화의 검증 방법

1. 이번 계측을 기준선으로 보존하고, 후보 변경 전후에 같은 fixture·Node·저장소·쿼리를 사용한다. 소스와 빌드 식별자는 각각 기록하며 다른 빌드의 결과를 같은 것으로 합치지 않는다.
2. 단순 `get` 합계와 함께 검증 단계·원문 범위를 구분해 센다. 예를 들어 기억 materialize, 안정성 확인, 회상 조립, 프레임 게시 전후, X 원문과 Y 현재 문맥을 분리한다. SQL/파싱/물리 I/O 비용을 주장하려면 그 계층의 별도 계측이 필요하다.
3. 비교 대상은 같은 카드·본문·버전·출처, 같은 선택과 현재 입력 기준, 같은 실제 저장 ContextFrame이다. 직접 application 호출과 실제 CLI/Web 요청 흐름을 나눠 확인한다. 캐시 적중률만 비교하지 않는다.
4. 검증 사이에 정정·잊기·권한 축소·원본 변조/삭제·새 사용자 입력·취소를 끼워 넣어 이전 문맥과 늦은 모델 응답이 여전히 거절되는지 확인한다. 다른 담당/사용자/세션/동일 ID, 응답 유실·재시작, 만료, 부분 검색·저장소 읽기 오류도 유지해야 한다.
5. 정상 작은 흐름의 호출·읽은 바이트가 실제로 줄고 위 거절·보존 조건이 유지될 때만 해당 경로를 개선했다고 기록한다. 필요한 경우 기억 수·본문 크기·공유 출처 수를 제한된 표본으로 늘리며, 단회 시간 차이를 평균·백분위·전체 런타임 개선으로 확대하지 않는다.

C03 결과에서 사용할 수 있는 표현은 “원문을 유지하는 개인 기억 흐름과 비용 기준선을 확인했다”이다. “기억 호출을 효율화했다”, “캐시로 대부분의 조회를 제거했다”, “105B만 읽어 다음 모델 입력을 만들었다” 또는 “토큰 비용을 절감했다”는 이번 결과가 뒷받침하지 않는다. 실제 모델·Windows·운영 환경 성능 및 C05 최적화 완료 여부는 별도 검증 대상이다.
