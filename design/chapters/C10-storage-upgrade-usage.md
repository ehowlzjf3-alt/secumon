# 엔진 업데이트와 저장 형식 확인

2026-09-08 · checkpoint389 구현 사용법. [결과](C10-storage-upgrade-result.md)에 소스별 로컬 검증과 미실행 범위를 기록했다. 실제 모델/API 시험 중단과 플랫폼·운영 인수 미완료를 유지한다.

엔진 버전은 실행 코드의 버전이고, 저장 형식 버전은 DB나 문서 폴더를 읽는 규칙의 버전이다. 엔진을 바꿔도 담당 ID·대화·기억·진행 업무는 같은 담당 디렉터리에 남는다. 새 엔진이 그 자료 형식을 지원해야 다음 작업을 이어갈 수 있다.

## 사용 순서

대상 엔진의 설치와 호스트 등록을 먼저 완료한다. 상세 조건은 [담당별 엔진 사용법](C10-launcher-extensions-usage.md)을 따른다.

```sh
secumon-agent lifecycle check --directory ./agent1 --engine ./version-b --json
secumon-agent lifecycle backup --directory ./agent1 --destination ./backup-before-b --offline --json
secumon-agent lifecycle update --directory ./agent1 --engine ./version-b --previous CURRENT_RELEASE_SHA256 --backup ./backup-before-b --offline --json
secumon-agent open --directory ./agent1
```

`CURRENT_RELEASE_SHA256`은 현재 담당이 고정한 엔진의 실제 지문으로 바꾼다. `--offline`은 실행 중인 담당과 직접 DB 접근을 중지했다는 운영자의 확인이며 명령 자체가 다른 실행자를 강제로 종료하는 옵션은 아니다.

- `check`는 실제 로컬 저장 형식과 대상 엔진의 지원 범위를 읽어 확인한다. 자료를 새 형식으로 변환하지 않는다.
- `backup`은 현재 자료와 엔진 고정을 보존한다. `update`는 정확한 현재 자료에 대응하는 백업을 요구하고 담당이 사용할 엔진 선택을 바꾼다.
- 다음 `open`은 선택된 엔진을 사용한다. 필요한 로컬 형식을 먼저 확인한 뒤, 기존 저장소 구현이 지원하는 이행을 수행한다. 상태 1/2→3에서는 조회용 색인을 재구성하고, 지식 1→2에서는 담당별 구획을 추가한다. 지식 원문과 영수증을 개인 기억으로 자동 승격하지 않는다.

긴 대화의 요약도 별도의 compact 형식을 사용한다. 새 배포 명세는 지원 형식을 명시하며 기존 명세는 이미 사용하던 형식1로 해석한다. 요약 테이블이 전혀 없으면 아직 요약을 저장하지 않은 정상 상태다. 일부 테이블만 있거나 지원하지 않는 형식이면 거절한다.

## 실패했을 때의 의미

알려진 미지원 형식이나 모호한 버전 기록은 쓰기 가능한 저장소를 열기 전에 거절한다. 최초 실행의 아직 없는 DB와 지원되는 초기화 중단 상태는 기존 초기화 절차로 이어갈 수 있다. 선검사는 모든 자료의 무결성을 미리 증명하거나 여러 DB를 한 번에 변경하는 기능이 아니다. 실제 이행은 각 저장소의 트랜잭션으로 수행되며 다른 종류의 오류나 검사 이후 변경은 각 저장소가 다시 처리한다.

엔진을 이전 버전으로 되돌리는 일과 과거 백업으로 자료를 복원하는 일은 다르다. 이전 엔진이 현재 저장 형식을 읽지 못하면 해당 엔진으로 전환할 수 없다. 과거 자료 복원은 백업 이후의 기록을 잃을 수 있고 이미 발생한 외부 동작을 되돌리지 않는다. 복원 전에는 백업 이후 기록과 외부 효과를 별도로 대조해야 한다.

SQLite는 읽기 전용 확인에서도 WAL 조정 파일을 만들 수 있다. 형식·본문을 변경하지 않는다는 설명을 모든 파일 경로와 바이트가 전혀 바뀌지 않는다는 뜻으로 확대하지 않는다. PostgreSQL 선택은 기존 별도 호스트·백업·이행 절차를 사용하며 이 로컬 검사만으로 원격 저장소까지 검증했다고 표시하지 않는다.
