# C09 명령 응답이 끊겼을 때

2026-09-09 · checkpoint395. 아래는 구현하고 로컬 검증한 사용 계약이다. 같은 최종 build2에서 신규12개·관련95개가 통과했다. 로컬 검증 결과는 [결과 기록](C09-command-recovery-result.md)을 따른다.

저장소는 명령을 기록했지만 응답 전에 오류가 날 수 있다. 이때 오류를 받은 사실만으로 명령이 적용되지 않았다고 판단할 수 없다. 엔진은 같은 명령 ID와 입력 digest(원문 대조값)의 저장 영수증을 확인하고, 확인할 수 있을 때 기존 실행의 중단 신호를 복구한다. 호출자에게는 원 오류가 계속 전달된다.

세션 입력은 기존 메시지 ID와 원 payload(요청 내용)를 유지해서 재개한다. 새 메시지를 만들어 같은 작업을 다시 지시하는 방법으로 복구하지 않는다. 기존 SessionService.resume 또는 같은 메시지의 command 경로가 원 업무 명령을 확인하고 접수 상태를 정리한다. 원 영수증을 읽지 못했거나 원문이 다르면 이를 성공으로 표시하지 않는다.

## 과거 명령이 새 작업을 끊지 않는 이유

상태 번호가 10일 때 시작한 조회가 있고, 일시정지 명령이 11번에 저장됐다고 하자. 명령을 11번 원 영수증으로 확인하면 10번 상태에서 시작한 조회를 중단한다. 이후 명시 재개가 12번에 저장되고 새 조회가 12번 상태에서 시작했다면, 과거 11번 명령의 재전달은 이 새 조회를 중단하지 않는다. 현재 상태 번호를 과거 명령의 번호 대신 사용하지 않는다.

이 번호는 모델의 토큰·턴 예산이나 세션 수명이 아니다. 같은 업무의 저장 상태가 바뀔 때 증가하는 번호이며 실행 간 순서를 구분하는 데 사용한다. 대화 원문·개인 장기기억·원 사건·도구 결과는 기존 저장소에서 유지한다.

## 관측 담당 제어

resident 관측의 pause/stop도 정확한 원 checkpoint 영수증으로 이전 poll만 중단한다. 아직 진행 중인 원천 callback의 종료는 원천을 소유한 호스트가 담당한다. 관측 대기가 끝났다는 사실을 외부 작업 종료나 업무 완료로 해석하지 않는다.

현재 bare pause(workId)는 새 제어 의도다. 명령 ID가 없으므로 다른 호출자가 resume한 뒤 같은 함수를 호출하면 새 일시정지 요청으로 처리된다. 과거 요청의 재시도까지 구분해야 하는 채널에서는 후속 명령 ID·예상 상태 API가 필요하다. 일반 사용자 업무의 세션 command는 이미 원 메시지 ID와 영수증으로 재시도를 식별한다.

실제 모델/API 시험은 중단 상태다. 이 계약의 로컬 검증과 실제 사내 서비스·네트워크 단절·운영 환경 검증은 구분해 기록한다.
