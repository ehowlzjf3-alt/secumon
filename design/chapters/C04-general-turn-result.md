# C04 일반 요청 주턴 연결 결과

2026-09-07 · **첫 연결 단위의 로컬·Linux 검증 완료.** 이 문서는 C04의 첫 일반 요청 연결 단위를 설명한다. C04 전체나 전체 개발 목표의 완료를 뜻하지 않는다.

이제 담당 디렉터리에서 시나리오를 고르지 않고 요청 원문을 접수하면, 기존 지속 세션과 실행기를 통해 답변·질문·계획 중 필요한 흐름으로 진행할 수 있다. 여기서 **주턴**은 현재 요청과 문맥을 받아 다음 행동을 판단하는 모델 호출 한 번을 뜻한다. 단순 답변은 별도의 사실 관측이나 도구 작업이 없어도 답변 요구에 맞춰 완료를 판정한다.

현재 CLI/Web에서 연결하는 제공자는 **명시적으로 선택한 합성 규칙 제공자**다. 알려진 시험 문구와 실제 저장된 자료를 사용해 흐름을 검증한다. 임의 질문의 의미를 이해하는 실제 모델이 연결되었다는 뜻은 아니다. 실행 예시는 [사용 안내](C04-general-turn-usage.md), 채택한 범위는 [구현 계획](C04-general-turn-plan.md)에 있다.

## 사용자에게 달라진 점

| 흐름 | 구현한 동작과 의미 |
| --- | --- |
| 요청 접수 | 원문을 먼저 저장하고 접수 응답을 남긴다. 같은 접수 ID와 같은 내용의 재전송은 기존 업무를 사용한다. 모델이 업무 ID나 권한을 정하지 않는다. |
| 바로 답변 | 단순 교정 시험은 주턴 1회, 도구 0회로 끝난다. 답변이 필요한 요청이라는 조건을 목표에 기록하며, 사실을 관측한 것으로 꾸미지 않는다. |
| 자료 확인 후 답변 | 기존 `fixture.read` 도구 1회와 주턴 2회로 실제 관측 자료를 읽고 답변한다. 도구 결과 이후의 답변 작성만으로 계획 변경 비용을 추가하지 않는다. |
| 질문과 보충 입력 | 질문을 보내면 같은 업무에서 기다린다. 질문 ID를 지정한 답변은 그 질문을 해결하고 진행한다. 일반 추가 입력은 질문을 자동 해결하지 않는다. |
| 부족한 초안 수정 | 아직 부족한 요구가 있는 초안은 최종 답변으로 보내지 않고 다음 주턴의 참고 자료로 사용한다. 반복은 기존 호출·진행 한도 안에서만 가능하다. |
| 다음 업무와 재시작 | 완료한 X의 실제 답변이 같은 세션의 Y 문맥에 들어간다. 실행을 중단했다가 다시 열어도 저장된 호출 응답을 재사용한다. 업무별 목표·사용량은 분리한다. |
| 컴팩트 후 계속하기 | 기존 요약 엔진에 알려진 합성 문구 규칙을 연결했다. 원문 대화는 보존하고, 정확한 인용이 있는 요약과 최근 입력을 다음 업무에 제공한다. |

CLI의 새 `chat` 경로는 `session`, `ask`, `followup`, `resume`, `status`, `history`를 제공한다. 기존 `work` 경로는 유지한다. `--provider synthetic`가 없으면 제공자를 자동 대체하거나 담당을 먼저 초기화하지 않는다. `auto/fast/deep`는 업무 진행 방식이며 세션 문맥을 버리는 설정이 아니다.

Web도 같은 접수 서비스를 사용한다. 접수와 실행은 구분되며, 접속·조회·재접속 자체는 모델을 실행하지 않는다. 화면에는 접수, 질문, 결과와 필요한 진행 상태를 전달하고 내부 도구 호출 기록을 대화 말풍선으로 계속 추가하지 않는다. 다른 선택 세션의 업무 조회·실행은 거절한다.

## 기존 코어에 연결한 방식

새 프레임워크나 별도 도구 루프를 만들지 않았다. C01 담당 저장소, C02 세션·컴팩트, C03 개인 기억, 기존 계획 검사·작업 실행·호출 정산·결과 전달을 재사용했다.

| 경계 | 이번 연결과 코드 |
| --- | --- |
| 원문과 목표 | [AgentTurnService](../../runtime/src/application/agent-turn-service.ts)는 기존 `SessionService.accept/command`를 사용한다. `responseRequirement`는 최초 요청 ID·본문 지문·답변 형식을 기록하는 선택 조건이다. 이 조건이 있을 때만 사실 기준이 빈 목표를 허용하며 기존 사실형 목표의 직렬화는 유지한다. |
| 모델 입력과 호출 | [주턴 런타임](../../runtime/src/application/agent-turn-runtime.ts)은 기존 계획 런타임의 예약·실행·응답 저장·채택 경로를 사용한다. [구조화 어댑터](../../runtime/src/infrastructure/structured-agent-turn.ts)는 응답 형식, 제공자 식별, 원문·프롬프트 입력, 사용량을 검사한다. 잘못된 응답을 고치려고 숨은 추가 모델 호출을 만들지 않는다. |
| 최초 요청과 최신 입력 | 질문에 답해도 최초 요청 조건은 유지하고, `AppliedSessionInput`은 실제로 반영한 최신 입력을 가리킨다. [원 요청 검증](../../runtime/src/application/agent-turn-request.ts)은 컴팩트로 최초 요청이 모델 입력에서 빠져도 원 세션 저장소에서 확인한다. |
| 완료 판정 | [완료 판정](../../runtime/src/domain/completion.ts)은 현재 목표·계획·자료 세대·입력과 일치하는 채택된 답변을 요구한다. 사실 근거, 반증, 미완료 작업, 검토할 입력·기억, 미해결 의무에 대한 기존 검사도 유지한다. |
| 초안과 최종 전달 | [답변 검증](../../runtime/src/application/generated-answer.ts)과 [이전 초안 검증](../../runtime/src/application/agent-turn-previous.ts)은 입력·응답·답변 원본과 권한을 확인한다. 현재 답변의 지문을 결과 ID·전달·조회에도 반영하므로 사실이 같더라도 과거 답변을 현재 결과로 재사용할 수 없다. |
| 실제 사용자 진입 | [담당 프로필 연결](../../runtime/src/presentation/agent-turn-profile.ts), [CLI](../../runtime/src/presentation/agent-turn-cli.ts), 기존 Web 경로가 같은 서비스와 저장소를 사용한다. SQLite와 파일 저널 상태 저장, 기존 개인 기억 선택을 유지한다. |

답변 평가는 `model_self_review`, 즉 모델 자신의 검토다. `counterarguments`는 검토한 반론 목록이고, 해결하지 못한 사항은 `missing`에 남겨 완료를 막는다. 자체 검토가 통과했다고 독립적인 사실 근거를 얻은 것으로 계산하지 않는다. 별도 반론 에이전트가 독립 자료를 조사하는 구조까지 이번에 구현한 것은 아니다.

## 초기 실패와 보강

첫 신규 시험은 **66개 중 65개 통과, 1개 실패**였다. 실제 읽기 자료 `doc-current`의 값은 30일인데 시험이 90일을 기대한 문제였다. 원 자료와 실제 실행 결과를 확인해 기대값을 수정했다. [첫 원로그](../../runtime/evidence/C04-turn-new1.log)와 [현재 흐름 시험](../../runtime/src/tests/agent-turn-flow.test.ts)에 이 차이가 남아 있다.

통합 과정에서 시험 코드의 선택 속성·타입 좁히기 오류도 수정했다. 최종 build5가 성공하기 전 빌드 실패를 통과로 취급하지 않았다. [초기 타입 검사](../../runtime/evidence/C04-turn-typecheck1.log), [build2](../../runtime/evidence/C04-turn-build2.log), [build4](../../runtime/evidence/C04-turn-build4.log), [최종 build5](../../runtime/evidence/C04-turn-build5.log)를 각각 보존했다.

검토 중 확인한 연결 부족도 보강했다. 최초 요청과 최신 답변 입력을 분리했고, 이전 초안의 복사된 본문만으로 원본 검증을 통과하지 못하게 했다. 기존 합성 컴팩트 규칙이 새 주턴 시험 문구를 처리하지 못하던 부분은 같은 엔진의 명시 규칙 확장으로 연결했다. 알려지지 않은 원문을 임의 요약으로 만드는 기능은 추가하지 않았다.

로컬 신규·관련 시험은 동결된 build5 산출물을 사용했고, 두 실행 후 현재 소스·빌드 일치를 확인했다. 매 실행 직전 지문은 별도로 수집하지 않았다. 당시 시험 프로세스의 정확한 Node 버전도 기록하지 않았으므로 후속 증거 확정 프로세스의 버전을 시험 버전으로 대신하지 않는다.

build5의 소스 지문은 `8441f542d0c7394474524ff8e46f30d99b3ed8fc86a7dece153e22cd035647a3`, 빌드 파일 지문은 `f96274dbbb1cc7d14f82c71cb7dd1b43b1e228054114d803cf42327c17f68667`, 파일 수는 1,521개다. 회수한 Linux 빌드 지문과 같은 값임을 최종 증거에서 대조했다.

로컬 build5 manifest는 Node v25.8.0를 기록했다. 지원 버전 Node 24로 로컬 증거 확정기를 실행하자 verifier의 실행 버전 일치 검사에서 한 번 거절됐고, 실제 로컬 빌드 버전으로 대조해 원 지문을 확인했다. 소스·빌드·원로그를 고치거나 시험을 반복하지 않았다. NAS의 지원 Node 24.20.0 결과와 로컬 빌드 환경을 구분한다. [빌드 manifest](../../runtime/evidence/C04-turn-local-build5-manifest.json) · [진단](../../runtime/evidence/C04-turn-finalize-diagnosis.json).

## 남은 범위

현재 일반 요청의 **접수 → 판단 → 도구/질문/답변 → 검증 → 전달 → 같은 문맥에서 다음 업무** 연결을 구현하고 로컬·Linux에서 검증했다. 실제 모델 연결과 품질 평가, 브라우저 실기 확인은 별개로 남아 있다.

Windows 네이티브 실행·파일 경계 검증과 PostgreSQL 연결은 기존 챕터의 미완료 항목이다. 이번 결과로 지원 완료로 바뀌지 않는다. 사내 MCP·Knox 연결, 도구·기억 조회 효율 개선, 독립 반론 에이전트와 다중 에이전트 협업도 후속 범위다. C04의 다음 항목은 [모델 입력 한도와 compact 조정](C04-context-window-plan.md)을 따르며, 이 문서만으로 챕터나 개발 목표를 완료 처리하지 않는다.
