# P4-01 다음 소단위: 게시판 쓰기와 작업 의무

2026-09-06 · 게시/철회·영수증 복구 로컬 검증 완료 · 요청/의무 구현 전

구현 선택: 결과 증명은 실제 저장 효과와 입력 자료의 유효성을 분리한다. 명령 식별자는 runtime 시도에 고정한다. 영수증이 없으면 즉시 미실행으로 판정하지 않고, 게시판 상태를 바꾸지 않는 종료 기록을 같은 명령 식별자로 원자 커밋하여 늦은 저장을 막는다. 현재 게시판 두 저장소의 커밋/중복 계약을 이 방식으로 확장한다. 첫 도구는 게시/철회이며, 인용은 해당 작업이 이미 읽고 현재 검증한 게시글에 한정한다.

## 배울 개념

게시글이 저장된 것, 상대가 요청을 수락한 것, 답변이 도착한 것, 요청자가 답변을 확인한 것, 전체 업무가 끝난 것은 서로 다른 상태다. 도구가 성공했다는 문장 하나로 이 상태들을 합치지 않는다. 게시판과 작업 저장소는 각각 커밋할 수 있으므로 두 저장 사이에서 프로세스가 종료돼도 이미 한 동작을 확인하고 이어갈 수 있어야 한다.

## 구현할 결과

1. 게시·철회·요청·수락·답변·확인을 기존 tool catalog/broker의 쓰기 도구로 등록한다. 실제 주체와 소비 업무는 실행 context에서 가져오고, 모델이 주체·권한·예산을 선언할 수 없게 한다. 게시판 관리 권한을 일반 대화 역할의 도구로 노출하지 않는다.
2. 하나의 실제 시도에 명령 식별자와 입력 digest를 붙이고 게시판 receipt 및 작업 receipt로 저장 여부를 확인한다. 게시판 저장 뒤 응답이 없어도 같은 명령으로 대조하며 글이나 요청을 다시 만들지 않는다. 확인할 수 없는 상태는 효과 미확정 의무를 유지한다.
3. 질문·수락·답변의 의무를 WorkState에 연결한다. 답변이 와도 요청자의 확인 전에는 완료 조건을 자동으로 충족시키지 않는다. 철회·기한·상대 역할 비활성화는 해당 의무의 재검토 조건이다.
4. 대기 상태에서는 모델 호출을 반복하지 않는다. 현재 로컬 workflow의 wake와 상태 조회를 재사용하고, 이벤트의 중복 수신과 재시작 후 누락 처리를 검사한다. 메시지를 실제 사람에게 보내는 채널 연동은 별도다.

## 순서와 완료 기준

먼저 단일 게시/철회 도구와 durable receipt 대조를 구현한다. 정상 저장, 저장 전 실패, 저장 후 응답 유실, 같은 명령 재시도, 변경된 입력의 같은 명령 식별자, 권한 변경을 시험한다. 결과 artifact만 있고 게시판 receipt가 없으면 저장 완료로 인정하지 않는다.

그다음 요청/수락/답변/확인 상태와 작업 의무를 연결한다. 두 상태 저장소에서 취소·기한 경과·철회된 답변·이미 처리된 이벤트·양쪽 저장 중 한쪽만 성공한 상태로부터 재개를 시험한다. 질문이나 답변은 도구 budget을 사용하고, 단순 대기/상태 확인은 숨겨진 모델 반복을 만들지 않아야 한다.

마지막으로 두 역할이 같은 대상에 대해 서로 다른 자료를 가진 로컬 fixture를 실행한다. 새 반증이 기존 가설/계획의 어떤 부분을 다시 검토하게 하는지 기록하고, 중단·compact·재개 후 남은 의무가 유지되는지 확인한다. 이 흐름이 다른 주체의 예산 위임을 필요로 하면 현재 예산의 동일 주체 제한을 임의로 풀지 않고 다음 계약 단계로 분리한다.

## 범위와 기록

현재 BoardService의 관리·출처·중복·대기 관계 검사를 재사용한다. 핵심은 runtime 연결과 두 장부의 복구이며 Python 원본 비교는 선행 절차가 아니다. 각 소단위의 설계 선택·실패 원인·검증 결과를 WORKLOG와 결과 문서에 저장한다. 실제 모델/API·사내 서비스·Knox·외부 A2A 시험은 포함하지 않는다. 이 계획만으로 P4-01 전체를 완료 처리하지 않는다.
