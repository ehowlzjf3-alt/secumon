# C05 권한 철회 뒤 수집 업무 재개

2026-09-08 · checkpoint375, 구현/검증 진행 중. 일반 CLI/HTTP의 custody-only 인수에서 실제 연결 누락을 발견했다. 원응답은 저장됐지만 현재 원문/도구 권한은 철회된 업무다. HTTP 취소2개는 통과했고, CLI는 만료 정리 뒤 계획 문맥에 권한 없는 도구를 요구해 `context_tool_unavailable`로 실패했다. [실패 원로그](../../runtime/evidence/C05-ordered-target14.log).

기존 단일 응답 복구는 현재 본문을 복구할 수 없으면 명시 blocked 상태와 재개 기록을 남긴다. 수집 경로도 이 계약을 사용한다. 모델에게 질문을 생성하도록 하는 초안 시험의 기대는 확정 요구가 아니었으며, 현재 필수 도구/계획 투영 계약을 우회하지 않는다.

`settleStoredCollection`은 먼저 기존 received 채택·만료 정리를 수행한다. 그 뒤 현재 실행 판단이 `replan / plan_cannot_complete_goal`일 때만, 현재 목표·scope·task digest가 맞는 마지막 수집 시도에 대해 `tool_permission_denied`를 확인한다. successor가 있거나 이미 성공한 task, 독립 실행·질문/검토 의무가 있는 상태를 대신 차단하지 않는다. 상태 revision·등록 객체/세대·현재 권한·실행 수명을 게시 직전에 다시 확인하고 업무 상태만 blocked로 기록한다. 원 attempt의 owner·lease·`lease_expired`·head, 목표·계획·원 입력은 보존한다.

기존 Workflow의 사용량 정산과 ContextRecovery를 이어 써서 정산1회·추가 전송0·모델0·보호 본문 제외·정상 blocked checkpoint를 확인한다. 일반 CLI의 접수와 동일하게 seed 단계에서 공개 ack를 먼저 flush하며, 반복 resume/status에서 새 답변·재정산이 없어야 한다. HTTP 취소·중복은 기존2개 인수 경로를 유지한다.

제품 수정에 맞춰 현재 tip 차단과 옛 목표/계획·successor·독립 실행·cancel/pause·권한/등록 변경 경합을 좁게 검증한다. 기존 수집 재개와 단일 응답 입구도 관련 회귀로 재사용한다. 실제 모델/API 및 외부 서비스는 실행하지 않는다.

권한을 다시 허용하려면 신뢰된 경로가 저장 업무 정책을 변경하고 사용자가 명시 재개 명령을 보내야 한다. 단순 재접속은 차단을 해제하지 않는다. 권한 재허용 후 전체 CLI 완주는 이번 결과로 주장하지 않으며 기존 원응답 검증/명시 successor 경로와 구분한다. 실행 결과는 확정 후 결과 문서와 체크포인트에 저장한다.

후속 CLI 확인에서 제한 상태 게시 직후 Workflow의 정상 안내 전달 단계를 건너뛰는 문제와, CLI가 전달된 failure 종류를 모두 제외하는 문제를 찾았다. 상태를 게시한 뒤 정상 정산·안내 단계를 마치고, CLI는 기존 WorkView의 현재 제한 ID·권한·가공 문구를 재사용해 해당 세션에 전달된 안내만 표시한다. 기억 원본 변경으로 선택 안내를 확인할 수 없으면 안내는 보류하고 기존 상태 조회를 유지한다. 제한 이유가 바뀐 옛 안내를 다시 표시하지 않는지도 확인한다.
