사용자는 저장소 종류의 단순 분류보다 PostgreSQL·SQLite·파일 디렉터리의 지원과 효율적인 기본값 선정을 요청했다. 원하는 상호작용은 같은 대화 문맥에서 여러 작업을 이어가고 필요할 때 compact하는 방식이다. 공통 실행기는 한 번 설치하고, 담당마다 별도 디렉터리에서 설정·스킬·기억·세션을 관리하는 배치 예시를 제시했다.

이 문서가 저장 기본값·담당 디렉터리·지속 세션에 대한 최신 설계 기준이다. `agent-lifecycle-and-memory-boundaries.md`의 미결정 저장 후보를 여기서 좁힌다. 협업 관계·정보 정책 등 별도 미결정 사항까지 일괄 채택하는 것은 아니다. 기존 코드 보존 자체를 요구로 삼지 않되, 아래 동작을 만족하는 기반은 재사용한다.

## 1. 선택한 기본 구성

**공통 엔진 한 벌 + 담당 디렉터리별 데이터 + 이어지는 세션 + 로컬 SQLite/파일 기본 + 명시적으로 설정한 PostgreSQL 지원.**

| 관심사 | 기본값 | 선택 지원 |
|---|---|---|
| 실행기 | TypeScript 기반 공통 CLI 패키지, 담당 디렉터리 밖에 설치 | 같은 실행기를 서비스/API 어댑터에서 호출 |
| 담당 식별 | 디렉터리에 보관한 지속 ID와 호스트가 확인한 실행 주체 | 디렉터리 이동/등록 경로 변경 |
| 대화 세션 | 같은 담당·같은 대화는 작업 완료 후에도 유지, 필요 시 compact | 명시적인 새 세션/다른 대화/독립 병렬 실행 |
| 작업 상태·대화 이력·복구 | 담당별 로컬 SQLite, 의미별 테이블/기록 구분 | 계약을 만족하는 PostgreSQL 또는 파일 저널 어댑터 |
| 개인 장기기억 | 담당의 `memory/memory.sqlite` | 문서 파일 기반 기억 어댑터, 설정된 PostgreSQL 기억 저장 |
| 설정·스킬 | 디렉터리의 JSON 설정과 스킬 파일 | 배포자가 관리하는 공통 기본 설정/스킬을 명시적으로 연결 |
| 큰 원문·이미지·산출물 | 담당 디렉터리의 파일 저장소 | 외부 객체/문서 저장소 연결 |
| 게시판·아카이브 | 기본 비활성, 필요한 배치에서 연결 | 로컬/공유 저장소, 기존 시스템/MCP 연결 |

SQLite를 기본으로 고른 이유는 별도 DB 서버 없이 로컬 실행할 수 있고, 구조화 조회와 갱신·정산·버전 관리를 기존 기반으로 제공할 수 있기 때문이다. 담당별 DB 파일로 기본 배치를 나누어 전역 대화 DB에 모든 담당의 기록을 모으지 않는다. 이것이 모든 규모에서 최저 지연을 입증한 선택이라는 뜻은 아니다. [SQLite 공식 사용 범위](https://www.sqlite.org/whentouse.html)

개인 장기기억을 문서 파일로 관리하는 선택도 지원 대상으로 둔다. 파일 방식에서는 원자적 갱신·버전·소유자·검색 계약을 구현한다. 동일 기억의 DB 본문과 문서 본문을 각각 독립적인 정본으로 두지 않는다. DB 방식에서 문서로 내보내기는 가능하되 내보낸 사본의 편집을 자동으로 별도 정본으로 취급하지 않는다.

## 2. 배치 예시와 전역 명령

다음은 목표 디렉터리 구조다. 현재 생성하거나 설치한 구조는 아니다.

```text
공통 설치 위치/
  secumon-agent 실행기 · 버전별 엔진 · 공통 도구 구현

~/digisecu/secumon/
  agent1/
    config.json                 담당/모델/연결 설정
    skills/                     이 담당이 사용하는 지침
    memory/
      memory.sqlite             기본 개인 장기기억
    .secumon/
      identity.json             자동 생성된 지속 담당 ID
      runtime.sqlite            세션·대화 이력·작업 상태·자원 장부
      artifacts/                큰 원문·도구 결과·복구 산출물
    workspace/                  작업 파일과 사용자 산출물
  agent2/
    ...                         agent2의 독립된 설정·세션·기억
```

`secumon-agent`는 설계상의 명령 이름이다. 현재 npm 패키지의 전역 실행 명령이 등록됐다는 뜻은 아니다. 셸 함수로 핵심 로직을 복제하기보다 PATH에서 호출하는 표준 실행기를 제공한다. Node 패키지의 실행 파일을 전역 명령 경로로 연결할 수 있다는 배포 방식은 npm 공식 문서에 설명되어 있다. [npm 실행 파일 배치](https://docs.npmjs.com/cli/v11/configuring-npm/folders/)

설계상의 사용 모습은 `secumon-agent --workspace ~/digisecu/secumon/agent1`이다. 담당 디렉터리 안에서 실행하면 해당 루트를 사용하고, 처음 초기화한 담당은 새 세션을 시작한다. 같은 담당으로 돌아오면 같은 사용자/채널 범위의 마지막 대화 세션을 이어갈 수 있게 한다. 다른 사용자·다른 채널의 세션까지 전역 최신 항목 하나로 자동 선택하지 않는다.

관리 동작으로 담당 초기화·기존 담당 열기·명시적 새 세션·지속 서비스 실행을 제공할 수 있다. 명령 세부 문법은 구현 시 정한다. 단순한 디렉터리 생성이나 CLI 예시가 실제 서비스 배치/등록을 뜻하지 않는다.

## 3. 경로는 위치이며 지속 ID는 별도로 보존

‘어느 디렉터리에서 호출했는가’는 담당을 찾는 기본 기준으로 사용한다. 절대 경로 문자열 자체를 영구 식별자로 삼으면 이름 변경이나 이동을 새 에이전트로 오인할 수 있으므로 디렉터리 내부에 한 번 생성한 ID를 보관한다.

- 담당 루트를 명시하거나 현재 디렉터리에서 가장 가까운 담당 표식을 찾는다. 일반 하위 작업 폴더로 이동했다고 새 담당을 만들지 않는다.
- 디렉터리를 이동하고 다시 등록해도 ID·세션·기억은 유지한다.
- 이동/복구와 복제해 새 담당 만들기는 다른 관리 동작이다. 복제본을 원본과 동시에 같은 ID로 운영하지 않도록 등록/소유권 충돌을 확인한다. 새 담당 복제는 새 ID·새 세션을 기본으로 하고 기억 복사는 명시적 선택으로 둔다.
- ID 파일을 모델이 바꿨다고 실행 중인 주체와 접근 권한이 바뀌지 않는다. 호스트가 실행 맥락을 결정한다.
- 같은 세션에 두 실행기가 동시에 상태를 덮어쓰지 않도록 쓰기 소유권을 관리한다. 여러 세션이나 독립 작업은 별도 범위에서 병렬 실행할 수 있다.

실행 중 DB 파일을 무조건 복사하는 방식 대신 정지/일관된 백업/복구 절차를 제공해야 한다. 이동 가능한 디렉터리라는 말이 실행 중 파일 복사만으로 항상 완전한 백업이 된다는 뜻은 아니다.

## 4. 지속 세션이 작업 엔진을 사용한다

현재의 작업별 실행/재개 기반을 지속 담당·세션 안에서 사용하는 구조를 설계 기준으로 삼는다.

```text
담당 agent1
  └─ 지속 세션 S
       ├─ 현재 대화 문맥 · 최근 대화 · compact 요약
       ├─ 작업 X의 목표/계획/검증/사용량 → 완료
       ├─ 문맥을 유지한 채 다음 요청 수신
       └─ 작업 Y의 목표/계획/검증/사용량 → 계속
```

작업 X의 complete는 S의 종료가 아니다. 세션은 답변을 전달하고 다음 요청을 기다린다. 다음 요청이 X의 후속 변경이면 관련 작업 갱신으로, 새 목표라면 별도 Y로 연결한다. 어느 경우에도 작업 경계 자체를 이유로 문맥을 초기화하지 않는다.

compact는 입력 용량·관련성에 따라 현재 문맥을 재구성한다. 세션의 핵심 합의·현재 목표 연결·미해결 질문·관련 근거·기억 조회 경로를 유지한다. 오래된 완료 작업의 세부 결과는 필요할 때 다시 읽는다. 대화 이력의 보존과 모든 원문을 매번 모델 입력에 싣는 것은 다르다.

사용자의 과거 합의와 최근 맥락은 개인 장기기억에 반드시 등록하지 않아도 같은 세션에서 유지되어야 한다. 장기기억은 여러 세션/작업을 가로질러 재사용할 가치가 있는 항목의 별도 저장이다. 아카이브 조회 결과는 현재 문맥에서만 사용한 뒤 정리할 수 있고 개인 기억으로 자동 승격하지 않는다.

자원 배정은 X/Y 및 위임 작업의 장부에 연결한다. 세션·담당의 존재에 유한한 생애 토큰을 강제하지 않는다. 자원 부족 시 정해진 운영 정책에 따라 대기/추가 요청/재배정을 처리하며 문맥·기억을 폐기하지 않는다. compact는 누적 사용량을 초기화하지 않는다.

이 문서는 사용자가 원하는 연속 사용 경험을 명세한다. Codex나 Claude의 내부 구현을 그대로 확인하거나 복제했다는 주장은 하지 않는다.

## 5. 공통 본체와 확장 영역

공통 엔진은 담당마다 복사하거나 직접 수정하는 대상이 아니다. 담당은 설정·지침·도구 연결을 달리해서 구성한다. 핵심 목표/계획/실행/검증/복구 의미는 공통 엔진이 소유한다.

전역 실행 파일 등록 자체는 쓰기 보호를 보장하지 않는다. 배치에서는 공통 설치 경로를 업무 도구의 쓰기 범위에서 제외하고, 필요한 보호 수준에 따라 실행 주체와 설치/업데이트 주체를 분리하거나 읽기 전용 배치를 사용한다. 같은 OS 사용자가 임의의 셸/파일 권한을 모두 가진 상태에서 디렉터리 관례만으로 본체 수정 불가능을 보장하지 않는다.

코어 업그레이드는 배포 작업이다. 버전과 호환되는 설정/저장 schema를 확인하고 기존 상태를 이행해야 한다. ‘본체를 건드리지 않는다’는 것은 개별 업무나 담당의 사용자화가 코어 소스 수정을 요구하지 않는다는 의미이며, 제품 개발 자체를 영구 중단한다는 의미가 아니다.

설치형 패키지, 담당별 엔진 버전 선택, 저장 형식 호환성, 업데이트/되돌리기 절차는 [설치·버전 관리 설계](installation-and-versioning.md)에 구체화했다. 작업 완료뿐 아니라 엔진 업데이트도 담당 정체성·대화 문맥·기억을 초기화하는 동작이 되어서는 안 된다.

담당별 skill과 도구 연결은 코어의 공개 계약을 통해 로딩한다. 외부 도구는 기존 MCP나 별도 실행 경계를 우선 활용할 수 있다. 임의 확장 코드가 코어 모듈을 덮어쓰는 방식을 기본으로 하지 않는다. 권한은 스킬 텍스트나 모델이 수정한 설정만으로 확대하지 않는다.

## 6. PostgreSQL은 명시적 연결과 역할 선택 뒤 사용

PostgreSQL이 시스템에 설치돼 있거나 기존 Digisecu가 사용한다는 사실만으로 자동 접속·등록·이행하지 않는다. 사용자가 연결 프로필과 사용할 역할을 설정한 배치에서만 연결한다. 설정에는 접속 비밀 자체 대신 비밀 참조를 둘 수 있다.

| PostgreSQL 연결 목적 | 의미 |
|---|---|
| 기존 자료 조회 | 기존 시스템의 허용된 자료를 읽는 도구/자료 공급자. 에이전트 내부 상태를 그 DB에 쓰지 않음 |
| 공유 게시판·아카이브 | 지원되는 schema/서비스와 권한이 있을 때 선택한 공유 기능에 사용 |
| 에이전트 영속 저장 | 다중 호스트/동시 운영 등 필요에 따라 별도 관리 schema와 어댑터를 설정해 상태/기억 저장에 사용 |

연결 가능한 DB와 테이블을 만들거나 기록할 수 있는 DB는 같지 않다. 등록/쓰기 기능은 실제 연결이 지원하는 능력에 맞춰 노출한다. 명시적으로 PostgreSQL을 정본으로 선택한 뒤 연결이 끊겼다고 새 SQLite 정본을 자동 생성하지 않는다. 일관된 대기/오류/복구 경로를 사용한다. 저장 방식 변경은 검증된 이행 절차로 처리한다.

기본 사내 배치 예시는 agent1/agent2의 세션·개인 기억은 각자의 로컬 저장에 두고, 필요한 게시판/아카이브 또는 기존 업무 자료만 PostgreSQL/MCP로 연결하는 방식이다. 모든 배치가 공유 기능을 가져야 하는 것은 아니다.

## 7. 여러 담당과 임시 서브에이전트

agent1/agent2는 지속적인 업무 담당의 작업 공간이다. 두 담당은 같은 엔진과 같은 모델을 사용해도 ID·세션·개인 기억·검색/캐시·파일 범위를 분리한다. 글로벌 설정에는 공통 기본값을 둘 수 있지만 모든 담당의 대화/기억을 자동 통합하지 않는다.

짧은 반론 검토를 위한 임시 서브에이전트마다 영구 담당 디렉터리와 장기기억 DB를 새로 만드는 것은 기본값이 아니다. 요청별 별도 실행 문맥과 식별자, 필요한 자료/도구 범위, 결과 참조와 자원 장부를 갖게 한다. 호출한 cwd가 같다는 이유로 부모의 활성 세션을 공유·수정하지 않는다. 부모 개인 장기기억에 대한 자동 쓰기도 부여하지 않는다. 계속 존재할 담당이 필요할 때만 정식 담당 작업 공간으로 등록한다.

같은 자료를 읽을 수 있는 역할끼리 협업할 수 있지만, 공유 자료 접근과 서로의 개인 문맥을 섞는 것은 다르다. 검토 의견·근거·반론을 결과로 반환하고 호출한 작업이 평가하여 자기 상태에 반영한다.

## 8. 기존 코드와 구현 순서

현재 패키지는 합성 로컬 CLI이며 전역 실행기를 등록하는 `bin` 항목이 없다. 로컬 프로필은 작업 단위 상태/기억 어댑터를 구성하지만, 지속 담당 등록과 여러 작업을 잇는 세션은 아직 완성되지 않았다. 이 사실을 목표 동작의 제약으로 삼지 않는다.

우선 구현 순서는 다음과 같이 정한다. 이는 다음 제품 구현의 순서이며 이번 문서 작성으로 각 항목이 완료된 것은 아니다.

1. **담당 디렉터리와 실행기 경계:** 초기화/지속 ID/설정 schema/루트 탐색/주체 바인딩/공통 엔진 패키징.
2. **지속 세션:** 대화 이력과 활성 문맥, work 연결, 작업 완료 후 대기, 같은 세션의 새 작업, compact/재시작 연속성.
3. **개인 기억·저장 프로필:** 담당별 SQLite 기본, 문서 기억 선택, 기억 참조/검색 범위/선택 등록, 원문 파일 연결.
4. **다중 담당 운영 검증:** 같은 모델·사용자·호스트에서 두 담당의 문맥/기억/검색/캐시/복구가 독립되는지, 동일 세션 동시 쓰기와 이동/복제를 확인.
5. **공개된 도구/지침 경계:** 디렉터리별 skill/MCP 구성, 임시 검토 실행과 장부, 본체 쓰기 경계.
6. **선택 공유/서버 저장:** 필요한 게시판·아카이브·PostgreSQL 역할별 연결과 이행. 실제 사내 시스템 연결은 별도의 실제 계약에 맞춰 진행.

기존 가설·근거·실행·영수증·복구·도구 계약은 목표 동작을 만족하면 재사용한다. 작업마다 새 문맥을 전제로 하는 접수/세션 구성은 변경 대상이다. 기존 데이터/소스/검증 이력을 버리는 파괴적 작업은 수행하지 않는다.

## 9. 완료 판정에서 확인할 것

- 새 담당 초기화 후 같은 디렉터리에서 다시 실행하면 동일 담당과 허용된 지속 세션을 복원한다.
- X 작업 완료 뒤 Y 작업에서도 관련 합의/문맥이 남고 목표·장부는 섞이지 않는다.
- compact/재시작 뒤 활성 작업·대화 흐름·기억 조회 경로가 유지된다.
- A의 자료와 B의 개인 문맥이 자동 섞이지 않으며, 공유 자료를 읽었다고 개인 기억에 자동 등록되지 않는다.
- 디렉터리 이동/하위 폴더 실행은 정체성을 바꾸지 않고, 새 담당 복제는 원본과 다른 ID/세션을 사용한다.
- 등록되지 않은 PostgreSQL 없이 기본 실행할 수 있고, 외부 조회만 연결한 DB에는 내부 상태를 기록하지 않는다.
- 선택된 정본 장애 시 새 로컬 정본으로 조용히 갈라지지 않는다.
- 담당의 업무 도구가 공통 엔진 설치 경로를 수정할 수 없는지 배치 경계에서 검증한다.

위 항목은 아직 실행하지 않은 검증 기준이다. 이번 턴은 설계와 기본값 선정이며 전역 설치·제품 코드 변경·실제 모델/API 시험은 수행하지 않았다.

## 10. 첫 호출 시 초기 설정 — 추가 사용자 요구

사용자는 해당 디렉터리에서 호출했을 때 필요한 기존 정보가 없다면 set-up 절차를 제공해 달라고 추가했다. 명시적인 초기화 명령과 함께 첫 일반 호출에서도 현재 상태를 판별해 짧은 안내를 제공한다.

| 발견한 상태 | 기본 처리 |
|---|---|
| 담당 설정·ID·기존 상태가 없음 | 새 담당 초기 설정 |
| 정상적인 담당 설정과 상태가 있음 | 해당 담당을 열고 같은 사용자/대화 범위의 세션 이어가기 |
| 일부 설정만 없거나 손상됨 | 기존 상태/ID를 확인하는 복구 절차. 새 담당으로 자동 덮어쓰지 않음 |
| 설정/저장 schema가 현재 실행기와 호환되지 않음 | 버전/이행 절차 안내. 조용히 빈 새 저장소로 시작하지 않음 |
| 설정된 외부 저장소에 연결할 수 없음 | 연결 복구 상태 표시. 신규 SQLite 담당으로 대체하지 않음 |

첫 설정은 다음 정도로 간단하게 한다.

1. 현재 담당 루트와 기본 이름을 제시한다. 이름은 디렉터리명에서 가져올 수 있고 역할 설명은 선택 입력으로 둔다.
2. SQLite 개인 상태/기억과 파일 저장, 게시판/아카이브 비활성이라는 기본값을 적용한다. 사용자가 저장소 엔진이나 모든 기술 옵션을 처음부터 선택해야 할 필요는 없다. 고급 설정에서 다른 지원 저장소를 고를 수 있다.
3. 사용할 모델 연결을 확인한다. 이미 설정된 허용 연결 프로필을 선택할 수 있고, 없으면 필요한 연결 정보만 입력하거나 나중에 설정할 수 있다. 외부 모델/사내 MCP/게시판을 자동 탐색·호출하지 않는다. 모델 연결 미설정이면 로컬 작업공간 준비와 모델 실행 준비 상태를 구분해 표시한다.
4. 지속 ID, 최소 설정, 담당 전용 디렉터리/DB를 생성하고 원자적으로 초기화 완료 상태를 기록한다. 이후 첫 대화 세션을 열거나 연결 설정 대기 상태를 안내한다.

모델 자격증명은 설정 화면/기록에 원문을 반복 표시하지 않고 연결 프로필의 비밀 참조로 관리한다. 현재 중단된 실제 모델/API 시험을 이번 설계 논의의 초기 설정으로 재개하지 않는다.

일반 파일이 있는 디렉터리라도 담당 등록은 가능하지만 기존 파일을 덮어쓰거나 모든 파일을 자동으로 개인 장기기억에 등록하지 않는다. 이미 존재하는 .secumon 또는 DB가 설정과 일치하지 않으면 먼저 식별한다. ID가 누락되었을 때 DB의 기존 소유 정보 등으로 일관된 복구가 가능한지 확인하고, 불명확한 상태에서 새 ID를 자동 부여해 기존 기억과 분리하지 않는다.

초기화 도중 중단되면 다음 실행에서 완료된 부분을 확인하고 이어갈 수 있어야 한다. 같은 디렉터리를 두 프로세스가 동시에 처음 열어 서로 다른 담당 ID를 만들지 않도록 초기화 소유권과 완료 표시를 관리한다. 비대화형 서비스 배치에서는 동일 절차를 명시적 설정 파일/옵션으로 수행하고 입력이 부족하면 명확한 상태/오류를 반환한다.

검증에는 완전 신규·정상 재호출·부분 초기화·중복 초기화·누락 ID·모델 미설정·외부 저장 장애·기존 파일 보존을 포함한다. 첫 설정 UI와 CLI 명령은 아직 구현하지 않았다.

## 11. Markdown 기억과 SQLite 기본값의 판단 근거

사용자가 디렉터리 기반 제안의 합리성과 Codex의 Markdown 저장을 질문했다. 이 컴퓨터의 Codex 저장 영역에서 Markdown 기억 파일, JSONL 이력, SQLite 파일이 함께 존재하는 것을 읽기 전용으로 확인했다. 해당 확인은 파일 종류/경로 수준이며 자격증명·개인 대화 본문이나 DB 내부를 조회하지 않았다.

공식 OpenAI 문서는 로컬 기억 파일을 `~/.codex/memories/`에 저장한다고 설명한다. 또한 `history.jsonl` 이력과 `sqlite_home` 아래의 SQLite 기반 에이전트 작업/재개 상태를 명시한다. 따라서 기억을 문서로 표현하는 것과 실행 상태 전체를 문서 파일만으로 관리하는 것은 구분해야 한다. Codex의 모든 내부 저장/검색 구현을 파악했다는 의미는 아니다.

- [Codex 로컬 기억](https://learn.chatgpt.com/docs/customization/memories?surface=app)
- [Codex 설정과 이력 위치](https://learn.chatgpt.com/docs/config-file/config-advanced)
- [Codex SQLite 상태 저장 설정](https://learn.chatgpt.com/docs/config-file/config-reference)

우리 설계에서 Markdown은 읽고 수정할 지침·선별 경험·업무 지식을 관리하는 합리적인 선택이다. 작은 담당별 기억은 파일만으로도 시작할 수 있고, 양이 늘면 파일을 정본으로 유지하면서 재생성 가능한 검색 색인을 추가할 수 있다. Markdown 파일이라는 이유로 전체 본문을 매번 문맥에 넣을 필요는 없다.

SQLite 기본값은 자동 기록/수정, 작성자·출처·시점·적용 범위 조건 조회, 버전 확인을 일관되게 제공하려는 설계 선택이다. 모든 작업에서 Markdown보다 빠르다고 측정한 결과는 아니다. 실행 장부·재시작·자원 정산처럼 함께 갱신되어야 할 구조화 상태와 사람이 읽을 장기기억 본문의 요구는 별도로 판단한다.

이번 검토만으로 기본값이나 제품 코드를 다시 변경하지 않는다. 현재 선택한 SQLite 기본과 Markdown 기억 어댑터 지원을 유지한다. Markdown을 선택해도 담당별 기억 분리, 출처/버전, 필요한 항목 조회, 지속 세션/compact의 의미가 같아야 한다. 저장 형식 자체가 추론 능력이나 문맥 연속성을 결정하는 것은 아니다.
