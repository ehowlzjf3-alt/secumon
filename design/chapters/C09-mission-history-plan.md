## 개념과 관측한 문제

현재 사용하는 규칙 목록과 원기록 보존은 다르다. 규칙 ID가 같은 경우 이전 목표의 종료된 규칙까지 현재 규칙으로 읽어 재등록이 실패한다. 다른 ID로 우회하면 종료된 규칙이 16개 한도를 차지한다. 원 checkpoint·영수증·사건은 보존하면서 현재 목록에서 과거 목표를 정리해야 한다.

제어 확인은 현재 전체 사건 본문을 읽으며 동일 발행 영수증도 중복 조회한다. 필요한 상태 번호 구간의 원문을 페이지로 읽고 같은 검증 안의 이미 읽은 발행 영수증을 재사용한다. 저장 직전의 독립 재확인과 현재 권한 검사는 유지한다. 파일 저널은 매 조회의 원파일 검증을 유지하므로 반환량 감소를 물리 디스크 I/O 감소로 설명하지 않는다.

## 재사용·수정·추가

1. 기존 MissionRuntime, 사용자 목표 변경, 원 checkpoint/영수증, 세션과 rule ID를 재사용한다. 고정 리드–워커나 새 상주 에이전트를 만들지 않는다.
2. 실제 목표 변경 명령이 닫아 둔 과거 규칙은 새 등록 때 현재 목록에서 제외하고 원 자료·원 목표 변경 영수증을 보존한다. 현재 목표에서 같은 ID/내용의 재시도와 다른 내용 충돌은 기존 동작을 유지한다. 이전 규칙 본문의 종료 게시를 새 등록의 선행 조건으로 강제하지 않는다. 이전 source가 설정에서 제거돼도 새 규칙 등록이 가능해야 하며, 과거 본문·커서·읽기 확인은 새 목표로 가져오지 않는다. 기존 refresh의 종료 증명 검사는 그대로 둔다.
3. StateRepository에 원문 사건 페이지 조회를 추가한다. afterRevision 초과/throughRevision 이하, 선택 beforeSequence 미만, 내림차순, 최대 128개와 다음 위치를 제공한다. 선택 type은 정확히 일치하는 종류만 조회한다. memory/SQLite/file/PostgreSQL 어댑터를 연결한다.
4. 제어 증명은 해당 checkpoint 발행 뒤부터 현재 기준 상태까지의 user_command만 읽는다. 완료 복구도 최신 완료와 그 뒤의 종료 기록만 읽되 기존 원문 재구성 검사를 유지한다. 같은 검증 안의 발행 영수증 중복 조회를 없앤다.
5. 저장소 페이지 계약, 새 목표에서 규칙 재사용·용량 반환·원기록 보존, 긴 이력/다중 페이지와 재검증 거부를 확인한다. 직접 관련 기존 임무·저장소 회귀, 빌드·코어·구조 검사와 최종 소스 대조를 실행한다.

## 검증과 잔여 범위

실제 임시 SQLite/file 저장소와 결정적인 로컬 callback을 사용한다. PostgreSQL은 연결부와 가능한 SQL 계약 시험을 구분하며 실제 서버 연결은 하지 않는다. 실제 모델/API 시험 중단·사내 서비스 연결 없음 유지. 실제 Linux/native Windows·Knox·외부 A2A·모델 품질은 이번 검증 범위가 아니다.

세션 컨텍스트의 전체 비용, 장기 실행 이벤트 중복 판별 창, 다른 프로세스의 즉시 제어, 명령 ID를 갖는 resident UI 제어 및 C05/C06/C10/최종 통합 잔여는 유지한다. 변경된 자료 접근 권한이나 삭제 세대를 원기록 조회 제한 우회로 처리하지 않는다. 결과와 미완료 사항은 실행 후 별도 기록한다.

구현 중 소스 검토: 첫 build1/core1은 통과했으나 새 등록 전에 모든 과거 source를 재확인하면 제거된 source 때문에 무관한 새 등록이 막히는 회귀를 확인했다. 시험 실행 전 등록과 과거 종료 게시를 분리했다. build1 시험은 실행하지 않았고 최종 빌드에서 검증한다.
