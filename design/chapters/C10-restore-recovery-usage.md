# C10 복원 불일치 회복 준비 사용법

2026-09-08 · checkpoint391 구현 소스 기준. 같은 최종 build2에서 신규 API8개·CLI3개와 관련26개, 고유37개가 모두 통과했다. 별도 공개 CLI의 file-journal·documents 흐름도 원자료 보존과 준비 후 실행 차단을 확인했다. 실제 적용·교체·신원 재등록·새 대조는 필수 후속 단계로 남는다. [검증 결과](C10-restore-recovery-result.md) · [최종 소스 대조](../../runtime/evidence/checkpoint391-final-source.json). 실제 모델/API·현재 Linux/native Windows·PostgreSQL·설치 binary 실행은 이번에 수행하지 않았다.

외부에 처리 결과가 남아 있지만 과거 백업을 복원한 담당에는 원 실행 기록이 없을 수 있다. 이때 실패 복원본을 보존하면서, 원 기록을 포함한다고 판단해 선택한 **완전한 담당 백업**을 회복 후보로 준비한다. 외부 영수증 하나로 사라진 세션·권한·사용량 이력을 만들어 넣지 않는다.

이번 구현은 회복 패키지의 준비와 검사다. 이후 **호스트에 맞는 적용 → 담당 신원 재등록 → 새 복원에 대한 외부 기록 대조 → 일반 재개**는 필수 후속 작업으로 남아 있다. 준비 성공은 적용·목표 완료·자원 정산의 성공이 아니다. 기존 담당의 실행 차단은 준비만으로 해제되지 않는다.

## 준비 대상과 경로

현재는 로컬 전체 백업을 지원한다. SQLite 또는 file-journal 상태와 로컬 기억·문서·세션·산출물을 함께 보존한다. PostgreSQL을 선택했거나 관련 이관 상태가 있는 담당은 로컬 폴더만으로 전체 원자료를 보존할 수 없으므로 거절한다. 원격 전체 snapshot 경로와의 연결은 후속 범위다.

선택 백업은 다음 조건을 충족해야 한다.

- 현재 담당과 정확히 같은 담당 신원 및 원래 경로를 가진, 기존 백업 검사에 통과하는 전체 백업이다.
- 사용자가 지정한 백업 지문, 백업 내부 identity/config, 엔진 고정 정보가 서로 맞는다.
- 파일 이름이나 생성 시각이 나중이라는 이유만으로 최신·정답이라고 판정하지 않는다. 원 업무·영수증·사용량 등을 포함하는지 실제 기록을 확인해 선택해야 한다.

담당, 원백업, 새 회복 폴더, 호스트 신원 등록표와 엔진 설치 폴더는 서로 겹치지 않아야 한다. 소유자만 관리하는 비공개 폴더를 사용하고, 명령에는 대상이 분명한 절대경로를 권장한다. `--directory`를 생략하면 기존 lifecycle 명령처럼 현재 디렉터리를 사용한다. 출력 대상 `--destination`은 아직 없는 새 경로여야 하며 기존 담당이나 실패한 출력 폴더를 덮어쓰지 않는다.

## CLI 사용

담당 실행기, 구형 엔진과 직접 DB 접근을 중지한 후 진행한다. `--offline`은 이 조건의 명시이며 코어가 다른 프로그램을 대신 종료하는 옵션은 아니다. 원래 담당의 신원이 현재 복원 디렉터리에 등록되어 있어야 한다. 호스트가 별도 신원 등록 경로를 사용한다면 기존처럼 같은 설정을 전달하는 호스트 시작 프로그램을 사용한다.

먼저 기존 백업 검사와 신원 조회로 사용할 지문을 확인한다.

```sh
secumon-agent lifecycle verify-backup --source "<선택 백업 절대경로>" --json
secumon-agent lifecycle identity-status --directory "<현재 복원 담당 절대경로>" --json
```

`--digest`에는 선택 백업의 `manifest.digest`, `--previous`에는 현재 호스트 신원 등록의 `registration.digest`를 사용한다. 지문은 특정 원문·등록 내용을 식별하는 비교값이다. `--operation`은 이번 준비를 식별할 UUID 형식의 작업 번호다.

```sh
secumon-agent lifecycle restore-recovery-prepare --directory "<현재 복원 담당 절대경로>" --source "<선택 백업 절대경로>" --destination "<새 회복 폴더 절대경로>" --digest "<선택 백업 SHA256>" --previous "<현재 호스트 신원 head SHA256>" --operation "<이번 준비 UUID>" --offline --json
```

준비 과정은 담당의 유지보수 잠금과 신원 검사를 사용한다. 원자료·선택 백업·신원·잠금이 준비 중 바뀌면 성공으로 처리하지 않는다. 모델·도구·메신저를 실행하거나 외부 기록을 대조하는 명령은 아니다.

CLI는 다음과 같은 요약만 출력한다.

| 출력 | 의미 |
| --- | --- |
| `directory`, `manifestPath` | 회복 폴더와 상세 명세 `recovery.json`의 위치 |
| `preservedPath`, `selectedBackupPath` | 보존 복원본과 선택 백업의 실제 복사본 위치 |
| `operationId`, `agentId`, `targetRoot` | 준비 작업 번호, 담당 ID, 원래 담당 경로 |
| `digest`, `selectedBackupDigest` | 준비 명세와 선택 백업의 지문 |
| `activation: "not_applied"` | 준비 묶음을 만들었으며 원 담당에 적용하지 않았다는 기록 |
| `changes` | 선택 백업 기준의 추가·제거·변경·동일 항목 개수 |

전체 파일 목록과 지문은 디스크의 `recovery.json`에 남긴다. 원문 전체나 파일 목록을 매번 CLI 출력·에이전트 문맥에 넣지 않는다. 관리 표식 차이도 비교에 포함되므로 변경 개수를 복구한 업무 수나 손실량으로 해석하지 않는다. 파일 차이는 두 업무 이력이 같은 흐름으로 이어진다는 증명도 아니다.

## 생성되는 패키지와 검사

```text
<새 회복 폴더>/
  recovery.json
  preserved/
  selected-backup/
    backup.json
    data/
```

`preserved/`에는 현재 복원본의 자료와 복원 완료·대조 영수증·임시 게시 표식을 원문 그대로 보존한다. 살아 있는 runtime lease와 준비 명령 자신의 유지보수 기록만 제외한다. `selected-backup/`에는 지정한 원백업 전체를 복사한다. 선택 백업의 데이터 일부를 추출해 현재 DB에 덮어쓰지 않는다.

`recovery.json`은 양쪽 원문 복사·지문 대조가 끝난 뒤 마지막에 게시한다. 명세에는 원 신원 head, 복원 표식 지문, 양쪽 자료 목록과 지문, 비교 결과가 들어간다. 이것은 고정된 원자료의 준비 묶음이며 운영체제 수준의 수정 불가능 잠금을 뜻하지 않는다. 내용이 바뀌면 이후 검사가 이를 거절한다.

```sh
secumon-agent lifecycle restore-recovery-status --source "<회복 폴더 절대경로>" --json
```

상태 명령은 준비 패키지의 실제 파일과 명세·원백업을 다시 검사해 같은 요약을 출력한다. 현재 담당 디렉터리나 외부 시스템이 여전히 준비 당시와 같다는 뜻은 아니다. 이 결과만으로 적용하거나 실행을 재개할 수 없다.

## 중단과 남은 적용 단계

준비가 실패해도 원 담당·원백업을 수정하거나 실패 출력물을 자동 삭제하지 않는다. 부분 출력은 증거로 보존한다. `recovery.json`이 없으면 패키지는 미완료이며 검사에서 `agent_restore_recovery_incomplete`가 나온다. 명세와 실제 복사본이 다르면 검사 실패로 남긴다. 기존 출력 경로를 재사용하지 말고 원자료 상태를 확인한 후 별도의 새 경로로 준비한다.

동일한 준비 패키지의 조회는 가능하지만 준비 명령을 같은 destination에 반복해 덮어쓰지는 않는다. `operationId`는 준비 묶음의 식별자이며, 중단된 폴더 복사를 자동 이어주는 적용 저널은 아니다.

다음 적용 구현은 준비 당시 원자료가 현재도 같은지 확인하고 현재 담당을 정확한 디렉터리 객체 기준으로 보존 이동해야 한다. 이어서 비어 있는 원경로에 선택 백업을 복원하고, 신원을 재등록한 뒤 [외부 기록 대조](C10-restore-reconciliation-usage.md)를 새로 수행해야 한다. 두 이력의 자동 병합이나 한 이력이 다른 이력의 앞부분이라는 자동 판정은 제공하지 않는다. 원기록 교체에 따른 차이는 적용 전에 검토할 대상으로 유지한다.

현재 단위에서 자동 적용·폴더 교체·기존 차단 해제는 구현하지 않았다. 이것은 전체 회복 목표의 완료가 아니며 호스트별 적용과 중단 복구는 다음 필수 작업이다. native Windows runtime, 실제 PostgreSQL·사내 MCP·Knox·A2A 등의 운영 환경은 이번 사용법으로 검증된 것으로 보지 않는다. 실제 모델/API 시험 중단을 유지한다.

비용은 원자료 두 벌의 읽기·복사·재검사에 따른다. 기존 lifecycle 한도를 재사용하며 패키지 전체 4 GiB, 파일 하나 1 GiB, 항목 100,000개 제한을 적용한다. 준비 명세는 최대 32 MiB다. 큰 자료를 복사하는 시간을 모델 추론 비용이나 외부 도구 호출 절감으로 표현하지 않는다.
