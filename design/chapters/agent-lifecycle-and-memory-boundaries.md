# 상주 에이전트·작업 자원·기억 경계 정리

사용자는 여러 업무 담당 에이전트를 지속적으로 운영하고, compact로 문맥 상태를 관리하면서 각 담당의 단기·장기기억이 확실히 분리되기를 원한다. 과거 여러 에이전트의 대화기록을 같은 DB에 저장하면서 서로 간섭한 경험을 설명했다. 과거 시스템의 구체적 원인을 이번에 재현하거나 확인한 것은 아니다.

이 문서는 현재 구현 사실, 사용자에게 확인된 요구, 구현 후보를 구분한다. 제품·HTML 변경, 실제 모델/API 연결, 상주 서비스 실행은 수행하지 않는다. 기존 `P4-design-reconciliation.md`의 검토 우선 상태를 유지한다.

**후속 확인 우선:** 사용자는 작업 완료마다 담당의 문맥을 버리고 새로 시작하는 기본 흐름을 원하지 않는다. 같은 담당의 이어지는 대화/업무 흐름은 작업 경계를 넘어 문맥을 유지해야 한다. 아래 작업별 분리는 계획·상태·장부의 분리이며, 작업마다 새 대화 문맥을 강제한다는 의미로 적용하지 않는다. 현재 구현과 이 요구의 차이는 9절에 기록한다.

## 1. 이번에 확인한 핵심 요구

- 업무 담당 에이전트는 한 질문이 끝나도 정체성·장기기억을 유지한다. 상주 운영과 compact/재개를 지원해야 한다.
- 여러 에이전트의 단기 문맥과 개인 장기기억은 분리되어야 한다. 같은 사용자·모델·DB를 사용해도 자동으로 섞이지 않아야 한다.
- 단기기억은 현재 모델 문맥에, 장기기억은 영속 공간에 두고 문맥에서 찾아갈 수 있어야 한다. 대화 원문 이력은 둘과 구분한다.
- 같은 담당과 이어지는 대화에서는 개별 작업이 끝나도 문맥을 유지한다. compact는 문맥 크기/관련성 관리에 따라 수행하며 작업 완료가 문맥 초기화 조건이 되지 않는다.
- 저장 방식의 후보는 PostgreSQL, SQLite, 파일 디렉터리로 명시적으로 구분한다. 아카이브에서 읽은 자료를 개인 장기기억에 자동 등록하지 않는다.
- 게시판은 서로의 경험에 대해 질문하고 답변하는 선택 기능이다.
- 아카이브는 성공·실패·유의미한 대화와 사례를 보존/조회하는 선택 기능이다. 에이전트 등록과 기존 시스템 조회를 모두 고려한다.
- 범용 코어가 특정 게시판·아카이브 형식, 특정 DB, 모든 업무의 공유 지식 흐름을 강제하지 않아야 한다.

## 2. 자원이 붙는 대상과 에이전트 수명

현재 `WorkState`에 `budget`이 있고 위임 장부는 `parentWorkId`와 `childWorkId`를 연결한다. `BoardFunding`도 특정 요청을 수행하는 자식 작업을 만든다. 자원이 직접 붙는 대상은 에이전트라는 지속적 존재 자체가 아니라 목표를 가진 작업이다. 수행자는 임시 서브에이전트나 기존 담당 에이전트일 수 있다.

| 구분 | 의미 | 수명 |
|---|---|---|
| 담당 에이전트 | 역할·지속 식별자·장기기억·수신 경로를 가진 운영 단위 | 여러 작업과 프로세스 재시작을 가로질러 유지 |
| 작업(work) | 목표·완료 조건·계획·근거·실행 상태를 가진 처리 단위 | 한 번의 조회부터 여러 날의 후속 업무까지 |
| 실행 구간 | 현재 문맥에서 진행하는 작업의 일부 | compact, 대기, 재시작을 거쳐 여러 구간으로 나뉠 수 있음 |
| 자원 장부 | 그 작업의 모델/도구 호출·토큰·재계획 사용량과 배정량 | 사용 이력 유지, 작업/위임 종료 시 정산 |

질문 한 개와 작업 한 개는 반드시 일치하지 않는다. 같은 목표에 관한 추가 질문은 기존 작업을 갱신할 수 있고, 하나의 요청이 여러 작업으로 나뉠 수도 있다. 계속 감시하는 담당 역할의 존재와 유한한 개별 분석 작업을 구분하면, 분석이 끝나도 담당은 다음 사건을 기다리며 유지된다.

자원 배정은 동시 작업들이 같은 가용량을 중복 사용하지 않게 하고, 어느 업무가 얼마를 사용했는지 기록하기 위한 것이다. 현재 의미는 논리적인 호출/토큰 장부이며 모델 가중치·GPU 메모리를 에이전트별로 나누는 기능이 아니다. 물리적인 동시 실행 용량은 별도 운영 계층의 관심사다.

compact는 현재 입력 문맥의 크기를 관리하는 동작이다. 누적 사용 토큰을 지우거나 이미 사용한 자원을 반환하지 않는다. 반환은 위임에 잡아 둔 미사용 여유분을 정산 후 다시 사용할 수 있게 하는 의미다. 작업 자원 부족을 에이전트의 정체성 삭제나 장기기억 폐기로 연결하지 않는다.

상주 운영에는 역할별 수신함/예약·진행 중 작업 목록·재시작 시 동일 정체성 복원 경로가 필요하다. 프로세스는 떠 있어도 사건이나 진행할 일이 없으면 모델 호출 없이 대기할 수 있다. 기존 유한 work를 무조건 무한 기한으로 바꾸는 구현만으로 상주 운영을 완성했다고 볼 수 없다.

기간별 운영 자원을 사용한다면 담당 에이전트가 기간 풀에서 작업에 자원을 배정하거나 추가 요청하는 구성을 둘 수 있다. 기간 풀이나 보충 정책은 아직 구현 확정이 아니며, 에이전트 생애 전체에 고정 총량을 부여할 필요는 없다. 에이전트의 배정/추가 요청/회수 판단과 런타임의 기록·집행·정산은 기존 요구를 유지한다.

## 3. 사용자 개념 네 가지와 필수 복구 상태

| 개념 | 무엇을 담는가 | 기본 소유/공유 | 코어의 관계 |
|---|---|---|---|
| 단기기억 | 현재 모델 입력에 들어가는 목표, 대화 일부, 작업 상태, 읽어온 자료 | 담당별 지속 대화 문맥, 필요 시 독립 작업 문맥 | 각 실행의 필수 기능 |
| 장기기억 | 해당 담당이 여러 작업에서 재사용할 지식·경험·선호·절차와 출처 | 에이전트 소유 공간, 명시적인 공유 공간은 별도 | 장기 운영에 필요한 독립 저장/조회 계약 |
| 게시판 | 질문·답변·관측·후속 요청과 담당/진행 상태 | 선택한 게시판의 참여자 | 선택 연결 기능 |
| 아카이브 | 성공/실패 사례, 보관할 대화, 산출물·근거·당시 판단과 적용 범위 | 개인/프로젝트/팀 등 배치가 선택 | 선택 자료 공급자/보관 기능 |

이 네 가지 아래에는 작업의 영속 정본이 필요하다. 진행 중 목표·가설·계획·미완료 도구 호출·대기 조건·반론·사용량·체크포인트는 아카이브를 끄더라도 저장되어야 한다. 사용자가 별도로 사례를 등록해야만 재시작할 수 있게 만들지 않는다.

컨텍스트를 복구하기 위해 요약이나 대화 일부를 DB에 저장했다고 해서 그 기록이 곧바로 재사용할 장기기억이 되는 것은 아니다. 대화 이력은 이력이고, 장기기억은 선별된 기록이다. 아카이브의 모든 사례를 모든 에이전트의 개인 기억에 자동으로 복사하지 않는다.

장기기억에서 읽은 기록도 현재 판단에 사용할 때는 단기 문맥에 들어온다. 저장된 원본은 장기 공간에 남고 현재 문맥에는 필요한 내용과 참조만 들어간다. compact 후에는 목표·미해결 작업과 기억 조회 경로를 보존하고 필요한 자료를 다시 읽는다.

## 4. 가장 먼저 명확히 할 격리 계약

권고하는 논리 식별자는 다음과 같다. 기존 코드에 모두 구현된 필드라는 의미는 아니다.

- `agentId`: 재시작 뒤에도 유지되는 담당 에이전트의 식별자. 같은 사람이 만든 여러 에이전트도 각각 다르게 가진다.
- `workId`: 그 담당이 수행하는 특정 목표/작업의 식별자.
- `sessionId`: 대화나 모델 문맥 흐름을 구분하는 식별자. 표시용 메신저 방 번호와 내부 문맥 소유권을 동일시하지 않는다.
- 조직 경계가 있으면 그 위에 조직 식별자를 둔다. 단일 조직 설치에 불필요한 운영 기능까지 강제하지 않는다.

에이전트 A의 같은 대화 흐름에서는 작업 X가 끝나고 작업 Y를 시작해도 지속 문맥을 유지한다. X와 Y의 목표·계획·완료 조건·자원 장부는 구분하고, 현재 실행 대상이 무엇인지 표시한다. A의 별도 사용자 대화나 독립 병렬 작업은 다른 문맥으로 분기할 수 있지만 모든 작업에 분기를 강제하지 않는다. 에이전트 B는 B의 문맥과 기억 공간을 사용한다. A와 B의 자료 공유는 지정된 게시판/공유 자료 조회를 통해 명시적으로 일어난다.

소유 범위의 예:

```text
담당 A (지속 정체성)
  ├─ 이어지는 대화 문맥 · compact 요약 · 체크포인트
  │    └─ 작업 X 수행 → 문맥 유지 → 작업 Y 수행
  ├─ 작업 X / Y의 개별 목표 · 실행 상태 · 자원 장부
  ├─ 필요한 경우에만 별도 대화/병렬 작업 문맥
  └─ A의 장기기억 · 검색 공간

담당 B (지속 정체성)
  ├─ B의 지속 대화 문맥 · 요약 · 체크포인트
  ├─ 작업 Z의 개별 목표 · 실행 상태 · 자원 장부
  └─ B의 장기기억 · 검색 공간

선택 연결: 공유 게시판 / 사례 아카이브 / 사내 자료 시스템
```

같은 DB에 저장하는 배치를 허용하되 모든 저장/조회 경로에서 소유 범위를 지킨다. 대화 메시지뿐 아니라 compact 요약·체크포인트·기억 검색·색인·캐시·작업 파일·수신/전달 경로가 같은 구분을 사용해야 한다. 업무 문맥은 현재 작업으로, 개인 기억 검색은 현재 담당의 기억 공간으로 기본 범위를 한정한다. 공유 자료를 읽더라도 그것이 다른 담당의 대화나 개인 기억을 자동 편입한다는 의미가 되어서는 안 된다.

모델이 도구 인자로 임의의 agentId를 입력했다고 그 에이전트의 권한을 얻으면 안 된다. 호스트가 인증된 실행 맥락에 담당과 기억 공간을 연결하고 adapter가 범위를 적용한다. 모델에는 ‘내 기억 검색’처럼 이미 범위가 정해진 기능과 필요한 공유 자료 연결만 보인다. 현재 실행 주체(principal)와 에이전트 정체성의 연결 방법은 구현 단계에서 정하되, 여러 에이전트가 같은 사용자 계정이나 외부 시스템 자격증명을 사용한다는 이유로 기억 소유권까지 합치지 않는다.

별도 DB/파일 디렉터리 배치도 선택할 수 있다. 물리 분리 유무와 무관하게 같은 격리 계약을 유지하고, 어댑터를 바꿔도 같은 검증을 적용해야 한다. 현재 사용자가 보고한 과거 문제의 원인을 DB 공유 자체라고 단정하지 않는다.

## 5. 게시판과 아카이브를 선택적으로 연결하기

코어는 구체적인 DB 테이블·티켓 형식·사내 시스템을 알지 않고 작은 계약을 통해 연결한다. 제품의 모든 기능을 빈 객체로라도 반드시 켜두는 방식은 피한다.

| 배치 | 필요한 연결의 예 |
|---|---|
| 개인 업무 담당 | 자신의 문맥·장기기억·작업 정본 |
| 여러 담당의 협업 | 위 구성 + 게시판 또는 동료 요청/응답 연결 |
| 사례를 축적하는 팀 | 위 구성 + 사례 저장/검색 아카이브 |
| 기존 사례 시스템이 있는 조직 | 해당 시스템의 조회 adapter, 필요할 때만 등록 기능 |

게시판의 최소 의미는 글/질문/답변/참조와 후속 요청 상태다. 아카이브의 최소 의미는 사례 검색과 참조로 읽기이며, 등록 기능은 지원하는 공급자에서만 노출한다. 기존 시스템이 읽기만 지원하면 등록을 필수로 요구하지 않는다. 미연결 기능의 도구나 지침은 해당 에이전트 문맥에 로드하지 않는다.

아카이브는 원문 형식을 통일하기보다 필요한 공통 정보만 연결하는 방식을 후보로 둔다: 제목/요약, 자료 참조, 출처·시점·버전, 사례 종류·결과(알려진 경우), 적용 범위, 사용 권한. 나머지는 공급자별 본문으로 유지한다. 실패 분석·완료 작업·대화는 서로 다른 사례 유형으로 확장할 수 있다. 모든 자료에 성공/실패 값을 억지로 붙이지 않는다.

등록은 에이전트가 의미 있는 경험을 제안하거나, 시스템이 정해진 사건을 수집하는 경로를 둘 수 있다. 게시판 답변을 장기 보존할 때 사례로 연결할 수 있지만 모든 글이 자동 승격될 필요는 없다. 이미 보관된 실행 기록을 참조할 수 있으면 원문을 중복 복제하지 않는다. 외부 원문이 삭제되거나 바뀌었으면 참조의 현재 상태와 과거 보관본을 구분한다.

자산·SIEM·EDR 같은 현재 시스템 조회는 사례 아카이브와 별도 자료 도구로 남을 수 있다. 기존 시스템에 사례 기록이 있을 때는 그 부분만 아카이브 adapter로 연결한다. 범용 코어에 보안 업무 전용 분류를 하드코딩하지 않는다.

현재 개인/공유 기억 구현에는 별도 검토된 공유 기록 정책이 있다. 이 기존 정책을 모든 게시판 대화나 모든 아카이브 등록에 자동으로 강제하는 것은 이번 요구가 아니다. 개인 기억의 소유권 분리, 공유 글의 가시성, 사례의 검증 상태는 각각 정해야 한다.

## 6. 현재 코드에서 확인한 사실과 남은 차이

| 코드 | 확인한 사실 | 이번 요구와의 차이 |
|---|---|---|
| `domain/model.ts`의 WorkState | 작업별 목표·문맥 참조·예산·가설·실행 기록 | 지속 담당과 여러 작업을 묶는 운영 계약은 별도 필요 |
| `domain/budget-delegation.ts`, `application/board-funding.ts` | 자원 장부는 작업 간 배정 | 담당 생애 자원이나 모든 협업의 조직도로 해석하지 않음 |
| `domain/knowledge.ts` | 조직·namespace·scope·작성 주체와 개인/공유 가시성 검사 | 별도 agentId 기반 개인 기억 자동 생성/바인딩 계약은 없음 |
| `application/knowledge-tools.ts` | 기억 읽기/검색 시 인증된 주체와 현재 업무 범위를 사용 | 호스트의 지속 담당→주체/기억 공간 연결을 명확히 해야 함 |
| `presentation/local-profile.ts` | 합성 로컬 프로필은 synthetic/learner와 local namespace 사용 | 같은 설정을 여러 담당의 자동 분리 구현으로 제시할 수 없음 |
| `infrastructure/local-channel.ts` | 메시지를 조직·주체·채널·conversationId로 조회 | 메신저 방/사용자와 담당/업무 문맥의 라우팅 규칙 보강 필요 |
| `application/compose-runtime.ts` | board와 knowledge를 선택적으로 주입 | 게시판의 선택 연결 기반은 있음. 범용 아카이브 공급자 계약은 별도 검토 필요 |

서로 다른 주체·기억 공간을 검사하는 기존 기반은 있으나 ‘같은 사용자가 만든 여러 담당을 같은 DB에 띄우면 기본적으로 개인 기억이 완전히 분리된다’는 제품 수준 계약이 완료됐다고 주장하지 않는다. 기존 로컬 시험 이력은 있으나 이번 턴에 새 시험을 실행하거나 과거 혼입 현상을 재현하지 않았다.

## 7. 구현 순서 후보와 완료 기준

우선순위는 게시판/아카이브 확장보다 담당 정체성과 개인 기억의 분리다.

1. 지속 담당 식별자, 인증된 실행 주체, 작업/대화 문맥, 개인 기억 공간의 관계를 정한다. 실제 저장소 포맷을 정하기 전에 분리 기준을 합의한다.
2. 같은 DB·같은 사용자·같은 모델로 두 담당을 실행하는 로컬 검증을 준비한다. A의 이어지는 대화는 작업 X→Y에서도 유지되고 B의 문맥은 섞이지 않아야 한다. A 내부의 서로 다른 작업 목표/장부와 별도 대화 세션도 구분되어야 한다.
3. 문맥 생성·검색·요약·캐시·체크포인트·재시작·메신저 라우팅에서 같은 소유 범위를 적용한다. 본문 직접 읽기와 검색 결과 모두 확인한다.
4. 대기/이벤트 재개와 여러 작업 관리로 상주 역할의 수명을 연결한다. 작업 완료·자원 소진·compact가 담당 정체성이나 개인 기억을 지우지 않아야 한다.
5. 게시판/아카이브를 선택 연결로 구성한다. 미연결, 읽기 전용 외부 사례 시스템, 등록 가능한 사례 저장소 각각을 확인한다.
6. 명시적으로 공유된 한 사례를 다른 담당이 읽을 수 있되 작성자의 다른 개인 기억/대화는 따라오지 않는지 확인한다.

이 완료 기준은 앞으로의 검증 요구이며 이번 턴의 통과 결과가 아니다. 필요 조건을 만족하는 기존 코드와 adapter는 재사용하고 불필요한 전면 재작성은 하지 않는다.

## 8. 파일 경로·DB 참조와 저장 효율 — 추가 요구 반영

사용자가 기억의 경로가 파일일 수도 DB일 수도 있으며 효율을 비교해 달라고 추가했다. 물리 저장 위치와 에이전트가 사용하는 참조를 분리하는 안을 추천한다.

예를 들어 ‘내 기억의 항목 42’라는 논리 참조를 런타임이 현재 담당의 소유 범위에서 해석한다. 파일 adapter는 허용된 디렉터리의 파일/구간으로, DB adapter는 레코드로, 외부 자료 adapter는 기존 시스템의 자료 ID로 연결할 수 있다. 참조의 구체 표기나 API는 아직 확정하지 않는다. 참조를 알고 있다는 것 자체가 접근 권한을 뜻하지 않으며 DB 접속 정보가 모델 문맥에 들어갈 필요도 없다.

| 저장 형태 | 장점/적합한 사용 | 별도로 필요한 것 |
|---|---|---|
| 텍스트 파일 | 사람이 직접 읽고 편집할 노트, 작은 독립 자료, 반출/복사 | 범위 있는 경로 해석, 원자적 갱신/버전 충돌 처리, 양이 늘면 검색 색인 |
| 구조화 DB | 작업 상태·소유권·검색 조건·기억 메타데이터·동시 갱신 관리 | schema/adapter와 운영·백업 전략 |
| 파일 본문 + DB 색인/참조 | 큰 원문을 보관하면서 제목·소유자·시점으로 필요한 항목 검색 | 파일과 메타데이터의 버전/완결성 확인, 복구 시 일치 검사 |
| 기존 사내 시스템 연결 | 이미 관리되는 사례/지식을 중복 저장하지 않고 조회 | 공급자가 지원하는 검색·읽기·등록 계약과 자료 신선도/접근 처리 |

이 구분에서 SQLite는 파일에 저장되는 DB이므로 ‘파일 대 DB’는 엄밀하게는 일반 문서 파일과 구조화 저장/조회 방식의 비교다. 저장 매체 하나가 항상 더 빠르다고 단정하지 않는다.

현재 프로젝트의 로컬 단일 호스트 기준 제안은 구조화된 작업 상태와 기억 메타데이터/작은 본문에는 기존 SQLite 기반을 재사용하고, 문서·이미지·큰 로그 등 원본에는 파일 artifact 저장을 활용하는 것이다. 사용자가 직접 관리할 노트는 파일로 제공할 수 있으며, 파일을 정본으로 삼을지 편집용 내보내기로 삼을지 구분해 이중 정본을 만들지 않는다. 이는 초기 운영 후보이고 PostgreSQL 또는 특정 물리 배치를 코어 필수 조건으로 채택한 것이 아니다.

SQLite 공식 문서는 로컬 응용 저장에 적합한 용도와 다중 호스트/많은 동시 쓰기에서 서버형 DB가 적합할 수 있는 조건을 구분한다. 특히 DB 파일 하나에는 동시에 하나의 쓰기 작업만 허용된다. 다중 서버 확장 여부와 실제 쓰기 경합을 확인해 adapter를 선택한다. [SQLite의 적합한 사용 범위](https://www.sqlite.org/whentouse.html)

에이전트 관점의 효율은 저장 장치 속도와 함께 조회 결과의 크기/관련성을 측정해야 한다. 처음부터 모든 장기기억 본문이나 모든 tool 명세를 모델 입력에 싣지 않고, 현재 담당/작업으로 범위를 정한 검색→제목·짧은 설명·참조→선택 항목 읽기 순서를 지원한다. 작은 결과가 이미 충분하면 불필요한 두 번째 호출을 강제하지 않는다. 파일은 필요한 구간을, DB는 필요한 필드/레코드를 반환할 수 있어야 한다.

비교할 지표는 대표 업무의 검색/읽기 지연, 동시 쓰기 경합, 문맥에 들어간 토큰/바이트, 도구 호출 수, 관련 기억 회수와 무관한 기억 혼입, compact/재시작 복구 시간이다. 저장소를 바꿔도 담당별 격리·현재 버전 확인·삭제/정정 반영 계약은 동일하게 검증한다. 이번 턴에 성능 비교를 실행한 것은 아니다.

## 9. 작업 완료 후 지속 문맥 — 현재 구현과 목표 동작

사용자는 ‘작업 하나를 하고 컨텍스트를 버리고 새로 시작하는 구조’인지 질문하며 그 방식은 원하지 않는다고 명확히 했다. 이전의 작업별 분리 설명을 담당의 대화 초기화로 해석하지 않도록 요구와 코드의 차이를 기록한다.

### 현재 확인한 사실

- `ConversationService.accept`와 합성 `LocalWorkbench.accept`는 새 접수에서 `newWork`를 호출한다. 초기 계획·근거·시도 등이 비어 있는 작업 상태를 만들고 이전 작업의 문맥 참조를 자동 연결하지 않는다.
- `ContextFrameStore`는 프레임의 `workId`가 현재 작업과 같은지 확인한다. `ContextRecovery.restore`도 지정한 work의 정본에서 재개 문맥을 구성한다.
- 따라서 같은 작업에서 계속 실행하거나 compact/재시작 뒤 복구하는 기반과, 여러 작업을 가로지르는 담당의 지속 대화 문맥은 별개다. 후자는 아직 구현 완료가 아니다.
- 기존 업무 상태·원문·기억을 작업 완료 때 모두 삭제하는 코드는 이번 확인 경로에 없었다. ‘데이터 삭제’와 ‘새 작업 문맥에 이전 맥락이 자동 포함되지 않음’을 구분한다. 매 모델 호출에 대화 전체를 그대로 전달한다는 주장도 하지 않는다.

### 목표 동작

담당의 지속 정체성 아래에 계속되는 대화 문맥을 둔다. 같은 흐름의 새 작업은 새 목표/장부를 만들 수 있지만 대화 문맥을 자동으로 초기화하지 않는다. 작업 완료는 그 목표의 종료 상태를 뜻하며 담당·대화 세션의 종료를 뜻하지 않는다.

문맥에서는 현재 작업의 목표/완료 기준을 분명하게 표시하고 지난 작업은 완료된 기록으로 구분한다. 지난 결론을 새 작업의 현재 사실로 자동 승격하지 않는다. 오래된 대화나 큰 도구 결과는 관련성/용량에 따라 compact하고 원문 참조를 남긴다. 현재 결정에 필요한 제약·핵심 대화·미해결 질문·진행 작업과 기억 조회 경로를 유지한다. 모든 원문을 영원히 모델 입력에 싣는 요구는 아니다.

연속성에는 장기기억 등록이 필수 선행 조건이 아니다. 아카이브 검색 결과는 현재 문맥에서 사용하고, 더는 필요하지 않으면 활성 문맥에서 정리할 수 있다. 업무 근거/호출 기록에 필요한 참조는 보존하되, 담당이 재사용할 가치가 있다고 판단한 항목만 개인 장기기억에 별도 등록한다. ‘사용한 자료’와 ‘개인 기억으로 채택한 자료’를 구분한다.

### 구현 후보와 검증 기준

기존 작업 엔진 위에 담당의 지속 세션 상태와 현재 작업 연결을 관리하는 책임을 추가하는 안을 우선 검토한다. 작업 완료 후 세션을 닫는 기본 동작을 두지 않고, 새 접수는 기존 작업의 후속인지 같은 세션의 새 작업인지 판단한다. 명시적인 새 대화, 별도 사용자/업무 경계, 독립 병렬 처리가 필요한 경우에는 문맥을 나눌 수 있다.

다음 항목은 앞으로 검증해야 할 사항이다.

1. A의 작업 X에서 합의한 조건을 같은 대화의 Y가 이어서 사용할 수 있고, X 완료가 문맥 초기화를 일으키지 않는다.
2. A의 지속 문맥을 B가 자동으로 받지 않는다. 다른 대화 세션도 분리된다.
3. X와 Y의 목표·근거의 현재성·완료 조건·사용량이 서로 덮어써지지 않는다.
4. compact/재시작 뒤 같은 담당과 대화 흐름·진행 작업 연결을 복원한다.
