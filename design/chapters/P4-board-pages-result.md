# 게시판을 필요한 크기로 읽기

2026-09-06 · v0.44 · 조회 서비스 검증 완료 · P4-01 진행 중

## 이번에 배울 개념

대화가 길어져도 매번 게시판 전체를 모델 입력에 넣을 필요는 없다. 현재 업무가 접근할 수 있는 글을 대상별로 골라 제한된 페이지로 읽을 수 있다. 그러나 페이지의 마지막에 도달한 사실은 모든 자료를 수집했거나 반증이 없다는 뜻이 아니다. 게시판 접근 권한 밖의 글, 현재 유효하지 않은 글, 게시판에 아직 올라오지 않은 자료가 있을 수 있다.

가설도 증거가 생긴 뒤에만 적을 수 있게 하면 초기 탐색을 표현하기 어렵다. 이제 근거 없는 가설을 저장하고 `unverified`로 표시한다. 실제 출처를 인용한 글에는 `cited`를 표시하며, 이것도 글의 해석이 검증됐다는 뜻은 아니다. 원 출처의 `complete/partial/unknown`을 각 인용에 표시한다. 독립 출처 수와 자료의 완전성은 서로 다른 조건이다.

## 구현 결과

- `BoardService.readPage`는 현재 역할과 소비 업무의 주체·scope·허용 등급을 함께 확인한다. 대상 entity 필터, 글 수 1~20개, 전체 응답 JSON의 UTF-8 바이트 1,024~32,768 한도를 적용한다.
- 각 글의 본문과 인용을 온전히 반환한다. 다음 글까지 넣으면 한도를 넘는 경우 다음 페이지로 넘긴다. 글 하나도 들어가지 않으면 `board_page_item_too_large`를 반환하므로 더 큰 한도로 다시 읽을 수 있다.
- cursor는 게시판 revision과 마지막 반환 글을 가리킨다. 같은 revision에서는 저장소를 닫았다 열어도 이어갈 수 있다. 게시판이 바뀌면 `board_cursor_stale`, 마지막 글에 접근할 수 없게 되면 `board_cursor_invalid`로 처음부터 현재 상태를 조회하게 한다.
- 페이지의 entity와 출처 집계는 반환한 글만 기준으로 한다. `discussion_not_independent_evidence`, `permitted_current_posts_only`, `returned_posts_only`를 명시하며 새 WorkState Evidence를 생성하지 않는다. 요청 의무의 상태를 페이지에 섞어 오래된 상태를 재사용하게 하지 않는다.
- 같은 조회 안에서는 출처 검증을 재사용한다. 새 조회는 다시 확인한다. 5개 독립 출처 중 첫 글 1개를 요청한 시험에서는 본문 1개와 다음 페이지 유무 확인용 1개, 총 원본 2개만 읽었다.
- 근거 없는 가설은 저장·재열기가 가능하고 독립 사실·완료 답변으로 인정되지 않는다. 인용이 없어도 작성 업무에 남은 기억 입력 의존성을 검증하므로, 인용 삭제로 이미 무효가 된 입력 검증을 우회할 수 없다.

## 검증

관련 81/81개가 통과했다. 게시판 63개와 기억 도구 18개이며 이번 신규 시험은 20개다. 두 역할·문서/관측 업무·SQLite/파일 저널의 페이지 이어가기, UTF-8 크기, coverage, 가설, 권한·철회·cursor·조회 중 변경을 확인했다. 원본 5개 중 첫 페이지를 읽는 비용을 별도로 확인했다.

전체 `npm run verify`는 **2,180/2,180**, 실패·취소·skip 0으로 통과했다(305580.099625ms). 빌드·코어 타입, 계층 108파일/위반 0, 합성 4개 시나리오/22개 체크포인트도 통과했다. [실행 기록](/Users/seunghanee/Documents/secumon/runtime/evidence/P4-board-pages-local-verification.json)에 명령·시각·로그와 현재 빌드 정보를 저장했다. 초기 타입 검사에서 선택 필드와 `exactOptionalPropertyTypes`의 불일치를 발견해 도메인 계약을 맞췄고, 그 뒤 빌드·관련 시험을 통과했다.

## 남은 연결과 한계

이 결과는 조회 서비스의 구현이다. 아직 에이전트 도구 목록에 등록하지 않았고, 반환한 페이지를 저장한 뒤 모델·다음 도구·compact·완료·전달 시점에 원 게시글을 재검증하는 공통 입력 계층은 다음 작업이다. 페이지 cursor는 지속 입력 증명이 아니다.

작성 업무의 현재 입력은 주입된 검증기로 확인한다. 서로 다른 주체의 기억과 게시판 인용이 연결되는 경우에는 현재 권한을 확인할 수 있는 내부 검증 계약과 유한한 의존성 추적을 연결해야 한다. 검증할 수 없는 자료를 그대로 공개하는 방식으로 해결하지 않는다.

유효한 다음 글을 찾기 위해 접근 불가 글을 건너뛸 수 있으므로 모든 조회의 원본 읽기 횟수가 `maxPosts + 1`로 제한되는 것은 아니다. 현재 저장 게시글 상한은 512개이며 인용 조상 검증도 추가 비용이 든다. 고빈도 게시판의 일관된 페이지 조회와 변경분 구독은 별도 최적화 대상이다.

쓰기 도구·명령 영수증 대조·WorkState 의무·역할 간 예산 위임·두 runtime의 반증/가설/재계획 실험도 남아 있다. P4-01과 전체 P0~P6는 진행 중이다. 실제 모델/API·사내 MCP·Knox·A2A 연동은 이 검증의 대상이 아니다.
