# C10 로컬 패키지에서 실행 설치본 준비

2026-09-08 · checkpoint388. 기준선은 checkpoint387 `b8d1e0d736d8a5e4fbc31a7381872ee2f93191d3`이며 직전 설치형 자동 최초 pin은 게시 완료다. 이번 작업은 npm/개발 실행 경로를 그 초기화에 연결한다. 실제 모델/API와 외부 서비스 연결은 실행하지 않는다.

새 담당의 일반 CLI가 release 없는 패키지에서 실행됐다면 로컬 원본을 읽어 검증 가능한 설치본을 준비하고, 그 설치본에 동일 명령을 전달한다. 설치본이 원 ID·첫 pin·완료 영수증을 만든다. 원 npm/개발 파일에는 manifest나 담당 자료를 쓰지 않는다. 프로그램 API의 호스트 콜백을 자식 프로세스로 직렬화하지 않으며 직접 API의 실행 코드 선택은 호출 호스트 책임으로 유지한다.

## 구현 순서

1. 기존 bundler의 읽기 전용 release 계산을 추출한다. 실제 포함 파일의 지문과 현재 플랫폼/Node/형식 지원을 그대로 사용한다. package 내부에 실행 필수 의존성이 있는지 확인하고 외부 hoist·링크를 조용히 따라가지 않는다. npm version/range 해결기를 새로 만들지는 않는다.
2. 기본 준비 저장소는 `~/.secumon/engine-releases`이며 기존 엔진 등록표와 분리한다. release 지문별 폴더에 UUID attempt의 bundle/engine을 만들고, 검증·등록·원 source 재확인 뒤 `selected.json`을 덮어쓰지 않고 게시한다. selector는 설치 경로의 UUID와 release/등록 지문을 담는 포인터이며 실제 파일 검사를 대체하지 않는다.
3. 같은 원본의 완료 설치를 재사용한다. 등록만 실패한 완료 engine은 같은 실제 release로 다시 등록할 수 있다. manifest 없는 부분 복사본은 보존하고 새 attempt에서 재시도한다. 동시 준비는 완료 selector의 승자를 재독하며 타인의 부분 결과를 삭제하지 않는다. 한 지문당 후보 수에 상한을 둔다.
4. 일반 CLI의 검증된 신규 초기화만 준비 대상으로 삼는다. 기존 무핀/clone/restore·이미 고정된 담당·상태 조회/help/version·관리 명령은 기존 경로를 유지한다. 일반 setup 옵션 검사는 실제 명령과 launcher가 공유해 잘못된 저장 선택으로 준비 자료를 만들지 않게 한다. 준비 도중 다른 초기화가 승리하면 최신 원 선택을 다시 확인한다.
5. 작은 metadata release로 재사용·변조·등록 실패·실제 중단·동시성을 확인한다. 기존 실제 offline npm pack/global install 시험을 확장해 npm 원본→준비 설치→실제 child 초기화→업무/재설치 후 이어가기를 같은 설치 세트에서 확인한다. 관련 launcher/초기화 회귀와 필수 빌드·코어·계층 검사를 실행한다.

build2에서 신규14개·기존 및 확장한 설치/CLI 회귀32개를 확인한 뒤, 정적 검토에서 두 중단/변경 경계를 보완했다. 원 source 전체 재독은 선택 설치/등록의 마지막 검사 전에 수행한다. 설치 manifest 공개의 실제 hardlink 직후 중단돼 정확한 원 manifest와 같은 객체의 pending이 남았다면 해당 후보를 보존하고 새 attempt로 진행한다. 그 후보를 완료 설치로 실행하거나 임의 삭제하지 않는다. 두 경계 재현을 포함한 신규16개가 최종 build3에서 통과했다. [결과](C10-engine-preparation-result.md)와 checkpoint388에 소스별 기록을 보존했다. build2 시험을 이후 수정한 소스의 재실행으로 표시하지 않는다.

기본 동작은 사용자 소유의 자체 의존성을 가진 패키지에 적용한다. 원 tgz, 상위 폴더에서만 해결되는 의존성, npm link/pnpm식 링크, 관리자 소유 prefix까지 지원했다고 주장하지 않는다. 각각의 실제 지원·Linux/native Windows·운영 검증은 남겨 기록한다. 저장 이행·C09/C05/C06 후속과 전체 goal 미완료를 유지한다.
