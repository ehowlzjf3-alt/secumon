# C09 프로세스 간 관측 제어 안내

2026-09-09 · checkpoint398. 실행 결과는 별도 결과 문서에 기록한다.

기존 [관측 제어 명령](C09-resident-command-usage.md)의 사용법은 그대로다. 한 프로세스가 같은 담당의 관측을 실행하고 다른 CLI 프로세스가 올바른 대화·연결로 pause 또는 stop을 저장하면, 관측 프로세스가 저장 상태의 변화를 감지한다. 이미 접수한 사건 업무의 일반 제어와 관측 제어는 구분한다. 기존 mission 원천 조회에도 같은 감지 helper를 연결했다.

## 동작과 비용

- 실제 source `poll` 응답을 기다릴 때만 기본250ms 간격으로 저장 버전의 후보를 확인한다. 하나의 대기 안에서 앞선 검사가 끝나기 전에 다음 검사를 만들지 않는다. 정상 응답·오류·취소 후에는 다음 타이머를 제거한다.
- SQLite는 해당 업무의 revision 컬럼을 읽는다. PostgreSQL은 기존 등록·담당 범위를 검사하는 읽기 트랜잭션 안에서 같은 컬럼을 읽는다. 파일은 기존 디렉터리 경계를 확인하고 발행 기록명을 열거한다. 파일명 수에 따른 비용과 메타데이터 읽기는 남으며 매번 전체 원문을 읽는 방식은 아니다.
- 후보가 달라지면 기존 현재 권한과 전체 상태 검사를 수행한다. 같은 후보여도 기본5초마다 다시 검사한다. 후보 자체는 새 명령 적용이나 정상 권한의 증거가 아니다. 선택 포트를 제공하지 않는 저장소는 정식 상태 검사로 동작한다.
- 검사에서 관측의 최초 기준이 더 이상 유효하지 않으면 해당 관측의 취소 신호를 전달한다. 빠른 pause→resume을 마지막 active 상태만 보고 놓치지 않는다. 이후 시작한 새 관측은 새 기준을 사용하므로 옛 명령의 단순 재전달 때문에 취소되지 않는다.

250ms는 예약 간격이며 최대 응답시간 보장은 아니다. 저장소 응답과 이벤트 루프 지연이 더해진다. 휴면 중인 담당 전체에 타이머를 추가하지 않으며 모델·도구 실행이나 새 사건 접수도 발생시키지 않는다.

## 오류와 수명

명령 저장과 관측 중단, 실제 원천 I/O 종료는 구분한다. 대기 중인 source가 취소에 협조하지 않으면 관측 호출은 먼저 끝나도 원 I/O가 나중에 끝날 수 있다. 원천을 연 호스트가 원 I/O의 종료와 drain을 담당한다. 감지 도중 시작한 저장소 읽기도 포트가 취소를 지원하지 않으면 늦게 끝날 수 있으나, 끝난 관측을 다시 변경하거나 다음 감지를 예약하지 않는다.

감지 실패와 권한·저장소 오류를 ‘제어 적용 완료’나 ‘원천 조회 성공’으로 표시하지 않는다. 관측 호출은 기존 상태 변경 오류 또는 실제 검사 오류를 반환하며, 원 명령의 결과는 명령 ID로 영수증을 확인한다. 기존 driver의 호출 결과·오류 처리는 호스트가 담당하며 명령이 추론이나 새 관측 실행을 자동 시작하지 않는다.

## 지원 범위

이 연결은 resident와 mission의 활성 원천 조회를 대상으로 한다. 다른 프로세스와 데이터는 같은 담당 저장소를 통해 공유되어야 하며, 다른 담당·사용자 대화의 권한을 늘리지 않는다. 실제 검사한 플랫폼·데이터베이스는 결과 문서를 따른다. 파일·PostgreSQL 지원 코드를 네이티브 Windows 또는 실제 PostgreSQL 운영 검증으로 해석하지 않는다.

브라우저 미확정 제어 요청의 새로고침 뒤 복원, 실제 Knox 전송, 전체 세션 컨텍스트 비용과 장기 사건 보관은 별도 잔여 항목이다.
