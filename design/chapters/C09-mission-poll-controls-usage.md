## 대기를 멈추는 것과 원천 작업을 끝내는 것

원천에 새 사건을 요청한 뒤 응답을 기다리는 중에도 업무 일시정지·취소·목표 변경이나 관측 제어가 들어올 수 있다. 이번 연결은 같은 프로세스에서 해당 제어가 실제로 새로 저장된 뒤 그 관측 응답을 기다리는 실행 경로를 중단시킨다. 일반 업무에서는 `AbortError`로 반환하며, resident 제어의 기존 오류 계약은 아래 표를 따른다. 이전 단위의 “늦은 응답을 채택하지 않음”에 관측 대기 중단을 이어 붙인다.

원천 callback은 호스트가 등록한 조회 함수다. callback이 중단 신호에 협조하면 자체 작업을 끝낼 수 있지만, 신호를 무시하면 관측 대기가 끝난 뒤에도 계속 실행할 수 있다. 외부 프로세스를 강제로 죽이거나 이미 수행한 외부 작업을 취소했다는 뜻은 아니다. callback의 정리와 drain, 즉 진행 중 호출이 끝날 때까지 확인하는 절차는 원천 소유자의 종료 수명과 별도로 다룬다.

## 사용할 제어의 대상

| 의도 | 기존 제어 경로 | 연결한 동작 |
| --- | --- | --- |
| 개별 업무를 쉬거나 취소하기 | 기존 코어 업무 pause/cancel | 제어 저장 후 진행 중인 해당 관측 대기 중단 |
| 개별 업무의 목표 바꾸기 | 기존 목표 변경과 명시 재개 | 이전 목표의 진행 중 관측 결과를 새 목표에 반영하지 않도록 중단 |
| resident의 관측을 쉬거나 규칙 종료하기 | 호스트의 관측 pause/stop | 진행 중 poll은 기존 `resident_mission_changed` 오류로 종료. 이후 tick의 paused/closed 상태 반환은 유지 |
| 호스트 driver·프로필 종료하기 | 기존 소유자 종료 경로 | 관측 대기와 실제 원천 callback의 종료를 구분하여 정리 |

기존 제어 사용법은 [임무 제어 사용 흐름](C09-mission-controls-usage.md)을 따른다. 새 명령·새 세션·새 기억 저장소를 만드는 단위가 아니다. 관측을 일시정지했다고 해서 개별 업무가 완료되는 것은 아니며, 업무를 취소했다고 해서 관측 규칙 전체가 자동으로 재등록되는 것도 아니다.

중단 결과는 경로별 기존 계약을 따른다. 일반 업무의 refresh/tick은 `AbortError`, resident의 명시 pause/stop은 `resident_mission_changed`를 사용한다. 호출자 자신의 취소는 기존 호출자 취소 경로다. 이 오류 이름을 업무 완료나 원천 callback의 실제 종료로 해석하지 않는다.

호스트 조합은 선택적 `RuntimeServices.workCancellation`의 register/interrupt를 기존 `ExecutionRuntime`에 연결한다. register는 현재 관측의 중단 함수를 등록하고, interrupt는 해당 업무에 등록한 대기를 중단시킨다. `MissionRuntime.refresh`는 이 신호와 기존 수명 신호를 결합하여 사용하고 `finally`에서 등록을 해제한다. 런타임이 `beginClose`로 종료를 시작한 뒤에는 새 취소 등록도 즉시 중단된다. 별도로 구성한 호스트에서 이 선택 포트를 연결하지 않으면 같은 즉시 신호 전달이 생긴다고 가정하지 않는다.

## 늦은 응답을 받았을 때

중단된 관측의 늦은 응답을 새 사건으로 넣거나 커서를 앞으로 옮기지 않는다. 늦은 오류도 업무의 새로운 결과로 채택하지 않는다. 새 사건이 없었던 관측 횟수인 idle 값도 증가시키지 않는다. 제어가 실제 반영된 상태, 원 사건·접수 이력·대기 의무와 지속 세션은 보존한다.

관측을 다시 시작하거나 업무를 명시 재개할 때는 기존 원 상태와 커서를 사용한다. 늦은 응답을 현재 조회의 정상 결과처럼 사용하거나 원 기록을 지우고 다시 접수하지 않는다. 중단된 관측의 `finally` 정리는 원 호스트 수명을 사용하는 cleanup 신호로 처리한다. 원 호스트 권한이 유효한 경우에만 자기 점유를 해제하며, 프로필 권한까지 종료됐다면 새 정리 쓰기를 하지 않고 원 점유·영수증을 보존해 임대 만료에 맡긴다. 실제 자기 claim을 해제할 때 기존 `controlRevision`을 증가시켜 과거 체크포인트와 같은 명령 ID로 합쳐지지 않도록 보완했다. 신규 caller/driver-close 시험에서 실제 `claim: null`을 확인했다. 이는 새 상태 필드가 아니다. 진행 중 조회가 중단 오류로 끝나는 것과, 이미 paused/closed인 controller를 다음 tick에서 상태로 확인하는 것은 다른 시점의 결과다.

## 이번에 지원하지 않는 즉시 전파

제어 요청이 실제로 저장됐는지 응답만으로 알 수 없는 경우와 다른 프로세스에서 저장한 제어를 즉시 중단 신호로 전달하는 기능은 미구현이다. 프로세스 내 등록을 재시작 후에도 유효한 신호 구독으로 취급하지 않는다. 저장 상태와 원 영수증을 확인하는 기존 재열기 경로는 별도로 유지하며, 이를 프로세스 간 즉시 신호 전파의 증거로 사용하지 않는다.

로컬 신규12개·직접 관련37개와 최종 소스 대조 결과는 [결과 기록](C09-mission-poll-controls-result.md)에 남긴다. 실제 모델/API 시험은 중단 상태이며, 로컬 결과를 실제 사내/외부 원천·Linux/native Windows·운영 배포 검증으로 표시하지 않는다.
