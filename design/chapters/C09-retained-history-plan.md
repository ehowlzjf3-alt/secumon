# C09 보존 이력과 계속 실행

2026-09-09 · checkpoint401 · 기준선 `b9fa88d5acf051bc34e69d300b4b5a7f3003cc7a`.

직전 checkpoint400은 구현·검증·푸시 완료한 진척이다. 이번에는 이미 이름 붙인 장기 관측의 용량·보관 흐름을 이어 구현한다. 원자료를 삭제하거나 새 DB를 강제하지 않는다.

현재 mission/resident는 checkpoint를 저장할 때마다 현재 state.artifacts에도 참조를 누적한다. 저장 직전 검사와 전체 상태 영수증의 크기가 함께 커진다. 새 저장부터 검증된 이전 관측 head만 현재 참조 목록에서 교체한다. 다른 현재 구조에서 사용하는 참조는 남기고 과거 원파일·원영수증·원사건은 그대로 둔다. 과거 제어 재전달과 이력 조회는 정확한 원영수증에서 참조를 찾되 현재 권한·삭제 세대·원 해시를 대조한다. 기존 누적 목록을 일괄 청소하는 이행은 하지 않는다.

업무 mission의 seen512개는 한 보관 구간으로 사용한다. 새 사건으로 구간이 넘치면 직전의 확정 checkpoint와 그 발행 revision을 가리키는 작은 seenHistory 연결을 보존하고 다음 구간을 시작한다. 과거 ID 확인은 이 연결을 따라 원영수증·원 checkpoint를 대조한다. 모든 제어 사건을 반복 조회하는 별도 인덱스/DB는 만들지 않는다. 연결은 같은 담당·업무·goal·세대·규칙에서만 유효하고 revision이 감소해야 한다. 원자료 오류는 새 사건으로 우회하지 않는다.

기존 event_capacity 종료는 명시적인 continueAfterCapacity API로 마지막 수락 위치에서 다시 연다. 일반 register 재전달은 기존대로 멱등이며 다른 종료 사유·취소/완료 업무를 되살리지 않는다. 새 구현은 정상 구간 교체에서 event_capacity로 자동 종료하지 않는다. 기존 maxResumes/noProgress/idle 제한은 그대로다.

검증은 두 저장 방식의 구간 교체·옛 중복/충돌·재열기·원자료 보존, legacy 용량 종료의 명시 재개, resident 다회 저장의 현재 참조 수·과거 제어 재전달을 묶는다. 이미 있는 관련 회귀만 실행하고 가상 장애 행렬을 새로 확장하지 않는다. 측정은 논리 읽기/반환량/현재 참조 수로 한정한다.

원문 장기 보관은 기존 영수증·자료 저장소에 유지된다. file-journal의 전체 원기록 검증 비용과 전체 디스크 누적량 자체는 없어지지 않는다. 실제 용량·보관 기간·보관소 이관은 기존 설치/백업/저장소 이행 기능과 연결해 남은 운영 조건을 분명히 기록한다. 실제 모델/API·사내 연동은 이번에 실행하지 않는다.
