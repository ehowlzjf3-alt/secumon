# C09 이력 조회 비용과 사건 한도 처리

2026-09-09 · checkpoint400 · 기준선 `ab5c0761ed80936fce86b3497b19fe22da454294`.

직전 checkpoint399는 웹 요청 복원 구현·29개 시험·실제 브라우저 대조·원격 main 일치까지 완료한 진척이다. 이번에는 남은 C09 이력·문맥 비용을 실제 코드 경로에서 확인한다. 새 포괄 저장소나 스킬을 추가하지 않는다.

## 확인한 문제와 선택

`SessionOriginals.read`는 최대64개인 한 페이지에서도 같은 업무의 전체 상태를 원문마다 다시 읽는다. SQLite/PostgreSQL의 세션 이력 조회는 이미 범위·권한·페이지 제한이 있으므로 재작성하지 않는다. compact된 원문을 다시 검증하는 과정도 유지한다. 한 페이지 안의 반복 상태만 제한된 메모리에서 재사용하고, 페이지 종료 전에 원 상태가 그대로인지 정식 조회로 다시 확인한다. 페이지가 끝나면 폐기하며 호출 간 캐시나 저장 버전 후보를 권한 증명으로 쓰지 않는다. 최대8개 업무·직렬화4MiB를 넘으면 기존 조회로 처리한다.

업무에 붙는 `MissionRuntime`은 같은 목표에서 최대512개 사건을 기억한다. 현재는 다음 page가 한도를 넘으면 그 원문을 받아들이지 않으면서 cursor/snapshot을 전진시켜 종료한다. 새 page를 수락하지 못했다면 이전 cursor/snapshot과 기존 사건·읽기 확인을 보존하고 명시적인 용량 종료를 남기도록 고친다. 한도 초과를 목표 완료나 새 사건 처리 성공으로 표시하지 않는다. 최근512개 캐시 밖에서도 원 session intake·영수증으로 중복을 확인하는 상주 `ResidentMissions`의 기존 경로는 재사용한다.

## 확인 방법

- 같은 업무의 실제 세션 입력을 반복해 원문 수·history 페이지·업무 상태 조회 수·반환 bytes를 비교한다. 물리 디스크 I/O나 실제 모델 토큰 사용으로 확대하지 않는다.
- 페이지 중 상태·권한이 바뀌면 문맥 후보가 발행되지 않는지, 메모리 한도 초과 시 기존 경로로 처리되는지 확인한다.
- 동일 목표의 사건 한도에 도달한 뒤 새 page를 받을 때 원 cursor/기록을 보존하고, 한도 안에서의 중복·충돌·읽기 확인 동작이 유지되는지 확인한다.
- 관련 기존 시험을 선택해 한 번 실행하고 결과·실패·측정·다음 행동을 저장해 푸시한다. 실제 모델/API 시험 중단은 유지한다.

이번 변경으로 원문 전체 검증 비용이나 장기 저장 공간이 없어지지는 않는다. 원문·receipt의 누적 보관 및 중복 근거를 유지하는 이관/용량 정책은 별도 잔여다. 이를 임의로 삭제하거나 이번 좁은 비용 측정을 장기 저장 운영 검증으로 표시하지 않는다. C05/C06·C10·실환경·최종통합의 원래 요구도 유지한다.
