# C09 브라우저 제어 요청 복원 결과

2026-09-09 · checkpoint399 · 기준선 `c295c611`.

미확정 제어 요청을 같은 탭에서 새로고침한 뒤 복원하도록 연결했다. 서버가 확인한 담당·사용자 세션·대화별로 나눈 `sessionStorage`에 최초 요청 ID와 제어 버전, 대상 ID와 명령 종류만 저장한다. 새 요청을 보내기 전에 저장하며, 원 응답이나 확정 거절을 확인한 뒤 제거한다. 상태 조회와 연결 종료는 미확정 기록을 삭제하지 않는다.

복원한 요청은 기존 접이식 패널에서 선택·재확인한다. 새로고침은 제어 명령을 자동 전송하지 않으며, 과거 화면 상태를 현재 상태로 복원하지 않는다. 화면에서 나갔다 돌아오는 경우에도 연결을 다시 확인하고 복구 기록을 읽는다. 저장 실패·손상·최대16건/UTF-8 32KiB 초과는 기록을 버리고 새 명령으로 진행하지 않고 오류로 표시한다. 대화나 증거 원문·인증정보는 저장하지 않는다.

## 확인한 범위

- 최종 build2에서 신규13개와 기존16개, **고유29개 모두 통과**했다. 실패·취소·건너뜀0이다. build1에서도 같은29개가 통과했고, 검증 보조 코드 교정 후 최종 소스에서 다시 실행한 것이므로58개로 합산하지 않는다.
- build2 exit0. 코어 타입 검사와 구조 검사203개/위반0은 build1에서 통과했다. 이후 변경은 테스트용 브라우저 helper의 사건 본문 조회뿐이며 코어 소스와 import 관계가 그대로여서 두 검사는 재사용했다. 최종 시험·브라우저 전후 소스와 컴파일2,571개 대조가 일치한다.
- 실제 Codex 내장 브라우저와 임시 SQLite에서 일시정지 요청의 저장 성공 뒤 HTTP 응답만 실패시켰다. 새로고침 후 같은 담당·대화의 요청이 표시됐고, 상태 본문은 복원되지 않았으며 신규 제어는 비활성 상태였다.
- 새로고침 직후 서버 기록은 명령 처리1회·원 영수증1개·같은 상태 버전이었다. 사용자 재확인은 **동일한 명령 ID·최초 버전**으로 처리됐으며 원 영수증·상태는 바뀌지 않았다. 이후 재개·종료까지 수행해 명령 처리4회 중 고유 제어는3개였다.
- 확인된 요청은 다시 새로고침해도 미확정 목록에 나오지 않았다. 종료 후 제어 버튼은 비활성화됐다. 최종 브라우저 실행의 모델·source poll 호출은0회이며 임시 서버와 탭은 종료했다.
- 담당·세션·대화 간 저장 격리, 다른 요청 보존, 저장·삭제 실패, 잘못된 응답, HTTP 인증·CSRF·선택 경계는 선택 시험으로 확인했다. 이를 여러 담당의 실제 브라우저 동시 조작 검증으로 확대하지 않는다.

## 검증 과정에서 교정한 것

첫 브라우저 실행의 기록 수집 helper가 `event.data.command`를 읽어 실패했다. 실제 사건 본문은 기존 계약의 `event.data.payload.command`에 있다. helper만 고치고 원 영수증의 digest·revision 대조도 연결했다. 제품 동작의 실패로 분류하지 않는다.

첫 화면 기록에는 스크립트의 제어 조작 외에 일반 업무2개도 보였고, 종료 시 결정적 모델 대역 호출1회를 감지했다. 발생 주체는 확인하지 않았으며 이 실행을 모델 호출0인 최종 인수로 계산하지 않는다. 실제 모델/API 연결은 없었다. 최초 화면 자료와 [진단 기록](../../runtime/evidence/C09-browser-command-recovery-fixture-error.json)을 보존하고, 새 임시 서버의 완결된 실행을 최종 근거로 사용했다.
