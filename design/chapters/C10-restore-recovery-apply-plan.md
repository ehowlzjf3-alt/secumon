## 처리 순서와 재사용

1. 사용자가 선택한 준비 패키지의 정확한 지문과 전체 원문을 기존 `inspectAgentRestoreRecovery`로 확인한다. 현재 담당의 실제 객체·신원 head·복원 표식·자료도 준비 명세의 원 기준과 대조한다. 선택 백업을 자동으로 최신이나 정답이라고 간주하지 않는다.
2. 담당·준비 패키지의 원문 집합과 분리된 호스트 소유 위치에 적용 진행을 기록한다. 같은 작업의 재시도와 이미 완료된 이동·복원을 구분할 수 있어야 한다. 진행 기록만 믿지 않고 원경로와 보존 경로의 실제 객체·자료를 확인한다.
3. 원 담당을 같은 부모 안의 새 보존 경로로 이동한다. 목적지가 존재하면 덮어쓰지 않는다. 이동 전후 부모·원 객체·보존 객체와 원 유지보수 기록을 확인하고, 원 lease의 종료가 새로 복원할 담당의 경로를 건드리지 않도록 연결한다.
4. 비어 있는 원경로에 패키지의 `selected-backup/`을 기존 `restoreAgentBackup`으로 복원한다. 원 담당을 병합하거나 기존 폴더 위에 덮어쓰지 않는다. 새 복원 고유 번호를 원 완료 표식으로 확인한다.
5. 기존 `rebindRestoredAgentHostIdentity`로 원 head·선택 백업·정확한 새 디렉터리 객체를 대조해 신원을 재등록한다. 재호출에서는 이미 완료된 같은 rebind를 재사용한다. rebind의 operation은 `local:<선택 백업 지문>`이며 준비 작업 UUID와 구분한다.
6. 결과를 `stage: "restored"`, `reconciliationRequired: true`로 반환한다. 이후 등록된 호스트 소스로 새 복원의 외부 기록을 대조해야 일반 실행을 재개한다. 적용 완료만으로 작업·목표 완료, 자원 정산, 새 실행 허가를 만들지 않는다.

기존 백업·자료 복사·완료 표식·신원 복구·외부 대조를 다시 만들지 않는다. 추가 구현은 적용의 진행 기록, 원 담당의 정확한 보존 이동, 중단 단계 확인과 기존 API 호출 연결에 집중한다.

## 보존 이동과 플랫폼 경계

전체 디렉터리 보존 이동에는 같은 부모 안에서 목적지를 덮어쓰지 않는 호스트 기능을 사용한다. macOS의 `renameatx_np`, Linux의 `renameat2`, Windows의 `rename_new`를 해당 플랫폼 어댑터로 연결한다. 플랫폼에 맞게 빌드한 `.node` 네이티브 모듈이 필요하며, 없는 환경에서 일반 덮어쓰기 가능한 rename으로 자동 대체하지 않는다.

플랫폼 구현이 존재하는 것과 해당 OS에서 실제로 실행·검증한 것은 별도다. 현재 개발 호스트의 통과를 Linux/native Windows의 운영 인수로 표시하지 않는다. 경로는 담당·준비 패키지·엔진·호스트 신원 등록표와 겹치지 않게 유지하며 원 자료와 중단 흔적을 삭제하지 않는다.

## 중단 뒤 이어가기

원 담당 이동 전에 중단됐다면 원 자료가 준비 기준과 같은지 확인하고 이어간다. 이동 뒤 응답이 유실됐으면 원경로 부재와 정확한 보존 객체를 확인해 이동을 반복하지 않는다. 다른 폴더나 다른 operation의 자료가 나타나면 그 위에 복원하지 않는다.

POSIX의 기존 restore는 일부 복사된 대상이 있으면 단순 재호출할 수 없다. 이번 적용 경로에서는 **원 pending의 복원 UUID별로 부분 복원본을 별도 보존**하고 비어 있는 원경로에서 새 복원을 시작한다. 부분 결과를 삭제하거나 원백업과 무관한 파일을 이어 붙이지 않는다. Windows는 기존 pending·정확한 원백업 기반의 복원 재개 기능을 활용할 수 있다. 어느 경로든 새로 시도한 복원과 기존 완료 복원을 구분한다.

복원 완료 뒤 중단됐다면 완료 표식과 선택 백업의 원문 대조를 재사용하고 다시 복사하지 않는다. 신원 재등록 뒤 중단됐다면 같은 원 head·백업·operation·실제 디렉터리 객체에 대한 기존 재호출 경계를 사용한다. 적용 완료 이후 작업으로 자료가 변경될 수 있으므로 완료된 적용을 과거 백업 재적용으로 오인하지 않는다.

`restore-recovery-apply-status`는 저장된 적용 진행과 역사 영수증을 조회한다. 그 결과가 현재 외부 기록 대조의 완료 증거는 아니다. 새 복원에 대한 현재 상태는 기존 `restore-status`와 `restore-reconcile`로 확인한다. 미해결이면 자료와 차단을 유지하며 원 도구 입력·메시지를 자동 재전송하지 않는다.

## 공개 입구와 검증 항목

`restore-recovery-apply --source 준비패키지 --digest 준비SHA --offline`로 적용하고 `restore-recovery-apply-status --source 준비패키지`로 조회한다. `--digest`는 선택 백업 지문이 아니라 준비 패키지의 `recovery.json` 지문이다. CLI는 필수 인수와 offline을 먼저 확인한 뒤 프로필에 접근한다. 기존 준비·조회 명령은 유지한다.

- 실제 외부 효과를 가진 과거 복원본을 준비한 뒤 현재 담당 보존 이동 → 선택 백업 복원 → 신원 재등록 → 새 외부 대조 → 일반 재개를 확인한다. 원문·세션·영수증·사용량과 외부 파일을 보존하며 원 동작을 반복하지 않아야 한다.
- 준비 지문·현재 신원·원문 불일치, 겹치거나 이미 존재하는 보존 목적지, 유지보수 충돌은 원 자료를 바꾸기 전에 거절한다.
- 이동 직후, 일부 복원, 복원 완료, rebind 완료 경계의 중단을 원 기록과 실제 파일로 재개한다. 이미 완료한 단계와 보존 이동을 반복하지 않는다.
- CLI 필수 인수 경계와 상태 출력, 관련 준비·복원·신원·대조 회귀, 빌드·코어 타입·계층 검사를 필요한 범위에서 수행한다. 플랫폼 네이티브 helper의 빌드·실행 결과는 별도로 남긴다.

실제 모델/API 시험 중단과 사내 서비스 미연결을 유지한다. C10의 이번 적용 경계 이후 C09 취소·목표 변경·일시정지·저널 응답 불명·이력 비용, C05/C06 후속, 현재 Linux/native Windows·실제 PostgreSQL·사내 연동·운영 배포·최종통합이 남는다. 이번 계획이나 부분 검증을 전체 goal 완료로 기록하지 않는다.
