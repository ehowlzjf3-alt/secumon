# C10 저장 형식 이행과 최초 재열기

2026-09-08 · checkpoint389 · 기준선 `53019cf4625f7f95b11995fa32fce0c9a0e90fe6`

직전 checkpoint388은 설치 준비 코드·문서·검증 결과를 커밋/푸시하고 원격 일치를 확인한 진전이다. 이번 단위는 기존 형식 이행을 재사용하고, 엔진을 바꾼 뒤 저장소를 처음 열 때의 자료 보존을 확인한다.

## 확인한 기존 구현과 공백

SQLite 상태 저장소에는 1/2→3의 트랜잭션 이행과 조회 색인 재구성이 있다. 지식 저장소에는 1→2의 담당별 구획 이행이 있고 원 JSON·영수증·색인 상태를 보존한다. 개인 기억의 별도 저장소 이관과 PostgreSQL 이관은 이미 다른 명시 절차를 사용한다. 이 기능들을 새로 만들지 않는다.

현재 일반 저장소 열기는 상태→지식→대화 순으로 쓰기 가능한 객체를 만든다. 뒤쪽 저장소가 지원하지 않는 형식이면 앞쪽의 이행이 끝난 뒤 실패할 수 있다. 엔진 pin 확인은 실행 코드/설정 확인이므로 저장 형식 검사를 대신하지 않는다. lifecycle의 읽기 전용 형식 확인을 재사용하되 최초 초기화의 없는 DB·빈 DB·소유자만 기록한 DB를 기존 복구 절차로 열 수 있어야 한다.

기존 실제 A/B 설치 시험은 동일한 현재 저장 형식 구현과 서로 다른 응답 formatter를 사용한다. 버전 전환·재개 증거지만 이전 물리 형식의 최초 재열기 이행 증거는 아니다.

## 이번 구현과 검증 순서

1. 공통 로컬 저장 형식 읽기 검사를 추출한다. lifecycle의 엄격한 준비 완료 조건을 유지하고, 일반 open에서는 기존 초기화/복구 상태를 허용하는 읽기 검사로 사용한다. 알려진 미지원 형식과 모호한 버전 기록은 쓰기 가능한 저장소를 열기 전에 거절한다. DB 소유 확인과 각 저장소의 실제 트랜잭션 검사는 유지한다.
2. 긴 세션의 compact 저장 형식도 확인한다. 기존 manifest에는 compact 형식1 지원을 적용하고 새 manifest는 해당 지원을 명시한다. 지원 범위 선언과 실제 자료 버전 확인을 구분한다.
3. 실제 이전 상태/지식 테이블과 원 자료를 이용해 check·backup·pin은 형식을 바꾸지 않고, 선택 설치본의 최초 open이 기존 이행 코드를 실행하는지 확인한다. 원 업무·대화·근거·영수증·지식 원문과 백업을 대조하고 재열기의 멱등성을 확인한다. 과거 엔진 바이너리 자체를 실행했다는 주장과 구분한다.
4. 뒤쪽의 미지원 형식/모호한 버전/compact 형식을 앞쪽의 구형 상태와 조합해 원 상태 형식·본문 보존을 확인한다. 정상 fresh open·중단 초기화·자료 구획·기존 이행 회귀를 변경 범위에 맞게 실행한다. 소스 변경과 시험 실행은 겹치지 않는다.

읽기 선검사는 서로 다른 파일 DB를 하나의 트랜잭션으로 묶거나 이후 모든 오류를 미리 검출하는 기능이 아니다. 실제 이행은 기존 각 저장소 트랜잭션과 재열기 재시도에 맡긴다. 미확정 외부 효과 대조·현재 Linux/native Windows·실제 PostgreSQL/사내 서비스·운영/최종통합과 C09/C05/C06 후속은 유지한다. 실제 모델/API 시험은 중단 상태다.

로컬 구현과 검증을 마쳤다. 최종 경계9개·문서 기억8개는 build3, 두 실제 설치 시나리오와 나머지 회귀는 build2 기록이다. 처음의 지문 순서/공개 오류 코드 실패와 교정은 [결과](C10-storage-upgrade-result.md)에 보존했다. 전체 C10/goal은 미완료다.
