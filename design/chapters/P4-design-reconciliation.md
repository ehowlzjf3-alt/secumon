# P4 수정 범위 정리 — 구현 재개 전 검토 기준

2026-09-06 계획 통합: 이 문서의 요구/검토 결과는 [통합 플랜 C01~C10](/Users/seunghanee/Documents/secumon/design/03-migration-plan.md)에 반영했다. 아래 과거 구현 순서 후보보다 최신 통합 플랜을 우선하며, 기능 구현 완료를 의미하지 않는다.

2026-09-06 · 현재 요청은 변경 내용 정리 · 제품 코드 수정 보류

이 문서는 최근 게시판·자료 경계·리드/워커 논의를 한곳에 모은다. 사용자에게 확인된 요구, 현재 코드의 사실, 제안 중인 변경을 구분한다. 앞선 설명을 곧바로 구현 확정으로 간주하지 않는다. `P4-shared-board-simplification.md`는 검토 초안이며 이 문서의 결정 상태를 우선한다.

## 1. 사용자에게 확인된 요구

- 범용 에이전트이며 기존 시큐몬의 구조를 필수 전제로 삼지 않는다.
- 고정된 리드–워커 이중구조를 강제하지 않는다. 대화·조사·검토를 맡은 에이전트 모두 사내 모델을 사용할 수 있어야 한다.
- 게시판의 글 숨김·승인 가공 때문에 읽고 답하는 협업이 지나치게 복잡해지는 것을 피한다.
- 원문 접근 경계는 대안 비교 후 결정한다. 과거의 “리드 원문 차단”을 모든 배치의 고정 요구로 승격하지 않는다.
- 자원 배정·추가 요청·회수/재배정은 에이전트가 판단하고 런타임이 사용량·정산·반환을 집행한다.
- 지금은 방향 변경을 반복하며 구현하지 않고 수정할 내용을 정리한다.

## 2. 현재 상태와 오해를 바로잡을 부분

`02-target-design.md`는 이미 고정 리드 계층을 강제하지 않는다고 명시한다. `05-data-boundary-options.md`와 P2 결과에서도 외부 리드/전체 내부/내부 주도+외부 자문의 운영 채택은 미결정이다. `composeRuntime`은 역할별로 같은 실행·계획·기억·도구 구성요소를 조합한다. `AgentRole`에 고정 leader/worker 종류나 상위 에이전트 필드는 없다.

다만 최근 `BoardFunding`은 지원 역할과 수행 역할의 특정 요청을 부모/자식 작업의 자원 배정으로 연결한다. 이 경로는 **한 요청의 비용을 지원하는 구현**이며 모든 협업의 유일한 경로로 만들면 안 된다. 게시 도구가 작업의 전체 공개 등급을 게시물에 전파하면서 요청자가 읽을 수 없는 답변이 생기는 현재 동작도 확인했다.

따라서 고정 리드–워커 구조를 이미 전면 채택했다고 표현하는 것도, 동등 에이전트의 자율 협업이 이미 완성됐다고 표현하는 것도 부정확하다. 공통 코어를 유지하고 협업·자원·정보 경계의 결합을 검토하는 것이 현재 범위다.

## 3. 유지할 설계와 기반

- TypeScript 코어, 저장소 포트와 adapter 구분, 특정 PostgreSQL/MCP/모델 제품에 대한 코어 독립성.
- goal/state, planner, plan validator, task graph, executor, evidence, 가설·반증, 상태 갱신과 continue/replan/wait/complete의 책임 구분.
- 원본/영속 상태 보존, compact 후 필요한 문맥 재구성, 미사용 도구 명세 정리와 필요 시 조회.
- 실제 실행·근거·효과·목표 완료의 구분, 현재 권한 확인, 취소·멱등성·영수증·복구.
- 도구 catalog, 호출 장부·재사용, 기억/skill 선택 조회, 컴퓨터 유즈의 관찰·행동·결과 확인.
- 자원 사용량 기록·예약·정산·미사용 반환. 현재 부모/자식 장부는 필요한 위임에서 재사용한다.
- CLI/Web/Knox의 접수·필요 질문·결과 중심 표시와 상세 실행 상태 분리.

이 목록은 유지할 설계/기반이며 모든 항목의 구현 완료를 뜻하지 않는다. 기존 검증 이력도 보존한다.

## 4. 수정 항목과 제안

| 항목 | 수정할 내용 | 구현 경계 |
|---|---|---|
| 에이전트 역할 | 요청자·수행자·검토자·대화 담당을 업무별 역할로 둔다. 한 에이전트가 업무에 따라 역할을 바꾸며 직접 협업한다. | 공통 runtime 유지. 영구적인 상위/하위 agent 종류를 도입하지 않는다. 조정자는 필요한 업무에서만 선택한다. |
| 모델 배치 | 모든 역할의 사내 모델 사용을 기본 검증 사례로 둔다. 모델 선택과 협업 역할을 독립시킨다. | 외부 리드 또는 별도 외부 모델 호출을 필수 구성으로 만들지 않는다. 실제 모델 시험 재개는 현재 범위가 아니다. |
| 데이터 접근 | 역할명 대신 주체·업무 범위·자료·모델/전달 목적지의 정책으로 결정한다. | 대화 담당/조정자도 허용되면 원문을 읽을 수 있다. 내부 모델이라는 이유로 무제한 권한을 부여하지도 않는다. 저장소의 물리적 분리는 필요할 때만 한다. |
| 게시판 | 참여 범위를 정한 공유 게시판을 기본 후보로 삼는다. 정상 게시된 글은 그 범위의 참여자가 읽고 답할 수 있게 한다. | 일반 글마다 사람 승인·별도 가공 workflow를 강제하지 않는다. 글 본문과 원문 근거의 접근을 구분한다. 강한 격리는 선택 배치로 남긴다. |
| 응답 책임 | 관측글은 선택 반응, 질문/위임은 담당 역할과 상태를 가진 요청으로 처리한다. | 영속 알림→담당 실행→수락/거절→답변/추가 정보 요청/근거 부족→미응답 처리. 모든 글을 모든 에이전트에게 방송하지 않는다. |
| 자원과 협업 | 자원 배정 관계와 협업 관계를 분리한다. 독립 자원으로 응답하거나 기존 작업으로 협업하는 경로도 둔다. | 질문마다 새 자식 생성/별도 배정을 강제하지 않는다. 부모/자식은 작업별 비용 장부이며 조직도나 자료 권한 상속 규칙이 아니다. |
| 수락 판단 | 요청을 읽고 수락 여부를 판단하는 비용과, 수락 후 실제 업무 수행 비용을 구분한다. | 현재 준비 작업의 모델 전면 금지가 에이전트의 수락 판단을 막는지 검토한다. 자체 자원으로 판단한 뒤 위임 자원을 사용하는 경로가 후보이며, 아직 구현 확정은 아니다. |
| 사람 대화 | 대화 담당도 같은 범용 에이전트이며 사람이 보는 창구 역할을 맡는다. | 모든 내부 요청과 답변을 반드시 대화 담당/리드에게 경유시키지 않는다. 사람의 요청 범위 변경·취소와 결과 전달은 기존 계약을 유지한다. |

**분리해야 할 네 가지:** 누가 누구와 협업하는가, 어느 작업이 비용을 부담하는가, 누가 어떤 자료를 읽는가, 어느 모델에서 추론하는가. 하나의 리드–워커 구분으로 네 가지를 함께 결정하지 않는다.

## 5. 아직 확정하지 않을 선택

- 게시판별 공유 가능한 자료 범위와 원문 접근 정책. 같은 사내 모델 사용만으로 모든 정보 공유가 자동 허용되는 것은 아니다.
- 엄격한 정보 격리가 필요한 배치의 구체적 공개 절차. 게시글마다 승인하는 방식을 기본값으로 확정하지 않는다.
- 수락 판단에 쓸 자체 자원/임무 자원의 소유 방식과 부족할 때의 처리.
- 어떤 업무에서 조정자를 두고, 누가 미응답 요청을 재배정하는지에 대한 최소 실행 정책.

기본 후보는 내부 모델을 쓰는 동료 역할들이 공유 게시판에서 협업하고, 필요한 업무에만 위임·조정·강한 격리를 추가하는 방식이다. 이는 조직의 모든 원문을 공개하자는 결정이 아니다. 원문 접근 제한과 원문에서 유래한 정보 자체의 공유 금지는 다른 요구다. 자연어 요약만으로 후자를 보장한다고 가정하지 않는다.

## 6. 변경하지 않을 것과 구현 순서

지금은 제품·시험·빌드 코드와 기존 보관 자료를 변경하지 않는다. 현재 기능을 통째로 다시 쓰거나 이름을 일괄 변경하지 않는다. 과거 비공개 게시물을 자동으로 공개하지 않으며 권한 검사를 통과시키기 위해 기존 테스트 기대만 낮추지 않는다.

다음 구현은 이 수정표의 기준을 정리한 뒤 진행한다.

1. 역할/모델/자료/자원 관계의 계약과 기본 협업 시나리오를 정한다.
2. 영향 범위를 현재 코드에서 확인한다. 우선 `board-funding.ts`, `board-service.ts`, `board-commands.ts`, `board-watch.ts`, `compose-runtime.ts`와 자원/정보 정책의 연결부를 본다. 파일명 변경 자체는 목적이 아니다.
3. 작은 단위로 실제 변경을 구현한다. 독립 역할의 요청/응답을 먼저 검증하고 위임 자원·미응답 재배정·선택 격리로 확장한다.
4. 기존 기반 회귀와 변경된 사용자 흐름을 함께 검증한 뒤 결과·남은 항목을 기록한다. 새 아이디어가 나오면 바로 코드로 바꾸기 전에 이 수정표의 영향과 필요성을 먼저 확인한다.

## 7. 통과 기준 후보

- 같은 runtime을 사용하는 A가 B에게 요청하고, 다른 업무에서는 B가 A에게 요청할 수 있다. 고정 리드나 외부 모델이 없어도 진행한다.
- 단일 에이전트 처리·동료 협업·선택적 위임이 각각 가능하다. 협업 요청이 자원 장부의 순환 배정/중복 소비를 만들지 않는다.
- 공유 게시판의 정상 답변을 요청자가 읽고 후속 질문할 수 있다. 원문 참조의 직접 검증 여부와 전달받은 주장을 구분한다.
- 일반 내부 공유 흐름은 사람의 글별 승인 없이 진행하고, 자료 정책상 거절된 내용은 명확한 실패/대안 요청으로 남긴다. 읽을 수 없는 정상 답변을 기다리는 상태를 만들지 않는다.
- 수락 여부를 판단할 수 있으며, 거절·추가 정보 필요·미응답 상태를 유실하지 않는다. restart/compact 후 담당 요청과 실제 사용량이 유지된다.
- 배정·정산을 구현해도 에이전트의 권한이나 원문 접근이 자동 확대되지 않는다. 실제 모델 품질과 로컬 대역 검증을 구분한다.

## 8. 현재 검증 기록과 재개 주의

직전 전체 검증 기준선은 v0.50의 2416/2416이다. 진행 중인 funding 변경은 신규 44/44를 통과했으며 `P4-board-funding-verify1` 전체 실행은 이 문서 작성 시 종료 기록이 아직 없었다. 이를 전체 통과로 표시하지 않는다. 이전에 시작한 로컬 검증은 결과만 보존하며 새 구현을 자동으로 시작할 근거로 삼지 않는다.

`runtime/evidence/P4-board-funding-finalize.cjs`는 이전 다음 작업 방향으로 문서와 backlog를 갱신하는 미실행 helper다. 최신 정리 지시를 반영하기 전에는 실행하지 않는다. 원 실행 로그와 결과는 보존한다. 전체 목표는 완료로 표시하지 않되, 최신 사용자 요청에 따라 지금은 설계 정리에 머문다.
