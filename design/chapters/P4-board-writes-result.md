# P4-01 게시판 게시·철회와 저장 결과 복구

2026-09-06 · v0.47 · 전체 2276/2276 · 관련 195/195 검증 완료

이번 단위에서는 `core.board.publish`와 `core.board.retract`를 실제 runtime 도구 목록과 broker에 연결했다. 원래 Python 시큐몬과 비교하지 않고 새 요구사항의 정상·실패·복구 기준을 사용했다. 저장소는 SQLite와 파일 저널이며 코어가 특정 저장소 구현을 직접 참조하지 않는다.

## 배운 개념

게시판에 글이 저장된 사실, 도구 응답이 작업 장부에 도착한 사실, 그 결과가 현재 목표에 채택된 사실은 다르다. 예를 들어 저장 직후 연결이 끊기면 첫 번째 사실만 참일 수 있다. 같은 글을 다시 쓰기 전에 원래 명령의 영수증을 읽어 저장 여부를 확인해야 한다. 저장이 확인돼도 응답 기한이나 목표 조건이 맞지 않으면 결과를 자동 채택하지 않는다.

영수증이 없다는 사실만으로 아직 실행되지 않았다고 단정할 수도 없다. 저장소 앞에서 기다리던 호출이 나중에 도착할 수 있기 때문이다. 이번 구현은 같은 명령 식별자에 대해 실제 저장 또는 **미실행 종료 기록** 중 하나가 원자적으로 먼저 커밋되도록 한다. 종료 기록은 게시글을 바꾸지 않으며, 이후 늦게 도착한 같은 명령의 저장을 거부한다. 이는 로컬 게시판 저장소 계약으로 보장하는 동작이고 일반 외부 API에 자동으로 적용되는 보장은 아니다.

| 확인한 상태 | 현재 판단 | 다음 동작 |
|---|---|---|
| 저장 영수증은 있고 응답은 없음 | 저장 효과 확인, 결과 채택은 미완료 | 원래 결과 이력을 보존하고 후속 계획 |
| 영수증은 없고 호출이 진행 중 | 아직 저장 여부를 모름 | 실행 또는 기한 종료를 기다림 |
| 같은 명령의 미실행 종료 기록이 확정됨 | 늦은 저장도 거부됨 | 재계획 시 새 시도 여부 결정 |
| 원본 proof/현재 권한이 유효하지 않음 | 과거 주장만으로 현재 효과 의무를 해소할 수 없음 | 미확정 의무 유지, 원본/권한 복구 또는 검토 |


## 구현

- 도구 입력에서 actor·workId·commandId를 받지 않는다. 조직 directory와 실행 세션의 현재 권한을 함께 확인하며 좁은 세션 권한을 확대하지 않는다. host가 현재 주체를 확인하고 작업·시도로부터 명령 ID를 만든다. 게시 시 근거 ID는 현재 작업의 근거만 가리킨다. 인용과 답글의 대상은 해당 작업에서 이미 읽고 현재 검증 가능한 게시글이어야 한다.
- 게시/철회는 일반 tool budget과 호출 장부를 사용한다. 실제 저장 직전 현재 권한·목표·기한을 다시 확인한다. 철회는 같은 작업이 작성한 글에 한정한다.
- 일반 `EffectReceipt` 계약을 Attempt/ToolResult에 추가했다. outcome·원래 명령 ID·검증 artifact·관찰 시각을 보관한다. artifact에는 본문 대신 명령 digest와 저장 revision 등 최소 metadata가 들어간다.
- 저장 여부 대조는 원래 ToolResult artifact를 덮어쓰지 않는다. 응답이 없으면 없는 상태, 오류 결과가 있으면 그 원본을 보존하고 별도 효과 영수증을 추가한다. 확인된 효과 의무는 정리하지만 원래 시도를 자동 성공 채택하거나 목표 완료로 바꾸지 않는다.
- 저장 효과 검사는 현재 권한·원래 dispatch·명령 digest·원본 proof·게시판 receipt를 확인하며 proof 조회가 끝난 뒤 현재 작업 경계와 권한을 다시 확인한다. 입력 자료 검증을 재귀 호출하지 않으므로 게시판·기억의 출처 그래프와 함께 사용할 수 있다.
- compact와 재개에는 효과 metadata와 원본 참조를 남긴다. proof가 사라졌거나 현재 권한에서 읽을 수 없으면 컨텍스트 사용을 거부하고 효과 의무를 다시 연다. 원본을 새 요약으로 조용히 대체하지 않는다.

## 검증

정상 빌드 뒤 관련 193개와 전체 2274개를 통과한 뒤, proof 읽기 중 권한 철회 결함을 추가로 재현·수정했다. 최종 신규 시험은 **40개**이며 같은 20개 사례를 두 저장소에서 실행했다. 최종 전체 **2276/2276**, 관련 **195/195**도 통과했고 실패/취소/skip/todo 0, 빌드·코어 타입·계층 115/위반 0·fixture 4/22를 통과했다. 전체 시험 시간은 314703.539333ms다. [실행 기록](/Users/seunghanee/Documents/secumon/runtime/evidence/P4-board-writes-local-verification.json).

새 사례는 정상 게시/철회, 저장 뒤 응답 유실, 원래 오류 artifact 보존, 실행 기한 뒤 도착한 정상 결과, 아직 진행 중인 호출의 무단 종료 방지, 종료 기록 이후 늦은 저장 거부, stale revision, 원본 proof/저장 receipt 유실, 현재 권한 철회, 조작된 결과/다른 시도의 증명, tool 입력 권한 주입 거부, 잘못된 종료 기록의 변경 거부, compact 효과 metadata 변조, 기조회 인용, 재개를 포함한다.

owned 저장 작업자를 실제 SIGKILL한 사례는 두 개다. 이는 runtime에서 만든 명령을 저장하는 작업자 경계의 강제 종료 시험이다. 에이전트 전체 프로세스를 강제 종료한 새 시험으로 표현하지 않는다. 확인을 위한 로컬 저장소 조회는 모델 호출이나 게시 동작을 다시 수행하지 않으며, 시험에서 호출 budget이 추가 소비되지 않는지 확인했다.

첫 전체 실행은 2270개 중 2268개 통과, 2개 실패였다. 인용 시험의 1초 실시간 lease로 결과 저장이 끝나기 전에 반환된 경로를 확인해 정상 흐름 fixture에 10초 lease와 pending 종료 확인을 적용했다. 만료 시험은 가짜 시계 20초 전진으로 계속 검사한다. 컴퓨터 복구의 파일 저장소 사례는 `partial`이 반환됐다. 상세 진단을 추가한 두 번째 전체 실행은 2274개 중 2273개 통과, 같은 복구 시험 1개 실패였고 코드가 `computer_interrupted`임을 확인했다. 취소 명령이 없는 해당 흐름에서 20초 실시간 실행 lease가 병렬 proof I/O 중 만료되는 경로였다. Save 이후 두 단계 복구 시험의 요청 lease를 60초로 늘렸으며 실제 예약은 원 작업 deadline으로 제한된다. 원래 actionDeadlineAt·누적 한도·입력/저장 횟수 검증과 컴퓨터 제품 로직/운영 기본값은 변경하지 않았다.

첫 두 빌드는 시험 helper의 비동기 기본값 문법과 ResumePacket 필드 경로 오류로 실패했다. 타입 실패 중 방출된 dist를 사용한 첫 관련 실행은 175개 중 173개가 통과했지만 최종 검증으로 채택하지 않았다. 이후 정상 빌드에서 경로 수정·추가 복구 사례를 포함한 183개를 다시 실행했다.

세 번째 전체 2274개 통과 후, proof 조회 중 권한을 철회하는 두 사례에서 `true !== false`가 재현됐다. 현재 작업과 권한을 조회 후 다시 확인하도록 고쳤다. 이 결함 재현 로그도 최종 기록에 남긴다.

## 남은 범위

P4-01 전체는 진행 중이다. 요청·수락·답변·확인 도구와 양쪽 작업의 의무 연결, 사건 기반 wake, 역할 간 예산, 두 runtime의 반증·가설·재계획 전체 흐름은 다음 단위다. 현재 모든 효과 receipt metadata를 컨텍스트에서 보호하므로 장기 실행에서는 예산에 맞는 묶음 조회/보존 정책이 추가로 필요하다. 예산 부족 시 필요한 효과 기록을 조용히 버리는 방식은 사용하지 않는다. 병렬 시험에서 파일 저널의 복합 proof 조회 시간이 증가하는 것을 관찰했으므로, 후속 성능 평가에서는 저장소별 조회 횟수·시간과 재검증 비용을 따로 계측해야 한다. 이번 시험의 대기 시간 조정은 그 성능 개선이 완료됐다는 의미가 아니다.

기존 읽기 입력을 스스로 철회하는 등 입력을 변경하는 쓰기는 과거 관측을 무효화할 수 있다. 저장 효과 확인과 입력 격리/재계획은 별도 절차이며 현재 receipt 복구가 그 입력을 새로 유효하게 만들지 않는다. 실제 모델/API·사내 SIEM/EDR/Knox·외부 A2A·운영 배포 시험은 수행하지 않았다.
