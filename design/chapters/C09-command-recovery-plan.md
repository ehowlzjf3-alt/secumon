# C09 저장 응답 불명과 원 명령 복구

2026-09-09 · checkpoint395 · 기준선 b783902. 구현·로컬 검증을 마쳤다. 같은 최종 build2에서 신규12개·관련95개, 고유107개가 통과했고 소스·컴파일2,505파일의 최종 대조가 일치했다. 최초 타입 오류2건과 교정은 결과 문서에 기록했다. 직전 checkpoint394는 구현·같은 빌드49개 통과·푸시·원격 일치까지 완료했다. 이번 단위는 이미 처리한 명령의 복구와 새 실행의 보호를 연결한다. 전체 C09와 goal은 진행 중이다.

## 문제와 결과 행동

파일 저널에 제어 명령을 게시한 뒤 응답이 실패하면 저장은 되어 있어도 관측 중단 신호가 누락될 수 있다. 원 명령을 다시 읽으면 기존 구현은 중복으로 반환하므로 같은 조회가 계속 기다릴 수 있었다. 반대로 과거 명령이라고 무조건 현재 업무를 중단하면 명시 재개 후 시작한 새 조회까지 멈춘다.

각 취소 등록은 작업을 시작할 때 사용한 상태의 revision(저장 상태 번호)을 보유한다. 명령을 저장한 원 revision보다 이전 상태에서 시작한 실행만 중단한다. 원 명령 영수증과 현재 업무 상태를 분리하며, 영수증 확인이 새 실행이나 업무 완료를 뜻하지 않게 한다.

## 구현 순서와 재사용

1. 기존 transact 반환에 commandRevision을 더한다. 실제 새 저장·원 영수증 조회·저장소 중복 반환 모두 원 명령의 게시 번호를 제공한다. 현재 상태 번호를 과거 명령 번호로 사용하지 않는다.
2. 기존 ExecutionRuntime 취소 등록에 시작 상태 번호를 더한다. 업무 제어의 새 저장·중복 재개는 원 게시 번호 이전의 실행만 중단한다. 모델·도구·컴퓨터 대조·임무 관측은 이미 읽은 상태 번호를 전달한다. 별도 타이머나 이력 전체 검색을 추가하지 않는다.
3. 저장 호출 실패 때 정확한 명령 ID·입력 digest와 원 영수증을 대조한다. 확인된 경우에만 중단 신호를 복구하고 원 오류는 그대로 호출자에게 전달한다. 원문 조회 실패·불일치·게시 전 실패를 저장 성공으로 바꾸지 않는다. 이후 원 세션 입력 재개는 기존 접수·정산 경로를 따른다.
4. Resident 관측 제어도 예정 checkpoint와 정확한 원 게시 영수증을 확인하여 기존 poll 중단을 회복한다. 원 호스트 권한·원 사건·커서·세션·영수증·공유 source 수명을 보존한다.
5. 실제 로컬 파일 저널의 게시 전·후 오류, 원 명령 재개, 명시 재개 후 새 poll 보호를 검증한다. 원 로그와 최종 소스 지문을 기록하며 직접 영향 회귀만 실행한다.

## 검증과 한계

신규 시험은 실제 저장소와 제어 가능한 원천 callback을 사용한다. 파일 저널의 published 단계 오류와 실제 fsync 오류 주입을 구분해 기록한다. 실제 모델/API 시험은 중단 상태이며 사내 서비스 호출은 하지 않는다. 테스트 수·성공 여부는 실행 종료 후 결과 문서와 checkpoint395에 기록한다.

다른 프로세스에서 발생한 명령의 즉시 전달, 취소 비협조 callback 강제 종료는 이번 단위의 완료 범위가 아니다. 현재 resident pause(workId)는 새 의도를 전달하는 API다. 다른 호출자가 resume한 뒤 같은 bare pause를 호출하면 과거 요청과 구별할 ID가 없으므로 새 pause로 처리된다. 이 경우까지 재시도를 식별하려면 후속 제어 입구에 명령 ID·예상 상태를 연결해야 한다.

후속은 C09 이력/컨텍스트 비용·과거 규칙·제어 UI, C05 권한 재허용 완주, C06 기억 HTTP·권한·브라우저, C10 초기 복원·플랫폼·설치·실제 PG와 최종 통합이다. 이전 검증을 이번 실제 연동 증거로 합산하지 않는다.
