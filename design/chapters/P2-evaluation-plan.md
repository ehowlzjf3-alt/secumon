# P2-05 고정 전체 실행 평가

2026-09-05 · 착수 기준 v0.27 / 1,168개 로컬 시험

이전 예산 단위는 실제 할당·진입·정산을 구현하고 90개 새 시험과 전체 1,168개 검증·학습 기록을 남겼으므로 진전이다. 이번에는 [모드 계획의 5번](/Users/seunghanee/Documents/secumon/design/chapters/P2-modes-plan.md), [실행 모드 평가](/Users/seunghanee/Documents/secumon/design/11-execution-modes.md), [재생/새 추론 구분](/Users/seunghanee/Documents/secumon/design/14-scope-and-priorities.md)을 실제 실행 세트와 측정으로 연결한다. 전체 P0–P6 목표를 유지한다. 실제 모델/API 시험 중단도 유지한다.

## 고정할 비교와 판정

두 업무군(문서 비교/관측 검토), 두 영속 저장소(SQLite/파일 저널), 세 요청 모드(auto/fast/deep)를 같은 입력·도구·계획 스크립트·완료 기준으로 비교한다. 기존 네 fixture는 원자료로 재사용하고 기존 정적 checkpoint 점수를 전체 실행 평가 점수로 쓰지 않는다. 한 work의 실제 누적 상태와 영수증·결과를 관측한다.

예상 최종 제어, 필요한 원본 ID/사실/가설 판단, 완료 가능 업무 여부, 금지된 결과/호출을 실행 전에 고정한다. runtime의 완료 함수가 true라는 이유만으로 성공시키지 않고 독립적인 fixture 정답 조건과 중간 결과를 검사한다. 잘못된 완료는 최종 상태뿐 아니라 중간의 completed 상태와 result 전달에서도 확인한다.

빠른 모드의 정당한 제한은 계약 준수다. 실제 목표를 완료한 것과는 따로 센다. 회신 대기·사용자 취소·자료 결손을 완료 성공으로 바꾸지 않는다. 성공 수/분모, 미완료 수, 비교에서 제외한 이유를 함께 보고한다.

## 실행 세 가지

1. **새 실행:** 새 디렉터리와 새 work에서 고정된 로컬 planner/tool/sink 대역을 실제 runtime 경로로 실행한다. 모델 호출은 scripted fresh이며 실제 LLM 추론이 아니다.
2. **실행 재개:** 모델 또는 도구 응답이 저장됐지만 아직 채택되지 않은 시점에 저장소를 닫고 다시 연다. 기존 응답은 다시 호출하지 않고 채택하며, 이후 필요한 새 호출과 비용은 재개 실행에 기록한다. 다음 날 회신과 compact도 같은 정본에서 이어간다.
3. **기록 재생:** 저장한 이벤트/명령 영수증 상태·model/tool 원응답·최종 전달 projection·재개 패킷을 읽어 무결성과 판정을 확인한다. workflow.run을 호출하지 않는다. 상태 commit/artifact put에는 실패하는 계수기를 두고 model.propose/tool.execute/sink.send/sink.lookup capability는 재생 API에 제공하지 않는다. 자료/정책/버전이 없거나 달라지면 재생 불가를 기록한다.

이벤트만으로 모든 상태를 다시 만드는 범용 event-sourcing reducer는 현재 없다. 이번 기록 재생은 실제 저장된 receipt snapshot과 원응답을 검증하는 기능이다. 과거 delivery 전체 이력은 별도 평가 관측에 보존한다.

## 필요한 시나리오

단순 완료, 복잡 조사, 늦은 반증, 부분 결과, 원본 결손, 권한 철회, 반복 도구 오류, 반복 모델 오류, 다음 날 회신, 실행 중 모드 변경, 실행 중 취소, 저장 모델 응답 재개, 저장 도구 응답 재개, compact 뒤 재개, 전달 결과 불명, 상태 조회를 같은 업무군/저장소/모드 조합에 적용한다. 예약 중 취소와 과거 계약/자료 무효화는 별도 실패 시험에도 포함한다.

늦은 반증과 회신은 처음부터 기다려야 하는 조건 또는 처음 계획의 미완료 자료로 선언한다. 완료한 업무에 임의로 자료를 덧붙여 과거의 완료를 실패로 재분류하지 않는다. 복잡 요청의 fast 상한으로 진행하지 못한 시나리오는 실제 도달 단계도 기록한다.

## 기록과 지표

- 입력/기대 조건, 실제 실행 종류, 목표/정책·planner/도구/지침/context/progress 버전, 소스/lock/환경 hash를 manifest로 고정한다. source와 실제 dist의 대응·현재 hash를 빌드 기록으로 확인하고 평가 진입 전과 종료 후 변경을 검사한다. 결과 파일은 과거 실행을 덮어쓰지 않는다.
- 논리 사용/예약/사용량 불명과 실제 model/tool/send/lookup 진입, 채택·재사용·고유 조회·반복 조회를 구분한다. 내부 조회 bytes·context bytes/추정 토큰은 외부 실제 청구액과 분리한다.
- 접수, 첫 검증 근거, 첫 유용한 **전달 답변**, 검증 완료 시각을 구분한다. 접수 문구와 근거를 내부 저장한 시각을 첫 유용한 답변으로 세지 않는다. 답변이 없으면 지연은 null이다.
- 고정 가상 시계의 지연과 실제 로컬 파일 I/O를 포함한 wall time을 분리한다. p50/p95와 표본 수/산식을 명시하고, 적은 합성 표본의 결과를 운영 성능 보장으로 주장하지 않는다.
- 상태 조회/재생이 추가 추론·전송·예산 차감·원장 초기화를 하지 않는지 확인한다. 대기 구간에도 모델 반복 실행이 없어야 한다.

## 구현 순서와 완료 조건

평가 타입/독립 판정·집계 → 고정 사례와 실제 workflow runner → 원응답/receipt 재생 및 실패 검증 → CLI/보고서 → 두 업무군·두 저장소·모드별 전체 세트 실행 → 원본/버전/지표와 학습 기록 순서로 진행한다. 독립 검토와 회귀 시험으로 누락된 범위를 보완한다. 새 실행/재개/재생을 모두 연결해 검증한 뒤 P2-05의 local_contracts를 판정한다. 실제 모델 조건이 남은 전체 작업 상태는 in_progress다.

학습의 핵심은 “안전하게 멈췄다”와 “답을 완성했다”, “기록을 재생했다”와 “추론을 다시 수행했다”, “합성 시간을 줄였다”와 “실제 서비스를 빠르게 만들었다”를 각각 구분하는 데 있다.
