# C04 첫 구현 — 일반 요청에서 답변까지

2026-09-07 · 첫 연결 단위의 구현·로컬·Linux 검증을 마쳤다. 아래는 착수 당시 계획이며 현재 사실은 [결과](C04-general-turn-result.md)와 [사용법](C04-general-turn-usage.md)을 따른다. C04 전체는 진행 중이다.

사용자가 시나리오를 고르지 않고 요청하면, 기존 세션에 원문을 저장하고 같은 실행 루프로 답변·추가 질문·도구 실행을 이어가게 한다. 긴 업무를 위한 기반이 단순한 문장 교정에도 쓰이도록 연결하는 단계다. 새 실행 엔진이나 필수 리드–워커 구조를 만들지 않는다.

[연결 지점 검토](C04-entry-preparation.md)와 [앞선 범용성 검토](prompt-generality-review.md)를 따른다. C03의 검증된 원문·compact·개인 기억 계약을 선행 조건으로 사용한다. PostgreSQL과 Windows 연결은 C03/C01에 남겨 두며, 이 순서 변경으로 해당 범위가 완료되거나 제외되는 것은 아니다.

## 이번에 완성할 사용자 흐름

담당 열기 → 요청 원문 접수 → 업무와 자원 귀속 → 현재 문맥 조합 → 모델의 답변/질문/계획 제안 → 검증 → 필요한 도구 실행 → 답변 준비와 전달 → 같은 세션의 다음 요청.

짧은 요청은 한 번의 주 모델 턴으로 답변할 수 있다. 도구가 필요한 요청은 기존 계획 검사·실행기를 거쳐 관측을 얻은 뒤 답변한다. 질문을 보냈으면 대기하고, 사용자 답변이 원문에 적용된 다음 재개한다. 도구 실행 성공과 답변 준비, 사람에게 전달된 상태는 구분한다.

첫 연결은 명시적으로 선택한 합성 제공자로 검증한다. 실제 모델이 없으면 연결되지 않았다고 표시하고, 자동으로 대역이나 외부 API로 바꾸지 않는다. 실제 모델/API 시험 중단을 유지한다.

## 채택할 경계

| 항목 | 이번 선택 |
|---|---|
| 요청의 주인 | 기존 `SessionService.accept`가 원문과 정상 업무를 확정한 뒤 모델을 예약한다. 처음부터 업무 ID와 같은 자원 장부를 사용한다. |
| 새 업무/진행 업무 | 첫 단위에서는 CLI/Web이 명시적으로 선택한다. 진행 업무는 기존 업무 ID·목표 버전과 원문을 대조한다. 모델이 임의 업무나 권한을 선택하지 않는다. |
| 응답 요구 | 새 Goal에 선택적인 응답 요구를 추가한다. 이 요구가 있는 경우만 사실 조건의 빈 배열을 허용한다. 기존 Criterion 구조·직렬화·해시와 사실 조건의 의미는 보존한다. |
| 답변의 근거 | 생성한 본문, 사용한 근거, 자체 검토 결과를 따로 기록한다. 자체 검토를 독립 관측이나 사실 검증으로 세지 않는다. 사실 조건이 있으면 기존 근거 검사를 함께 충족해야 한다. |
| 완료 판정 | 본문·출처·권한·원문과 기억의 현재성 검사, 유효한 답변 평가, 미완료 의무 검사를 통과해야 결과를 준비한다. 필수 전달 의무까지 끝나야 completed다. 모든 답변에 사람 승인이나 별도 critic 호출을 강제하지 않는다. |
| 질문 | 기존 response 의무와 outbox를 사용한다. 질문 전송만으로 업무를 완료하지 않으며 재시작 때 같은 질문을 중복 생성하지 않는다. |
| 모델 호출 | 기존 PlanningRuntime의 예약·호출·응답 저장·사용량 정산·재개를 확장한다. 목적별 입력/채택은 작은 helper로 분리할 수 있지만 별도 장부나 두 번째 루프는 만들지 않는다. |
| 프롬프트 | 공통 행동 원칙·담당 목적·현재 packet·필요한 지침·반환 형식을 조합한다. 실제 고정 입력에 버전/지문을 포함하고, 설정이나 모델이 바뀐 오래된 호출을 재검사한다. |
| 스킬 | off이면 지침을 로딩하지 않는다. explicit/on-demand는 기존 선택 계약으로 제한한다. 전체 목록과 본문을 첫 입력에 일괄 삽입하지 않는다. |
| 답변 교체 | 후보/평가·본문 지문을 결과 ID와 전달 전 검사에 연결한다. 사실값이 같아도 새 답변과 옛 답변을 구분한다. 기존 사실 전용 결과의 ID 계산은 유지한다. |

응답 요구에 원문 message ID/본문 지문을 넣을 수 있지만 자기 자신을 포함하는 최종 접수 영수증의 지문을 다시 payload에 넣지는 않는다. 실제 적용 기준은 기존 `conversation.session`의 원문 영수증 연결을 재사용한다. 컴퓨터 용어로 이 자기 참조는 계산이 끝나지 않는 순환 해시를 만들기 때문이다.

## 구현 순서와 담당 경계

1. **공통 계약과 완료 의미.** 응답 요구, 주 턴 결과, 답변 후보/평가를 작게 정의한다. domain의 완료·제어·모드 판정과 application 계약이 같은 조건을 사용하게 한다. 일반 요청을 가짜 facts.done이나 가짜 도구 관측으로 표현하지 않는다.
2. **기존 모델 수명에 연결.** 답변/질문/계획을 구분하고 현재 packet을 사용한다. 새 목적의 지문을 명시적으로 확장하되 기존 planning/compact의 저장 형식을 보존한다. 완료한 읽기를 다시 수행하지 않고 필요한 최종 답변 턴으로 진행한다.
3. **원문 접수와 전달.** 일반 요청의 공통 application 진입점을 만들고 기존 세션·outbox를 조합한다. 답변 artifact와 질문 의무를 채택하며, 전송 직전 현재 후보·원문·자료 범위를 재검사한다.
4. **CLI/Web과 호스트 조립.** 기존 담당 저장소를 사용한다. 모델 프로필은 호스트가 등록한 제공자에 연결하며, 첫 합성 제공자는 명시 선택한다. 접수·필요 질문·의미 있는 상태·최종 결과만 대화에 표시한다.
5. **같은 소스 검증과 기록.** 신규 사용자 흐름과 영향을 받은 기존 회귀를 먼저 확인하고, 최종 소스가 고정되면 Linux 통합 검증을 한 번 수행한다. 실패가 없고 관련 변경도 없으면 같은 전체 시험을 반복하지 않는다.

위 단계는 한 번의 사용자 흐름을 완성하는 순서다. 계약 파일 작성이나 대역의 단독 응답만으로 이번 단위를 완료하지 않는다. API 키, Knox, 사내 MCP 등록, PostgreSQL 서버는 이 검증의 선행 조건이 아니다.

## 수용할 증거

- 시나리오 ID 없는 문장 교정과 한 번의 읽기 후 답변을 실제 CLI/HTTP 접수부터 기존 저장·실행·전달까지 확인한다.
- 질문 → 사용자 답변 → 같은 업무 재개, X 완료 → 같은 세션 Y, compact 요약과 선택 기억의 실제 모델 입력을 확인한다.
- 늦은 모델 응답에서 수정·취소·기억 정정·모델/프롬프트 변경을 반영하고, 이미 사용한 자원을 숨기지 않는다.
- 답변 저장 뒤 실제 프로세스 종료와 같은 ID 재개에서 저장된 응답을 재사용하고 전달을 중복 생성하지 않는다.
- 같은 사실로 답변 후보만 바뀐 경우 옛 본문 전달을 막는다. 전달되지 않은 상태를 완료로 표시하지 않는다.
- 잘린 반환·거절·usage 불명·용량 초과·무진전을 성공으로 처리하지 않는다. 불필요한 도구·가설·스킬 호출은 만들지 않는다.
- 기존 Goal·계획·compact·결과 ID 호환 회귀를 확인한다. 기본 SQLite를 중심으로 검증하고 문서 기억/파일 저널에는 변경된 조립 경계만 추가 확인한다.

대역의 정답과 구조 검사를 실제 모델의 의미 품질로 확대하지 않는다. 글의 적절성·자연어 목표 해석·장기 재계획의 실제 품질, 독립 반론/C08, 자동 기억 선별·호출 최적화/C05는 별도 남은 범위다. 선택 기능과 Windows/PostgreSQL의 미완료 항목은 전체 백로그에서 계속 추적한다.
