# C09 상시 임무 제어 명령과 사용자 입구 결과

2026-09-09 · checkpoint397 · 기준선 `c741ffaa76cbae8cc334d3eaaf48255f88543de3`.

상시 임무의 관측 일시정지·재개·종료에 **명령 ID와 예상 제어 버전**을 연결했다. 같은 요청의 응답이 유실되면 원 영수증으로 확인하며, 그 사이 재개한 관측을 과거 일시정지의 재전달로 다시 멈추지 않는다. CLI와 Web에서 등록 당시 사용자 대화와 연결 전체를 확인한다. 이미 접수한 사건 업무의 제어와 관측 제어는 별개다.

## 구현 내용

- 기존 checkpoint의 선택 `controlPublication`에 원 명령을 보존하고 같은 단일 commit에서 `resident_control` 영수증을 저장한다. 명령 키는 담당·제어 업무·명령 ID로 정한다. 원문 SHA checkpoint 식별자는 유지하며 별도 alias 영수증이나 DB 쓰기 프로토콜을 추가하지 않았다. 후속 일반 poll·기존 호스트 저장은 명령 정보를 제거하고 종전 SHA 영수증을 사용한다.
- 같은 ID·같은 요청은 원 적용 번호와 새로 조회한 현재 상태를 반환한다. 다른 요청 내용은 충돌, 새 요청의 오래된 기준 번호는 stale로 거절한다. 현재 권한·원 자료·영수증·담당 정의를 다시 확인한다. 저장 결과 불명은 원 오류를 보존하며 명시 재전달로 회복한다.
- `mission status/pause/resume/stop` CLI는 이미 준비된 담당만 열고, 등록·새 사용자 대화·관측·모델 실행을 자동 시작하지 않는다. Web의 별도 상태/명령 API는 현재 선택 사용자 세션과 binding, 기존 인증·CSRF, 화면 공개 조건을 확인한다. 일반 업무의 기존 세션 경계를 완화하지 않았다.
- Web 접이식 패널은 접수 안내와 상태를 간결하게 표시한다. `active`는 ‘관측 허용’으로 표시하며 실제 실행 중이라는 뜻으로 쓰지 않는다. 같은 탭에서 응답이 불명인 명령의 ID·최초 기준을 보존하고 상태 조회만으로 확정하지 않는다. 현재 제어 버전은 내부 claim 정리에서도 증가하므로 명령 횟수가 아니다.

사용법과 실제 호출 예시는 [사용 안내](C09-resident-command-usage.md)에 있다.

## 실행한 검증

최종 코드에 대응하는 **신규16개·관련46개, 고유62개**가 통과했다. 재실행한 시험을 고유 개수에 더하지 않았다.

| 실행 | 빌드 | 결과 | 범위 |
| --- | --- | --- | --- |
| target1 | build3 | 5/5 | SQLite/file-journal 명령 재전달·재열기, 재개 후 새 poll 보호, 실제 저널 발행 전/후 오류 |
| entry1 | build3 | 10/11 | 실제 CLI 자식 프로세스4개, localhost HTTP4개, 브라우저 상태 helper3개 |
| resident1 | build3 | 20/21 | 기존 resident 입구·관측 제어·중단·명령 회복 |
| host1 | build3 | 25/25 | CLI 옵션·선택 엔진 launcher, 일반 대화 HTTP·기존 Web 서버 |
| target2 | build4 | 9/9 | 수정한 CLI 시험4개와 기존 resident 제어 시험5개 전체 재실행 |

최초 두 기능 시험 실패는 제품 수정 없이 시험의 입력/기대값을 보완했다.

1. `--control-revision -1`은 Node 옵션 파서가 먼저 거절했다. `--control-revision=-1`로 수치 검사를 확인하고, 원 전달 방식의 파서 거절도 별도 단언으로 유지했다.
2. 기존 pause/resume 반복 시험은 과거 active 상태와 현재 상태를 통째로 비교했다. 새로 조회 가능한 제어·상태 버전의 정확한 `+2` 증가와 나머지 대화·사건·대기 데이터 보존을 함께 확인하도록 보완했다.

build3→build4의 컴파일 파일2,538개 중 두 시험의 JS·소스맵4개만 바뀌고 **나머지2,534개 및 제품 바이너리는 같았다**. 변경 파일9개 시험을 다시 실행하고 동일 파일의 기존 통과를 재사용했다. 원 실패 로그와 [파일 대조](../../runtime/evidence/checkpoint397-build-comparison.json)를 보존한다.

build4와 core3는 exit0이다. 구조 검사202개/위반0이며 이후 제품 import 관계가 같아 재사용했다. core3 이후 코어 제품 소스는 바뀌지 않았다. 최초 core1의 nullable subscription 오류, build1의 nullable 반환 추론 오류는 명시 검사와 never 함수 선언으로 교정했고 실패 빌드에서 기능 시험을 실행하지 않았다. build2는 성공했으나 Web 상태 용어를 정정한 build3에서 기능 시험을 시작했다. 시험 후 최종 소스·컴파일 대조도 일치한다.

## 남은 범위

이번 검증은 macOS arm64, 실제 임시 SQLite/file-journal, 로컬 CLI 프로세스와 HTTP다. 모델은 호출하지 않거나 기존 결정적 대역만 사용했다. UI helper 시험은 실제 DOM·클릭·렌더링 시험이 아니다. 브라우저 새로고침 이후 pending 명령 복원도 아직 제공하지 않는다.

다음은 **다른 프로세스의 resident 제어를 진행 중인 관측 호스트에 즉시 전달하는 연결**이다. 현재 상태는 저장되지만 다른 프로세스의 진행 중 poll을 즉시 취소하는 신호까지 제공하는 것은 아니다. 전체 세션 컨텍스트 비용, 동일 목표의 장기 사건 중복 확인·용량·보관도 남는다.

C05 권한 재허용 뒤 원 수집 완료 사용, C06 기억 HTTP·권한·지연·브라우저, C10 초기 복원 중단·현재 Linux/native Windows·실제 PostgreSQL·설치 네이티브 패키징, 사내 MCP/Knox·외부 A2A·배포/최종통합 잔여를 유지한다. 실제 모델/API 시험은 사용자 중단을 유지한다. **C09와 전체 goal은 진행 중**이다.

사용자의 메인 프롬프트 질문은 현재 `agent-turn-prompt.ts`와 `StructuredAgentTurnAdapter` 소스로 구현·연결을 확인해 답했다. 프롬프트를 재작성하지 않았으며 실제 모델의 범용 추론·반론·한국어 응답 품질을 검증 완료로 표시하지 않는다.
