# MCP 호출 제한: 기다린 뒤 이어가기

2026-09-06 · v0.41 · 로컬 구현·검증 완료

도구가 제한 응답을 보내면 다음 호출이 가능한 시각을 작업 상태에 저장한다. 같은 작업을 다시 열거나 compact를 수행해도 이 시각을 현재 시각부터 다시 계산하지 않는다. 시각이 되기 전에는 해당 조회의 예약과 전송을 막고, 별개의 실행 가능한 작업은 계속 선택한다.

## 배운 개념

- **기한과 재개 시각:** deadline은 그때까지 끝내야 하는 상한이고 retryAt은 그때부터 다시 호출할 수 있는 하한이다. 같은 타이머 의미로 처리하면 안 된다.
- **대기는 실패 반복과 다르다:** whole-tool 제한은 ReadDeferral로, 일부 항목 제한은 ReadItem.retryAt으로 저장한다. 실패를 빈 성공 페이지로 바꾸지 않으며 실제 수행한 호출은 예산에서 남는다.
- **요약과 근거:** retryWakeAt은 스케줄 조회를 돕는 값이다. 실행 직전에는 저장된 응답과 checkpoint로 시각을 확인한다. 여기서 원본은 실행 중 수집한 응답을 뜻한다.
- **명시 재개:** 다음 TaskSpec.readResume는 이어받을 부모와 checkpoint를 지정한다. 완료한 항목·snapshot·cursor·누적 호출 한도를 이어받으며, 이미 성공한 항목은 다시 읽지 않는다.

## 구현 연결

ReadResponse/ReadCheckpoint에 대기를 추가하고 기존 ReadCollections → ReadCheckpoints → execution/planning 경로에 연결했다. MCP 응답 해석은 외부 어댑터에 둔다. 검토된 지연 값을 최초 응답 저장 시각에 더하며, 음수·소수·overflow·과도한 지연·상충 정보를 거절한다. 코어는 MCP나 특정 저장소에 종속되지 않는다.

Control.wait와 저장소 runnable(now)를 재사용한다. CLI는 대기 상태에 다음 확인 시각을 표시한다. 현재 시험에서는 host가 시계를 진행시키고 runnable/workflow를 명시 호출하며, 상시 백그라운드 스케줄러는 이번에 구현하지 않았다.

요약의 phase나 successor 표식으로 원본 검사 대상을 먼저 줄이면 대기를 우회할 수 있다는 검토 결과를 반영했다. 현재 목표의 조회 checkpoint를 확인한 뒤 대기 여부를 결정하고, 후속 실행이 있다는 주장도 실제 부모·자식 연결로 검증한다.

## 검증 기록

관련 시험 **110/110**이 통과했다. 실제 로컬 MCP 문서 batch·관측 page와 SQLite/file journal을 사용했다. 프로세스 SIGKILL 후 재개 4개에서 고정 시각 3500을 유지하고, 그 전 모델·새 원격 호출·후속 실행 예약이 없으며, 시각 도래 후 남은 항목만 처리하는 것을 확인했다. 공개된 대기 시각과 pause·취소·기한·호출 한도는 순수 제어 시험으로도 확인했다.

첫 관련 실행은 109/110이었다. 새 요약 변조 시험의 준비 단계가 저장소 스키마에서 먼저 거절되었으므로, 구조상 유효하되 원 응답과 다른 요약을 만드는 방식으로 시험을 수정했다. 수정 후 전체 110개가 통과했다. 최초 실패 로그도 보존한다.

전체 native verify는 **2089/2089**, 실패·취소·건너뜀 0으로 종료했다. 코어 타입 검사, 계층 검사 99파일/위반 0, fixture 4개/22판정도 통과했다. 신규 시험은 MCP 30·복원 4·제어 8·checkpoint 4·proof 3으로 49개다. [실행 로그·소스/빌드 기록](/Users/seunghanee/Documents/secumon/runtime/evidence/P3-mcp-waits-local-verification.json)에 현재 파일과 실행 산출물의 일치를 저장했다. 별도 lint 명령은 없다. 과거 Python 구현·압축 파일 전체·이전 모든 검증 기록의 반복 대조는 수행하지 않는다.

## 한계와 다음 단계

실제 모델/API 시험은 취소 상태다. 사내 MCP·Knox·운영 시스템·실제 HTTP Retry-After는 검증하지 않았다. 대기 중 로컬 원본 검증 비용은 발생하므로 “모델·원격 호출 0”을 “비용 0”으로 해석하지 않는다. 동일 work/query 범위의 제한이며 조직 전체의 endpoint quota는 별도 정책이다.

다음 구현 단위에서는 수집 종료를 업무 완료의 근거로 사용할 수 있는 조건과, 응답을 받았으나 진행 상태에 아직 반영하지 못한 경우의 복원 정책을 정한다. 과거 코드와의 동작 일치를 완료 조건으로 삼지 않는다. 이후 채널 통합과 다중 에이전트 단계는 전체 플랜을 따른다.
