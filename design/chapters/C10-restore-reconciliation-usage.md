# C10 복원 뒤 외부 기록 대조 사용법

2026-09-08 · checkpoint390 구현 소스 기준. 주 작업에서 같은 최종 build1의 고유72개(대상26개·관련 회귀46개)가 모두 통과했다. 실패·취소·건너뜀0, 빌드·코어 타입 검사 exit0, 계층200/위반0, 최종2,454파일 대조 일치다. 로컬 계약·실제 파일 효과·CLI/HTTP·강제 종료 복구 범위의 결과이며 실제 사내 서비스 인수는 아니다. [검증 결과](C10-restore-reconciliation-result.md) · [체크포인트](../../runtime/evidence/checkpoint390.json). 커밋·푸시와 원격 일치 확인은 이 기록 시점에서 주 작업이 진행할 단계다.

과거 백업을 복원해도 백업 이후 보낸 메시지나 외부에 쓴 파일은 남아 있다. 이번 연결은 복원된 담당의 기록과 외부 기록이 일치하는지 확인한 뒤 일반 실행을 재개하도록 한다. 백업에서 사라진 실행을 다시 보내는 문제를 막기 위한 경계다.

| 단계 | 확인하는 사실 | 다음 단계와의 관계 |
| --- | --- | --- |
| 파일 복원 | 지정한 백업의 자료가 원래 경로에 복원됐다. | 외부 시스템의 과거 동작을 취소하지 않는다. |
| 신원 재등록 `identity-rebind` | 기존 담당 ID가 이번 복원 디렉터리를 가리켜도 되는지, 같은 백업·등록 이력으로 확인한다. | 외부 효과까지 대조했다는 뜻은 아니다. |
| 외부 기록 대조 `restore-reconcile` | 이번 복원본과 외부 실행·송신 등의 기록이 맞고, 등록된 조회 소스들이 현재성을 확인했다. | 일반 실행 입구의 복원 차단을 해제한다. |
| 작업 재개·완료 | 기존 실행 루프가 원래 작업의 근거·권한·완료 기준을 검사한다. | 대조 영수증만으로 작업·목표를 완료하거나 자원을 정산하지 않는다. |

원래 호스트의 담당 신원 등록이 남아 있다면 기존 `identity-rebind` 절차를 먼저 따른다. 새 호스트에서의 신원 등록과 외부 기록 대조 역시 별개의 조건이다. [신원 복구 구현](../../runtime/src/infrastructure/agent-host-identity-recovery.ts)과 [이번 계획](C10-restore-reconciliation-plan.md)을 함께 참고한다.

## 상태 조회와 실행

상태 조회는 저장소나 모델 제공자를 열지 않고, 신원을 새로 등록하지도 않는다. 일반 실행과 같은 호스트 신원 등록 경로를 사용해야 한다.

```sh
secumon-agent lifecycle restore-status --directory "<담당 절대경로>" --json
```

| 반환 내용 | 의미와 다음 행동 |
| --- | --- |
| `not_restored` | 복원 완료 표식이 없는 일반 담당이다. 이 대조 절차의 대상이 아니다. |
| `required` | 이번 복원의 대조가 필요하다. `reason`에 신원 등록 필요, 복원 고유 번호 없음, 외부 대조 필요, 영수증 불일치 또는 게시 중단 등이 나온다. |
| `unresolved` | 대조 명령이 발견한 미확인·불일치 기록을 `reports[].unresolved`로 반환한다. 영수증을 발급하지 않으며 이후 상태 조회는 계속 `required`다. |
| `reconciled` | 이번 복원과 신원에 묶인 대조 완료 영수증이 있다. 일반 입구에서 원래 작업을 재개할 수 있다. |

대조 실행에는 호스트가 등록한 조회 소스가 필요하다. 다음은 해당 등록을 제공하는 호스트 시작 프로그램의 명령 형태다.

```sh
node "<등록된 호스트 시작 프로그램>.mjs" lifecycle restore-reconcile --directory "<담당 절대경로>" --offline --json
```

`--offline`은 담당의 실행기, 구형 엔진과 직접 DB 접근을 중지했다는 명시다. 인터넷 연결을 끄는 옵션은 아니며, 외부 기록 대조에 필요한 읽기 전용 조회는 수행할 수 있다. 관리 절차는 유지보수 잠금을 사용하므로 실행 중인 담당이나 다른 유지보수 작업과 겹치면 거절한다.

표준 시작 프로그램에는 임의의 사내 시스템 대조 소스가 내장되어 있지 않다. 등록 없이 실행하면 `agent_restore_sources_required`가 나온다. `--confirm` 같은 일괄 승인 옵션이나 보고서 JSON을 입력해 완료 처리하는 옵션은 없다. `--json`은 출력 형식만 바꾼다.

## 호스트에서 조회 소스 등록

호스트 시작 프로그램이 [runAgentCli](../../runtime/src/presentation/agent-cli.ts)에 등록을 전달한다. 아래는 연결 부분을 설명하는 TypeScript 예시다. 실제 배포 엔진에서 `runAgentCli`와 [AgentRestoreReconciliationSource 타입](../../runtime/src/application/agent-restore-reconciliation-contracts.ts)을 가져오고, 배치한 시스템에 맞는 조회 어댑터를 준비해야 한다.

```ts
async function startRestoreManagement(
  args: string[],
  identityRegistryDirectory: string,
  sources: ReadonlyMap<string, AgentRestoreReconciliationSource>,
) {
  await runAgentCli(args, {
    identityRegistryDirectory,
    restoreReconciliation: { sources, timeoutMs: 30_000 },
  });
}
```

`sources`는 소스 ID와 읽기 전용 어댑터의 목록이다. 담당 내부 설정·모델 답변이 실행 권한을 만들어 내는 경로로 사용하지 않는다. 모든 소스의 함수와 버전은 조회를 기다리기 전에 캡처한다. 조회 도중 등록 목록이나 함수를 바꿔 다른 검증기로 대체할 수 없다.

각 어댑터는 다음 계약을 충족해야 한다.

- `revision`: 해당 조회 어댑터 계약의 버전이다.
- `inspect(basis, signal)`: 이번 복원의 기준을 받아 원본 기록을 읽고 보고서를 만든다. `basis`에는 담당 ID, 복원 고유 번호, 백업·완료 표식·호스트 신원·로컬 자료의 지문이 들어간다. 지문은 자료가 같은지 비교하는 값이다.
- 보고서: `sourceId`, `sourceRevision`, `basisDigest`가 등록·이번 대조 기준과 맞아야 한다. 원본을 찾을 수 있는 `evidence` 참조와 지문, 원본의 현재 버전인 `sourceHead`, `consistent` 또는 `unresolved` 판정과 미해결 목록을 포함한다.
- `verify(basis, report, signal)`: 게시 직전 원본 증거가 유효하고 외부 기록의 현재 버전이 여전히 보고서와 맞는지 다시 조회한다. 저장한 문자열을 자기 자신과 비교하거나 항상 `true`를 반환하는 구현은 검증이 아니다.

등록된 소스들은 합쳐서 담당의 **전체 외부 실행·메시지 송신·위임 작업·자원 배정 및 정산 기록**을 다뤄야 한다. 하나의 소스가 모두 조회할 수도 있고 여러 소스로 나눌 수도 있다. 코어가 임의의 외부 시스템 목록이나 누락된 연결을 자동 발견하는 것은 아니다. 배치 호스트가 조회 범위를 빠짐없이 등록할 책임이 있다.

특히 복원본의 `attempts`에 남은 실행만 조회해서는 안 된다. 백업 이후 외부에서 처리됐지만 복원본에는 없는 기록도 찾아야 한다. 빈 실행 목록은 “외부 효과 없음”의 증거가 아니다. 메시지 전달·작업 접수 영수증은 각각 외부 시스템의 상태를 뜻하며, 상대 작업 완료나 원래 목표 달성을 자동 입증하지 않는다.

소스의 두 메서드는 조회만 한다. 원 도구 입력 재전송, 메시지 발송, 원격 자료 수정, 누락 영수증의 임의 생성, 자원 정산은 수행하지 않는다. 취소 신호인 `AbortSignal`을 외부 조회에 전달하고 중단을 처리해야 한다. 원본을 읽을 수 없거나 누락 범위를 입증할 수 없다면 미해결로 남긴다.

## 중단·재시도와 복원 고유 번호

새 복원마다 `restorationId`라는 고유 번호를 발급한다. 같은 백업을 나중에 다시 복원해도 이전 대조 영수증을 재사용하지 않는다. 진행 중인 동일 복원을 이어갈 때는 원 번호를 유지한다. 복원 완료 표식과 대조 영수증·임시 게시 표식은 새 백업으로 계승되지 않는다.

구형 완료 표식에 고유 번호가 없으면 `restore_occurrence_required`로 재개를 보류한다. 보존한 원본과 검증된 백업을 유지하고 현재 복원 명령으로 다시 복원하는 절차가 필요하다. 기존 디렉터리를 덮어쓰거나 표식에 번호를 임의로 채우는 절차는 제공하지 않는다.

영수증 게시 중에는 `.secumon-restore-reconciliation-pending.json`을 남긴다. 완료 영수증 파일이 이미 생겼어도 이 표식이 남으면 상태는 `required`, 사유는 `reconciliation_publication_pending`다. 같은 명령을 다시 실행해 원 기준을 대조하고 등록된 모든 소스를 다시 조회·검증한다. 임시 영수증이 있다면 기준과 보고서가 모두 같을 때 원 영수증을 유지하며 게시를 마무리한다.

중단 이후 원문·신원·복원 기준이 달라졌거나 임시 영수증의 보고서가 새 조회와 다르면 `agent_restore_reconciliation_recovery_required`로 멈춘다. 표식과 영수증, 원본을 보존해야 한다. 다른 기준으로 임시 영수증을 교체하거나 충돌을 해결하는 일반 회복 절차는 후속 구현 항목이다. 표식을 무조건 삭제해 재개하는 방법으로 해결하지 않는다.

정상 게시가 완료된 뒤 같은 복원·신원으로 다시 호출하면 같은 영수증을 돌려주고 소스를 반복 조회하지 않는다. 이후 일반 작업이 메모나 이력을 갱신하는 것은 정상 동작이다. 일반 재시작은 매번 전체 로컬 자료를 이전 지문과 비교하지 않는다. 이후 개별 실행의 현재성은 기존 실행·권한·외부 효과 확인 경로가 담당한다.

## 비용과 확인 범위

일반 시작 경로는 작은 복원 표식·영수증과 현재 신원 연결을 검사한다. 매번 외부 조회나 전체 자료 해시 계산을 실행하지 않는다. 명시적인 오프라인 대조에서는 로컬 자료 지문을 만들고 외부 조회 전후·게시 경계에서 다시 확인한다. 기존 lifecycle 한도는 전체 4 GiB, 파일 하나 1 GiB, 항목 100,000개이며 큰 담당의 대조 비용은 자료량에 비례한다.

`timeoutMs` 기본값은 30초, 허용 범위는 1~60,000ms다. 모든 소스의 조회와 재검증에 하나의 마감시간을 적용한다. 소스마다 30초씩 새로 주지 않는다. 최초 로컬 자료 준비는 이 외부 조회 마감시간보다 앞서 수행되므로 명령 전체의 30초 완료를 보장하는 값은 아니다. timeout 후 늦게 도착한 보고서는 대조 완료로 채택하지 않는다.

이번 문서는 구현된 계약과 사용 경로를 설명한다. 실제 PostgreSQL·사내 MCP·Knox·A2A 등의 전체 기록 조회 소스, 운영 환경의 조회 권한·범위·성능은 검증하지 않았다. 실제 모델/API 시험 중단도 유지한다. 오래된 백업에 누락된 효과를 안전하게 가져와 작업·정산 기록과 합치는 일반 회복은 후속 작업이며, `unresolved`를 성공으로 간주하지 않는다.
