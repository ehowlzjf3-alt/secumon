# C10 복원 후 외부 기록 대조 결과

2026-09-08 · checkpoint390 · 기준선 `158b82b540cfd5d27e3a49b3e68fd3730eb10cc0`

복원 완료와 실행 재개를 분리했다. 담당을 여는 공통 입구는 현재 복원에 대응하는 외부 기록 대조 완료 증명이 있어야 저장소를 연다. 백업 이후 외부에서 이미 실행된 동작이 복원본에 없으면 등록된 조회 source가 불일치를 보고하고 재개를 보류한다. 기록이 일치하는 복원은 기존 세션·업무를 정상 재개할 수 있다.

[계획](C10-restore-reconciliation-plan.md) · [사용법](C10-restore-reconciliation-usage.md) · [실행 기록](../../runtime/evidence/checkpoint390.json)

## 구현한 내용

- 로컬/PG 새 복원에 `restorationId`를 붙였다. 같은 백업을 다시 복원해도 다른 번호이며 pending/완료 표식의 재시도는 원 번호를 보존한다. 기존 신원 rebind는 번호를 포함한 원 표식을 대조한다.
- 호스트 등록 source의 읽기 전용 `inspect`/`verify`를 연결했다. 모든 등록 source에서 현재 복원·자료 지문에 대응하는 보고서와 자료 참조가 필요하다. unresolved가 하나라도 있으면 완료 증명을 발급하지 않는다. 명령 인수나 모델 답변만으로 승인하는 통로는 없다.
- offline maintenance와 현재 신원을 유지한 채 원 자료를 확인한다. 조회 중 원문·표식·신원이 바뀌거나 source의 최신 확인이 실패하면 발급하지 않는다. 외부 조회·확인의 기본 전체 시간은30초, 설정 최대60초다. 동기 함수가 timer를 지연시키는 경우에도 단조 시간계로 제한을 검사한다. 최초 로컬 자료 준비를 포함한 명령 전체의 시간 상한은 아니다.
- 대조 기록 게시 중에는 별도 pending 표식으로 일반 재개를 막는다. 게시 뒤 검사가 실패해도 provisional 영수증만으로 재개되지 않는다. 동일 원 자료·신원·외부 보고서를 다시 확인한 재시도는 원 영수증을 유지하고 pending을 해제한다.
- 일반 `openAgentStores`의 신원 확인 뒤, 저장소 생성 전에 대조 완료를 확인한다. 정상 새 담당은 그대로 열린다. 대조가 끝난 담당의 매번 재시작에서 전체 자료나 외부 source를 다시 읽지 않고 작은 완료 기록의 결합을 확인한다.
- 로컬/PG 백업·엔진 이행 비교·복원·신원 rebind에 대조 완료/pending 기록의 제외 규칙을 일관되게 적용했다. 두 기록을 담은 archive는 거절한다. 이전 복원의 완료 증명이 새 복원으로 따라오지 않는다.
- 관리 입구 `lifecycle restore-status`와 `restore-reconcile --offline`을 추가했다. source 등록은 호스트 API이며 실제 배치 시스템용 조회 구현은 별도 연결한다.

개별 attempt/컴퓨터 유즈의 기존 read-only 복구·권한·정산·원문 보존 코드를 재사용했다. 대조 증명 자체는 도구 결과를 가져오거나 목표를 완료하거나 자원을 정산하지 않는다.

## 실제 로컬 동작으로 확인한 내용

쓰기 전 백업을 만든 뒤 등록된 도구로 담당 폴더 밖에 실제 파일을 쓰고 원 실행을 채택했다. 그 과거 백업을 복원하자 이후 실행 영수증은 사라졌지만 외부 파일은 남았다. 신원 rebind 뒤에도 일반 실행 입구가 거절됐고, source가 외부 파일 전체 목록과 복원 SQLite를 대조하여 사라진 실행을 찾아냈다. 모델 호출·추가 파일 쓰기·채널 send가 증가하지 않았고 복원 DB·송신 기록·보존 원본·원백업은 유지됐다.

반대로 실제 쓰기와 원 영수증이 들어 있는 백업은 대조 후 같은 세션·업무를 이어갔다. 이미 채택한 도구와 근거는 그대로였고, 시험용 모델의 답변 호출만1회 추가돼 전체 도구1회·모델2회로 완료했다. 다시 열어 같은 완료 업무를 재개해도 모델·쓰기·답변 전달을 반복하지 않았다. 이 시험의 외부 효과는 실제 임시 파일이며 모델은 정해진 응답을 반환하는 시험 제공자다.

게시 직후 원문을 바꾸는 장애 주입에서 provisional 영수증이 남아도 재개가 막혔다. 원문을 보존한 같은 기준으로 되돌린 통제 시험에서는 source 재검증 후 영수증 바이트를 그대로 유지하며 이어갔다. 같은 백업을 두 번 복원한 경우의 새 번호, 과거 완료 기록 복사 거절, 다음 백업의 대조 기록 제외도 확인했다.

## 남은 범위와 다음 행동

source는 신뢰 호스트 확장이다. 담당의 외부 실행·송신·위임·자원 이력을 빠짐없이 대조하는 책임이 있으며, 복원된 attempt가 비었다는 이유만으로 효과가 없다고 답하면 잘못된 구현이다. 코어는 원격 서비스의 진실이나 등록 범위의 완전성을 스스로 증명하지 않는다. 실제 source의 조회 권한·원 기록·범위는 해당 연결에서 검증해야 한다.

**불일치를 감지하고 막는 것과 누락된 기록을 되살리는 것은 다른 작업이다.** 오래된 백업에 없는 효과를 현재 외부 원기록/보존된 담당에서 가져와 충돌을 해결하는 공통 기능은 남아 있다. 게시 중 변경된 자료로 새 대조를 발급하는 복구도 이번에는 자동화하지 않았다. `agent_restore_reconciliation_recovery_required`에서는 표식/영수증을 삭제해 강제로 재개하지 않는다. 동일 기준의 재시도, 또는 원 자료를 보존하고 검증한 백업을 명시적으로 재복원하는 기존 경로는 사용할 수 있다.

legacy 복원 완료 표식에 고유 번호가 없으면 새 증명을 발급하지 않는다. 원백업을 현재 복원 명령으로 복원해야 한다. 현재 엔진의 일반 입구에서 확인한 결과이며, 구형 바이너리나 직접 DB 접근까지 새 게이트를 적용했다고 보지 않는다.

이번 소스의 실제 Linux/native Windows, PG 복원/재시도, 사내 MCP/Knox/외부 A2A, 설치본을 통한 새 관리 명령 인수와 운영 배포/최종 통합은 미실행이다. 실제 모델/API 시험 중단을 유지한다. C09 취소·목표 변경·일시정지/저널 불명/이력 비용, C05 권한 재허용 완주, C06 기억 HTTP·권한·브라우저도 남는다.

다음은 기존 원 영수증·개별 효과 복구·보존 담당/백업을 재사용하여 **unresolved인 복원을 안전하게 해결하는 연결**을 정리하고 구현하는 것이다. 이미 검증한 설치 준비·저장 이행·이번 일치 복원 재개는 다시 만들지 않는다. C10과 전체 goal은 미완료다.
