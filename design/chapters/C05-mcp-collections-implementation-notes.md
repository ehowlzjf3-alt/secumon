# C05 collection 일반 입구 구현 메모

이 문서는 구현 중 선택과 관측을 기록한다. 사용자 흐름 전체나 C05의 완료 보고서는 아니다. 현재 재개 지점과 실행 중인 시험은 [IMPLEMENTATION-RESUME](../IMPLEMENTATION-RESUME.md)을 기준으로 한다.

## 실제 채택한 구조

기존 `ReadCollections` 하나를 compose에서 실행기와 broker에 함께 연결했다. 기존 계획의 별도 임시 permit API 네 개는 채택하지 않았다. `isCompleteResumeCandidate`는 스케줄링 후보를 찾는 동기 검사이고, `assertCompleteResume`는 현재 부모·쿼리·계약·원문을 검증한다. `consumeComplete`는 완전히 받은 부모에서 명시적으로 지정된 다음 시도를 만들며, 원격 source/fetch 인자를 받지 않는다.

모델이 `stored_complete` 표식을 보더라도 실행 허가가 생기는 것은 아니다. 표식은 검증된 완료 부모를 계획에 재사용할 수 있다는 안내다. 예약·실행 직전·결과 게시와 채택에서 현재 계약, 원문, 권한을 별도로 확인한다. context recovery의 복원용 packet과 모델 입력 compiler의 표식을 구분해야 한다.

기존 예약→dispatch→receive→adopt 장부를 그대로 사용한다. 부모의 실패·소유자·원응답은 보존하고 자식 연결만 추가한다. 로컬 재사용은 논리 실행 한 번으로 정산하지만 원격 전송은 0회여야 한다. 실제 등록 도구의 execute, fetch, 일반 reuse callback에 들어가지 않는지 별도 시험한다.

저장된 collection의 정산은 일반 workflow에서 compact/최초 context보다 앞에 놓았다. 완성된 checkpoint만 있고 바깥 결과를 받지 못했다면 부모를 성공으로 바꾸지 않는다. 원문을 복구한 뒤 모델의 명시적인 후속 계획을 거친다. 아직 다음 페이지나 실패 항목 재시도가 필요하면 현재 원문과 실제 다음 요청 가능성을 검사한 뒤 연결 대기를 낸다. 독립 업무나 검토 필요 판단이 우선한다.

## 첫 통합 관측

검토 사본 30개 기록 중 실제 변경 29개를 원본 백업과 SHA 대조 후 한 번에 반영했다. [통합 기록](../../runtime/evidence/C05-mcp-collections-integration1.json)에 입력 manifest와 파일별 출처가 있다. 첫 두 빌드는 새 fixture의 반환형 선언에서 실패했고, 공개 온라인 options 타입을 명시해 세 번째 빌드를 통과했다. core 타입 검사와 구조 검사도 통과했다.

읽기 검토에서 collection이 없는 일반 도구에도 새 선행 권한 검사가 적용되는 회귀를 발견했다. collection 후보를 고른 뒤 검사하도록 범위를 좁혔다. 실제 받은 일반 read 결과의 권한 철회 후 거절 정산, 원결과와 알려진 사용량 보존 회귀를 추가했다.

첫 집중 시험은 110개 중 103개 통과·7개 실패였다. 실패한 바이트 배열 비교, 자식 checkpoint 이벤트 조회, 복원 packet의 표식 기대를 현재 저장 형식과 비교 중이다. [원로그](../../runtime/evidence/C05-mcp-collections-new1.log)는 그대로 보존한다. 이 결과를 전체 통과로 표시하지 않는다.

## 다음 검증 경계

- 원 실패를 좁혀 수정하고 해당 파일을 다시 검증한다. 현재 변경에 연결되는 기존 회귀를 별도 선정해 확인한다.
- 실제 로컬 MCP peer와 프로세스 강제 종료를 사용해, 일반 CLI의 완료 원응답 복구→compact→명시 재사용→답변을 SQLite와 파일 저장소에서 검증한다.
- 일반 HTTP의 미완료 원응답 복구→반복 연결 대기→명시 온라인 재연결→다음 페이지 또는 실패 항목만 재시도를 검증한다.
- 정상 채택된 partial 결과도 반복 대기 중 원문·작업·자원 장부를 잃지 않는지 확인한다.

앞의 시험은 합성 모델과 로컬 peer를 사용한다. 실제 모델/API 시험 중단은 유지하며, 사내 MCP·Knox, native Windows와 PostgreSQL의 실제 연동 완료를 뜻하지 않는다. 이전 offline 단위의 완료 증명과 이번 변경의 검증은 별개다.

## 집중 교정 후 관측

원래 실패한 세 시험파일은 교정 후41/41로 통과했다. compiler 모델 입력은 표식을 유지하고, runtime recovery 정본은 표식 부재와 전체 원목록 일치를 검사했다. 선정34개 기존 관련파일은456/456, fixture 명령은exit0이었다. 다른 제품 구현을 추가로 바꾸지 않아 이미 통과한 신규 파일·core/구조 검사는 반복하지 않았다. 각 단계의 source/build·원로그·실제 종료는 [부분 검증 기록](../../runtime/evidence/C05-mcp-collections-local-integration-result.json)에 저장했다. 일반입구의 새 collection 강제중단·compact 인수는 여전히 작성 중이다.

## 일반 입구 검증에서 보완한 두 연결

new8에서는 실제 CLI 두 저장소의 강제 종료 후 복구, session compact, 저장된 수집 결과 소비, 생략된 근거 조회와 최종 답변을 확인했다. HTTP의 반복 연결 대기와 다음 페이지·실패 항목 재시도도 포함해 선정 시험 183개가 통과했다. 이 실행은 로컬 대역 모델과 실제 로컬 프로세스·저장소를 사용했으며 모델 품질이나 NAS 검증 결과는 아니다.

첫째, 저장소에 있는 정보와 모델이 현재 입력에서 보는 정보는 다르다. 기존 선택기는 byte 한도에 여유가 크고 token 한도가 작으면 같은 전체 선택을 6번 확인한 뒤 최소 정보만 남길 수 있었다. 일부 정보를 포함한 요청은 실제 추정상 들어갈 수 있는 반례를 두 컴파일 경로에서 재현했다. 다음 예산을 줄일 때 실제 선택 비용을 상한으로 사용하도록 두 계산식을 고쳤다. 필수 문맥 보호와 최종 요청 크기 검사는 그대로다. 전체를 최적으로 배치하는 새 알고리즘을 구현한 것은 아니다.

둘째, 이미 저장된 근거를 처음 찾아 읽는 일도 답변 준비에 필요하다. 예를 들어 계획 → 근거 A 조회 → 근거 B 조회가 전부 무진전으로 계산되면 기본 한도 3에 걸려 답변 전에 멈춘다. 현재 허용된 원근거를 정확히 찾아 읽은 최초 행위에만 내용 기반 준비 진전 키를 남긴다. 키는 같은 내용을 읽은 사실을 기억하는 식별값이다. 카드 조회와 본문 조회를 구분하고, 본문을 읽으면 해당 카드도 이미 본 것으로 센다.

이 준비 진전은 새 사실을 관측했다는 의미가 아니다. 근거·목표·완료 조건과 실행 권한은 그대로 유지한다. 같은 내용의 재조회, 표시용 ID·위치·시각 변경과 파생 복사본은 준비 진전을 늘리지 않는다. 실제 두 저장소에서 최초 조회 후 동일 조회가 세 번 반복되면 기존 무진전 제한으로 멈추는 회귀도 통과했다. 원문 raw 조회의 별도 진전 판정은 이번에 확장하지 않았다.

related3의 519개 중 한 시험은 최초 evidence 조회도 무진전으로 보던 이전 기대값 때문에 실패했다. 새 동작은 목표가 아직 충족되지 않았으므로 재계획을 요청한다. 해당 기대값을 수정하면서 원근거 동일, 원 도구 재호출 없음, 목표 미완료, 기본 무진전 한도 3을 계속 검사하도록 했다. 이 마지막 시험 변경 후의 동일 source 검증 상태는 [현재 재개 기록](../IMPLEMENTATION-RESUME.md)을 따른다.
