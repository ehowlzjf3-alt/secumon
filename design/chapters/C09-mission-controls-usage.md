관측을 멈췄다는 사실만으로 개별 업무가 취소되거나 완료되는 것은 아니다. 업무가 일시정지됐다는 사실만으로 담당 프로세스가 종료되는 것도 아니다. `stop`은 지정한 관측 규칙의 영구 종료이고, `close`는 이 프로세스 안의 driver 핸들을 닫고 진행 중 호출을 정리하는 동작이다. 프로필·저장소의 종료는 소유하는 프로필의 별도 종료 경로를 따른다. 사용자 대화에서는 “새 사건 관측을 일시정지했습니다”와 “이 업무를 일시정지했습니다”처럼 실제 대상을 밝혀 표시한다. 이번 제어 노출은 호스트 API이며 새 CLI·Web·Knox 명령·버튼은 미구현이다.

## 관측을 쉬었다가 이어가기

호스트 API에 제어 업무의 `workId`를 전달한다. 이 ID는 사건별 업무 ID와 구분한다. 두 메서드는 변경 후 상태 스냅샷을 반환한다. 상태는 `active`(관측 가능), `paused`(호스트가 관측 일시정지), `closed`(규칙 종료)다.

```ts
const paused = await driver.pause(controllerWorkId);
const resumed = await driver.resume(controllerWorkId);
```

새 담당이나 새 세션을 만들 필요 없이 원 커서와 대기 사건을 이어간다. 이미 paused인 규칙에 다시 pause하거나 active인 규칙에 다시 resume하면 저장 내용을 바꾸지 않는다. stop한 규칙을 resume하면 `resident_mission_closed` 오류로 거절한다.

일시정지 중 `tick`은 `{ kind: 'paused', reason: 'host_paused' }`를 반환하며 `drive`도 paused 결과로 반환한다. 내부적으로 구독은 active 상태를 유지하고 선택적인 `suspended` 표식으로 관측 일시정지를 나타낸다. 제어 업무 자체의 `WorkState`는 기존 설계부터 paused 상태다. 이 업무 상태와 관측 상태를 같은 것으로 해석하지 않는다.

제어와 사건 접수가 동시에 진행됐다면 원 접수 영수증으로 실제 접수 여부를 판단한다. 이미 저장된 접수는 보존한다. 늦게 도착한 관측이나 같은 사건의 재전달을 근거로 업무를 중복 생성하거나 호출을 반복하지 않는다. 일시정지는 이미 실행한 외부 효과를 되돌리는 기능이 아니다.

poll 중 pause 후 늦은 응답을 거절하고 같은 커서에서 이어가는 경계를 확인했다. 취소에 협조하지 않는 원천의 poll 자체를 영속 제어 명령과 연결해 즉시 중단하는 기능은 아직 미구현이다. 관측 제어 호출의 성공을 진행 중 원천 조회가 즉시 끝났다는 뜻으로 해석하지 않는다. 과거 규칙 ID를 다시 사용하는 관리 흐름도 미구현 후속이다.

## 업무를 쉬거나 목표를 바꾼 뒤 이어가기

개별 사건 업무에는 기존 코어 제어 명령을 사용한다. 일시정지에서는 원 사건과 대기 상태를 유지하고 명시적으로 업무를 재개한다. 취소에서는 원 기록을 남기면서 임무 메타데이터와 원 체크포인트를 취소의 의미에 맞게 정리한다. 관측 재개와 개별 업무 재개는 따로 선택한다.

목표를 바꾼 업무는 원 접수 영수증을 통해 원 사건과의 관계를 확인하되, resident가 같은 사건을 다시 받았다는 이유로 자동 실행하지 않는다. 해당 `tick`은 사건 결과에 `continuation: 'explicit_resume_required'`와 `result: null`을 넣어 반환하고, 사건을 resident 대기 큐에서 분리한다. 업무를 삭제하거나 완료했다는 뜻은 아니다.

목표 변경과 이후 실행은 기존 `turns.changeGoal`과 `workflow.run` 경로를 통해 해당 업무를 명시적으로 이어간다. 변경 전 목표에서 읽었던 사건이나 완료 기록을 변경된 목표의 새 증명으로 사용하지 않는다.

담당의 대화 세션은 이어진다. 사건마다 업무 목표·계획·근거·사용량을 나누는 기존 구조와 개인 기억은 유지한다. 상태 전환을 이유로 대화 전체를 버리거나, 사건을 개인 장기 기억으로 자동 복제하지 않는다.

## 완료와 중단 뒤 확인

실제 업무 완료는 기존 완료 사건과 영수증으로 확인한다. 취소·일시정지·목표 변경이나 관측 재개 성공을 업무 완료로 표시하지 않는다. 실제 완료 후 일부 임무 마감만 빠졌다면 기존 [완료 마감 복구](C09-mission-terminal-recovery-result.md)를 사용한다.

중단 후에는 저장된 원 접수·업무·체크포인트를 조회하여 상태를 확인한다. 원문이나 영수증을 지우고 다시 접수해서 맞추는 흐름은 사용하지 않는다. 이번 로컬 경합·명시 재개·reopen 결과는 [결과 기록](C09-mission-controls-result.md)에 남겼다. 이번 단위에서 실제 프로세스 SIGKILL은 실행하지 않았다.

파일 저널의 저장 후 응답 불명 주입, 긴 이력 조회 비용·과거 규칙 관리, 실제 모델·사내 연동·현재 Linux/native Windows·운영 배포는 이 사용 흐름의 검증 완료 범위가 아니다.
