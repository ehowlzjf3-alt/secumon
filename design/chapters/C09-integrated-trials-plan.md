# C09 동일 문제 비교와 게시판·임무 결합

2026-09-08 · checkpoint382 · 기준선 `b2684ffaab48953409bf6325b25ff55ddb52b7e2`. 시작 시 작업 트리는 깨끗했다. 직전 단위는 임무 읽기 확인·종료 교정, 로컬 검증과 문서, 커밋·푸시 및 원격 일치 확인으로 진행했다. 전체 goal과 C09는 미완료다.

같은 문제를 혼자 풀 때와 동료의 도움을 받을 때를 실제 독립 담당의 실행 경로로 비교한다. 두 경우의 질문·원 자료·모드·판정 기준은 동일하게 유지하고, 모델 합의 대신 각 경우가 확인한 원 근거와 실제 답변을 평가한다. 시간과 사용량은 이 로컬 대역 실행의 측정값이며 실제 모델의 추론 품질이나 운영 속도를 뜻하지 않는다.

1. 기존 일반 프로필·SQLite·동료 요청/실행/회신 조립을 재사용한다. 단독은 원 자료 조회→답변, 협업은 실제 동료 왕복→자신의 원 자료 조회→같은 답변을 수행한다. 일반 `turns.accept`를 사용하고 종료 후 goal/criteria/근거/사용량을 가공하지 않는다. 원 commit 상태·전달 기록과 모든 참여 업무의 최종 로컬 사용량을 수집한다.
2. 기존 비교기와 근거 평가기를 재사용한다. 일반 입구의 빈 criteria와 responseRequirement를 기존 평가기가 어떻게 처리하는지 실제 표본으로 먼저 확인한다. 필요하면 명시적인 exact-text 응답 oracle(미리 고정한 정답과 원문 해시)과 실제 저장 답변 관측을 추가한다. 근거가 요구된 비교에서는 원 자료·사실·상반 근거·시간 조건도 계속 검증한다. 모델 자체 평가나 완료 플래그만으로 통과시키지 않는다.
3. 같은 프로필/업무에서 실제 게시판과 임무 원천을 함께 연결한다. 현재성 검사와 새로고침, 한쪽 알림 확인/철회가 다른 쪽의 원문·알림·커서를 보존하는지 확인한다. 실제 게시판 등록·자료를 사용하고 sentinel 시험으로 대체하지 않는다. 기존 게시판 fixture에 필요한 선택 seam만 추가하고 기본 동작은 유지한다.
4. 작성자 동결 후 Node v24.20.0 빌드→신규 사례→실패 교정→직접 영향 회귀 순서로 실행한다. 소스 지문·원 실패·terminal exit를 기록하며 살아 있는 시험 중 dist를 재빌드하지 않는다. 이미 끝난381의135개를 반복하지 않는다.

다중 rule의 종료 체크포인트와 완료 후 종료 게시 전 crash 복구는 계속 남아 있다. 실행 전 정적 검토 결과로만 기록하며, 원 완료 receipt/원문 검사를 완화하거나 모델을 재실행해 복구하지 않는다. C10은 같은 release의 다른 경로 재확인을 실제 업데이트로 부르지 않는다. 서로 다른 유효 release를 사용해 check→pin→backup→update→기존 신원/세션/기억 재열기와 오래된 백업 거절을 확인해야 한다.
