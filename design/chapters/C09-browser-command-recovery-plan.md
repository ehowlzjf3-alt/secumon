# C09 브라우저 제어 요청 복원

2026-09-09 · checkpoint399 · 기준선 `c295c6116bbc23cfbe7d5562a3b800ed48990b9b`.

직전 턴은 메인 프롬프트의 구현·호출 연결에 대한 읽기 전용 설명이었다. 새 구현 진척으로 계산하지 않는다. 현재 main 작업 트리는 깨끗하며 checkpoint398의 프로세스 간 관측 제어는 다시 구현하지 않는다.

## 이번 변경

기존 명령 ID·최초 제어 버전·원 영수증 재확인과 Web 상태/제어 API를 재사용한다. 브라우저의 메모리에만 있던 미확정 요청을 같은 탭의 `sessionStorage`에 저장한다. 새로고침 후에도 서버가 확인해 준 담당 ID·사용자 세션 ID·대화 ID가 모두 같을 때만 복원한다. 탭 종료 이후의 영구 복구나 여러 기기 사이의 동기화는 이 저장소의 보장 범위가 아니다.

저장 내용은 대상 제어 업무 ID, 원 명령 ID, 최초 예상 제어 버전, pause/resume/stop 종류뿐이다. 대화·자료 원문, 상태 본문, 모델 문맥, 인증정보를 넣지 않는다. 정상적인 상태 조회만으로 미확정 요청을 지우지 않고, 원 명령의 응답 또는 명확한 거절을 확인한 뒤 지운다. 인증 만료는 화면과 메모리를 비우며 같은 선택으로 인증된 뒤에만 요청을 다시 보여준다.

새 명령은 복구 정보를 저장한 다음 전송한다. 저장할 수 없거나 기존 기록이 손상되었으면 조용히 새 ID로 진행하지 않고 짧은 오류를 표시한다. 미확정 목록은 최대16건과 크기 상한을 두고 오래됐다는 이유로 자동 삭제하지 않는다. 다른 제어 업무로 이동해도 남은 요청을 선택할 수 있다. 새로고침 자체로 POST를 실행하지 않는다.

## 구현·확인 순서

1. 작은 저장 어댑터와 검증을 만들고 기존 화면 상태 관리에 연결한다.
2. 미확정 요청 선택 목록과 복원 안내를 기존 접이식 제어 패널에 넣는다. 일반 채팅 이력에 반복 진행 메시지를 쌓지 않는다.
3. 저장 실패·선택 격리·새로고침·원응답 대조를 선택 시험으로 확인한다. 기존 HTTP 인증/제어 시험을 관련 회귀로 실행한다.
4. 브라우저 스킬로 실제 localhost 화면에서 응답 손실 → 새로고침 → 동일 요청 재확인 → 다음 제어를 수행한다. 실제 임시 SQLite와 서버의 원 명령 기록을 대조한다.
5. 결과·원로그·남은 항목을 저장하고 코드와 함께 커밋·푸시한다. 실제 모델/API 시험 중단을 유지한다.

전체 세션 컨텍스트 비용, 같은 목표의 장기 사건 중복 확인·용량·보관, C05 권한 재허용 완주, C06 기억 HTTP·권한·지연·화면, C10 초기 복원 중단·Linux/native Windows·실제 PostgreSQL·설치·운영·최종통합은 남은 범위다. 이번 로컬 화면 검증으로 전체 C09나 목표 완료를 주장하지 않는다.
