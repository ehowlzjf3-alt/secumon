# 게시판의 저장·권한·출처 계층

2026-09-06 · v0.43 · P4-01 첫 단계 로컬 검증 완료

두 역할이 같은 게시판에서 관찰·가설·질문·반증·결정을 공유하고, 누가 질문을 수락했는지 저장하는 서비스를 구현했다. 역할 ID는 프로세스와 분리되며 재시작 뒤 유지된다. 이번 단계는 호출 가능한 협업 서비스와 영속 저장을 검증한다. 실제 에이전트 도구·작업 의무·컨텍스트 복원 연결은 다음 단계다.

## 배운 개념과 구현 결과

개인 기억은 기존 KnowledgeService에 남긴다. 게시판에는 원 근거 참조와 설명을 명시적으로 게시한다. 질문이나 가설도 게시할 수 있으므로 게시판에 보인다는 사실을 조직의 확정 지식으로 해석하지 않는다. 문서 비교와 합성 관측 두 업무군 모두 같은 BoardService를 두 역할로 호출했다. 개인 기억의 본문은 동료의 조회와 게시판에 노출되지 않았다.

인용과 새 근거는 다르다. 동료의 글을 인용하면 원 업무·원 근거·자료 버전·관측/기록 시각·원 출처 계통을 계승한다. 같은 원본을 두 역할이 인용해도 독립 출처는 하나다. 다른 원본이 다른 값을 제시하면 두 출처와 충돌을 함께 표시한다. 파생 가설이 원 자료를 참조한다는 사실도 해당 가설에 직접 독립 증거가 생겼다는 뜻은 아니므로 두 수치를 구분한다. 게시글은 WorkState에 새 Evidence를 생성하거나 목표를 완료하지 않는다.

원 근거·상위 게시글의 철회, 원본 누락, 만료, 목표 개정, 현재 권한과 공개 정책을 조회 시 확인한다. 파생 인용도 원본의 변경을 따른다. 자유로운 본문은 작성 업무의 정보 등급을 계승한다. 낮은 등급의 자료만 첨부해서 본문의 공개 범위를 낮출 수 없다. 역할 비활성화와 비회원/다른 조직 접근도 차단한다. 실제 원문 격리 배치 선택이나 사내 자료 공개 검증을 수행한 것은 아니다.

공유 대상(entity)은 호스트가 승인한 ID·권한 있는 식별 체계·키·유효기간으로 등록한다. 같은 이름이어도 다른 시간 범위의 객체를 자동 병합하지 않는다. 관측 시각이 대상의 유효기간에 속하는지 확인한다.

질문 게시 → 특정 상대에게 요청 → 상대의 업무로 수락 → 근거 있는 응답 제출 → 요청자 확인을 각각 저장한다. 미해결 질문이 게시되었다는 이유로 동료에게 책임이 자동 배정되지는 않는다. 응답 제출과 요청자 확인도 별개다. 확인된 답이라도 근거나 선행 답이 철회되면 현재 상태는 다시 검토 필요로 표시한다. 명시적인 대기 관계의 순환을 거절하고, 답을 제출한 뒤에도 선행 답에 대한 의존성을 보존한다. 이 요청 상태는 아직 WorkState.obligations와 연결하지 않았다.

총 게시글·답글 깊이·진전 없는 연속 답글·총 요청에 각각 상한을 둔다. 동일 원인 이벤트의 중복 게시와 동일 명령 ID의 내용 변경을 거절한다. 같은 조회에서 여러 글이 같은 원본을 인용하면 원본을 한 번만 읽고 공유한다. 다음 조회에는 이 캐시를 남기지 않는다. 네 게시글이 같은 원본을 인용한 경우 원본 읽기 1회를 확인했고, 다음 조회에서 원 근거의 접근 철회를 반영했다.

## 저장과 검증

BoardRepository 포트 뒤에 SQLite와 파일 저널 구현을 두었다. 게시판 상태와 명령 영수증을 함께 저장하고 기대 개정 번호로 동시 갱신을 제어한다. 파일 저널은 동기화한 후보 파일을 원자적으로 게시하며 이력의 누락·내용 변경을 검출한다. 명령 결과를 돌려주기 전에 호출자가 응답을 잃어도 같은 명령을 다시 보내면 중복 게시하지 않는다.

신규 게시판 시험 **43개**와 관련 기억·정보 공개 회귀를 합친 **86/86**이 통과했다. 두 업무군 × 두 게시판/업무 저장소의 4조합, 두 저장소의 실제 worker SIGKILL 복구 2개를 포함한다. 별도 SQLite 기억 저장소는 기존 구현을 사용했으며 기억 저장소까지 두 종류로 검증했다고 주장하지 않는다. 재열기 후 역할·게시물·인용·상태와 명령 영수증을 확인했고 소유 worker 종료도 확인했다.

초기 타입 검사는 종료를 알리는 함수 선언의 제어 흐름 추론 문제를 수정했다. 첫 게시판 실행은 27/27이었다. 추가 관련 실행 82/84의 실패 2개는 공개 정책을 추가하는 시험에서 기존 업무 이력을 먼저 분류하지 않은 준비 오류였다. 분류 이력을 명시한 뒤 현재 코어의 보호 규칙을 유지한 채 86/86을 확인했다. 실제 시간이 바뀌는 호출에서는 한 변경의 저장 시각을 일관되게 사용하고, 최종 확인 중 만료되면 게시를 거절하는 시험도 추가했다.

전체 `npm run verify`는 **2,160/2,160**, 실패·취소·건너뜀 0으로 종료했다. 빌드·코어 타입, 계층 검사 108파일/위반 0, fixture 4개/22판정도 통과했다. 전체 시험은 301,744.081834ms이며 관련 86개를 이 분모에 다시 더하지 않는다. 현재 소스와 실행한 빌드의 일치를 확인했다. 별도 lint 명령은 없다. ## 다음 단계와 한계

P4-01 전체는 진행 중이다. 다음에는 두 composeRuntime 인스턴스가 이 서비스를 도구로 호출하게 하고, 게시판 조회 의존성과 요청 의무를 현재 작업·부모/자식 예산·compact/reopen에 연결한다. 도구용 카드는 필요한 범위만 읽고 출처별 coverage를 포함해야 하며, 게시판 변경 뒤 오래된 입력으로 계획하거나 완료하지 않도록 검증해야 한다. 모델이 본문을 실행 지침이나 새로운 독립 근거로 취급하지 않도록 구조화된 입력 계약을 적용한다.

현재 질문은 근거 없이 게시할 수 있지만 관찰·가설·반증·결정에는 근거 참조가 필요하다. 다음 단계에서는 근거가 아직 없는 초기 가설도 명시적인 초안으로 표현하고, 사실이나 근거로 승격되지 않는 경계를 검증해야 한다.

이번에 실제 모델·사내 MCP·Knox·A2A 상대·상시 스케줄러를 호출하지 않았다. 모델/API 시험 취소는 유지한다. 읽기 검사는 서로 다른 저장소 사이의 분산 트랜잭션이 아니므로 조회 중 개정·권한·기한이 변하면 명시적으로 거절한다. 파일 저널은 게시판당 최대 4,096개 개정·기록당 8 MiB이며 전체 상태를 기록한다. 대규모 이력의 저장 비용·보존/삭제/압축과 운영 성능은 아직 검증하지 않았다.
