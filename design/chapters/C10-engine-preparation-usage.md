# npm·개발 실행 경로에서 로컬 엔진 준비하기

2026-09-08 · checkpoint388 구현 사용법. 로컬 엔진 준비와 npm 입구 연결을 구현하고 로컬 확인 결과를 정리했다. 구체적인 확인 범위와 빌드별 실행 근거는 [확정 결과](C10-engine-preparation-result.md)를 따른다. 모든 사례를 최종 소스에서 다시 실행한 것은 아니며, 운영 설치나 전체 플랫폼 검증 결과로 확대하지 않는다.

## 처음 사용할 때

검증 가능한 `release.json`이 없는 지원 npm 설치나 빌드된 개발 디렉터리에서 새 담당을 실행하면, 입구가 로컬 파일로 설치 엔진을 준비한다. 사용자는 기존 명령을 그대로 사용한다.

```sh
secumon-agent init --directory ./agent1 --name '담당 1'
secumon-agent open --directory ./agent1
secumon-agent lifecycle status --directory ./agent1 --json
```

전역 명령이 가리키는 원 npm 패키지나 개발 파일에 `release.json`을 쓰지 않는다. 대신 필요한 파일과 의존성을 읽어 배포 지문을 계산하고, 별도의 로컬 공간에서 `bundle`(검증할 배포 묶음)과 `engine`(실행할 설치본)을 만든다. 설치·호스트 등록과 원 소스의 지문을 다시 확인한 후 그 설치본에 원 명령을 전달한다.

선택 엔진은 같은 Node 실행 파일의 자식 프로세스로 실행되며 원 인수 배열(`argv`), 현재 작업 디렉터리, 표준 입력·출력·오류를 유지한다. 명령을 문자열로 합쳐 셸에 넘기지 않는다. 이후 설치 엔진이 [자동 최초 pin 절차](C10-initial-pin-usage.md)에 따라 담당 ID, 설정, 첫 pin과 완료 영수증을 만든 뒤 저장소를 연다. 준비 helper 자체는 담당을 초기화하거나 pin을 만들지 않는다.

## 준비를 시작하는 명령

로컬 준비는 **원 실행 경로에 release가 없고, 대상 담당이 아직 초기화되지 않았을 때** 다음 입구에 연결된다.

- 일반 `init`, `open`과 명령을 생략한 기본 실행. 초기 설정 옵션을 먼저 검증한다.
- 파서가 일반 담당 경로로 분류한 `chat`·담당형 `work` 명령. 새 엔진이 실제 명령을 이어서 해석한다.
- `dispatch --directory ./agent1 -- init`처럼 기존 고정 전달 형식 안에서 위 조건에 해당하는 명령. 외곽 담당과 내부 경로 조건은 [dispatch 사용법](C10-launch-envelope-usage.md)을 따른다.

`help`, `version`, 최상위 `status`와 잘못된 초기 설정 옵션은 이 준비를 시작하지 않는다. `lifecycle`, `repair`, `clone`, `memory-migrate`와 일반 담당을 사용하지 않는 독립 `work --data-dir`도 새 로컬 엔진 준비의 대상이 아니다.

이 구분이 모든 명령의 의미 검사를 미리 끝낸다는 뜻은 아니다. 예를 들어 파서가 받아들인 `chat`·`work`는 실제 실행 단계에서 필요한 ID나 입력이 빠졌다고 거절될 수 있고, 그 전에 로컬 엔진 준비가 이루어질 수 있다. `chat history` 같은 하위 조회 명령도 최상위 `status`와 같은 분기로 취급하지 않는다. 모든 조회나 모든 오류 호출에 파일 변경이 없다고 일반화하지 않는다.

## 공유하는 것과 분리하는 것

같은 원본에서 계산한 배포 지문이 같으면 여러 새 담당이 **동일한 실제 설치 디렉터리**를 재사용한다. 두 담당마다 엔진 코드를 다시 복사할 필요가 없다. 재사용할 때도 저장된 선택만 믿지 않고 실제 설치 파일·등록·원 소스를 대조한다.

공유하는 대상은 엔진 코드와 그 의존성이다. 담당 ID, 설정, 스킬, 대화 기록, 개인 기억, 진행 업무와 pin은 각 담당 디렉터리와 기존 저장소 소유 경계에 남는다. 같은 엔진을 쓴다고 담당들이 하나의 개인 기억이나 대화 DB를 사용하도록 바꾸지 않는다.

원 소스의 **배포에 포함되는 파일**이 바뀌어 지문이 달라지면 다음 새 담당에는 새 지문의 설치를 준비한다. 기존 담당은 자신의 원 pin을 계속 따른다. 전역 npm 패키지나 개발 체크아웃이 바뀌었다고 기존 담당을 자동 업데이트하지 않는다. 기존 담당의 전환에는 [명시적 check·backup·update](C10-launcher-extensions-usage.md)를 사용한다.

## 로컬 저장 위치

```text
~/.secumon/engine-releases/
  <releaseDigest>/
    selected.json
    <attemptId>/
      bundle/
      engine/

~/.secumon/engines/
  <호스트 설치 등록 기록>
```

`releaseDigest`는 실제 배포 내용의 SHA256 지문이다. `attemptId`는 준비 시도마다 만드는 UUID(충돌을 피하기 위한 고유 식별자)다. `selected.json`은 해당 지문에서 선택한 완료 설치의 시도 ID와 등록 지문을 가리키는 기록이다. 이미 공개된 선택을 다른 후보로 덮어쓰지 않으며, 동시에 준비한 호출도 저장에 성공한 원 선택을 다시 읽는다.

`engine-releases`는 배포 파일 보관소이고 `engines`는 신뢰한 설치의 경로·내용·디렉터리 식별 정보를 담는 호스트 등록표다. 둘은 담당 데이터 폴더와도 분리한다. 여러 담당이 같은 설치를 참조할 수 있으므로 이 공간을 담당별 임시 파일처럼 취급하지 않는다. 이번 단위에는 미사용 설치의 자동 삭제 기능을 넣지 않았다.

프로그램에서 준비 helper를 직접 쓰는 호스트는 `prepareAgentEngine(input, agentRoot, { preparationDirectory, registryDirectory })`로 두 위치를 지정할 수 있다. 명시한 위치의 부모 디렉터리는 이미 있어야 하며, 원 엔진·담당·준비 공간·등록표가 겹치면 거절한다. 반환값의 `source: 'prepared'`는 이번 호출에서 새로 준비한 설치가 선택됐다는 뜻이고, `'reused'`는 기존 선택이나 이미 완성된 설치를 재사용했다는 뜻이다.

## 중단·실패 후 이어가기

- 설치의 최종 `release.json`이 아직 없는 부분 후보는 그대로 보존하고 새 시도 디렉터리를 사용한다. 중간 파일을 지워 없애거나 완성된 설치로 간주하지 않는다.
- manifest의 파일 연결 직후 멈춰 정확한 원 manifest와 같은 파일 객체의 임시 링크가 남은 경우도 그 시도를 보존하고 새 후보를 준비한다. 이 예외는 원문과 연결 관계가 일치하는 중단 자료에 한정하며, 손상된 설치를 실행하는 허용 규칙이 아니다.
- 설치는 끝났지만 호스트 등록이 실패했다면 완료 selector를 공개하지 않는다. 원인을 해결한 뒤 같은 원본으로 재호출하면 실제 완료 엔진을 다시 검증·등록하여 재사용한다.
- `selected.json`이 이미 가리키는 설치가 사라지거나 변조됐다면 멈춘다. 다른 같은 버전의 폴더로 대체하거나 원 선택을 고쳐 성공처럼 처리하지 않는다. selector 자체의 형식·지문이 맞지 않는 경우도 오류다.
- 준비 중 원 소스가 달라지면 그 원본을 기준으로 한 완료 선택을 확정하지 않는다. 정상 준비 후 담당을 열기 직전에도 다른 호출이 담당을 먼저 초기화했는지 다시 확인하고, 이미 결정된 담당의 엔진 선택을 따른다.

준비 시도는 한 지문당 제한돼 있다. 중단 자료가 계속 쌓여 한도에 도달하면 오류로 멈추며, 무한히 새 폴더를 만들거나 원 자료를 자동 정리하지 않는다.

## 지원 조건과 남은 범위

현재 대상은 사용자 소유의 자체 의존성을 갖춘 npm 설치와 빌드된 개발 실행 경로다. Node `>=24.20.0 <25`, 현재 플랫폼·아키텍처에 맞는 파일과 실행 입구가 있어야 한다. package 안에서 실행 필수 의존성을 찾고 실제 포함 파일과 manifest를 대조한다. 의존성의 버전 범위를 해결하는 일은 npm의 역할이며, 이 검사가 패키지 코드의 모든 동적 import나 외부 서비스 동작을 증명하지는 않는다.

준비 과정은 로컬 파일을 묶고 설치할 뿐, 네트워크 요청·다운로드·의존성 설치를 수행하지 않는다. 원 `.tgz` 파일을 직접 실행 입력으로 삼거나, 상위 폴더에만 있는 hoisted 의존성, npm link/pnpm 방식의 링크, 관리자 소유의 전역 설치 prefix까지 지원하는 경로로 확대하지 않는다. 지원 가능한 독립 설치 파일을 갖추는 작업은 별도다.

자동 준비·자식 실행은 설치된 CLI 입구의 기능이다. `runAgentCli(args, hostOptions)`처럼 모델·도구의 동적 콜백을 주입하는 프로그램 API는 그 객체를 자식 프로세스에 자동 직렬화하지 않는다. 직접 API를 쓰는 호스트는 실행 코드 선택과 등록 객체 연결을 계속 책임진다.

현재 Linux/native Windows·운영 npm 배치·실제 PostgreSQL 및 사내 연동·최종 통합의 확인은 별도 범위로 남는다. 실제 모델/API 시험 중단을 유지한다. [구현 계획](C10-engine-preparation-plan.md)과 [checkpoint388 확정 결과](C10-engine-preparation-result.md)를 함께 확인한다.
