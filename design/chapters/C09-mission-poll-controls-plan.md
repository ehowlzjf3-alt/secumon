# C09 제어 명령과 진행 중 관측의 중단 연결

2026-09-09 · checkpoint394 · 기준선 `ff3e2d8`. **현재 상태: 구현·로컬 검증 완료.** 같은 최종 build1에서 신규12개와 관련37개, 고유49개가 모두 통과했다(실패·취소·건너뜀0). 빌드·코어 타입 exit0, 구조202개/위반0, 소스·컴파일2,499파일의 최종 지문 일치를 확인했다. 직전 turn에서는 읽기 검토로 누락된 연결을 찾고 세 문서의 초안을 작성했으나 소스 구현 없이 사용량 한도로 중단했고, 이번 turn에서 구현을 재개했다. 앞서 완료한 checkpoint393의 42개와 합산하지 않는다. C09 전체와 전체 goal은 미완료다. [사용 흐름](C09-mission-poll-controls-usage.md) · [결과 기록](C09-mission-poll-controls-result.md).

아래는 이번 단위에서 수행한 구현 계획이다. 최종 결과와 범위 제한은 결과 기록을 따른다. 모든 빌드·시험은 종료됐다.

## 이번에 연결할 행동

현재의 늦은 응답 거절에서 한 단계 이어, 코어 제어 명령이 같은 프로세스에서 실제로 새로 저장된 뒤 진행 중인 원천 관측의 대기를 `AbortError`로 중단하도록 연결한다. `durable command`는 저장소에 반영되어 재조회할 수 있는 제어 명령을 뜻한다. `poll`은 새로운 사건을 얻기 위해 원천에 요청하고 응답을 기다리는 조회다. 단순 요청·과거 명령 중복 반환·저장 응답 불명·다른 프로세스의 저장을 새로 확정한 로컬 저장과 혼동하지 않는다.

| 경계 | 이번 의미 |
| --- | --- |
| 제어 명령 저장 | 업무 pause/cancel/목표 변경 등 기존 코어 명령의 반영이 중단 연결의 근거다. |
| 관측 대기 중단 | 진행 중인 원천 응답을 기다리는 실행 경로를 중단한다. 이미 실행한 외부 효과를 되돌리지 않는다. |
| 늦은 응답·오류 | 중단된 관측의 결과를 사건·커서·idle 횟수에 반영하지 않는다. 늦은 오류도 새 업무 결과로 채택하지 않는다. |
| 실제 원천 callback 수명 | 취소에 협조하지 않으면 callback 자체는 계속 실행할 수 있다. 관측 대기 종료와 callback 종료는 별도다. |
| 원천 소유자의 종료 | 실행 중 callback의 정리·drain은 원천을 소유한 호스트의 수명 관리와 구분해 연결한다. 외부 프로세스 강제 종료 기능으로 표시하지 않는다. |

`idle 횟수`는 새 사건이 없었던 관측의 누적 횟수다. 중단된 관측을 정상적인 빈 관측으로 계산하면 규칙이 의도치 않게 종료될 수 있으므로 기존 값을 보존한다. 세션·개인 기억·원 사건·접수 영수증과 이미 반영된 제어 명령은 그대로 유지한다.

## 구현과 검토 순서

1. root가 선택적 `RuntimeServices.workCancellation`의 register/interrupt 포트를 기존 `ExecutionRuntime`에 연결한다. `composeRuntime`에서 기존 취소 등록을 재사용한다. `MissionRuntime.refresh` 전체에 결합 신호를 전달하고 `finally`에서 등록을 해제한다. `beginClose` 이후 새 등록은 즉시 중단한다.
2. 별도 작성자가 resident의 관측 pause/stop과 pending poll 중단을 연결한다. 제어로 중단되는 관측 신호와 정리에 사용하는 `cleanupSignal`을 구분하여, `finally`의 제어 이력·점유 정리가 중단 신호 때문에 누락되지 않게 한다. 기존 업무 제어·관측 제어·driver 종료의 구분을 유지한다.
3. 늦은 성공·늦은 실패가 상태를 바꾸지 않는지, 사건·커서·idle 횟수와 원 기록을 보존하는지 연결한다. 중단 이후에도 실행 중인 callback은 원천 소유자의 정리와 구분한다.
4. 일반 업무의 진행 중 refresh/tick 중단은 `AbortError` 경로를 사용한다. resident의 명시 pause/stop으로 pending poll이 중단될 때는 기존 `resident_mission_changed` 오류 계약을 유지하며, 호출자 취소는 기존 취소 경로를 따른다. 이미 일시정지/종료된 controller에 나중에 `tick`을 호출했을 때의 기존 paused/closed 반환은 유지한다. 제어 저장 응답 불명과 다른 프로세스의 명령을 즉시 신호로 전파하는 기능은 이번 미구현 후속이다.
5. 소스 동결 후 root가 신규 인수와 직접 영향 회귀를 실행한다. 기존 checkpoint393의 42개를 새로 구현하거나 불필요하게 전부 반복하지 않는다. 실패 원로그·수정·최종 소스와 실행 결과를 구분하여 기록한다.

## 검증할 최소 경계

- 실제 저장된 제어 명령 이후, 원천 callback의 응답을 먼저 완료시키지 않아도 관측 대기가 끝나는지 확인한다. 저장 전 요청이나 실패한 명령과 혼동하지 않는다.
- 중단 후 늦은 성공 또는 늦은 오류가 도착해도 새 사건·커서 전진·idle 증가·자동 실행이 발생하지 않는지 확인한다.
- 업무 제어와 resident 관측 제어에서 원 사건·의무·접수 영수증·지속 세션을 보존하는지 확인한다. 다음 명시 재개는 기존 경로를 사용한다.
- 관측 대기 종료와 실제 callback 종료를 각각 관측한다. 원천 소유자의 정리 없이 callback이 종료됐다고 표시하지 않는다.

신규 target1은 같은 build1에서 12/12 통과했고 실패·취소·건너뜀은 0이다. 직접 회귀 6개 파일은 아직 실행 중이며 최종 수·결과는 종료 후 기록한다. 로컬 callback으로 검증하며 실제 모델/API 시험 중단을 유지한다. fake clock, 제어 가능한 callback, 예외 주입, 실제 프로세스 종료는 서로 구분한다.

소스 검토에서 담당 종료·호출자 취소 뒤 자기 claim을 해제하는 본문이 이전 체크포인트와 같아져 과거 명령으로 처리될 수 있는 경계를 확인했다. 시험 전에 실제 자기 claim 해제 시 기존 `controlRevision`을 증가하도록 보완했으며 새 필드는 만들지 않았다. 신규 caller/driver-close 시험에서 실제 `claim: null`을 확인했다. 수정 전 실행 실패를 재현한 기록은 아니며 이번 신규 시험 실패는 없다.

## 지원 범위와 후속

즉시 중단 연결은 같은 프로세스의 새 저장 완료를 기준으로 한다. 제어 명령 저장 후 응답 불명이나 다른 프로세스의 저장을 즉시 중단 신호로 전달하는 기능은 미구현이다. 프로세스 내 취소 등록을 재시작 후에도 살아 있는 구독으로 취급하지 않는다. 기존 저장 상태 조회·재열기와 별도의 프로세스 간 신호 전파를 구분한다.

파일 저널 `journal_commit_unknown` 오류 주입, 긴 사건 이력 조회 비용·과거 규칙 ID 재사용, 새 CLI/Web/Knox 제어와 기존 C05/C06/C10 잔여는 각각의 현재 상태를 유지한다. 현재 Linux/native Windows·실제 PostgreSQL·사내 MCP/Knox·외부 A2A·설치/운영·최종 통합을 이 단위로 완료 처리하지 않는다.
