## 1. 추천하는 구성

한 에이전트의 판단 과정에서 중요한 가정과 대안 설명을 간단히 점검하고, 근거 충돌·큰 영향·독립 검토 가치가 있을 때 같은 실행 엔진으로 검토 역할을 임시 실행하는 방식을 추천한다. 검토 요청을 받는 기존 동료 에이전트도 같은 결과 계약으로 응답할 수 있다.

서브에이전트는 모델 자체의 필수 기능이 아니다. 실행 시스템이 별도 문맥과 도구 사용 범위를 가진 작업을 만들고 모델을 호출하는 방식이다. 서로 다른 모델이 필수는 아니며 같은 사내 모델로도 구성할 수 있다. 다만 같은 모델을 여러 번 호출했다는 사실만으로 판단이나 근거의 독립성이 보장되지는 않는다.

| 방식 | 적합한 상황 | 검토할 한계 |
|---|---|---|
| 현재 계획 호출 안에서 자체 검토 | 간단한 가정 점검, 명확한 판별 조건 | 기존 설명을 반복할 수 있음 |
| 별도 문맥의 임시 검토 역할 | 중요한 결론, 상충 근거, 누락 가능성 | 추가 호출과 문맥 구성 필요 |
| 다른 조사 방향을 맡은 복수 역할 | 서로 독립적으로 확인할 만한 대안이 여러 개 | 중복 조사와 조정 비용을 평가해야 함 |

복수 역할을 모든 업무에 강제하지 않는다. 검토 역할은 반대 의견의 개수를 채우거나 반드시 원래 판단을 뒤집을 의무가 없다. 의미 있는 반론이 없다는 결과도 허용한다.

## 2. 흐름에 넣을 위치

1. 목표·완료 기준·현재 자료를 바탕으로 가설과 초기 계획을 제안한다.
2. 핵심 가정이 틀렸을 가능성, 대안 설명, 필요한 판별 질문을 검토한다. 계획 수립 호출과 합칠 수 있다.
3. 별도 검토가 도움이 되는 경우 검토 대상과 범위를 정해 요청한다. 임시 검토 역할이나 기존 동료가 수행한다.
4. 반론 중 목표의 판단이나 실행 방향에 영향을 줄 항목을 고른다. 검증 가능한 질문을 작업으로 변환한다.
5. 기존 계획 검증을 거쳐 실행하고 실제 관측을 근거로 저장한다.
6. 가설·반론의 상태를 갱신한다. 설명 유지, 범위 수정, 반박, 근거 부족을 구분한다.
7. 기존 계획으로 충분하면 계속하고, 필요한 구간만 재계획한다. 중요한 미해결 반론은 완료 검토에서 다룬다.

실행 후 새 근거가 예상과 다르거나 계획이 반복해서 진전하지 않을 때도 2~4로 돌아갈 수 있다. 매 도구 호출 뒤 동일한 비평 호출을 강제하지 않는다. 큰 계획 변경이나 중요한 완료 판단을 기준으로 묶어서 검토할 수 있다.

예시: H1은 ‘처리 지연이 서버 부하에서 발생한다’이다. 검토 역할은 H2 ‘외부 API 응답 지연’을 제안하고, 두 설명을 구분하려면 구간별 처리 시간을 확인해야 한다고 답한다. 해당 자료를 조회한 뒤 어느 구간이 지연됐는지 근거를 연결한다. 이는 설명용 가상 사례이며 실제 관측이 아니다.

## 3. 검토 역할에 전달할 내용

- 목표와 완료 기준, 검토할 질문·주장·계획의 범위.
- 관련 관측과 원문 근거 참조, 자료 시점·적용 범위, 알려진 제한과 이전 검증 결과.
- 필요할 때 조회할 수 있는 도구와 자료 범위. 같은 자료를 읽을 권한이 있는 경우 별도 비밀 경계를 만들지 않는다.
- 원하는 산출물과 중단 조건. 추가 조사 필요와 실제 조사를 수행했음을 구분한다.

독립적인 대안 탐색을 맡길 때는 먼저 질문과 원자료에서 설명을 만들게 하고 기존 결론과 비교할 수 있다. 특정 주장을 검토할 때는 그 주장과 근거를 제공해야 한다. 기존 전체 대화의 복제가 기본일 필요는 없지만, 결정적 반대 자료나 적용 조건을 숨겨서도 안 된다. 문맥 분리는 기존 결론에 덜 끌리도록 하기 위한 선택이며 자료 접근 차단과 다른 개념이다.

## 4. 반론을 실행 가능한 기록으로 만들기

처음에는 별도 복잡한 논증 엔진보다 다음 정도의 결과 계약을 후보로 둔다. 명칭과 스키마는 구현 확정 전 정한다.

| 내용 | 설명 |
|---|---|
| 검토 대상 | 어떤 가설·가정·계획 단계·완료 조건에 대한 이의인가 |
| 반론 또는 대안 | 무엇이 다를 수 있으며 어떤 조건에서 문제가 되는가 |
| 근거 | 실제 확인한 자료의 참조. 아직 근거가 없으면 가설임을 표시 |
| 판별 질문/작업 | 어떤 관측이나 검사를 하면 설명 사이를 구분할 수 있는가 |
| 판단에 미치는 영향 | 결과가 달라질 때 계획·결론의 어느 부분이 바뀌는가 |

예를 들어 ‘다른 원인일 수도 있다’만으로는 후속 작업을 선택하기 어렵다. 반대로 원문의 명백한 모순을 발견한 경우 새 도구 호출 없이 기존 근거로 바로 평가할 수 있다. 모든 반론이 반드시 추가 조회를 발생시켜야 하는 것은 아니다.

반론 자체를 counterevidence로 저장하지 않는다. 실제 관측을 수집한 뒤 근거와 가설의 반대 관계를 연결한다. 검토자의 결론도 검증 대상이며, 원래 업무를 맡은 에이전트는 수용·기각·추가 조사 결정을 짧은 이유와 근거로 남긴다. 모델 내부 사고 전문을 저장하는 요구는 아니다.

## 5. 동적 작업 구성과 기존 코어의 관계

- Planner는 검토 요청과 판별 작업을 제안한다. 코드로 정한 정책은 권한·도구 계약·사용량·완료 조건을 검사한다. 검토 결과가 임의로 최상위 목표나 완료 기준을 바꾸지 않는다.
- 검토 역할은 같은 범용 runtime을 사용한다. ‘반론 담당’은 임무이며 영구적인 하위 에이전트 종류가 아니다. 어떤 역할도 필요하면 다른 역할에 검토를 요청할 수 있다.
- 검토를 도구 형태로 노출하더라도 긴 작업은 영속 요청·상태·결과 참조로 관리한다. 단순 함수의 즉시 반환만으로 장기 실행을 표현하지 않는다.
- 검토 대상의 목표·계획·근거 버전을 남긴다. 검토 중 대상이 바뀌면 기존 결과를 현재 평가로 자동 채택하지 않고 여전히 적용되는지 확인한다.
- 가설/반론/근거/후속 작업의 연결과 미해결 상태를 정본에 보존한다. compact 후에는 요약과 참조를 읽고 필요할 때 원문을 다시 연다.
- 복수 검토자의 동의는 독립 관측 수가 아니다. 원본의 계보를 기준으로 중복 근거를 구분한다. 다수결만으로 사실을 확정하지 않는다.
- 자원량 선택·추가 요청·반환은 기존에 논의한 에이전트 판단과 런타임 집행으로 연결한다. 모든 검토 요청에 새 자식 예산을 만드는 경로만 강제하지 않는다.
- 사람에게는 검토 때문에 결과나 일정이 달라질 때 의미 있는 진행 상황을 보인다. 상세 반론·근거·검토 이력은 작업 상세에 두고, 내부 토론 전문을 채팅창에 계속 출력하지 않는다.

## 6. 효율과 종료 판단

별도 검토 호출의 후보 신호는 상충 근거, 검증되지 않은 핵심 가정, 결과에 영향을 주는 큰 계획 변경, 반복 실패/무진전, 사용자가 요청한 독립 검토다. 모델이 말하는 자신감 숫자 하나만으로 결정하지 않는다. 명확한 규칙과 에이전트의 구체적 검토 이유를 함께 사용한다.

첫 배치에서는 자체 검토와 필요 시 한 번의 독립 검토를 비교 가능한 기준으로 삼고, 추가 검토는 새 근거 또는 다른 판별 경로가 있을 때 요청하는 안을 고려한다. 이 횟수는 고정 채택값이 아니다. 동일 질문·근거의 반복 검토는 기존 결과를 재사용하고, 독립 자료 조회는 병렬화할 수 있다.

완료를 막는 것은 ‘반론이 한 개라도 존재한다’는 사실이 아니라, 목표 완료 조건에 영향을 주는 문제가 해결되지 않았다는 사실이다. 근거가 부족하면 그 한계를 남긴다. 사용자가 요구한 목표가 허용하면 ‘현재 자료로는 확정 불가’도 올바른 결과일 수 있다. 추가 호출 여력이 없다는 이유로 미해결 반론을 해결됐다고 표시하지 않는다.

## 7. 현재 구현과 검토할 변경

현재 `Hypothesis`에는 주장·예측·반증 조건·지지/반대 근거가 있고, `hypothesesRequireReview`는 목표/근거 집합 변경에 따른 평가를 요구한다. `structured-planner.ts`는 가설과 계획을 함께 제안하고 단순 작업의 빈 가설 목록을 허용한다. `plan-validator.ts`의 구조/참조 검사는 의미상 반론의 충분성을 판단하는 검토 모델을 대신하지 않는다.

검토할 변경은 반론 결과와 후속 작업의 연결, 별도 검토 여부의 선택, 영속 검토 요청/응답, 버전 변경과 완료 판단에 대한 반영이다. 기존 코어 전체를 교체하거나 별도 모델 제품·그래프 DB·특정 skill을 필수로 도입할 이유는 아직 없다.

구현 순서 후보:

1. 반론의 산출물과 평가 사례를 먼저 정한다. 틀린 가설뿐 아니라 올바른 가설, 무관한 반론, 상충 자료, 근거 부족을 포함한다.
2. 한 에이전트의 가설/계획 호출에서 반론→판별 질문→작업→근거→판단 연결을 구현한다.
3. 같은 결과 계약을 별도 문맥의 검토 작업에 재사용한다. 요청/응답·대기/재개·취소·버전 변경을 검증한다.
4. 조건부 호출과 기존 동료 역할의 협업으로 확장한다. 자체 검토 대비 실제 성능 이득을 비교한다.

평가에는 목표 달성, 놓친 중요한 반론, 근거 없는 반론으로 맞는 결론을 뒤집은 비율, 추가 호출/시간/토큰, 근거 재사용, 압축/재시작 뒤 미해결 항목 보존을 포함한다. 로컬 대역 시험은 상태 흐름을 검증하며 실제 모델의 반론 품질을 입증하지 않는다. 실제 모델/API 시험 중단은 유지한다.

## 8. 공개 사례와 이번 제안의 구분

- Anthropic의 2024년 패턴 설명은 하위 작업을 동적으로 나누는 orchestrator-workers와 별도 호출로 평가·피드백하는 evaluator-optimizer를 구분한다. 이번 제안은 동적 검토 요청과 결과 평가를 조합하는 해석이며, 특정 조직 구조를 그대로 채택하는 것이 아니다. [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Anthropic의 2025년 연구 시스템 사례는 별도 문맥과 도구를 쓰는 서브에이전트의 병렬 조사 및 명확한 임무 전달을 설명한다. 그 제품은 리드/워커 구조를 사용하지만, 우리 설계에서는 검토 임무의 일시적 관계로 활용하는 안이다. 해당 글은 추가 토큰과 조정 비용도 보고한다. 제품별 수치를 모든 모델에 일반화하지 않는다. [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- ICLR 2024 연구는 당시 평가한 모델·과제에서 외부 피드백 없는 자기수정이 실패하거나 성능을 낮추는 경우를 보고했다. 최신 모델 전체에 불가능 판정을 내리는 근거로 사용하지 않는다. 우리에게는 모델 간 대화만 반복하기보다 실제 자료·도구 결과로 검토 효과를 평가해야 한다는 실험 설계상의 참고다. [Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798)
