# P4-01 게시판을 런타임에 연결하기

2026-09-06 · 구현 중

직전 단위는 게시판 저장·권한·출처 계층과 전체 2,160개 시험을 완료한 진전이다. 이번 단계도 P4-01의 남은 요구를 유지하며, 원래 시큐몬과의 비교 없이 현재 코어의 연결 지점으로 설계한다.

## 핵심 선택

첫 구현 단위는 `BoardService.readPage`의 범위/크기 제한, 출처 coverage와 미검증 가설 표시다. 이 서비스 결과 자체를 지속 입력 증명으로 취급하지 않는다. 도구 등록과 compact/reopen 이후 입력 검증은 아래 1번의 남은 작업이며, 조회 서비스 검증만으로 runtime 연결을 완료 표시하지 않는다.

입력 연결의 공통 기반은 [입력 검증 그래프](/Users/seunghanee/Documents/secumon/design/chapters/P4-input-validation-plan.md)에서 구현한다. 먼저 실제 기억의 출처 추적을 유한한 공통 큐에 연결하고, 게시판의 지속 입력과 교차 주체 검증을 같은 node/참조/guard 계약으로 확장한다.

게시판 읽기는 새로운 독립 Evidence를 생성하지 않는다. 읽은 글은 모델이 참고한 입력이며, 그 뒤 결과·계획·요약을 재사용할 때도 원 게시글과 원 출처를 확인해야 한다. 현재 기억 전용 의존성만으로 게시판 입력을 표현하지 않고, 도구가 검증 가능한 입력 원본을 제공하는 공통 계약을 추가한다. 원 출처가 다른 업무에 걸쳐 있으면 유한한 검증 큐에서 각 업무를 확인한다. 업무 사이의 참조 순환을 재귀 호출로 무한 추적하거나, 같은 노드를 재방문했다는 이유로 검사 전체를 생략하지 않는다.

과거의 사실 입력이 여전히 유효한 것과 새 게시글이 생긴 것은 다르다. 기존 게시글의 정정·철회·권한 변경은 입력 무효화이며, 새 글은 이후 조회할 변화다. 요청 상태는 현재 workflow 조건으로 재확인하고, 오래된 수락 상태를 사실 근거로 사용하지 않는다.

## 연결 순서와 검증

읽기 연결의 현재 구현·학습 내용은 [게시판 지속 입력 결과](/Users/seunghanee/Documents/secumon/design/chapters/P4-board-inputs-result.md)에 저장했다. 전체 2236/2236·관련 165/165 시험으로 읽기 연결을 로컬 검증했다. 다음 소단위는 [게시·요청·답변 도구와 의무 연결](/Users/seunghanee/Documents/secumon/design/chapters/P4-board-writes-plan.md)이다.

1. **읽기와 입력 원본:** 도구 카탈로그/브로커에 범위와 출력 크기가 제한된 게시판 읽기를 등록한다. 출처별 coverage와 명시적인 미검증 가설을 표현한다. 도구가 읽은 정확한 글과 응답을 저장하고 현재 원본을 재검증한다. 이 입력을 소비한 작업의 모델·후속 도구·저장 결과·공개/전달·compact/reopen 경계에 동일 검증을 적용한다. 두 역할/두 업무/두 저장소에서 실제 runtime 호출, 중복 원 출처, 새 반증 조회, 철회·권한 변경·재시작을 확인한다.
2. **쓰기와 의무:** 게시·요청·수락·답변 도구는 기존 쓰기 권한과 호출 예산을 사용한다. 게시판 커밋과 업무 장부 사이의 중단은 명령 영수증으로 대조한다. 질문/응답 의무는 기존 WorkState.obligations에 연결하고, 응답 수신·요청자 확인·업무 완료를 구분한다. 저장 후 결과 유실, 취소·기한·중복·대기 중 모델 무호출을 검증한다.
3. **역할 간 위임과 추론 흐름:** 현재 예산 위임의 동일 주체 조건을 무조건 제거하지 않는다. 조직이 허용한 상대 역할·업무 범위·수락·기한·공개 결과 계약을 확인한 뒤 예산을 할당한다. 수신 역할의 자료 권한과 요청자의 지출 권한을 분리한다. 두 runtime의 새 반증 → 가설/계획 갱신 → 중단/compact → 재개 → 완료 흐름과 부모 취소·예산 정산을 검사한다.

한 연결만으로 P4-01 전체를 완료 처리하지 않는다. 실제 모델/API 시험 취소를 유지하며, 모델 판단 품질·사내 서비스·외부 A2A 상대·상시 wake의 검증을 로컬 scripted 성공으로 대체하지 않는다. API/도구 인터페이스를 연결한 사실과 실제 모델이 그 도구를 올바르게 선택하는 능력도 구분한다.
