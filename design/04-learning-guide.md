# 함께 공부하며 만들기

2026-09-06 · v0.51 · 통합 플랜 C01~C10과 함께 공부할 개념

검토 중 논의한 전체 범위를 현재 플랜에 반영했다. 아래 주제별 수업은 관련 챕터에서 참고하며 과거 “다음 작업” 문장은 현재 착수 지시가 아니다. 공통 스킬을 반드시 호출할 필요 없이 개념 → 작은 계획 → 구현 → 관련 검증 → 결과 기록을 진행한다.

실제 착수 순서는 [통합 구현 플랜](/Users/seunghanee/Documents/secumon/design/03-migration-plan.md)을 따른다. 아래 수업은 개념별 참고이며 전부 읽은 뒤 구현을 시작할 필요는 없다.

## 챕터별 진행 방식

P0~P6를 큰 챕터로 삼고, 각 챕터를 기존 작업 ID와 선행 조건에 맞는 작은 구현 단위로 나눈다. 단위마다 다음 순서를 따른다.

1. **개념과 목표:** 이번에 해결할 문제, 필요한 개념, 이전 챕터와의 관계를 짧게 설명한다.
2. **구체적인 계획:** 작업 ID, 변경 범위, 입출력/상태 계약, 재사용할 코드, 실행 예제와 완료 기준을 먼저 기록하고 공유한다. 실제 구현에서 확인한 근거로 계획을 갱신한다.
3. **구현:** 기존 범용성·저장소 독립성·자료 경계를 지키며 확인 가능한 작은 동작을 만든다. 실제 코드/fixture를 함께 읽으며 설계가 동작으로 연결되는 지점을 설명한다.
4. **실행과 검증:** 정상 흐름과 관련 실패·중단/재개 사례를 실행한다. 예상과 실제 결과를 비교하고, 해당 작업의 통과 기준을 충족할 때 완료로 표시한다.
5. **기록과 챕터 정리:** 변경 내용·선택 이유·검증 증거·한계·남은 질문·다음 작업을 저장한다. 챕터 끝에는 그 시점까지의 흐름을 통합 확인하고 사용자가 결과와 핵심 개념을 검토할 수 있도록 설명한다.

매번 긴 전체 설계를 다시 작성하지 않는다. 전체 설계는 공통 기준으로 유지하고 현재 구현 단위에 필요한 상세 계획을 작성한다. 통상적인 로컬 구현/검증은 이미 허용된 범위 안에서 진행하며, 제품 방향을 바꾸는 미결정 사항은 근거와 대안을 제시한다.

사용자 지시에 따라 구현 스킬은 실제로 도움이 되는 경우에만 사용한다. 스킬 적용 자체를 형식적인 필수 절차로 두지 않으며, 필요한 계획·구현·검증·기록을 수행한다.

2026-09-06 진행 방식 보완: 새 프레임워크의 요구사항과 완료 기준을 설계의 기준으로 삼는다. 원래 Python 시큐몬은 참고 자료이며 매 챕터의 비교 기준이나 동작 호환 목표가 아니다. 기존 tool을 재사용할 때 필요한 입출력·권한·오류 계약만 확인하고, 새 TypeScript 코어 수정 뒤에는 영향받는 기능의 회귀를 검증한다. 과거 구현 전체·압축 원본 전체·모든 이전 검증 기록을 매번 대조하는 절차는 반복하지 않는다. 비교와 기록은 현재 선택 또는 완료 판단에 필요한 근거에 한정한다. 진행 설명도 현재 요구사항의 충족 여부를 중심으로 하고, 기존 구현과의 차이를 매번 설명하지 않는다.

협업 요청 실습에서는 “질문 게시”, “동료에게 요청”, “수락”, “근거 있는 답변”, “요청자 확인”을 구분한다. [요청/의무 구현 기록](/Users/seunghanee/Documents/secumon/design/chapters/P4-board-obligations-result.md)을 보며 답변을 만드는 작업은 계속 실행하고 기다리는 작업은 쉬는 이유를 살펴본다. 저장 직후 재시작해도 의무는 복원돼야 하며, 같은 요청을 다시 조회한 사실을 새 진척으로 세지 않는다. 다음은 [요청 발견과 사건 기반 재개](/Users/seunghanee/Documents/secumon/design/chapters/P4-board-wake-plan.md)다.

첫 챕터는 P0이며 첫 단위는 P0-01이다. 공개 문서 비교와 합성 관측 검토에 대해 목표·근거·가설/반증·대기·완료·실패 사례를 정의하고 입력/기대 결과 fixture를 만든다. 이어 P0-02의 최소 계약, P0-03의 구현 선택, 필요한 재사용/외부 계약 목록을 선행 조건에 따라 다룬다.

사용자가 종료한 API 키 탐색/모델 연결 시험은 재개하지 않는다. scripted/fake model로 코어의 상태 변경·계획 검증·도구 결과 수락·복구 규칙을 검증할 수 있다. 실제 모델의 추론 품질과 API 적합성은 미검증으로 남긴다. P1-06 등 실제 모델을 요구하는 작업이나 이를 선행 조건으로 갖는 단계 전체를 대역 성공만으로 완료 처리하지 않는다. 독립적으로 가능한 작업과 실제 모델이 필요한 검증을 구분한다.

이 진행 방식의 정리는 제품 구현 착수/완료 기록이 아니다. 중간 결론은 WORKLOG, 확정/열린 선택은 DECISIONS, 실제 작업 상태는 implementation-backlog.json, 검증 결과는 해당 작업의 기록을 기준으로 이어간다.

| 구현 단계 | 같이 공부하고 확인할 질문 |
|---|---|
| P0 합성 업무·계약 | 어떤 근거가 있어야 완료라고 할 수 있는가? 두 업무군을 같은 상태로 표현할 수 있는가? |
| P1 최소 코어 | 계획/가설/실행 상태는 어떻게 다른가? 결과 저장 전 프로세스가 죽으면 무엇을 다시 해야 하는가? |
| P2 저장소·기억·컨텍스트 | DB를 바꿔도 같은 보장이 유지되는가? 오래된 반증은 왜 남겨야 하는가? 다음 조회는 필요한가? |
| P3 도구·채널·컴퓨터 유즈 | 접수·완료·전달은 어떻게 다른가? 클릭 성공과 업무 성공을 어떤 근거로 구분하는가? |
| P4 협업·A2A·상시 임무 | 둘이 같은 자료를 인용하면 독립 근거가 늘어나는가? 회신 대기는 왜 추론을 계속하지 않아도 되는가? |
| P5 업무 배치 | 코어를 고치지 않고 지침·도구·권한·완료 기준만으로 새 업무를 배치할 수 있는가? |
| P6 복원·시범 | DB를 복원하면 이미 보낸 메시지는 어떻게 대조하는가? 삭제 자료가 백업에서 되살아나지 않게 하려면? |

각 구현 작업의 끝에 관찰 결과·실패·결정 근거·남은 질문을 WORKLOG와 작업별 검증 기록에 남긴다. 모델 내부 사고 원문을 저장하는 방식을 전제하지 않는다.

## 1. 먼저 구분할 개념

| 개념 | 뜻 | 새 프레임워크에서 볼 지점 |

| 사람 대화 역할 | 요청을 이해하고 업무·동료를 연결하며 결과 설명 | conversation과 work의 수명을 분리할 신규 경로 |

## 2. 첫 수업: 대화를 잃으면 무엇이 사라질까

합성 업무를 생각한다. 자료 A를 읽었고, 처음에는 H1이 맞아 보였지만 자료 B가 반박했다. 아직 자료 C의 답을 기다린다.

대화 창을 비우기 전에 남겨야 할 것:

- 목표와 성공 기준.
- A/B의 실제 근거 ID와 버전.
- H1이 왜 의심받는지와 경쟁 설명 H2.
- 자료 C가 필요한 이유와 기다리는 작업 ID.
- 다음 실행이 해야 할 일, 하지 말아야 할 일.

짧은 요약 하나를 유일한 기억으로 삼으면 무엇이 빠졌는지 알기 어렵다. 원문/이력·구조화 상태·재개 요약이 서로 다른 역할을 가진 이유다.

생각해 볼 질문: “자료 A의 사소한 문장이 나중에 중요해졌다면, 어떻게 다시 찾을까?” 이 질문으로 검색과 기억을 평가한다.

## 3. 두 번째 수업: 오래 기다리는 것과 오래 추론하는 것

담당자 회신을 사흘 기다리는 동안 모델이 계속 생각할 필요는 없다. 기다리는 이유와 조건을 저장하고 프로세스를 종료할 수 있다. 반면 새 증거가 생겼는데 과거 가설을 다시 검토하지 않는 시스템은 사흘 뒤 깨어나도 장기 추론을 잘하는 것이 아니다.

실습 목표: 종료·재시작, 가짜 clock으로 시간 이동, 늦은 응답을 넣어 다음 행동이 달라지는지 본다.

## 4. 세 번째 수업: 대화와 증거를 구분하기

에이전트 A가 “위험해 보인다”고 쓰고 B가 동의하면 의견은 두 개지만 독립 증거는 하나일 수 있다. B가 다른 로그를 찾아 반증하거나 뒷받침했을 때 새로운 정보가 생긴다.

게시판은 토론을 편하게 하되, 각 주장의 원본 출처와 관계를 남겨야 한다. 같은 글을 서로 인용하는 순환이 신뢰도를 높이지 않도록 한다.

실습 목표: 원본 근거 1개를 세 에이전트가 반복 인용했을 때 시스템은 1개로 세고, 진짜 반증이 오면 기존 결론을 바꾼다.

## 5. 네 번째 수업: 범용성을 무엇으로 확인할까

서브넷 관측 업무와 공개 문서 비교 업무 모두 “자료를 받아 질문을 만들고 동료에게 일을 요청한 뒤 근거가 있는 결과물을 만든다”는 구조를 갖는다. 다른 것은 자료·용어·도구·검증 기준이다. 사용자가 말한 영업 에이전트는 사람과 대화하는 역할이며 두 업무 모두의 창구가 될 수 있다.

실습 목표: 첫 업무군 다음에 두 번째 업무군을 붙이면서 공통 코드를 고치지 않는다. 맞추기 위해 `if domain == 'document_research'`를 코어에 넣게 되면, 어떤 개념이 잘못 들어갔는지 함께 살핀다.

대화 창 A에서 요청한 업무를 창 B에서 이어보는 경우도 생각한다. `conversation_id`는 바뀌어도 `work_id`는 유지되어야 한다. 사람이 “어디까지 했어?”라고 묻는 것과 “비교 기준을 바꿔”라고 지시하는 것은 다른 상태 변경을 만든다.

## 6. 다섯 번째 수업: 원문 없이도 판단할 수 있을까

동일한 합성 문제를 전체 내부 모델과 제한된 view를 받는 외부 역할에 풀게 한다. 제한된 역할이 내부에 무엇을 되물어야 하는지, 결과 품질과 비용이 어떻게 달라지는지 비교한다.

마스킹 통과가 완전한 비밀 제거를 의미하지 않고, 원문 접근을 막는 것도 동일한 판별력을 보장하지 않는다. 이 균형을 데이터와 결과를 보고 결정한다.

## 7. 여섯 번째 수업: 언어를 바꾸면 무엇이 달라질까

새 TS 코어가 TS 도구 또는 fake MCP에 요청하고 응답받는 한 경로를 따라가 본다. Python 없이도 핵심 업무가 실행되게 한다. TS 타입 검사가 통과해도 외부 도구가 약속과 다른 JSON을 반환할 수 있다. 실행 시 schema 검증이 필요한 이유다. 상태를 union으로 표현하는 것과 DB에 저장해 재시작 후 복원하는 것도 별개의 기능이다.

실습 목표: 같은 work/task/attempt/trace ID로 대화 요청, 상태 변경, 도구 결과를 추적한다. 실패한 실행을 저장된 응답으로 재생하고 실제 도구가 다시 실행되지 않는지 확인한다. 큰 정수 ID, 누락 필드, 잘못된 오류 상태를 넣어 경계 검증을 확인한다.

그다음 현재 업무에 필요한 도구 하나를 연결한다. 재사용할 도구가 있을 때만 입력·출력·권한·오류 계약을 확인한다. 내부 구현이 필요하면 Python 없는 새 코어의 요구사항에 맞춰 작성하고 설치·배포·오류 재현·패치 비용을 살핀다. 과거 구현과의 비교를 필수 실습으로 두지 않으며, 기대 결과는 현재 요구사항으로 정한다.

Rust를 적용할지는 실제 CPU·메모리·지연 측정으로 판단한다. 모델/API 응답을 기다리는 시간이 대부분이라면 코어 언어의 처리 속도만으로 전체 지연이 얼마나 줄 수 있는지 계산해 본다. [언어 비교와 디버깅 계획](/Users/seunghanee/Documents/secumon/design/06-language-and-migration.md)

## 8. 일곱 번째 수업: 계획·가설·실행 상태를 구분하기

문서 A/B의 내용이 다를 때 ‘적용 조건이 다름’, ‘개정 시점이 다름’, ‘서로 모순됨’이라는 설명을 생각한다. 가설은 다음에 무엇을 확인할지 결정하는 재료다. Planner는 판별 질문을 작업으로 만들고, Validator는 그 작업들이 실제 가능하고 목표에 연결되는지 확인한다.

실습 목표: 잘못된 의존성 계획은 실행 전에 거부하고, 새 반증이 들어오면 가설과 영향받는 계획만 수정한다. 도구는 모두 성공했지만 필수 비교 항목이 빠진 경우 완료를 거부한다. compact 뒤에도 핵심 반증과 다음 판별 질문을 복원한다. [메인 코어 상세](/Users/seunghanee/Documents/secumon/design/08-core-framework.md)

## 9. 여덟 번째 수업: 다음 호출이 정말 필요한가

같은 문서를 이미 읽었는데 대화 창에서 결과가 사라졌다면 원문을 다시 수집해야 할까? 저장된 근거 ID와 버전으로 찾으면 될 수 있다. 반대로 현재 시각의 상태를 묻는다면 오래된 성공 결과를 재사용해서는 안 된다. 도구 호출 장부와 memory 조회가 함께 필요한 이유다.

실습 목표: 현재 상태·특정 근거·과거 호출·조직 지식·skill을 서로 다른 조회 경로로 찾는다. 필요한 skill만 읽고 버전/제약을 compact 뒤에 복원한다. 단순 변환과 모순 조사에 각각 적합한 방법론을 선택하고, 호출 횟수 감소가 판단 품질도 유지하는지 비교한다. [호출·업무 방법론 상세](/Users/seunghanee/Documents/secumon/design/09-tools-memory-methods.md)

## 11. 실제 구현 수업: 입력 확인과 목표 달성은 어떻게 다른가

[P3-04 명시 대조 실습](/Users/seunghanee/Documents/secumon/design/chapters/P3-runtime-reconciliation-result.md)은 정상 입력, 응답 유실, 프로세스 종료, 재조회, 증명 유실을 같은 원 input ID로 비교한다. 영수증은 입력 적용 사실을 알려주고, 현재 관찰은 사후 조건을 확인하며, Evidence는 목표 판정에 쓰인다. 세 역할을 한 성공 표시로 합치지 않는다.

이번 단위의 계획→구현→실패/복구 검증→기록을 마쳤다. 다음은 이미 적용된 입력을 반복하지 않는 단일 successor와 현재 사후 조건 확인이다. 실제 모델/API 시험 중단과 P3-04 전체 진행 중 상태를 유지한다.

### 게시판 쓰기와 응답 유실 실습

[게시·철회와 저장 결과 복구](/Users/seunghanee/Documents/secumon/design/chapters/P4-board-writes-result.md)에서는 저장 사실, 응답 수신, 결과 채택, 목표 완료를 구분한다. 저장한 직후 응답이 사라진 상황을 만들고, 원래 결과를 보존한 채 영수증으로 저장 여부를 확인한다. 영수증이 없을 때는 늦은 호출까지 막는 미실행 종료 기록이 왜 필요한지 살펴본다. proof를 읽는 중 권한이 바뀌는 회귀도 함께 확인한다.

다음은 [요청·답변과 작업 의무](/Users/seunghanee/Documents/secumon/design/chapters/P4-board-obligations-plan.md)다. 상대의 수락과 답변 도착이 전체 완료를 뜻하지 않는 이유, 대기 중 모델을 반복 호출하지 않고 사건이 생겼을 때 재개하는 방법을 실습한다.

### 요청 발견과 사건 기반 재개 실습

[P4 요청 발견·재개](/Users/seunghanee/Documents/secumon/design/chapters/P4-board-wake-result.md)에서는 요청을 발견하는 것, 읽는 것, 수락하는 것, 답변을 완료하는 것을 나눠 본다. 각 역할은 자신의 수신 위치와 아직 처리하지 않은 참조를 저장하며, 같은 알림이 반복돼도 모델이나 채팅 메시지를 반복하지 않는다.

실습에서는 알림을 처리한 직후 저장 응답을 잃게 하고 다시 열어 본다. cursor와 알림이 함께 남아 있는지, 재개 후 요청이 한 번만 나타나는지 확인한다. 다음에는 원래 관측 이후 요청을 수락해 보고 과거 관측 기록이 보존되는지 확인한다. 마지막으로 목표 완료 조건만 먼저 충족시켜도 처리할 요청이 남아 있으면 완료가 거절되는지 확인한다. 검증 수치와 실제 모델/상시 dispatcher의 미검증 범위는 결과 문서를 따른다.

### 자원 배정·정산·반환 실습

에이전트가 하위 작업에 배정할 몫을 판단하고, 런타임이 실제 사용량과 장부를 관리한다. 사용자가 매번 숫자를 정하거나 정산할 필요는 없다. 도구 호출 100회 가운데 30회를 배정하고 12회를 사용해 종료했다면 18회를 반환한다. 다른 소비나 예약이 없을 때 새로 배정 가능한 몫은 88회다. 대화 턴 하나 안에 여러 모델/도구 호출이 있을 수 있으므로 채팅 턴 수와는 다르다.

[역할 간 권한·정산 실습](/Users/seunghanee/Documents/secumon/design/chapters/P4-budget-authority-result.md)에서는 다른 역할의 자료를 읽을 수 없는 부모가 자원을 지원하는 경우를 확인한다. 이어 취소했지만 사용량이 아직 도착하지 않은 모델 호출을 만들고, 예약을 유지하다가 늦은 사용량으로 한 번만 정산되는지 본다. compact 뒤에도 장부는 정본에서 이어진다. 이 기반 검증과 에이전트가 실제 배정 결정을 하는 전체 흐름의 검증은 구분한다.
