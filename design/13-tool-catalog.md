# 도구 카탈로그와 명세 로딩 설계

2026-09-05 · v0.10 · 설계 제안, 구현 전

도구가 많아져도 정확히 선택하고 적은 비용으로 호출할 수 있어야 한다. 전체 도구를 매번 프롬프트에 넣는 방식과 매 호출마다 검색부터 시작하는 방식 모두 피한다. [호출·메모리·방법론의 공통 경로](/Users/seunghanee/Documents/secumon/design/09-tools-memory-methods.md)를 구체화하는 문서다.

## 2. 현재 목록을 먼저 정리한 결과

| 구분 | 선언 수 | 이름 수 |
|---|---:|---:|
| 전체 정적 목록 | 160 | 143 |
| 테스트 경로 | 40 | 별도 fixture 목록으로 보존 |
| 비테스트 후보 | 120 | 114 |

`session_search`, `browser_query`, `web_fetch`, `report_inspection`, `dev_web_browse`, `web_site_sweep`는 비테스트 경로에 각각 두 선언이 있다. 기능·권한·입출력·등록 환경을 비교할 검토 대상이다. 같은 이름이라는 이유로 삭제하거나 같은 구현으로 합치지 않는다. 목록 밖의 외부 MCP와 동적 등록까지 포함한 실제 운영 도구 수는 미확인이다.

검토 JSON에는 파일·클래스·줄 번호와 직접 선언된 domain/deferred/힌트/capability 메타데이터를 넣었다. 상속된 값, 계산된 값은 미해석으로 남긴다. 모든 후보의 재사용 결정은 아직 `not_evaluated`다. 이름만 보고 읽기 전용·안전·멱등성을 부여하지 않는다.

## 3. 하나의 목록 대신 서로 다른 뷰

| 구분 | 내용 | 수명 |
|---|---|---|
| 제공자 카탈로그 | 연결된 서비스/로컬 adapter의 버전 있는 원본 명세 | 배포·연결·갱신 단위 |
| 권한별 사용 가능 목록 | 주체·조직·목표 범위·모델 목적지에 허용된 항목 | 정책/권한 변경 시 갱신 |
| 작업 후보 | 현재 단계에 필요한 capability의 작은 검색 결과 | 질문·계획 단계 단위 |
| 활성 명세 | 다음 모델 호출에 실제 제공하는 정확한 schema와 제약 | 호출별 예산 내 유지 |
| 호출 장부 | 선택된 도구 버전, 입력 참조, attempt, 결과/효과 상태 | 업무 보존 정책에 따름 |

명세를 활성 컨텍스트에서 내리는 것은 실행 이력이나 증거를 지우는 행위가 아니다. 과거 호출은 당시 도구 버전으로 설명하며, 재개 시 현재 사용 가능한 버전과 비교한다. 스키마가 로드되었다는 사실도 실행 권한을 부여하지 않는다.

## 4. 정본 메타데이터와 이름 규칙

영속 identity는 제공자 등록 ID + 원래 도구 이름 + 버전을 사용한다. 모델에 표시하는 짧은 별칭은 adapter가 해당 호출 범위에서 충돌 없이 만든다. 사람이 정한 서비스 표시 이름이나 원격 서버의 자기 소개 이름만으로 identity를 만들지 않는다.

하나의 검토된 명세에서 검색 카드, 모델 입력 schema, 문서, 예시/계약 검증 자료를 파생한다. 설명을 각각 수동 관리해 서로 달라지게 하지 않는다. 내부 명세와 공급자별 모델 형식 변환은 버전으로 추적한다.

필수 계약은 다음처럼 나눈다. 기존 필드에 모든 내용을 한꺼번에 강제하는 대신, 실제 실행에 필요한 항목부터 검증한다.

| 책임 | 필드·의미 |
|---|---|
| 식별·소유 | stable ID, provider, version, schema hash, 담당자, 변경 이력 |
| 발견 | 기능 설명, 자원/행동 태그, 한국어/영어 별칭, 적절한 사용과 오용 예시 |
| 실행 의미 | 입력/출력, 단위·시각·ID, scope, 읽기/변경 효과, 성공 후 조건 |
| 실패·복구 | 오류 분류, 부분 결과, cursor, 취소, deadline, 멱등성 지원과 범위, 결과 대조 방법 |
| 정책 | 권한·자격증명 참조, 실행 환경, 자료/모델 목적지 제한 |
| 효율 | batch/증분 조회, 예상 비용과 관측 지연, 결과 크기·신선도 |
| 수명 | draft/active/deprecated/disabled, 검증 상태, 대체 항목, 호환 범위 |

분류는 `문서/검색/기록/통신/브라우저/계산` 같은 확장 가능한 자원·행동 태그를 조합한다. 깊은 보안 전용 분류 트리를 코어에 고정하지 않는다. `search/list/read`, `draft/send`, `preview/apply`처럼 결과와 효과가 다른 기능의 차이를 설명한다. 하나의 거대한 범용 도구로 모두 합치면 명세가 다시 복잡해지고 실행 검증이 어려워진다.

MCP의 도구 이름·입출력 schema·annotation과 목록 기능은 adapter 입력으로 활용한다. annotation은 신뢰된 실행 정책의 대체물이 아니다. 여기의 소유자·승격·권한 view 등은 우리가 추가로 설계하는 런타임 계약이다. [MCP Tools, 2025-11-25 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

## 5. 선택과 로딩의 실제 경로

1. 현재 task의 기존 결과/직접 근거 참조로 답할 수 있는지 확인한다. [메모리 조회 순서](/Users/seunghanee/Documents/secumon/design/09-tools-memory-methods.md)를 따르되 불필요한 저장소 순회를 강제하지 않는다.
2. 이미 선택된 도구 ID와 명세가 현재 권한·버전에서 유효하면 재사용한다. 검색 모델 호출을 추가하지 않는다.
3. 새 capability가 필요하면 허용된 메타데이터에서 이름·별칭·자원/행동으로 후보를 찾는다. 기존 lexical 검색을 기준선으로 삼는다.
4. 필요한 후보의 정확한 명세만 활성화한다. 후보 수와 명세 토큰 예산을 함께 제한하고, 애매할 때만 검색을 확장한다.
5. 호출 목적·입력·도구/명세 버전과 효과를 Broker가 검증하고 실행 의도를 저장한다. 권한과 폐기 여부는 실행 직전에 다시 확인한다.

이는 논리적 단계다. 검색→선택→명세 읽기마다 반드시 별도 모델/RPC를 요구하지 않는다. 명확한 소수 후보는 검색 결과에 정확한 명세까지 함께 반환할 수 있고, 이미 로드된 도구는 바로 제안한다. 검색이 무관한 후보를 함께 찾았다는 이유로 모두 unlocked 집합에 추가하지 않는다.

on-demand 명세 로딩과 작은 사용 예시는 공개된 도구 설계에서도 제시된다. 검색 자체의 추가 왕복이 있으므로 작은 카탈로그까지 일률 적용하지 않고 비교한다. 특정 공급자의 베타 API·실행 언어·성능 수치를 우리 제품에 그대로 채택하지 않는다. [Anthropic의 도구 설계 사례](https://www.anthropic.com/engineering/advanced-tool-use)

활성 명세는 토큰 예산으로 관리한다. 당장 실행할 기능뿐 아니라 진행 중 비동기 작업의 상태 확인·취소·결과 조회처럼 후속 의무에 필요한 계약을 고려한다. 실행 중 호출의 버전 참조는 명세 퇴거와 무관하게 보존한다. 사용이 끝난 상세 설명은 내리고, 현재 계획/미완료 의무에 필요한 ID·버전·필수 제약만 ContextPacket에 남긴다. 나머지 과거 명세는 카탈로그/호출 장부에서 다시 찾는다. 모든 과거 ID를 패킷에 누적하지 않는다.

장기 미사용 명세와 관련 결과/설명의 정리는 [컨텍스트 수명 정책](/Users/seunghanee/Documents/secumon/design/15-context-lifecycle.md)을 따른다. 미사용 시간만으로 판단하지 않으며, 명세의 비활성화·카탈로그 폐기·실행 세션 종료를 구분한다. 재로딩 시 권한/버전을 검사하고 같은 명세의 반복 퇴거/재조회 비용도 측정한다.

모델 요청의 기본 명세와 직렬화 순서를 안정화하고 매번 불필요하게 섞지 않는다. 실제 prompt cache 지원/효과는 선택한 공급자와 요청 형식으로 측정한다. 오래된 권한의 명세를 캐시 적중을 위해 유지하지 않는다.

## 6. 동기화·캐시·변경 처리

외부 목록은 연결/갱신 때 수집하고 검증된 로컬 snapshot으로 검색한다. 모델 호출마다 모든 MCP 서버를 조회하지 않는다. MCP 목록의 pagination과 선택적 변경 알림은 협상된 버전에 맞게 adapter가 처리한다. 알림이 없거나 누락될 때의 TTL·재접속·명시 갱신 경로를 둔다. [MCP 목록 계약](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

- snapshot은 필요한 페이지를 모두 수집·검증한 뒤 원자적으로 발행한다. 중간 페이지 실패를 도구 삭제나 전체 목록 부재로 해석하지 않는다. 공급자가 일관된 revision을 제공하지 않으면 수집 시각/불확실성을 남기고 실행 시 명세를 재검증한다.
- 캐시는 제공자·조직·주체의 권한 view·정책 버전·카탈로그 revision으로 격리한다. 검색 결과와 '없음' 결과도 다른 권한에 공유하지 않는다.
- 명세 hash와 버전을 호출에 묶는다. 도중에 의미가 바뀌면 새 계획/호출 검증을 거치고, 폐기된 명세로 조용히 대체 실행하지 않는다.
- 권한 철회/긴급 disable은 오래된 snapshot보다 우선한다. 이미 전송된 외부 효과는 취소 성공을 확인하기 전까지 되돌아갔다고 표시하지 않는다.
- 사용 불가, 접근 불가, 연결 장애, 미검증 목록을 구분한다. 장애 시 대체 도구는 같은 권한·결과 의미를 만족할 때 선택한다.
- 외부 명세 본문은 실행 정책을 변경하는 지시로 받아들이지 않는다. 배포 revision을 검토/검증한 뒤 승격하고 결과·화면·trace와 같은 공개 경계를 적용한다.

초기에는 한 TS 서비스 안의 모듈과 저장 테이블로 구현할 수 있다. 별도 카탈로그 마이크로서비스나 벡터 DB는 필수가 아니다.

## 7. 목록 정리와 재사용 판정 절차

정적 후보 → 실제 필요한 기능 → 제공자/버전/등록 환경 확인 → 입력·결과·효과 fixture 비교 → 유지/TS 재구현/기존 MCP 연결/범위 제외를 기록한다. 사용되지 않은 후보도 검토 이유를 남긴다. 실제 폐기는 호출 의존성과 진행 중 업무, 대체 경로가 확인된 뒤 수행한다.

서로 다른 제공자의 비슷한 도구는 capability로 함께 찾되 원본 identity를 유지한다. 동작이 같은 wrapper의 통합은 fixture와 오류·권한·효과 의미가 같을 때만 검토한다. 검색 별칭 정리와 실행 코드 통합은 다른 결정이다. skill은 지침 registry, 도구는 실행 registry로 구분하면서 capability ID로 연결한다.

결과의 중간 집계·필터·정렬은 검증된 TS 변환이나 제한된 작업 묶음으로 수행할 수 있다. 거대한 원자료를 모델에 반복 전달하지 않는다. 묶음의 각 호출도 장부·권한·효과 검증을 통과하며, 임의 코드를 통해 Broker를 우회하는 구조로 만들지 않는다.

## 8. 성공 기준과 단계

| 검증 | 판단 기준 |
|---|---|
| 선택 품질 | 한국어/영어 요청, 유사 이름, 오용 예시에서 올바른 후보·최종 도구·인자 선택 |
| 후보 회수 | 정답 도구를 작은 후보 집합에서 찾는 비율과 실패 시 확장 비용 |
| 컨텍스트 비용 | 전체 명세/메타데이터/선택 명세의 토큰과 실제 모델 요청 수를 각각 측정 |
| 전체 효율 | 검색 포함 완료 지연·비용·성공률, cold/warm 목록을 구분 |
| 수명·권한 | 일부 페이지 실패, 새 버전, 폐기/권한 철회, compact 뒤 재조회 처리 |
| 기능 연속성 | 시작 후 상태/취소/결과 조회에 필요한 도구를 찾고 의무를 마무리 |
| 잘못된 통합 방지 | 같은 이름·다른 provider/효과의 fixture가 서로 바뀌어 실행되지 않음 |

P0에서 이번 정적 후보와 외부 MCP를 실제 요구에 매핑한다. P1은 작은 검토 목록·정확한 ID 경로·lexical 발견·선택 로딩·권한/버전 검증·장부부터 연결한다. P2에서 큰 합성 카탈로그로 예산/캐시/검색을 비교한다. 의미 검색·reranker·자동 추천은 선택 실패나 목록 크기가 그 비용을 정당화할 때 추가한다. 고정 도구 수 감소나 임의의 토큰 절감률을 성공으로 약속하지 않는다.
