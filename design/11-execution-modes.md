# 실행 모드와 필요한 만큼의 추론

2026-09-05 · v0.8 논의용 설계 · 자동/빠르게/깊게·지속 실행·UI 도구 · 구현 전

## 1. 권고

**사용자가 처리 수준을 지정할 수 있게 하고 기본값은 자동으로 둔다.** 단순 조회·변환에는 짧은 경로를 쓰고, 가설 검토·부분 재계획·다단계 조사가 필요한 업무만 해당 기능을 활성화한다. 롱 호라이즌을 지원하는 코어를 매번 무거운 추론 루프로 실행할 필요는 없다.

기존 08/09의 직접 처리 원칙을 사용자 모드·전환·예산 계약으로 구체화한다. 새 엔진 세 개나 모드별 독립 기억 저장소를 만들지 않는다. 아래 이름과 동작은 제안이며 사용자가 최종 채택하거나 구현한 상태가 아니다.

## 2. 서로 다른 제어 항목

| 항목 | 제어하는 것 | 예시 |
|---|---|---|
| 추론/작업 전략 | 계획 범위, 가설 탐색, 추가 검토, 동료 위임 | 직접 조회 또는 근거를 수집하며 반복 조사 |
| 모델별 추론 설정 | 해당 모델 한 번의 호출에 배정할 추론 자원 | 지원되는 모델의 호출별 effort/출력 한도 |
| 지속 실행 | 대기·재시작·세션 종료 뒤 업무를 이어갈 조건 | 내일 회신 확인, 결과 도착 후 재개 |
| 예산과 기한 | 총비용·모델/도구 호출·활성 실행시간·전체 경과시간 한도 | 제한 내 조사, 다음 날까지 응답 대기 |
| 표시/알림 | 얼마나 자세히, 어느 채널로 알릴지 | 접수·결과 중심, 주요 변화 알림 |

며칠간 회신을 기다리는 업무는 지속 실행이 필요하지만 매 순간 깊은 추론을 요구하지 않는다. 한 번의 복잡한 논증은 깊은 추론이 필요해도 며칠짜리 업무일 필요는 없다. 여러 초 걸리는 도구 하나도 지연의 원인이 될 수 있으므로 빠른 모드로 외부 지연까지 없어진다고 약속하지 않는다.

롱 호라이즌 모드를 모델 API의 단일 reasoning 설정과 동일시하지 않는다. 채팅 알림을 줄이는 것은 실행 모드를 바꾸는 행위도 아니다. 이 구분 때문에 단일 ON/OFF만을 내부 계약으로 삼지 않는다.

빠르게가 항상 작은 모델 사용을 뜻하지도 않는다. 검증된 강한 모델의 짧은 경로가 여러 작은 모델 호출보다 유리한지는 실제 지연·품질·비용으로 비교한다. 언어/모델 교체와 실행 구조 개선의 효과를 분리해 측정한다.

## 3. 사용자 모드

| 표시 | 기본 동작 | 범위를 넘을 때 |
|---|---|---|
| 자동 | 명확한 단순 요청은 직접 처리, 필요할 때 제한된 다단계 작업·조사로 확장 | 이미 합의된 목표·권한·예산·지속 조건 안에서 전환. 이를 넘는 변경은 사용자에게 필요한 결정을 요청 |
| 빠르게 | 짧은 계획 구간과 작은 작업 예산으로 처리. 불필요한 가설 생성·별도 critic·위임 생략 | 몰래 긴 조사로 승격하지 않음. 확인한 사실과 미완료 범위를 구분하고, 추가 조사 필요를 설명 |
| 깊게 | 어려운 질문에 필요한 근거 수집·반증 검토·재계획을 허용 | 총예산·기한·완료 기준은 그대로 적용. 목표를 달성하면 조기 종료 |

깊게를 선택해도 이미 답이 명확한 조회에 여러 모델을 강제로 호출하지 않는다. 빠르게에서도 외부 효과·필수 검증·근거 요건을 생략하지 않는다. 현재 예산으로 수행할 수 없으면 수행 불가/추가 작업 필요를 알리며 기준 미달을 성공으로 바꾸지 않는다.

초기에는 모드별 정확한 초·토큰·호출 수를 임의로 고정하지 않는다. P1/P2에서 대표 요청의 지연·완료율·비용을 측정해 기본 예산을 정한다. 빠른 모드의 반응성은 접수 지연, 첫 유용한 답변, 검증된 완료 지연으로 나누어 평가한다.

## 4. 공통 기반과 경량 경로

모든 모드에 필요한 계약은 유지한다: 인증된 요청/업무 연결, 권한·정보 공개 범위, 필요한 상태/근거 참조, 도구 의도·결과·중복 처리, 비용 한도, 취소, 결과 검증과 전달 상태. 질문에 비례한 최소 기록을 남기며 기억과 기존 업무를 삭제하는 모드를 만들지 않는다.

단순 대화는 대화 기록으로 처리할 수 있고, 일반적인 업무는 하나 또는 소수의 작업으로 표현할 수 있다. 단일 작업의 계약·계획은 코드 템플릿이나 같은 모델 호출에서 만들고 결정적 규칙으로 검사할 수 있다. 별도 planner 모델·가설 에이전트·critic·다중 worker·거대한 그래프 생성을 항상 거치지 않는다. 그 경우에도 필요한 실행 전 검사는 적용한다.

가벼운 경로의 개념은 `요청/제약 확인 → 필요한 직접 조회나 변환 → 결과 검사 → 답변`이다. 처리 중 정보가 모순되거나 범위가 커지면 다음 절의 모드 전환을 검토한다. 저장된 근거를 재사용할 때도 권한·시점·범위를 검사하고, 필요한 memory/skill만 읽는다. compact는 실제 컨텍스트 상태에 따라 동작하며 모드 변경마다 강제로 수행하지 않는다.

컴퓨터 유즈도 모드와 관계없이 대상·초점·필수 사후 조건을 확인한다. 모드는 관찰/탐색 예산을 조절하며, 빠르게에서 오래된 좌표를 재사용하거나 깊게에서 전체 화면 수집을 반복하도록 만들지 않는다. [관찰·행동 효율 설계](/Users/seunghanee/Documents/secumon/design/12-computer-use-tools.md)

## 5. 자동 선택과 실행 중 전환

초기 선택은 별도 상주 라우팅 에이전트보다 코어의 정책 모듈로 구현하는 안을 권고한다.

1. 명시된 모드·기한·총비용·지속 조건을 읽는다. 기존 업무 조회/수정/취소인지 먼저 구분한다.
2. 정형 조회·등록된 변환·기존 업무 상태 질문은 규칙과 계약으로 경량 경로에 배정한다. 조회 내용이 짧다는 이유로 최신성 검사를 생략하지 않는다.
3. 불명확한 일반 요청은 필요한 첫 해석/계획 호출에 선택 제안을 포함한다. 매 요청에 무조건 별도 분류 LLM 호출을 추가하지 않는다.
4. 복잡한 의존성, 새 근거의 충돌, 여러 번의 관측이 필요한 열린 질문, 현재 구간의 한계에서 확장을 검토한다. 자료 범위·실패 원인·남은 의무도 함께 확인한다.
5. 전환을 코드가 검증하고 모드/계획 버전·이유·기존 결과·누적 비용·남은 예산을 저장한다. 필요 부분만 확장하며 새 업무처럼 비용을 초기화하거나 완료 도구를 반복하지 않는다.

모델이 스스로 높다고 말하는 confidence만으로 경량 경로의 충분성을 판단하지 않는다. 결과 계약, 근거의 최신성/범위, 모순과 필수 미완료 항목을 사용한다. 권한 없음·외부 장애·필수 자료 누락은 깊게 바꾼다고 해결되지 않으므로 적절히 대기/질문/차단한다.

이미 승인된 범위·비용 안의 자동 전환마다 사용자 확인을 요구하지 않는다. 예상보다 큰 비용·새로운 외부 효과·별도의 지속 업무 등이 필요하면 변경되는 조건만 구체적으로 제시한다. 사용자가 빠르게를 지정했거나 명시적인 상한을 두면 그 상한을 우선한다. 자동 모드도 무제한 실행의 허가가 아니다.

## 6. 지속 실행과 중간 변경

지속 실행 조건은 업무별로 저장한다. 예약/회신 대기처럼 요청 자체에 포함된 지속성은 해당 업무에 적용하고, 단순 질문을 기본값만으로 며칠간 이어갈 업무로 바꾸지 않는다. 기다릴 때는 wake 조건과 기한을 저장하고 LLM 추론을 멈춘다. 대기 중에도 저장·예약·필요한 polling의 운영 비용이 있을 수 있다.

모드 선택은 기본적으로 새 요청에 적용한다. 진행 중인 특정 업무를 변경하려면 대상 업무에 연결된 변경으로 저장한다. 긴 조사가 진행되는 동안의 “지금 어디까지 됐어?”는 현재 상태를 읽는 빠른 대화 경로로 처리하고, 그 질문 때문에 원래 조사의 모드를 바꾸지 않는다.

깊게 → 빠르게 변경은 안전한 실행 경계부터 남은 선택 작업과 예산에 반영한다. 이미 시작된 외부 효과나 확인되지 않은 전송 결과를 없었던 것으로 처리하지 않는다. 새 한도 안에서 목표를 마칠 수 없으면 현재 결과와 남은 의무를 보존하고, 부분 결과/대기/종료 상태를 명확히 설명한다. 목표 범위를 줄인 것으로 임의 해석하지 않는다.

모드 변경, 알림 끄기, 현재 업무 중단은 별도 명령이다. 지속 실행을 해제하는 변경도 대상 업무에 어떤 대기/재개 조건을 멈추는지 명확해야 한다. 사용자가 실행 중 업무를 즉시 멈추려면 기존 pause/cancel 경로로 처리한다.

## 7. CLI·Web·Knox 표현

Web 입력 영역에는 `자동 / 빠르게 / 깊게` 선택을 제안한다. 자동을 기본으로 두고, 정확한 기한·비용·지속 조건은 필요한 업무 설정에서 다룬다. 매 요청마다 많은 옵션을 입력하도록 강제하지 않는다. 상태 카드의 실제 단계와 사용자가 요청한 모드는 구분한다.

CLI는 같은 세 모드의 명시 옵션과 업무별 조회/변경 명령으로 연결한다. 아직 명령어 스키마는 확정하지 않는다. Knox는 “빠르게 요약해 줘”, “근거까지 깊게 조사해 줘” 같은 자연어 또는 간단한 텍스트 명령을 지원하는 안을 둔다. 버튼·수정 기능은 실제 MCP 지원 확인 후 선택한다.

자동 경로 전환은 일반적으로 내부 상태에만 남긴다. 사용자에게 의미 있는 지연/범위 변화가 있으면 같은 작업 상태나 묶인 안내로 설명한다. “빠른 모드 시작”, “깊은 모드 전환”, “가설 검토 시작”을 매번 새 메시지로 보내지 않는다. 깊게에서도 접수·결과 중심의 대화 정책은 유지한다.

예시: 빠르게 요청한 비교에서 문서 버전 충돌이 확인되면 “현재 자료로는 두 문서의 적용 범위가 다릅니다. 개정 이력 확인이 남아 있어 최종 비교는 아직 어렵습니다”라고 한계를 알린다. 추가 조사는 허용된 범위/예산과 사용자 선택에 맞춰 진행하며 억지 결론을 만들지 않는다.

## 8. 구현·평가

P1은 같은 코어의 경량 경로와 제한된 다단계 경로, 명시 모드·제약 우선순위, 전환 시 상태/비용 보존을 먼저 구현한다. P2에서 자료 충돌·늦은 반증·잘못된 분류와 승격 기준을 평가하고 임계값을 보정한다. 단순 업무도 모두 장기 루프로 실행하는 기준선과 비교한다.

필수 합성 사례:

- 단순 상태 조회: 별도 계획·critic·새 장기 조사 없이 최신 공개 상태로 답변.
- 자동 비교 중 반증 발견: 허용된 범위에서 전환, 이전 근거/비용 보존, 중복 호출 없음.
- 빠르게 + 복잡한 조사: 제한을 넘기지 않고 미완료 범위를 설명, 거짓 완료 없음.
- 깊게 + 명확한 단순 질문: 충분한 답이 있으면 불필요한 탐색 없이 종료.
- 다음 날 회신 확인: 저장된 대기에서 재개, 대기 내내 LLM을 반복 실행하지 않음.
- 긴 업무 중 상태 질문/모드 변경/취소: 대상과 적용 시점이 정확하고 외부 효과 의미 보존.
- 권한 오류/자료 없음/도구 지연: 무조건 깊게 승격하지 않고 원인별 처리.

지표는 첫 유용한 답변/완료의 p50·p95 지연, 완료 업무당 비용, 라우팅 자체의 지연·호출 수, 불필요한 승격과 누락된 심층 검토, 예산 초과, 잘못된 완료, 사용자 개입, 전환 후 상태/근거 보존이다. 짧은 답변과 올바른 완료를 구분하며 같은 자료·모델 조건에서 비교한다. 수치 개선이나 실제 모드 전환 동작은 아직 미검증이다.

참고: [Anthropic의 에이전트 구성 원칙](https://www.anthropic.com/engineering/building-effective-agents)은 작업에 맞는 단순한 구성에서 시작하고 복잡성·지연·비용을 평가하라는 원칙과 routing 사례를 제공한다. 본문의 세 사용자 모드·지속성 분리·전환 계약은 이 프로젝트의 제안이다. 해당 글의 SDK/제품 목록을 현재 채택 근거로 사용하지 않았다.
