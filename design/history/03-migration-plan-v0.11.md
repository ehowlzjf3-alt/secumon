# 단계별 구현·검증 플랜

2026-09-05 · v0.11 · 코어·호출·컨텍스트·저장/복구·대화·우선순위 · 구현 전

## 1. 진행 원칙

첫 목표는 **사람이 요청한 한 업무가 중단·재개와 컨텍스트 교체를 견디는 공통 경로**다. 다음으로 두 에이전트의 근거 기반 협업, 그다음 여러 담당자와 상시 임무로 확장한다. 사람 대화 담당은 모든 업무군에서 사용하는 공통 역할이며, 특정 보안 모듈을 먼저 만들더라도 코어의 범용성을 비보안 예제로 계속 검증한다.

새 코어·대화·필수 도구는 Python 없이 TypeScript + 지원 중인 Node.js LTS로 구성하는 안을 우선 비교한다. TS+선택 Rust, TS+Python 도구 유지, Rust 중심 코어도 비용·기능·진단 기준으로 평가한다. 목표·상태·재개·예산은 새 코어가 소유한다. 기존 가드·업무 규칙·시험 자료를 활용하며, 전체 Python 엔진 번역을 선행 과제로 만들지 않는다.

필요한 기능을 먼저 정하고 기존 MCP 연결·코드 유지·TS 재구현·현재 범위 제외 중 선택한다. 정적 선언 160개(테스트 40개, 비테스트 후보 120개)를 전부 옮기거나 모든 Python 함수를 서비스로 감싸지 않는다. 신규 제품은 기존 gateway와 배포 구조에 묶이지 않게 설계한다. 원본 삭제·저장소 일괄 재배치·모든 skill 일괄 삭제는 수행하지 않는다.

시간을 미리 주 단위로 단정하지 않는다. 각 단계는 산출물·통과 조건·같이 공부할 질문으로 관리한다.

코어 구현 기준은 [메인 루프와 상태 계약](/Users/seunghanee/Documents/secumon/design/08-core-framework.md), 호출/배치 기준은 [도구·메모리·skill·방법론](/Users/seunghanee/Documents/secumon/design/09-tools-memory-methods.md)이다. 사용자 예시를 고정 순서로 강제하지 않고 업무 특성에 따라 필요한 구성만 사용한다.

## 2. 단계와 통과 조건

| 단계 | 사용자에게 보이는 결과 | 통과 조건 |
|---|---|---|
| P0 범위·계약·기준선 | Python 없는 구성과 재사용안의 비교, 필요한 도구 목록 | 실행 의존성·MCP 계약·총비용 근거 확인, 테스트 환경 분리 |
| P1 메인 코어와 한 업무 | 사람 요청, 가설/계획·검증·실행·상태 갱신·진행 결정 | 유효한 그래프만 실행, 복구·중복 방지·잘못된 완료 거부, 최소 도구/메모리/skill 경로 |
| P2 기억·컨텍스트·호출 효율 | compact 후 가설·반증·의무 유지, 필요한 결과·지침 재조회 | 다중 context 교체, 신선도/권한 검증, 품질을 유지한 호출·로딩 비용 평가 |
| P3 게시판·두 에이전트 협업 | 서로의 근거를 더해 공동 결과 도출 | 중복 근거 제거, 모순·늦은 응답·대화 루프 처리 |
| P4 MCP/A2A·상시 임무 | 실제 계약에 맞춰 도구·외부 동료 연결 | 취소/timeout/중복/예산/버전 협상, durable wait |
| P5 두 업무군·방법론·데이터 경계 | 보안과 공개 문서 연구가 같은 코어에서 각 방법론으로 동작 | 역할·지침·검증 규칙을 설정으로 배치, 코어 업무 분기 없음, A/B/C 배치 평가 |
| P6 도입·운영 | 새 제품에서 진행·근거·대기·비용 확인, 필요 시 기존 콘솔 연계 | 제한된 시범 운용·복구, 기존 전환 시 단일 소유권·롤백 |

### P0 — 지금 논의로 정할 것

산출물:

- 공통 개념의 최소 계약: identity, conversation/work/task/attempt, artifact, observation/claim, message, policy, budget. 대화와 장기 업무 ID를 분리.
- Goal/WorkState/EpistemicState, PlanProposal/PlanPatch, TaskResult, ControlDecision, ContextPacket의 최소 계약과 버전·상태 전이·커밋 경계 정의.
- 도구 registry/호출 장부, 메모리 직접 조회/검색, skill 활성화, 업무별 방법론·역할·완료 기준을 같은 task·권한·예산 계약에 연결.
- 도구/이벤트 wire schema의 정본과 버전 규칙 선택. 큰 정수 ID, 시각, null/필드 없음, 오류·부분 결과의 표현을 합성 fixture로 확인. Python이 필수 참여 언어라고 가정하지 않음.
- 지원 중인 Node.js LTS와 TS·MCP·LLM SDK의 호환 버전을 고정. 기존 package.json의 버전을 새 권장 버전으로 간주하지 않음.
- 현재 본체와 future-agent 사본의 차이를 검토해 요구·시험의 참고 기준을 선택. 새 제품은 독립 설계 가능하며 추출본은 읽기 기준으로 보존.
- [분류한 정적 후보](/Users/seunghanee/Documents/secumon/design/tool-catalog-review.json)의 비테스트 선언 120개(114개 이름)에서 필요한 기능을 선별. 테스트 선언 40개는 fixture 참고로 구분. 같은 이름 6개 그룹은 실제 등록 환경·효과·입출력을 비교한 뒤 코드 유지/TS 재구현/외부 MCP 사용/범위 제외와 근거를 기록.
- [카탈로그 계약](/Users/seunghanee/Documents/secumon/design/13-tool-catalog.md)의 제공자/identity·권한 view·명세 버전·정확한 선택·검색/로딩·동기화·폐기를 정의. 초기에는 작은 검토 목록과 lexical 검색을 사용하고 고급 검색의 필요성은 측정.
- [추가 연결 계약](/Users/seunghanee/Documents/secumon/design/14-scope-and-priorities.md)의 입력/산출물, 모델 요청/usage, 진행·재시도·예산, 재현 manifest, 기억 정정/삭제와 배치 수명을 최소 시제품 범위와 확장 범위로 나눔.
- 컴퓨터 유즈 대상 OS·앱·브라우저·원격 화면, 기존 driver/MCP와 접근성 지원 확인. browser_tool.py의 유효한 계약/시험을 재사용하고 관찰·행동+확인·조건 대기·세션 소유권을 새 계약으로 비교. [상세 재설계와 평가](/Users/seunghanee/Documents/secumon/design/12-computer-use-tools.md)
- 단순 조회, 상태·오류가 많은 연동, 언어 전용 라이브러리 의존 처리 중 실제 필요한 대표 기능으로 유지·재구현 비교. wrapper·배포·진단·패치 비용도 포함.
- Python 없는 제품의 실행 의존성 범위를 정의. 필수 gateway·subprocess·sidecar와 외부 MCP의 운영 주체를 확인하고, 빌드/개발 의존성은 별도로 기록.
- 아카이브에 없는 SIEM/EDR MCP의 입력/출력, 인증, scope, pagination, 오류, rate limit, cancellation, version 확인. 자격증명 값을 설계 문서에 복사하지 않음.
- Knox MCP 계약 확인: 발송 외에 수신 연결이 있는지, 인증된 사용자/방/메시지 ID, 전송 결과 ID·오류·중복 대조 수단 확인. 수정·스레드·버튼·첨부·읽음은 선택 기능이며 구현됐다고 가정하지 않음. 발송 전용이라면 별도 입력 경로가 필요함.
- CLI/Web/Knox 공통 공개 이벤트·접수 저장·답변 전달 장부와 업무별 기본 응답 경로 정의. 단체방 공개 범위와 계정 연결 방법 확인.
- 보안 관측 연결 예제와 공개 문서 비교·연구 예제를 합성 자료로 정의. 사람이 요청·변경·중단하는 흐름을 두 예제에 공통 적용.
- 전용 임시 DB와 fake MCP/A2A, 가짜 clock·외부 전달 수신기를 준비할 계획. 기존 conftest의 공유 DB 초기화에 기대지 않음.

실행 관리자 후보(TS+저장 포트 기반 직접 구현/LangGraph JS/Temporal TypeScript)는 같은 작은 흐름으로 비교한다. 선택 기준은 복구 의미, 긴 대기, 디버깅·재생, 운영 부담, 기존 도구 통합 비용, 버전 이행이다. “인기 있는 프레임워크”가 기준은 아니다. 각 후보는 짧은 적합성 실험으로 평가하고 선택된 하나만 제품 경로로 발전시킨다. 에이전트 본체는 DB/실행 프레임워크의 구체 저장 API에 의존하지 않는다.

완료 증거: 검증 가능한 업무 요구, 도구 계약표, 런타임 ADR, 측정 가능한 baseline 정의.

### P1 — 메인 코어와 한 업무

변경 후보: TS의 범용 업무 상태·이벤트·작업 포트, 사람 대화 입력/진행 전달, PG 등 구체 adapter, 합성 자료용 TS 도구 또는 fake MCP. 첫 시제품은 Python 없이 핵심 흐름을 실행한다. 기존 Python 도구 유지가 선택되면 별도 통합 항목으로 추가한다. GuardedHarness는 동작·시험 참고로 둔다.

작은 구현 순서:

1. **상태와 실행 의미:** 목표·실행/인식 상태, 계획 버전과 task graph, 실행 의도/결과 커밋. scripted planner와 고정 응답으로 잘못된 그래프·중복·재시작을 검증한다.
2. **제어와 완료:** Plan Validator, Scheduler/Executor, 결과 검증·State Updater, continue/replan/wait/blocked/완료 검토. 부족한 결과를 성공으로 끝내지 않는지 본다.
3. **실제 추론:** 합성 자료로 경쟁 가설·판별 질문·계획 변경을 모델이 제안하게 하고 코드 검증과 연결한다. 독립 검토 모델은 필요성이 있을 때 추가한다.
4. **선택과 기억:** 작은 도구 registry/호출 장부, 근거 ID 조회, 지침 하나의 선택 로딩, 방법론 선택과 최소 재개 패킷을 연결한다. 모든 기능을 단일 도구나 거대한 프롬프트에 하드코딩하지 않는다.

사람의 변경/취소/상태 조회와 대화-업무 ID 연결은 이 경로의 입력·출력으로 첫 단계부터 유지한다. 단순 업무에서는 가설 생성·전면 재계획·별도 critic을 생략하는 경로도 시험한다.

같은 코어의 경량 경로와 제한된 다단계 경로를 함께 만든다. 사용자 자동/빠르게/깊게와 실제 실행 정책·지속 실행·예산을 구분하고, 전환 시 기존 상태·근거·누적 비용을 이어 쓴다. 빠르게의 상한을 몰래 넘기지 않는지, 깊게에서도 목표 충족 후 조기 종료하는지 시험한다. [모드별 합성 평가](/Users/seunghanee/Documents/secumon/design/11-execution-modes.md)

fake 채널 수신기로 내구성 있는 요청 접수 → 짧은 접수 응답 → 공개 상태 → 검증 결과 → 최종 전달을 연결한다. 전체 계획 생성 전에 접수를 알릴 수 있어야 하며, 불명확한 요청은 이해 완료와 구분한다. `result_ready`에서 전달을 시작하고 필수 전달 의무를 완료 검증에 반영한다. 긴 모델 호출 중에도 취소 입력을 저장하고 신규 실행 배정을 막는 경로를 검증한다.

컴퓨터 유즈는 fake driver의 관측 ID·대상·단계 결과·기대 조건부터 연결한다. 오래된 대상, 부분 실행, 입력 전달 후 결과 불명확, 취소와 창 변경을 같은 attempt/상태 계약으로 시험한다. 첫 코어 단계에서 모든 OS driver를 만들지 않는다.

한 작업을 실행하기 전 의도를 저장하고, 결과를 저장한 뒤 다음 작업을 진행한다. 프로세스가 사라져도 목표·미완료 작업·승인·예산·대기 조건을 되살린다. 기존 자료를 이관할 때만 큐/finding ID를 별도 매핑하며 새 코어의 필수 필드로 두지 않는다. 사람에게 접수를 알리는 시점에는 업무가 실제 저장되어 있어야 한다. 대화 재접속, 메시지 중복 제거, 상태 조회, 목표 변경, 취소 요청과 실제 중단 상태를 첫 단계에서 다룬다.

완료 증거: 실행 전, 실행 후 결과 저장 전, 결과 저장 후 응답 전, 이벤트 재전달 중 각각 종료·재시작해도 상태가 일관됨. 순수 분석 중복 실행은 측정하되 외부 효과 중복은 허용하지 않음. 불확실한 외부 결과는 unknown으로 남음. 대화 종료가 업무 취소로 처리되지 않고 도구 경계에서 ID·오류 의미를 잃지 않음. Python 미설치 실행 환경에서 핵심 시나리오를 검증하고 필수 외부 서비스 목록도 함께 기록.

추론 완료 증거는 별도다. 뒤늦은 반증으로 가설/계획을 수정하고, 무효 계획을 실행 전에 거부하며, 유효 계획은 재계획 없이 이어가고, 필수 기준이 빠지면 완료를 거부해야 한다. 구체 합성 시나리오는 문서 08/09를 사용한다.

### P2 — 기억·compact·호출 효율

변경 후보: TS의 원문/이벤트 참조, 주장·근거 관계, 역할별 검색·컨텍스트 조립, 요약 검증. 기존 ContextEngine/stash에서 유용한 동작·시험 자료를 가져오되 정본·컨텍스트 수명 관리는 새 코어가 소유한다. 저장·조회에도 Python 실행을 필수 전제로 두지 않는다.

단순히 요약기를 리드에 연결하는 데서 멈추지 않는다. 활성 메시지를 완전히 비우고도 작업을 이어가는 시험을 한다. 초기의 작은 단서가 나중에 중요해지는 사례를 넣고 재조회 여부를 본다. 조직 지식 승격과 개인 업무 메모는 구분한다.

완료 증거: 필수 목표·중요 반증·미완료 의무·근거 ID를 5회 이상 context 교체 뒤에도 복원하는 합성 평가. `5회`는 초기 시험 조건이며 충분성 보장이 아니다. 자료 변경·검색 오류·권한 취소·요약 실패도 구분 처리.

추가 범위: compact의 스냅샷·패킷 검증·교체, 활성 skill 버전/제약 복원, 호출 결과 재사용/신선도, 부분 결과와 cursor, batch/동시성 상한, 필요한 후보만 조회하는 도구·지침 로딩. 반복 요약으로 가설·반증을 잃지 않고 검색 없음과 조회 불가를 구분한다. 완료율·근거 품질을 유지한 상태에서 총 도구/메모리/skill 로딩·모델 비용과 지연을 비교한다.

P2의 채팅 효율 평가도 함께 유지한다. 내부 사건 수가 늘어도 사용자 메시지가 같은 비율로 늘지 않도록 중간 상태를 합치고, 해결된 대기 질문을 보내지 않는지 확인한다. 접수·결과·필수 질문의 보존을 메시지 수 감소보다 우선한다.

자동 선택 기준은 단순 조회·복잡한 조사·모순 발견·대기 업무를 같은 세트에서 비교해 보정한다. 라우팅 자체의 호출/지연, 첫 유용한 답변과 검증 완료의 지연, 불필요한 승격/누락된 검토, 비용·완료율을 측정한다. 모드별 초·토큰 상한이나 절감률을 측정 전에 보장하지 않는다.

로컬 합성 웹 앱으로 TS/Playwright adapter의 목적별 관찰, 행동+확인, 조건 대기, 짧은 묶음을 순차 비교한다. 기존처럼 행동마다 모델이 왕복하는 기준선과 같은 성공 조건을 사용한다. 모델/MCP 왕복, driver 내부 조작, 이미지 비용, 대기·큐·검증 시간을 나누고 화면 변경·부분 실패·중복 효과를 함께 검사한다.

### P3 — 게시판과 협업

변경 후보: 공통 게시/구독·작업 할당, 메시지 ID, 수락/거절·결과·기한, claim 관계, dedup, 예산 상속.

두 에이전트가 서로 다른 자료를 갖고 하나의 질문을 푸는 시나리오로 시작한다. 처음부터 서브넷별 다수 상주 에이전트나 별도 탐정 서비스를 만들지 않는다. 조정/탐정은 같은 런타임의 역할로 검증한다. 대화 담당은 동료 작업을 기다리는 중에도 사람의 상태 질문·방향 변경을 처리할 수 있어야 한다.

완료 증거: 독립 근거의 결합, 같은 근거 반복 인용 제거, 근거 충돌 처리, 철회 전파, 제한된 대화 회수, 서로 상대 응답을 기다리는 교착 해소. 권한 없는 게시글·첨부를 다른 에이전트가 읽지 못함.

### P4 — 외부 계약과 상시 업무

변경 후보: 기존 MCP 연결 adapter, A2A client/server adapter, 구독·예약 재개, 관측 cursor, 작업/agent ID 매핑. 선택한 구현 언어와 무관하게 양쪽의 schema 버전·deadline·취소·오류 계약을 검증한다.

최초에는 fake 계약으로 개발하고 실제 MCP를 연결할 때 계약 적합성을 확인한다. 데이터 접근 정책이 확정되기 전에는 합성/비식별 자료만 사용하며, 실제 자료 연결은 P5의 경계 선택·검증이 선행되어야 한다. 모니터링의 수집·집계와 LLM의 판단을 분리한다. 이벤트 한 건마다 LLM을 깨우지 않고, 모듈 정책에 따른 묶음·변화에서 작업을 연다.

완료 증거: 전용 환경에서 timeout·rate limit·부분 결과·인증 만료·응답 지연·취소 후 늦은 결과를 처리. clock을 이동시켜 며칠 대기를 빠르게 검증한 뒤, 별도의 실제 시간 대기 시험으로 재개 서비스까지 검증. 실제 사내 MCP 조회는 범위가 정해진 통합 단계에서 수행한다.

P4의 Knox 연결은 확인된 기존 MCP와 채널 adapter를 사용해 텍스트 접수·최종 답변부터 시작한다. 먼저 CLI/Web과 같은 합성 시나리오를 fake 채널로 검증한다. 실제 발송은 대상·권한·환경이 정해진 통합 단계에서 수행한다. API 수락 이후 불명확한 전송은 대조 또는 확인 대기로 두고, 무조건 재발송하거나 분석을 재수행하지 않는다. 수정·스레드·버튼은 지원 확인 뒤에 추가한다.

컴퓨터 유즈의 실제 연결은 P4에서 확인된 환경/계약부터 수행한다. 브라우저 독립 세션과 같은 OS 화면의 조작 범위를 구분하고 사용자 인계·초점 변경·재시작을 시험한다. 네이티브 driver는 대상 OS/앱 선택 후 추가하며 실제 사내 자료에 연결하기 전에 아래 정보 경계 평가를 선행한다.

### P5 — 범용성과 정보 경계

보안 모듈과 공개 문서 비교·연구 모듈을 연결한다. 두 번째 모듈을 위해 공통 상태·scheduler·기억·게시판을 복제하지 않는다. 도메인 자료 스키마·판정 규칙·문서만 추가한다. 사람 대화 담당은 두 모듈에 공통이며 별도의 영업 업무군을 가정하지 않는다.

방법론과 배치 구성에는 입력/산출물·완료 기준, 역할·capability·권한, 지침/지식 버전, 메모리 범위, 예산·모델 위치와 평가 사례를 넣는다. 직접 조회·변환·비교·가설 조사·대기·지속 관찰의 방법을 단계별로 조합하고, 변경은 계획 버전과 연결한다.

전체 내부 추론, 외부 리드+공개 게이트, 내부 주도+외부 자문을 같은 데이터와 질문으로 비교한다. 원문을 숨기면 정확도가 얼마나 떨어지는지, 내부에 되묻는 비용이 얼마인지도 측정한다. 외부 모델을 더 쓰는 것이 늘 낫다고 가정하지 않는다.

완료 증거: 양쪽 모듈의 E2E, 잘못된 권한/목적지 차단, 승인되지 않은 정보가 합성 outbound capture에 없음, 동일 품질 조건에서 비용/지연 비교. 사람 지시와 A2A/도구 본문의 지시를 구분하고, 사람·대화 모델의 권한을 각각 확인하며, 목표 변경 전의 늦은 응답이 최신 결정을 덮어쓰지 않음. 합성 시험 통과를 모든 기밀 유출 가능성 0의 증명으로 확대하지 않음.

### P6 — 신규 도입과 기존 시스템 전환

새 제품에 예산·승인·runtime 관측과 업무 중심 보기를 제공한다. 적합한 기존 TS 콘솔은 활용할 수 있지만 기존 Python gateway·DB 구조를 도입의 필수 조건으로 두지 않는다. 현재 단계, 최근 근거, 모순, 차단 사유, 다음 재개, 누적 비용을 보여준다. 모델 내부 사고 원문을 노출하는 기능을 전제로 하지 않는다.

CLI·Web·Knox의 기본 대화에는 접수·필요 질문·결과를 두고 업무 상태/근거 상세와 실행 진단을 구분한다. 다중 업무, 웹 재접속, 단체방, 채널 간 이어보기, 수정/취소, 긴 결과를 같은 시나리오로 검수한다. 자동 갱신이 스크롤·키보드 초점을 빼앗지 않는지, 상태를 색만으로 전달하지 않는지도 확인한다. [채널별 표시·전달·평가 상세](/Users/seunghanee/Documents/secumon/design/10-chat-and-channels.md)

점진 도입: 저장된 비식별 자료 replay → 읽기 전용 shadow 평가 → 제한된 업무군 시범 → 범위 확대. shadow에서는 자료·결과 비교를 수행하고 실제 발송/조치 효과를 만들지 않는다.

독립 신규 도입은 새 업무로 시작하며 기존 시스템과 데이터·실행 소유권을 공유할 필요가 없다. 기존 운영 업무를 전환하는 경우에만 ID·증거·상태 이관과 소유권 전환을 추가한다. 업무 유형/범위별 활성 소유자는 하나이며 새 런타임에 넘긴 범위를 기존 러너가 동시에 배정하지 않는다. 롤백은 신규 배정 중지 → in-flight 정리/판정 → 상태·근거 보존 → 검증된 이전 경로로 소유권 복귀 순서로 한다. DB를 과거로 덮어씌워 이미 발생한 결과를 지우지 않는다.

## 3. 평가 매트릭스

아래는 **제안하는 품질 기준**이며 이번에 통과한 시험 결과가 아니다.

| 평가 | 초기 기준 |
|---|---|
| 복구 | 정의한 장애 구간에서 필수 상태 유실 0 |
| 저장소 정합성 | 상태/사건 동시 커밋, 원본-DB 사이 장애/고아 객체, 색인 지연·직접 조회, 작업 공간 승격 후 정리 검증 |
| 저장소 독립성 | DB/ORM 없는 코어 빌드/시험, 공통 계약 시험과 서로 다른 영속 구현 두 종류의 대표 시나리오, 코어 수정 없이 교체 |
| 복원/수명 | 격리 복원에서 DB·원본·키/버전·삭제/철회 대조, unknown 효과·중복 전달 처리, RPO/RTO·용량 측정 |
| 중복 외부 효과 | fake sink에서 중복 적용 0, 불명확 결과는 unknown |
| 컨텍스트 유지 | 고정 평가 세트의 필수 사실·반증·의무·근거 참조 보존 |
| 컨텍스트 수명 | 미사용 명세/중복 본문 축소, 의존성·권한·저장/참조 검사, 오래된 반증/대기 유지, 재로딩·진동·전체 비용과 실제 입력 검증 |
| 추론 품질 | 경쟁 가설·늦게 온 반증·부분 관측을 올바르게 처리 |
| 계획 검증 | 잘못된 의존성·범위·완료 기준 누락을 거부, 변경안의 기반 버전 확인 |
| 제어 판단 | 유효 계획은 continue, 필요한 부분만 replan, 대기·예산 끝남을 complete로 처리하지 않음 |
| 가설 품질 | 지지/반증·가정·판별 질문 유지, 반복 인용·검색 실패로 확신을 올리지 않음 |
| 호출/메모리 | 유효 결과 재사용과 필수 갱신 구분, 접근권한·범위·버전·부분 관측 유지 |
| 카탈로그/선택 | 테스트/후보/실제 등록 구분, 이름/제공자 충돌 처리, 후보 회수율·정확한 선택·schema 비용, 버전 변경/권한 철회/목록 부분 실패 처리 |
| 진행/예산 | 새 근거 없는 반복·중첩 재시도 제한, 부모/자식 예산 예약·사용 대조, wait/blocked/한도 소진과 완료 구분 |
| 입력/산출물·기억 수명 | 추출 위치·부분성·버전 보존, 정정/철회가 요약·색인·캐시·진행 중 결과에 반영 |
| 모델/배치 계약 | capability·목적지·usage 미확정 보존, 버전 있는 manifest, 새 추론과 결과 replay 구분, 검증 후 변경 승격 |
| skill/방법론 | 필요한 지침 선택·버전 복원, 단순 업무의 과잉 처리와 복잡한 업무의 검증 누락 측정 |
| 오류 의미 | 접근 오류/timeout을 정상·관측 없음으로 처리한 건수 0 |
| 협업 품질 | 같은 원본 증거를 다수 독립 근거로 세지 않음 |
| 협업 비용 | 대화·위임·총예산 상한을 넘어 자동 증식하지 않음 |
| 일반화 | 보안 다음 공개 문서 업무군 추가에 코어의 도메인 분기 추가 0 |
| 사람 대화 | 접수/진행 응답 지연·취소 반영 지연 측정, 재접속 후 상태 일치·메시지 중복 제거 |
| 채팅 가독성 | 접수·결과·필수 질문 보존, 일반 내부 이벤트는 새 말풍선 0, 의미 없는 진행 알림·허위 진행률 없음 |
| 전달 신뢰성 | 준비/완료/API 수락/전달/읽음 구분, 전달만 복구, 옛 목표의 발송 재검사·불명확 전송 대조 |
| 채널·다중 업무 | 인증된 사용자/방/업무/답변 경로 연결, 다른 채널 조회로 자동 발송 경로 변경 없음 |
| 사용자 제어 | 분석·알림 부하 중에도 접수·취소·상태 조회 지연 측정, 작업 간 처리 공정성 확인 |
| 실행 모드 | 경량 경로의 불필요한 계획/검토 호출 제거, 필요 시 범위 내 전환, 명시 상한·누적 비용·근거 유지, 미완료를 완료로 표시하지 않음 |
| 컴퓨터 유즈 | 동일 성공 조건의 모델/도구 왕복·이미지·대기·완료 지연 비교, stale 대상·부분 실패·unknown 효과·창 충돌 처리 |
| 언어 간 계약 | 고정 fixture에서 ID 정밀도·시각·오류·부분 결과 의미 손실 0 |
| 디버깅 | 한 업무 trace로 호출과 상태 변경 추적, 저장 응답 replay가 실제 효과를 재발생시키지 않음 |
| 실행 의존성 | Python 없는 구성은 Python 미설치 환경에서 핵심 시나리오 통과, 필수 gateway/sidecar/원격 서비스 의존성 명시 |
| 재사용 경제성 | 같은 요구·검토 기간에서 새 구현/검증 비용과 유지/연결/운영 비용 비교, 기존 코드량만으로 결정하지 않음 |
| 정보 경계 | 테스트용 금지 자료가 권한 없는 모델/에이전트 출력에 없음 |
| 효율 | 완료율·정확도를 유지한 상태에서 호출·토큰·지연의 변화 측정 |

비교는 가능한 한 같은 모델·자료·도구 응답으로 진행하고 실행별 변동을 보고한다. 예: A 현재 방식, B 지속형 상태, C 상태+기억, D 기억+협업. 여러 요소를 한 번에 바꿔 원인을 알 수 없게 하지 않는다. 값싼 모델로 바꾼 비용 감소와 구조 개선의 효과도 분리한다.

첫 단계부터 목표 토큰 절감률을 임의로 약속하지 않는다. 완료 업무당 비용, 반복 조회율, p50/p95 지연, 사람 개입률, 잘못된 완료 비율을 baseline과 비교한다.

## 4. 코드 재사용 지점

| 현재 지점 | 먼저 할 일 |
|---|---|
| `agent/engine.py`, `harness/runner.py` | 비교 baseline과 유용한 가드 계약/시험 참고. 새 TS 코어가 업무 수명을 소유 |
| `context_engine.py`, `context_summarizer.py`, `stash.py` | 동작·fixture 재활용. TS에서 보존·재개 체계 재설계하며 Python 저장소 호출은 선택 사항 |
| `_shared/lead_tools.py`, `session_registry.py`, `inspector_channel.py` | 위임/결과 계약은 살리고 영속 작업과 분리 |
| `TaskContract`, tool registry, 도메인 toolsets | 업무 규칙·계약·fixture 추출 후 코드 유지/새 구현을 비교. 기존 버그를 호환 요건으로 이식하지 않음 |
| `browser_tool.py`와 브라우저 수명/관찰/행동 테스트 | Playwright 기반·유효한 가드/fixture 재사용. 관측 버전·행동+확인·묶음·대기·세션 소유권은 새 도구 계약으로 재설계 |
| `LeadAdapter`, `ThreadAdapter`, `state_domain` | 현재 업무 ID·근거·결과를 공통 모델로 투영 |
| 기존 finding judge·마스킹·delivery·audit | 유효한 판정·권한 규칙과 시험 보존, 실행 코드의 유지/교체는 비용·보장 범위로 선택 |
| 플랫폼 gateway·control-plane·web·contracts | TS UI/계약은 선택 재사용. Python 없는 구성은 기존 gateway 의존성을 새 TS 경로로 대체 |

이 표는 변경 예정 지점이며 파일 이동·수정 명령이 아니다. 구현 기준 저장소와 작업 단위는 P0에서 정한다.

도구 목록의 `registry.py`, `tool_search_tool.py`, `discovery.py`도 검색·선택·필터·명세 구성의 참고다. 기존 검색 결과 전체 활성화, 이름별 수집, 모듈 import 방식은 새 요구에 맞게 비교한다. Python 코드의 줄 단위 번역을 필수로 두지 않는다.

## 5. 함께 진행할 첫 구현 단위

**사람 요청 → 목표·실행/가설 상태 → 필요한 기억·지침·방법 선택 → 계획·검증 → TS 도구/fake MCP → 근거·상태 갱신 → continue/replan/완료 검토.** Python 없이 합성 자료로 실행하며, 중단·재시작·사용자 변경·compact 뒤에도 가설·근거·의무와 다음 작업을 복원한다. 실제 기존 도구의 유지·새 구현 비교는 P0의 대표 기능 평가로 별도 수행한다.

먼저 비교할 결정은 저장 계약·실행 관리자 후보·기억의 단위다. 게시판·A2A·도메인 담당 조직은 이 최소 경로 위에 단계적으로 올린다. 첫 시제품부터 범용 업무 모델과 사람 대화 역할을 사용한다. [언어 전환 상세](/Users/seunghanee/Documents/secumon/design/06-language-and-migration.md) · [대화 역할 상세](/Users/seunghanee/Documents/secumon/design/07-conversation-agent.md)

## 6. v0.9 추가 범위의 단계 배치

P1에는 작은 카탈로그·단일 모델 adapter, 텍스트/JSON artifact, 공유 예산/deadline, 최소 진단 manifest, 정정/철회 상태를 포함한다. 기존 계획의 최소 compact/재개 패킷과 fake 채널/driver 계약도 이 수직 경로의 일부다. 기능마다 서비스를 분리하지 않는다.

P2에서 큰 합성 카탈로그·긴 자료·반복 compact·반복 실패·비용/명세 로딩·기억 정정 전파를 비교한다. P3/P4는 검증된 경로 위의 협업/외부 adapter 확장이고, 실제 자료 적재 전 권한·보존/삭제·모델 목적지 정책을 확정한다. P5/P6에는 형식·업무 확장, 배포 revision의 제한 평가/롤백과 저장소 복원 시험을 둔다.

다중 모델·전용 의미 검색·분산 카탈로그·네이티브 driver·자동 절차 학습은 별도 통과 근거가 생길 때 도입한다. [첫 구현 범위와 확장 조건](/Users/seunghanee/Documents/secumon/design/14-scope-and-priorities.md)은 상세 기준이며 일정이나 채택 확정이 아니다.

v0.10의 [컨텍스트 수명](/Users/seunghanee/Documents/secumon/design/15-context-lifecycle.md)은 P1에 필수 의무 보호·완료 단계 명세 비활성화·저장 후 결과 참조화·최소 재로딩을 연결한다. P2에서 긴 미사용 구간·반복 compact·새 권한/버전·늦은 반증·재로딩 비용을 비교한다. 정리용 LLM을 매 호출에 추가하거나 별도 서비스를 만들지 않아도 시작할 수 있다.

v0.11의 [저장소와 복구](/Users/seunghanee/Documents/secumon/design/16-storage-and-recovery.md)는 P0에 기준 데이터/쓰기 소유권·트랜잭션·원본/색인·보존·복구 목표를 정하고, P1에서 격리 DB와 artifact backend의 장애 구간을 확인한다. P2의 검색/컨텍스트·정정, P3/P4의 동시 작업/외부 효과, P6의 실제 복원/용량 평가로 확장한다. 전용 vector/graph DB·공유 캐시·분산 큐는 필요한 근거가 생겼을 때 선택한다.

사용자 정정 반영: PostgreSQL은 본체의 필수 의존성이 아니다. P0에 DB 제품 중립적인 업무 단위 저장 포트와 필수 보장을 정하고 SQL/DDL/ORM/DB 오류는 adapter에 둔다. P1/P2의 두 번째 영속 구현은 교체 적합성 실험으로 시작해 동일 계약과 대표 복구 시나리오를 검사한다. 메모리 대역만의 통과를 실제 저장소 교체 검증으로 간주하지 않는다.
